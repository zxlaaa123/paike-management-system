端到端耗时对比（默认退火 10s）
--------------------------------------------------------------------------------
规模   改动前端到端   改动后端到端   差异       说明
小     17315ms       17127ms       -188ms     批量落库改进微小
中     15369ms       15769ms       +400ms     波动（JIT/GC噪声）

结论：批量落库（insertBatch 单条 SQL）对端到端耗时改进微小（<0.3s）。
原因：本地 MySQL round trip ~1-3ms，300 条逐条 insert 仅 ~0.5-0.9s，批量省的不多。
端到端 15s 的成本构成：退火 10s（主因）+ context 装载 + rescore + 落库。
批量落库在本地收益有限，但在高延迟生产网络下会更有价值。

退火预算参数化价值（额外实测）

小规模（30 任务）退火 3s 质量降 2.78 分（92.19 < 旧最高 94.95，FAIL）。
原因：数据少时解空间小，退火需更多步数找到最优，3s 不够。
结论：退火预算参数化价值高，但小规模建议 ≥ 5s 保质量；中/大规模 3s 通常足够。

================================================================================
总结
================================================================================
1. 批量落库：本地环境改进微小（~0.2s），代码正确、生产环境（高延迟）受益更多。
2. 退火预算参数化：核心价值。用户可按规模/质量需求调整：
   - 默认 10000ms：最高质量（验收线三档全 PASS）
   - 小规模（≤30 任务）：建议 ≥ 5000ms 保质量
   - 中/大规模：3000ms 通常足够，端到端可降到 ~6s
   - 0ms：跳过退火，仅回溯可行解（最快，质量最低）
3. 验收线：默认配置（退火 10s + 批量落库）三档全 PASS，无回归。
