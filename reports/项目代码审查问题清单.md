## 致命问题

### F1. `deleteBatchSchedules()` 方法为空，清空自动排课结果无效

- **文件**: `backend/src/main/java/com/paike/scheduler/service/AutoScheduleBatchService.java:64-67`
- **代码**:
  ```java
  public void deleteBatchSchedules(Long batchId) {
      // 删除该批次自动生成的排课记录（source_type = AUTO 且 batch_id 匹配）
      // 由 ScheduleController 或 ScheduleService 处理，此处仅作标记
  }
  ```
- **原因**: 方法体为空，只有注释没有实现。前端"清空结果"按钮调用此接口，返回 200 成功但实际上什么都没做。
- **影响**: 自动排课结果无法清空，验收演示时会暴露。误以为清空成功，但排课数据仍然存在。
- **修复建议**: 注入 `ScheduleMapper` 或 `ScheduleService`，执行物理删除：
  ```java
  scheduleMapper.delete(new LambdaQueryWrapper<Schedule>()
      .eq(Schedule::getBatchId, batchId)
      .eq(Schedule::getSourceType, "AUTO"));
  ```
  同时清理关联的 `unscheduled_task` 记录。

### F2. `AutoScheduleBatchController.getBatchById()` 路径变量名称不一致

- **文件**: `backend/src/main/java/com/paike/scheduler/controller/AutoScheduleBatchController.java:33-34`
- **代码**:
  ```java
  @GetMapping("/batches/{batchId}")
  public Result<AutoScheduleBatch> getBatchById(@PathVariable Long id) {
  ```
- **原因**: URL 模板变量名为 `batchId`，但方法参数名为 `id`。Spring Boot 按名称绑定，`@PathVariable Long id` 找不到 `batchId` 变量，`id` 为 null。`selectById(null)` 返回 null，方法返回"批次不存在"。
- **影响**: 批次详情接口永远返回"批次不存在"。
- **修复建议**: 将参数名改为 `@PathVariable Long batchId`。

### F3. 分页查询在内存过滤后返回错误的分页数据

- **文件**:
  - `backend/src/main/java/com/paike/scheduler/controller/ScheduleController.java:52-75`
  - `backend/src/main/java/com/paike/scheduler/controller/TeachingTaskController.java:65-96`
- **代码模式**（以 ScheduleController 为例）:
  ```java
  Page<Schedule> result = scheduleMapper.selectPage(new Page<>(page, size), wrapper);
  // ↑ SQL 层面分页查 10 条
  List<Schedule> filtered = result.getRecords().stream()
      .filter(s -> { /* 按关联字段过滤 */ })
      .collect(Collectors.toList());
  // ↑ 内存过滤后可能只剩 3 条
  Page<Schedule> pageResult = new Page<>(page, size);
  pageResult.setRecords(filtered);
  pageResult.setTotal(filtered.size());
  // ↑ total 设成 3 而非数据库真实总数
  ```
- **原因**: 先 SQL 分页（查 10 条），再在 Java 内存中按关联字段（课程名、教师名、班级名）过滤。分页总数 `total` 设为内存过滤后的条数（如 3 条），而不是数据库真实匹配总数。翻到第 2 页时，SQL 查回第 11-20 条，可能包含第 1 页已经过滤掉的数据，但第 1 页那些被过滤的数据在第 2 页也搜不出来了，导致用户看到的数据不完整。
- **影响**: 排课列表和教学任务列表的搜索分页完全不可用。数据量大时，翻页会漏掉数据或出现空白页。
- **修复建议**: 方案一：在 SQL 层面通过 JOIN 完成关联过滤，让 MyBatis Plus 分页正常计数。方案二：对于简单的名称过滤，考虑在 `schedule` 表冗余存储课程名/教师名/班级名。方案三（临时方案）：先查全部符合条件的数据，在内存中完成过滤后再手动切分分页（仅适合数据量小的场景）。

### F4. 自动排课任务计数逻辑错误，部分成功任务被重复计数

- **文件**: `backend/src/main/java/com/paike/scheduler/service/AutoScheduleService.java:191-201`
- **代码**:
  ```java
  if (currentSuccess > 0) {
      successTaskCount++;
  }
  if (currentSuccess < remainingSlots) {
      failedTaskCount++;
  }
  ```
- **原因**: 一个教学任务需要 2 个大节（remainingSlots=2），自动排课只排了 1 个（currentSuccess=1）。这时 `currentSuccess > 0` 为 true 计入 `successTaskCount++`，同时 `1 < 2` 也为 true 计入 `failedTaskCount++`。一个任务被同时计为成功和失败。
- **影响**: 批次记录中的 `successTaskCount + failedTaskCount` 可能超过 `totalTaskCount`，统计数据自相矛盾。前端显示"成功 X 个 + 失败 Y 个 = 总共 X+Y 个任务"时，总数大于参与任务数。
- **修复建议**: 一个任务应只有一种最终状态——全部完成算 success，部分完成算 failed（或新增部分成功计数），不应同时计入两边。

## 高风险问题

### H1. 自动排课未清理旧的未排任务记录

- **文件**: `backend/src/main/java/com/paike/scheduler/service/AutoScheduleService.java:42-48`
- **原因**: `clearOldAutoSchedule=true` 或 `clearAllSchedule=true` 时，只清除了 `schedule` 表记录，未清理 `unscheduled_task` 表中旧批次产生的未排任务记录。重新执行自动排课后，新批次会产生新的未排任务记录，旧记录仍然可见。
- **影响**: 未排任务页面被历史数据污染，分不清哪些是当前批次的问题。
- **修复建议**: 清除 schedule 的同时，按 batchId 删除 `unscheduled_task` 记录。或者在创建新批次前先清理旧批次的未排任务。

### H2. 排课列表 N+1 查询风暴

- **文件**:
  - `backend/src/main/java/com/paike/scheduler/controller/ScheduleController.java:197-231`
  - `backend/src/main/java/com/paike/scheduler/controller/TeachingTaskController.java:226-233`
  - `backend/src/main/java/com/paike/scheduler/controller/TimetableController.java:180-215`
- **原因**: `fillRelation()` 对每个 `Schedule` 记录逐条执行 5-7 个 SELECT 查询（时间段、教室、教学任务、课程、教师、班级、批次）。列表页每页 20 条就会产生 100+ 次 SQL 查询。
- **影响**: 数据量大时页面加载极慢。MyBatis Plus 嵌套查询在循环中执行，带来严重的性能问题。
- **修复建议**: 批量收集所有 ID，用 `selectBatchIds` 或 `in` 条件一次查出全部关联数据，在内存中组装。例如一次性查出所有涉及的课程、教师、班级等。

### H3. `categorizeReason` 依赖中文文本匹配，极其脆弱

- **文件**: `backend/src/main/java/com/paike/scheduler/service/AutoScheduleService.java:370-385`
- **代码**:
  ```java
  private String categorizeReason(String reason) {
      if (reason.contains("已有课程") && reason.contains("老师")) return "TEACHER_CONFLICT";
      if (reason.contains("已有课程") && !reason.contains("老师")) return "CLASS_CONFLICT";
      ...
  }
  ```
- **原因**: 硬编码中文子串匹配。如果 `ScheduleConflictService` 中的错误消息文本发生任何修改（例如"已有课程"改为"已排课"），分类逻辑静默失败，返回"UNKNOWN"。没有单元测试覆盖这部分逻辑。
- **影响**: 未排任务的错误原因类型不准确，用户看到大量"未知原因"。
- **修复建议**: 方案一：在 `ScheduleConflictService` 中直接返回结构化原因类型码（如 `TEACHER_CONFLICT`），而不是纯文本。方案二：用 `categorizeReason` 匹配中文前做完整的映射表，并添加兜底日志。

### H4. 手动排课未检查排课规则配置

- **文件**: `backend/src/main/java/com/paike/scheduler/service/ScheduleConflictService.java:28-128`
- **原因**: `checkConflict()` 检查了教师禁排时间，但未检查 `TEACHER_MAX_DAILY_SLOTS`、`CLASS_MAX_DAILY_SLOTS`、`ALLOW_SAME_COURSE_SAME_DAY` 等排课规则配置。自动排课会检查这些规则，但手动排课不会。用户可以通过手动排课绕过规则配置的限制。
- **影响**: 排课规则配置对手动排课无效，规则一致性被破坏。设置了"教师每天最大课程数=3"，手动排课时仍然可以给同一位教师在第 5 个大节继续排课。
- **修复建议**: 在 `checkConflict()` 中增加对规则配置的检查，注入 `ScheduleRuleService`，验证手动排课也遵守规则配置。

## 中等风险问题

### M1. `UnscheduledTaskService.list()` 同样存在分页错误

- **文件**: `backend/src/main/java/com/paike/scheduler/service/UnscheduledTaskService.java:26-59`
- **原因**: 与 F3 相同模式——先 SQL 分页查询 10 条，再在内存中按课程名/教师名/班级名过滤，分页总数和实际数据不匹配。
- **影响**: 未排任务页面搜索分页同样不准确。
- **修复建议**: 同 F3。

### M2. `GlobalExceptionHandler` 不记录任何未处理异常日志

- **文件**: `backend/src/main/java/com/paike/scheduler/common/exception/GlobalExceptionHandler.java:51-53`
- **代码**:
  ```java
  @ExceptionHandler(Exception.class)
  public Result<Void> handleException(Exception ex) {
      return Result.fail(500, "系统异常：" + ex.getMessage());
  }
  ```
- **原因**: 没有调用任何日志记录器（如 `log.error()`），异常的堆栈踪迹完全丢失。生产环境出现 500 错误时，运维人员无法从日志中定位问题原因。
- **影响**: 系统异常排查困难，只能靠复现。如果异常包含敏感信息（如 SQL 语句），`ex.getMessage()` 可能直接暴露给前端用户。
- **修复建议**: 注入 Logger（或使用 Lombok `@Slf4j`），记录 `log.error("系统异常", ex)`。

### M3. 自动排课 `@Transactional` 回滚策略不完整

- **文件**: `backend/src/main/java/com/paike/scheduler/service/AutoScheduleService.java:39`
- **代码**: `@Transactional`
- **原因**: Spring 默认 `@Transactional` 只对 `RuntimeException` 和 `Error` 回滚。如果底层操作抛出受检异常（`SQLException` 等，虽然 MyBatis 包装了，但自定义受检异常不会回滚），事务不会回滚，导致部分记录已写入而部分未写入。
- **影响**: 数据可能处于部分一致的不完整状态。
- **修复建议**: 改为 `@Transactional(rollbackFor = Exception.class)`。

### M4. 自动排课每日上限检查宽松

- **文件**: `backend/src/main/java/com/paike/scheduler/service/AutoScheduleService.java:294-319`
- **代码**:
  ```java
  if (currentBatchId != null) {
      wrapper.ne(Schedule::getBatchId, currentBatchId);
  }
  ```
- **原因**: 在自动排课过程中检查每日上限时，排除当前批次的所有记录（因为当前批次尚未完成）。但同批次内已经安排好的课程不会被计数，导致每日上限检查比实际宽松。例如设置了班级每天最多 4 个大节，自动排课可能给一个班级安排到 8 个大节，因为同一批次内互不计数。
- **影响**: 自动排课可能违反每日上限规则。
- **修复建议**: 移除 `currentBatchId` 排除条件，让已保存的同批次记录参与计数。或者在内存中跟踪已排课数量。

### M5. 时间表查询通过 TeachingTask 间接查询，未排满任务不显示

- **文件**: `backend/src/main/java/com/paike/scheduler/controller/TimetableController.java:128-143`
- **代码**:
  ```java
  private List<Schedule> queryByClassId(Long classId) {
      List<TeachingTask> tasks = teachingTaskMapper.selectList(
          new LambdaQueryWrapper<TeachingTask>()
              .eq(TeachingTask::getClassId, classId)
              .eq(TeachingTask::getDeleted, 0)
      );
      if (tasks.isEmpty()) { return List.of(); }
      List<Long> taskIds = tasks.stream().map(TeachingTask::getId).collect(Collectors.toList());
      return scheduleMapper.selectList(
          new LambdaQueryWrapper<Schedule>()
              .in(Schedule::getTeachingTaskId, taskIds)
              .eq(Schedule::getDeleted, 0)
      );
  }
  ```
- **原因**: 先查教学任务列表再查排课记录。如果某个班级有教学任务但没有任何排课记录（任务创建后未排课），`tasks` 非空但 `schedules` 为空，课表正确显示为空表，功能正确。但边界情况：如果教学任务被软删除但排课记录仍存在，`tasks` 结果中不包含该教学任务，对应的排课记录不会被查询到。注意：`task.getDeleted() == 1` 的软删除会通过 MyBatis Plus 自动过滤，所以这种情况在实际操作中很少出现。
- **影响**: 正常情况下功能正确，但在教学任务先删后恢复等边界场景可能遗漏排课数据。
- **修复建议**: 增加一步直接查 schedule 表中属于该班级的排课记录，或作为补充。

### M6. 前端自动排课接口返回类型与实际不一致

- **文件**: `frontend/src/api/autoSchedule.ts:38`
- **代码**:
  ```typescript
  export function runAutoSchedule(data: {...}) {
    return request.post<ApiResponse<AutoScheduleBatch>>('/auto-schedule/run', data).then((r) => r.data.data)
  }
  ```
- **原因**: 前端声明返回类型为 `AutoScheduleBatch`（含 `id`, `batchNo`, `totalTaskCount` 等字段），但后端实际返回类型为 `AutoScheduleService.AutoScheduleResult`（含 `batchId`, `batchNo`, `totalTaskCount` 等字段）。两个类型字段不完全一致——`AutoScheduleResult` 使用 `batchId`，`AutoScheduleBatch` 使用 `id`。TypeScript 编译不报错，但 `latestBatch.id` 是 undefined。
- **影响**: 自动排课结果展示中部分字段为 undefined，前端页面可能显示缺失的数据。

## 低风险问题

### L1. 物理删除操作无事务保护

- **文件**:
  - `UnscheduledTaskService.java:83-90` (`clearByBatchId`, `clearAll`)
  - `ScheduleConflictReportService.java:97-102` (`clear`)
- **原因**: 执行 `delete`（物理删除，表无 `@TableLogic`），但方法无 `@Transactional`。中途异常时部分数据已删部分未删。
- **影响**: 极端情况下数据不一致。
- **修复建议**: 添加 `@Transactional`。

### L2. 无效导入

- **文件**: `backend/src/main/java/com/paike/scheduler/service/AutoScheduleBatchService.java`
- **原因**: 导入了 `import java.util.List;` 但从未使用（该类在第 1 行导入列表中）。
- **影响**: 无功能性影响，编译器警告。

### L3. 数据库升级脚本重复执行失败

- **文件**: `backend/src/main/resources/db/v2_alter_schedule.sql`
- **原因**: `ALTER TABLE schedule ADD COLUMN source_type VARCHAR(30)...` 在 `spring.sql.init.mode=always` 下每次启动都执行。第二次执行时因为列已存在而报错。MySQL 不支持 `ADD COLUMN IF NOT EXISTS`。
- **影响**: 服务器启动日志中出现 SQL 错误（但应用可能仍能启动，因为 Spring Boot 默认不因 SQL init 失败而停止启动）。
- **修复建议**: 将 `spring.sql.init.mode` 改为 `embedded` 或手动管理数据库迁移。

### L4. 课表评分页面没有空状态兜底

- **文件**: `frontend/src/views/schedule/ScheduleScoreReportView.vue:133-135`
- **原因**: 评分页面加载最新评分时，如果后台返回 null，页面上会显示"暂无评分数据"，功能正确。但当 `currentScore` 和 `latestReport` 同时为 null 时，页面逻辑正常。
- **影响**: 无实质性影响，可以接受。
