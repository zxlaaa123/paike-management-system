# V8 版本需求说明

日期：2026-06-12

前置：`V8_00_可行性研究.md`（已立项，决策已锁定）

## 1. 一句话目标

把 V3 方案生成的"贪心一遍过"引擎升级为"回溯保可行 + 模拟退火提质量"的求解引擎，且引擎运行期间不访问数据库。

## 2. 已锁定决策（不得在执行中变更）

| 决策 | 结论 |
|---|---|
| 技术路线 | 纯 Java 自研，**不引入 OR-Tools 或任何求解器依赖** |
| 周次/单双周 | 不做，数据模型零改动 |
| 旧引擎 | 不删、不改行为，新引擎作为新策略并存 |
| 接入点 | V3 方案生成（`/api/v3/schedule-generate`）新增策略 `SOLVER_V8`；`AutoScheduleService`（正式课表直排）本版**不改** |
| 新页面 | 不加。前端仅在现有策略下拉中增加一个选项 |

## 3. 需求列表

### R1 内存约束模型（必须）

排课开始时一次性加载学期全量数据，构建不可变的内存模型：

- 教学任务（status=1、目标学期）、时间段、教室、班级、课程、教师
- 教师禁排时间（`teacher_unavailable_time`）
- 排课规则（`TEACHER_MAX_DAILY_SLOTS` / `CLASS_MAX_DAILY_SLOTS` / `ALLOW_SAME_COURSE_SAME_DAY`）
- 软规则权重（`schedule_rule_weight`，SOFT 类型）
- 已锁定项（V4 锁定语义，作为预占用常量）

引擎求解过程中**禁止任何 Mapper / Service 调用**。

### R2 内存冲突检测器（必须）

与 `ScheduleConflictService.checkConflict` 的硬约束语义**完全一致**的内存实现：

教师/班级/教室同时段唯一、容量、房型匹配（实验课→LAB、机房课→COMPUTER）、教师禁排、每日上限、同课同日规则、每周课时上限。

语义一致性必须用"双跑对拍"测试证明（见 `V8_05`）。

### R3 回溯求解器（必须）

- 搜索单位：大节槽位 = (teachingTask 的第 n 个大节, timeSlot, classroom)
- 变量排序：MRV（剩余可行位置最少的任务先排），打平回退到现有 `SchedulingSupport.sortTasks` 顺序
- 值排序：LCV 或复用现有在线 candidate 评分作启发
- 回溯预算：可配置的最大回溯次数（默认 100_000），超限后对剩余任务退化为贪心收尾，保证总能结束
- 对"实际有解"的数据集，排满率必须 100%（测试集见 `V8_05`）

### R4 模拟退火优化器（必须）

- 初始解：R3 的可行解
- 邻域算子：单点移动（换时段/换教室）、两任务交换；只接受不破坏硬约束的邻居
- 目标函数：**直接复用** `ScoringFunctions` 离线 penalty 系列 + `schedule_rule_weight` 权重，即优化目标 = `rescore` 的打分口径
- 可复现：随机种子作为入参，同种子同数据必须产生同一结果
- 停止条件：时间预算（默认 10s，可配）或温度归零

### R5 接入与产物（必须）

- `strategyType = "SOLVER_V8"`，经 `V3ScheduleGenerateService` 现有流程落库：`schedule_plan` + `schedule_plan_item`（遵守 startPeriod 奇数、endPeriod=startPeriod+1 的现有不变式）
- 未排任务写现有 `schedule_unassigned_task` 流程，失败原因编码沿用现有 `[TYPE]` 标签体系
- 生成日志写现有 generate log 流程
- 生成后自动触发现有 rescore，使方案列表立即可比较
- 性能基线：经 `PerformanceBaselineService` 记录（规模、耗时、成功与否），extra 字段记录种子与回溯次数

### R6 前端（最小改动）

- 方案生成页策略下拉增加 `SOLVER_V8`（标签：智能求解）
- `status.ts` 的 `strategyText` 增加映射
- 不加新页面、新路由

## 4. 非目标（明确不做）

1. 周次/单双周/起止周。
2. 改动 `AutoScheduleService`、`ScheduleConflictService` 的现有行为。
3. 新增数据库表或字段（除非阶段验收发现确属必须，需先回到决策层确认）。
4. OR-Tools 或任何第三方求解器。
5. 多线程并行求解（单线程实现，避免复杂度失控；性能靠内存化已足够）。

## 5. 验收总口径

详见 `V8_05_测试与验收清单.md`。核心三条：

1. 对拍：内存冲突检测与 DB 版 `checkConflict` 在同一数据集上逐格结论一致。
2. 质量：同一数据集上 `SOLVER_V8` 方案的 rescore 总分 ≥ 现有四策略的最高分，未排任务数 ≤ 现有四策略的最少值。
3. 回归：现有 52 个 E2E 全绿；现有后端单测全绿；四个旧策略行为不变。
