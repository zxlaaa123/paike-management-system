# V8 引擎设计

日期：2026-06-12

前置：`V8_01_版本需求说明.md`

## 1. 包结构

新增包 `com.paike.scheduler.engine`（与现有 `service.scheduling` 并列，不混放）：

```
engine/
├── model/
│   ├── EngineContext.java        # 不可变内存模型（任务/时段/教室/规则/禁排/锁定/权重）
│   ├── EngineTask.java           # 任务 + 派生数据（requiredSlots、候选教室列表）
│   ├── Assignment.java           # (taskId, slotIndex, timeSlotId, classroomId)
│   └── EngineSolution.java       # 一组 Assignment + 未排列表
├── conflict/
│   └── InMemoryConflictDetector.java   # R2，占用位图 + 计数器
├── solver/
│   ├── BacktrackingSolver.java   # R3
│   └── SolverConfig.java         # 回溯预算 / 时间预算 / 种子
├── optimize/
│   ├── AnnealingOptimizer.java   # R4
│   ├── NeighborOperator.java     # 移动 / 交换算子
│   └── ObjectiveFunction.java    # 离线 penalty × 权重 的内存版
└── EngineFacade.java             # 唯一对外入口：solve(EngineContext, SolverConfig) -> EngineSolution
```

约束：`engine` 包内**不出现** Spring 注解、Mapper、Service 引用——全部纯 Java + 构造器传入数据，与 `SchedulingSupport` 的"纯计算、可直接单测"原则一致。Spring 侧由一个新的 `V8SolverGenerateStrategy`（放在 `service` 层）负责装载数据 → 调 `EngineFacade` → 落库。

## 2. 内存模型与数据装载（R1）

装载方（service 层，事务内一次性完成）：

| 数据 | 来源 | 备注 |
|---|---|---|
| 任务 | `TeachingTaskMapper`（status=1、semesterId） | requiredSlots = ceil(weeklyHours/2)，沿用现有口径 |
| 时段 | `TimeSlotMapper` | 按 dayOfWeek/periodNo 建索引数组 |
| 教室 | `ClassroomMapper`（status=1） | 预筛候选：容量 ≥ 班级人数 且 `SchedulingSupport.isRoomTypeMatched` |
| 禁排 | 复用 `SchedulingReferenceData` 的 unavailableKeySet 思路 | 转 `boolean[teacher][slot]` |
| 规则 | `ScheduleRuleService` 三个键 | int/bool 常量 |
| 权重 | `schedule_rule_weight` SOFT 规则 | ruleCode → weight 映射 |
| 锁定 | `ScheduleLockedItemMapper` / `ScheduleLockGuardService` 同源数据 | 转为预占用 Assignment，求解器不可移动 |

ID 全部映射为 0..n-1 的稠密 int 索引（`Map<Long,Integer>` 双向表），引擎内部只用 int，输出时再映射回 Long。

## 3. 内存冲突检测器（R2）

核心结构（n = 时段数）：

```java
boolean[][] teacherBusy;   // [teacherIdx][slotIdx]
boolean[][] classBusy;     // [classIdx][slotIdx]
boolean[][] roomBusy;      // [roomIdx][slotIdx]
int[][] teacherDailyCount; // [teacherIdx][day 1..7]
int[][] classDailyCount;
boolean[][][] classCourseDay; // 同课同日 [classIdx][courseIdx 稀疏化为 map 亦可][day]
int[] taskScheduledCount;  // 每任务已排大节数
```

操作 `place(assignment)` / `remove(assignment)` / `check(assignment)` 均 O(1)。

`check` 的判定顺序与失败编码**逐条对齐** `ScheduleConflictService.checkConflict` 的 `[TYPE]` 标签：`TEACHER_UNAVAILABLE`、`TEACHER_CONFLICT`、`CLASS_CONFLICT`、`ROOM_CONFLICT`、`CLASSROOM_CAPACITY_NOT_ENOUGH`、`ROOM_TYPE_MISMATCH`、`TEACHER_DAILY_LIMIT`、`CLASS_DAILY_LIMIT`、`SAME_COURSE_SAME_DAY`、`TASK_NOT_FULLY_SCHEDULED`。

注意两处现有语义细节（对拍测试重点）：

1. DB 版每日上限用 `>=` 拒绝（待插入尚未入库）；`AutoScheduleService` 私有版用 `<` 放行——两者等价，内存版按"已计数 + 1 > max 则拒绝"实现。
2. 停用教师/班级/教室（`TEACHER_DISABLED` 等）在装载阶段直接过滤或标记，不进入候选集。

## 4. 回溯求解器（R3）

```
1. 把每个任务拆成 requiredSlots 个"待排大节"，锁定项先 place。
2. 主循环：
   a. MRV 选下一个待排大节：候选 (slot, room) 数最少者优先；
      并列时回退 SchedulingSupport.sortTasks 序。
   b. 候选按值启发排序（LCV：选择后剩余任务候选数减少最少的优先；
      实现成本高时退化为现有在线 candidate 加权分）。
   c. place 第一个候选，入栈；无候选则回溯：弹栈、remove、换下一候选。
3. 回溯次数超过 SolverConfig.maxBacktracks（默认 100_000）：
   停止回溯，剩余大节按贪心 first-fit 收尾，排不进的进未排列表。
4. 时间预算（SolverConfig.feasibleTimeBudgetMs，默认 5_000）同样触发收尾。
```

同任务多个大节的"同课同日"约束天然由检测器拦截；不允许同任务两个大节同一天（与现有 `usedDays` 语义一致，`ALLOW_SAME_COURSE_SAME_DAY=true` 时放开）。

## 5. 模拟退火优化器（R4）

```
输入：可行解 S0、ObjectiveFunction f（越小越好，f = Σ weight_i × penalty_i）、种子 seed
温度：T0 = 初始接受 ~50% 劣化的经验值（首轮采样 100 个随机邻居的劣化均值估出）
降温：T = T0 × 0.97^k，每温度等级迭代 L = max(100, 任务数 × 5) 次
邻居：
  - 70% 单点移动：随机选一个非锁定 assignment，换到随机可行 (slot, room)
  - 30% 两点交换：随机选两个非锁定 assignment 交换时段（教室按各自约束重选）
  生成的邻居必须通过 InMemoryConflictDetector.check —— 不可行直接丢弃重采样
接受：Δ<0 接受；否则以 exp(-Δ/T) 概率接受
停止：温度 < T0×1e-4，或耗时超 SolverConfig.optimizeTimeBudgetMs（默认 10_000）
输出：历史最优解（不是最后解）
```

### 目标函数与 rescore 对齐

`ObjectiveFunction` 复用 `ScoringFunctions` 的离线 penalty 系列（`penaltyVariance` / `penaltyDuplicateCourse` / `penaltyContinuous` / `penaltyClassroomUtilization` / `penaltyMorningPriority`），输入由 `EngineSolution` 转出的 `SchedulePlanItem` 临时列表构造，权重取 `schedule_rule_weight`。这保证"退火优化的分数"与"落库后 rescore 的分数"同源。

性能注意：penalty 系列是全量重算（O(items)），退火每步增量算分是后续优化项，**第一版允许全量重算**——内存内全量算一次远快于一次 DB 查询，时间预算兜底。

### 随机性纪律

- 全引擎只允许一个 `java.util.Random(seed)` 实例，从 `SolverConfig` 注入。
- 禁止 `Math.random()`、无种子 `new Random()`、`System.nanoTime()` 参与决策（计时只用于预算判断）。

## 6. 落库与接入（R5）

`V3ScheduleGenerateService.normalizeStrategyType` 增加 `SOLVER_V8` 分支，`strategyLabel` 增加"智能求解"。生成流程：

```
装载 EngineContext → EngineFacade.solve → EngineSolution
→ Assignment 转 SchedulePlanItem（slot.periodNo → startPeriod=2×periodNo-1, endPeriod=startPeriod+1，
   遵守 validatePeriodPair 不变式；冗余字段 teacherId/classId/courseId 照现有方式填）
→ 复用现有 plan 落库、未排任务落库、generate log、rescore 触发
→ PerformanceBaselineService.recordSafely(OP_*, ..., extra: {seed, backtracks, annealingSteps, initialScore, finalScore})
```

请求参数扩展（`ScheduleGenerateRequest` 加可选字段，旧策略忽略）：`solverSeed`（缺省随机生成并回写日志）、`solverTimeBudgetMs`（缺省 15_000，上限 60_000，防止压垮前端 120s 超时）。

## 7. 失败与降级路径

| 情形 | 行为 |
|---|---|
| 数据规模为 0（无任务/无时段/无教室） | 走现有空数据校验路径，行为与旧策略一致 |
| 回溯+收尾后仍有未排 | 正常产出 PARTIAL 方案 + 未排列表（与旧策略同语义） |
| 退火时间预算内无改进 | 返回回溯可行解（退火只增不减质量，因为输出历史最优） |
| 引擎抛出任何 RuntimeException | 上抛由现有事务回滚 + 审计失败记录兜底，不留半成品方案 |
