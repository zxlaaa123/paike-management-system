# V8 可行性研究：排课引擎 2.0

日期：2026-06-12

状态：已立项（2026-06-12 决策确认，见文末决策记录）

前置版本：V7 Final（V1-V7 已全部收口，最终验收 52/52 E2E 通过，见 `docs/v7/V7_FINAL_最终验收记录.md`）

## 1. 背景与定位

`V7_FINAL_项目最终说明.md` 的结论是"不建议继续扩展为 V8 功能迭代"。本研究不推翻该结论的本意——**不再横向增加功能页面**——而是论证一个纵向方向：重构排课核心算法。

理由：系统功能广度已闭环（基础数据 → 教学任务 → 自动/手动排课 → 方案管理 → 质量评分 → 修复流程 → 系统治理），但作为系统"心脏"的排课引擎，算法成熟度是全项目最低的部分。V8 若立项，应当只做这一件事。

## 2. 现状诊断

### 2.1 算法层面：贪心首次适配，无回溯

`AutoScheduleService` 的实际算法：

1. 任务按启发式排序（`SchedulingSupport.sortTasks`，按教师禁排数等排序）。
2. 逐任务调用 `arrangeOneTask`，内部对每个待排大节做 slot × room 双层循环，找**第一个**无冲突组合（`tryFindFirstFitAssignment`）。
3. 某一节找不到位置时直接 break，任务进入未排课列表（`unscheduled_task`）。

问题：

- **无回溯**：前序任务占用了关键位置后，后序任务即使"换个位置就能全排下"也会失败。排课成功率取决于任务排序运气。
- **V3 多策略是伪多样性**：`V3ScheduleGenerateService` 的四种策略（`TEACHER_PRIORITY` / `CLASS_BALANCE` / `CLASSROOM_UTILIZATION` / `COMPREHENSIVE`）本质只是改变任务排序和候选偏好，底层仍是同一套贪心放置，方案间差异有限。
- **软目标零感知**：V4 评分规则衡量"周五下午节数、教师超载、班级超载"等指标，但生成器只找第一个不冲突的格子，对这些指标完全不优化。当前闭环是"贪心生成 → 评分发现问题 → V5 人工修复"，即先制造问题再修。

### 2.2 性能层面：内层循环直接打数据库

- `ScheduleConflictService.checkConflict` 单次调用包含 6+ 个 DB 查询（任务/时段/教室查询、同时段排课列表、任务已排计数、每日冲突计数）。
- 自动排课的复杂度约为 O(任务数 × 时段数 × 教室数) 次 `checkConflict` 调用。
- 估算：300 任务 × 20 时段 × 50 教室的院系规模下，最坏情况数十万次 DB 往返，单次排课分钟级起步，不可用。
- V7 已建好 `PerformanceBaselineService`（记录每次自动排课/方案生成的规模与耗时），但目前只记录、未驱动任何优化。

### 2.3 模型层面：缺周次维度

`Schedule` 实体没有起止周/单双周字段，整学期一张周课表。这是真实高校排课的硬需求，但属于数据模型大改，**本研究建议列为 V8 非目标**（可作 V9 候选），避免算法重构与模型重构耦合。

## 3. V8 目标

### 3.1 核心目标

1. **内存化约束模型**：排课开始时一次性加载学期全量数据（任务、时段、教室、已有排课、禁排、规则），冲突检测改为内存位图/哈希查询，引擎运行期间零 DB 读。预期内层检测从毫秒级降到微秒级（10-100 倍整体提速）。
2. **真正的求解算法**，两阶段：
   - 阶段一（可行解）：回溯搜索 + 启发式（MRV 最少剩余值选任务、LCV 最少约束值选位置），保证"有解必找到"，消灭贪心的伪失败。
   - 阶段二（优化解）：在可行解上跑元启发式（模拟退火或遗传算法），目标函数**直接复用 V4 评分规则**——生成器优化的就是评分器衡量的。
3. **新旧引擎并存**：新引擎作为 V3 方案生成的新策略接入（如 `SOLVER_V8`），旧贪心引擎保留作 baseline。正式课表入口默认策略可配置。

### 3.2 量化验收口径（复用现有基础设施）

| 指标 | 数据来源 | 目标 |
|---|---|---|
| 排课成功率（未排任务数） | `unscheduled_task` | 在相同数据集上 ≤ 旧引擎，回溯阶段对"实际有解"的用例 100% 排满 |
| 方案质量分 | V4 `schedule-score` | 优化阶段得分 ≥ 旧引擎所有策略的最优方案 |
| 耗时 | V7 `performance_baseline` | 300 任务规模 < 10s（贪心同规模做对照） |
| 回归 | 现有 52 个 E2E + 后端单测 | 全绿，旧引擎行为不变 |

这是本方向最大的优势：V4 评分、V5 修复、V7 性能基线现成地构成新引擎的评估体系，可产出"新 vs 旧：得分 +X、未排 -Y、耗时 -Z%"的量化报告，具备毕业设计/论文级别的叙事价值。

## 4. 技术选型

### 方案 A：自研回溯 + 模拟退火（推荐）

- 纯 Java 实现，无新依赖；算法本身是教学价值核心。
- 回溯负责可行性，退火负责软约束优化，工程量可控。
- 风险：退火调参（温度曲线、邻域算子）需要实验轮次。

### 方案 B：Google OR-Tools CP-SAT

- 课表问题是 CP-SAT 教科书场景，硬约束 + 软约束加权目标一次建模解决，求解质量上限最高。
- 引入 `com.google.ortools:ortools-java`（含原生库，约 70MB+，需验证 Windows 本地与 CI 兼容性）。
- 风险：黑盒求解器削弱"算法研究"的叙事；原生依赖增加部署复杂度。

### 方案 C：仅做内存化重构，不换算法

- 只解决性能问题（2.2），不解决质量问题（2.1）。
- 工程量最小，可作为 A/B 的第一阶段先行交付。

**建议路线：C → A**，即先内存化（独立可验收，立即拿到性能提升数据），再上回溯+退火。OR-Tools 作为 A 完成后的对照实验（可选阶段）。

## 5. 改动范围与风险

### 5.1 改动面（基于 codegraph 影响分析）

- `ScheduleConflictService.checkConflict` 仅 3 个调用方（`ScheduleService` 内），手动排课路径**不动**，新引擎内部自带内存版冲突检测。
- 新增：`engine/` 包（约束模型、回溯求解器、退火优化器、内存冲突检测器），不改现有 Service 行为。
- 接入点：`V3ScheduleGenerateService.normalizeStrategyType` 增加新策略分支；`AutoScheduleService` 可选切换。
- 数据模型：**零改动**（不加周次，复用现有表）。

### 5.2 主要风险

| 风险 | 缓解 |
|---|---|
| 内存模型与 DB 版冲突检测语义不一致 | 写"双跑对拍"测试：同一数据集下内存检测与 `checkConflict` 逐格比对结论 |
| 退火结果不稳定、难复现 | 固定随机种子入参；性能基线记录种子与得分 |
| 锁定课程（V4 lock）语义在新引擎中遗漏 | 锁定排课作为预占用常量写入约束模型，求解前置校验 |
| 回归面 | 旧引擎代码路径不删不改，策略开关隔离 |

## 6. 阶段划分（草案）

1. **阶段 1**：内存约束模型 + 内存冲突检测器 + 双跑对拍测试（= 方案 C）。
2. **阶段 2**：回溯求解器接入 V3 新策略，未排任务对比验收。
3. **阶段 3**：模拟退火优化器，目标函数对齐 V4 评分规则，质量分对比验收。
4. **阶段 4**：性能基线对比报告 + 文档收口（V8_FINAL）。
5. **阶段 5（可选）**：OR-Tools CP-SAT 对照实验。

每阶段独立可验收、可单独合入 main，任一阶段后停止项目仍处于可交付状态。

## 7. 结论

V8 立项**有必要且方向唯一**：不做功能扩展，只做排课引擎纵深重构。它解决的是系统当前真实存在的两个硬伤（贪心质量上限、DB 循环性能），且 V4/V5/V7 的既有设施天然构成其评估体系，投入产出比和叙事价值都显著高于任何横向功能。

## 8. 决策记录（2026-06-12，已拍板）

1. **立项 V8**，按 C → A 路线执行（先内存化，再回溯+退火）。
2. **技术选型：自研**（方案 A）。OR-Tools 对照实验**取消**（开发机配置有限，且原生依赖增加部署负担），第 6 节阶段 5 作废。
3. **周次/单双周确认为非目标**，推迟到 V9 候选。

执行文档见同目录 `V8_01` ~ `V8_06`。
