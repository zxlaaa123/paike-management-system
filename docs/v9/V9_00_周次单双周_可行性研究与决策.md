## 0. 一句话结论

**技术上可行，需求是真问题，但它是本项目耦合度最高的改造，贯穿"数据模型 → 输入源 → 冲突检测 → 评分 → 导出 → V4/V5 试算校验 → 正式课表应用 → V8 引擎 → 前端"九条链路。** 关键发现：`week_type` 字段已"半激活"（表有列、实体有字段、多处透传，但恒为 ALL、无 ODD/EVEN 分支），改造实质是"把恒为 ALL 的透传链路改成真实值 + 补齐漏掉的链路"。评估为 **3-4 周中大型改造**，建议走独立 V9 分支 + 原型验证先行 + 严格分阶段，**严禁在 main 上增量做**。

## 1. 为什么要做（需求来源）

### 1.1 真实排课场景的刚需

高校真实排课普遍存在以下场景，当前系统**全部不支持**：

| 场景 | 当前行为 | 真实需求 |
|---|---|---|
| 单双周课程 | 一门课只能固定排在某天某节，每周边上 | "体育"单周上、"思政"双周上，共用一个时段 |
| 起止周 | 任务从第 1 周排到学期末 | "前 8 周实验课"、"后 8 周实训课"，同一时段前后半学期不同课 |
| 周学时分布 | `weeklyHours` 只能表示"每周 N 节"，均匀分布 | "前 8 周 4 节/周 + 后 8 周 2 节/周" |

### 1.2 为什么 V8 没做

`V8_01_版本需求说明.md` 第 4 节明确列"周次/单双周/起止周"为非目标。原因是 V8 聚焦引擎质量（回溯+退火），且"数据模型零改动"是 V8 的锁定决策。**周次改造必然动数据模型，与 V8 决策冲突，因此被推迟。**

### 1.3 现状证据：概念已"半激活"（评审修正后）

> ⚠️ 本节为评审重点修正项。初稿称 weekType"全链路从未读写"是**错误事实断言**。两位评审模型独立 grep 后确认：字段被多处写入与透传，但恒为 "ALL"，从无 ODD/EVEN 分支。

| 层 | 周次概念现状 | 证据 |
|---|---|---|
| `schedule_plan_item` 表 | ✅ **有 `week_type` 列**，`VARCHAR(20) DEFAULT 'ALL'`，注释 `ALL/ODD/EVEN` | `db/v3_schedule_plan.sql:45` |
| `SchedulePlanItem` 实体 | ✅ **有 `weekType` 字段** | `entity/SchedulePlanItem.java:42` |
| **透传/写入点（评审新增）** | ✅ **多处存在，恒为 "ALL"** | `V3ScheduleGenerateService.java:504,581`（setWeekType("ALL")）、`ObjectiveFunction.java:73,98`（引擎构建时 setWeekType("ALL")）、`SchedulePlanService.java:724`（copy 透传）、`V4ScheduleReplanService.java:202`、`V5SimulationService.java:893,1368`、`SchedulePlanItemVo.java:102` |
| 前端 `SchedulePlanItem` interface | ✅ **有 `weekType: string`** | `frontend/src/api/schedulePlan.ts:38` |
| **单双周业务分支** | ❌ **全链路无 ODD/EVEN 判断** | grep 无任何 if/switch 分支 |
| `schedule` 表（正式课表） | ❌ **无 week_type 列**，14 字段纯 `time_slot_id` | `db/schema.sql:118-129` |
| **正式课表唯一键** | ❌ **三个唯一键均不含 week_type** | `db/v22_schedule_semester_unique.sql:44,55,66`——`(semester_id, time_slot_id, resource_id, active_key)` |
| `schedule_plan_item` 唯一键 | ❌ `uk_plan_task_slot` 不含 week_type | `v3_schedule_plan.sql:53` |
| V8 引擎 `TimeSlotData` | ❌ 只有 `(dayOfWeek, periodNo)` | `engine/model/EngineContext.java:30` |
| **`TeachingTask` 输入源** | ❌ **无任何周次输入字段**（评审新增） | `entity/TeachingTask.java`——只有 `weeklyHours`，无 weekType/startWeek/endWeek |

**定性**：`week_type` 是 V3 时期预留、后被多处透传但从未激活的字段。改造不是"从零接线"，而是"把恒为 ALL 的透传改成真实值，并补齐评分/导出/试算/正式课表等漏掉的链路 + 补 TeachingTask 输入源"。比"从零"容易，但**比初稿预估的更广**。

## 2. 影响面分析（全链路耦合点，评审补全版）

本节用代码实证列出**每一处需要改动的位置**。**带 ⚠️ 的为评审新发现/修正项**。

### 2.1 数据模型层（必改）

| 改动 | 位置 | 说明 |
|---|---|---|
| `schedule` 表加 `week_type` 列 | `schema.sql:118` | 正式课表当前无此列。新增迁移脚本 `v23_*.sql`：`ALTER TABLE schedule ADD COLUMN week_type VARCHAR(20) NOT NULL DEFAULT 'ALL'`。历史数据自动回填 ALL。 |
| ⚠️ **`schedule` 表三个唯一键重建** | `v22_schedule_semester_unique.sql:44,55,66` | 现唯一键 `(semester_id, time_slot_id, resource_id, active_key)` 不含 week_type，**单双周正式课表会被唯一约束挡掉**。必须 DROP + ADD 含 week_type 的新键。**这是逻辑漏洞，不改则功能不可用。** |
| `schedule_plan_item` 唯一键加 `week_type` | `v3_schedule_plan.sql:53` | 当前 `uk_plan_task_slot` 不含 week_type，单双周下同一任务同时段允许 ODD+EVEN 两条记录，当前唯一键会冲突。**数据正确性问题。** |
| 三个时间索引加 `week_type` | `v3_schedule_plan.sql:56-58` | 冲突检测性能依赖。 |
| `Schedule` 实体加 `weekType` 字段 | `entity/Schedule.java` | 对应表字段。 |
| ⚠️ **`TeachingTask` 加周次输入字段** | `entity/TeachingTask.java` | **评审关键发现：当前无任何输入源**。必须加 `weekType`（ALL/ODD/EVEN），可选 `startWeek`/`endWeek`（仅选项 B）。**不加则用户无法创建单双周任务，激活 week_type 无意义。** |

### 2.2 冲突检测层（核心难点，三套并行实现）

**这是改造最危险的部分**——系统里有**三套冲突检测**，语义必须同步一致，否则单双周课表会出现幽灵冲突或漏检。

| 实现 | 位置 | 当前时间判定逻辑 | 单双周需改为 |
|---|---|---|---|
| ① DB 版（正式课表用） | `ScheduleConflictService.checkConflict:54` | `teacher_id + time_slot_id` 唯一 | 加 week_type 维度 |
| ② V3 plan item 版 | `V3ScheduleGenerateService.hasConflict:416` | `weekday + startPeriod + resource` | 加 week_type 维度 |
| ③ V8 引擎内存版 | `InMemoryConflictDetector:60` | `boolean[resource][slot]` 占用位图 | 占用位图加 week_type 维度 |

**冲突矩阵规则**（必须三处统一实现 + 三路对拍测试）：

```
        ALL    ODD    EVEN
ALL     冲突   冲突    冲突
ODD     冲突   冲突    不冲突
EVEN    冲突   不冲突  冲突
```

### 2.3 V8 引擎层（影响最大）

| 组件 | 当前 | 单双周改造 |
|---|---|---|
| `EngineContext.TimeSlotData` | `(index, originalId, dayOfWeek, periodNo)` | 扩展。两种方案（评审建议方案 X）：方案 X = TimeSlotData 加 weekType，timeSlotIndex 物理翻倍（每个物理时段 × 2 周次）；方案 Y = Assignment 加独立 weekTypeIndex。**方案 X 下游改动小，推荐。** |
| `Assignment` record | `(task, slot, timeSlot, classroom)` | 方案 X 无需改；方案 Y 加 weekTypeIndex |
| `InMemoryConflictDetector` 占用计数 | 按 `(resource, slot)` | 按 `(resource, slot, weekType)`，内嵌冲突矩阵 |
| `NeighborOperator` 邻域 | 移动/换教室 | 可选扩展：换周次类型 |
| `ObjectiveFunction` | 按天均衡等 penalty | 见 2.5 评分链 |
| `BacktrackingSolver` MRV | 候选位置数 | 候选空间 ×2，需测回溯预算 |
| `IncrementalPenaltyState` | 按 weekday+startPeriod 聚合 | 见 2.5 |

引擎纯度约束（V8_06 红线）：`engine/` 包不得引入 Spring/Mapper/Math.random。周次逻辑必须保持纯内存。

### 2.5 ⚠️ 评分链（评审重点补全）

**评审发现：整个评分链路按 weekday+startPeriod 聚合，未纳入 week_type 维度。单双周下"教师日课时""班级日课时"计算口径不明。**

| 组件 | 当前聚合维度 | 问题 |
|---|---|---|
| `ScoringFunctions`（离线 penalty） | weekday+startPeriod | `ScoringFunctions.java:57` 等 |
| `ScheduleScoreService` | weekday+startPeriod | `:198` |
| `ObjectiveFunction`（引擎目标函数） | weekday+startPeriod | `:58` |
| `IncrementalPenaltyState` | weekday+startPeriod | 6 个聚合 Map |

**关键设计决策（必须先定）**：单双周课程如何计入日/周负荷？
- 方案 α：ODD/EVEN 按 0.5 倍计入，ALL 按 1 倍。
- 方案 β：按实际周次独立计数（单周看单周负荷，双周看双周负荷）。
- 方案 γ：不折算，单双周各算各的，ALL 与两者都冲突。

**此项不定，评分会漂移，rescore 结果与用户预期不符。**（风险 R7）

### 2.6 ⚠️ 导出链（评审发现逻辑漏洞）

**`TimetableService.java:309-314`** 用 `buildCellKey(dayOfWeek, period)` 做 map key，合并函数 `(first, second) -> first`。单双周下 ODD+EVEN 两条记录落到同一 key，**后者被静默丢弃，导出的 Excel 只显示一条**。

**这是逻辑漏洞，不是优化项。** 改法：单元格文本拼接（如 "体育[单] / 思政[双]"），或导出分单/双周两个 sheet。

### 2.7 ⚠️ V4/V5 试算与校验链（评审补全）

| 组件 | 位置 | 问题 |
|---|---|---|
| `V5RuleEvaluationService` | `:152` | 按 day/slot 聚合，单双周下可能假冲突 |
| `V5ConsistencyCheckService` | `:369` | 同上，一致性检查的硬冲突扫描线需纳入 week_type |
| `V5CandidatePositionService` | `:305` | 候选位置推荐按日聚合 |

**后果**：单双周课程在 V5 修复流程里会被误报为冲突，或候选位置推荐错误。

## 4. 方案选项（待裁决）

### 选项 A：仅单双周（ALL/ODD/EVEN）—— **推荐**

激活半预留概念，不动起止周。覆盖最高频场景（体育/思政单双周共用时段）。两位评审均推荐 A。

### 选项 B：单双周 + 起止周

`teaching_task` 加 start_week/end_week，冲突检测按周区间重叠判定。复杂度陡增，引擎时间模型需重设计。**两位评审均建议 B 后置。**

### 选项 C：不做，维持现状

适合演示/交付定位，不想承担回归风险。

| 1 | 项目定位 | **真实可用系统**（执行分阶段） | 虽是课程设计/演示场景，但向真实可用靠拢不冲突；目标定高，执行用 V9.1/V9.2 分阶段控制风险 |

| 5 | 评分折算规则（R7） | **β（单双周独立计数）** | 最符合真实体感；α 的 0.5 折算会导致引擎误判余量、单双周超排；γ 只管冲突不管负荷，评分会漂移。聚合维度从"按天"扩展为"按天×周次类型" |

### 评分折算规则 β 的具体含义（裁决依据）

β 方案下，单双周课程按实际周次独立计入负荷：

- 单周(ODD)课程 → 计入"单周负荷"
- 双周(EVEN)课程 → 计入"双周负荷"
- 全周(ALL)课程 → 同时计入单周负荷和双周负荷

排课引擎需**同时保证单周均衡和双周均衡**。举例：某老师周一第1-2节单周体育、双周思政，则单周周一负荷=1、双周周一负荷=1，两天各自均衡。这避免了 α 方案"算成0.5导致超排"的问题。

实现代价：`ScoringFunctions` / `ScheduleScoreService` / `ObjectiveFunction` / `IncrementalPenaltyState` 的聚合维度从 `(teacher/day)` 扩展为 `(teacher/day/weekType)`，已被阶段 4b（3-4天）预算覆盖。

### 未裁决的后续项（实施中再定）
