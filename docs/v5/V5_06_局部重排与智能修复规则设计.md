# V5_06_局部重排与智能修复规则设计

# 排课系统 V5 局部重排与智能修复规则设计

> 版本：V5 版本  
> 文档类型：局部重排与智能修复规则设计  
> 适用项目：排课系统仿真 / 高校排课管理系统  
> V5 定位：约束驱动的局部重排与智能修复优化版  
> 前置基础：V3 自动排课与评分规则、V4 质量分析与风险诊断、V5 数据库扩展设计、V5 API 接口设计、V5 前端页面设计  
> 重要原则：V5 的智能修复和局部重排必须先生成试算方案，不允许直接覆盖正式课表；AI 只能解释和辅助建议，不能直接修改排课数据。

---

## 一、文档说明

本文档用于说明排课系统 V5 版本中“局部重排”和“智能修复”的规则体系、算法思路、处理流程、评分方式、候选位置生成规则、修复建议生成规则、课程锁定保护规则、试算方案生成规则和验收标准。

V5 不是重新写一个全新的排课算法，也不是推翻 V3 已经建立的多方案自动排课机制，而是在 V3 / V4 的基础上继续深化：

```text
V3：生成方案、评分、对比、应用、回滚
V4：分析方案、解释评分、诊断风险、局部调整、课程锁定
V5：针对风险生成修复建议，并在锁定保护下进行局部重排试算
```

本文档重点回答以下问题：

1. 风险诊断结果如何转化为修复任务；
2. 系统如何生成可执行的修复建议；
3. 系统如何生成可替换的时间、教室和组合候选位置；
4. 局部重排时哪些课程可以动、哪些课程不能动；
5. 锁定课程如何参与约束判断；
6. 修复前后如何重新评分和对比；
7. 试算方案如何生成、保存、废弃和应用；
8. AI 在修复流程中能做什么、不能做什么；
9. 如何控制 V5 的复杂度，避免变成不可控的大型求解器项目。

---

## 二、V5 修复规则与前置版本的关系

### 2.1 与 V3 自动排课规则的关系

V3 已经定义了自动排课的基本规则，包括：

1. 教学任务排序；
2. 候选位置生成；
3. 硬约束过滤；
4. 软约束评分；
5. 多方案生成；
6. 方案总分计算；
7. 未排任务原因分析；
8. 排课日志记录；
9. 手动调整后重新评分；
10. 方案应用与回滚。

V5 不重写这些规则，而是复用它们。

V5 的区别在于：

```text
V3：从一批教学任务出发，生成完整排课方案
V5：从已有方案或正式课表中的问题出发，只修复局部问题
```

因此，V5 更关注：

1. 哪些课需要移动；
2. 哪些课不能移动；
3. 哪些位置可以替换；
4. 修复后是否比修复前更好；
5. 修复过程是否安全、可解释、可回退。

---

### 2.2 与 V4 风险诊断的关系

V4 已经提供了质量分析、评分详情、风险诊断和局部调整能力。

V4 风险诊断的结果一般包括：

1. 风险类型；
2. 风险等级；
3. 影响对象；
4. 关联课表项；
5. 风险描述；
6. 处理建议。

V5 在此基础上继续扩展：

```text
V4 风险诊断：发现问题、解释问题
V5 智能修复：生成候选修复方案、试算修复结果、比较修复前后效果
```

也就是说，V5 的入口通常来自 V4 的风险诊断中心。

---

### 2.3 与 V5 数据库和接口设计的关系

V5 修复规则需要与以下数据对象保持一致：

```text
schedule_repair_task          修复任务
schedule_repair_suggestion    修复建议
schedule_repair_candidate     修复候选位置
schedule_repair_scope         修复范围
schedule_repair_compare       修复前后对比
schedule_constraint_rule      约束规则字典
schedule_data_check_result    数据一致性检查结果
```

V5 修复规则也需要与以下接口保持一致：

```text
约束规则接口
修复任务接口
修复建议接口
候选位置接口
修复范围接口
试算方案接口
优化前后对比接口
数据一致性检查接口
AI 修复解释接口
```

开发时不能出现以下情况：

1. 规则文档说可以移动锁定课程，但数据库和接口禁止移动；
2. 接口允许直接应用试算结果，但规则要求先生成方案；
3. 前端显示“AI 自动修复”，但后端实际上只允许 AI 生成文字解释；
4. 局部重排绕过 V3 的 `schedule_plan` / `schedule_plan_item` 机制。

## 三、V5 修复规则总体原则

### 3.1 先诊断，后修复

V5 不应该无目的地重新排课。

正确流程应是：

```text
选择方案或正式课表
  ↓
执行风险诊断或质量分析
  ↓
发现具体风险或优化目标
  ↓
创建修复任务
  ↓
生成修复建议和候选位置
  ↓
生成试算方案
  ↓
对比修复前后效果
  ↓
用户决定是否应用
```

如果没有明确风险或优化目标，不建议直接执行局部重排。

---

### 3.2 先试算，后应用

V5 的所有修复结果必须先生成试算方案。

不允许：

```text
点击“智能修复”后直接修改 schedule 正式课表
```

必须采用：

```text
生成修复试算方案
  ↓
保存到 schedule_plan / schedule_plan_item
  ↓
展示修复前后对比
  ↓
用户确认
  ↓
再走已有应用方案流程
```

这样可以继续保持 V3 的核心安全原则：

> 自动排课结果和正式课表必须分离。

---

### 3.3 先保护锁定课程，再移动其他课程

局部重排时，锁定课程具有最高优先级。

被锁定课程默认不能被移动、删除、替换或覆盖。

只有满足以下条件时，才允许处理锁定课程：

1. 用户明确解除锁定；
2. 锁定类型允许部分变更；
3. 后端确认变更不违反锁定规则；
4. 前端明确提示用户该操作会影响已锁定课程。

---

### 3.4 先保证硬约束，再优化软约束

V5 修复必须遵循和 V3 一致的基本顺序：

```text
硬约束过滤
  ↓
修复约束保护
  ↓
软约束评分
  ↓
偏好约束排序
  ↓
生成推荐建议
```

硬约束不满足的位置，不能作为有效候选位置。

软约束不满足的位置，可以作为候选，但需要扣分并说明原因。

---

### 3.5 修复建议必须可解释

V5 的修复建议不能只显示：

```text
推荐移动到周三第5-6节
```

而应说明：

```text
推荐移动到周三第5-6节，原因是该时间段教师、班级、教室均无冲突，教室容量满足要求，且移动后方案总分预计提升 6 分。
```

每条修复建议至少应说明：

1. 修复目标；
2. 修复动作；
3. 修复后是否仍有冲突；
4. 评分变化；
5. 风险变化；
6. 影响范围；
7. 推荐理由。

---

### 3.6 不追求全局最优，追求局部可控

V5 不建议直接引入复杂求解器。

V5 的目标不是求出理论最优课表，而是：

1. 修复已有冲突；
2. 减少明显风险；
3. 尽量保持课表稳定；
4. 避免大规模改动；
5. 让用户看得懂、能确认、可回退。

因此，V5 推荐使用：

```text
规则过滤 + 候选评分 + 局部贪心 + 小范围重试
```

而不是一上来使用：

```text
大型约束求解器 / 遗传算法 / 模拟退火 / 禁忌搜索
```

这些复杂算法可以作为论文展望，不作为 V5 主线。

## 四、核心概念说明

### 4.1 修复任务

修复任务表示一次明确的排课修复操作。

它可以来源于：

1. 某条风险诊断记录；
2. 某个未排教学任务；
3. 用户手动选择的课程范围；
4. 正式课表的一次局部优化请求；
5. 数据一致性检查发现的问题。

修复任务不是最终方案，而是一次修复流程的管理对象。

---

### 4.2 修复建议

修复建议是系统根据修复任务生成的具体处理方案。

例如：

```text
更换教室
更换时间
更换时间 + 教室
拆分课时
重新安排未排任务
忽略低风险项
生成局部重排方案
```

一条修复任务可以有多条修复建议。

---

### 4.3 候选位置

候选位置表示某节课可以尝试安排到的位置。

候选位置通常由以下元素组成：

```text
weekday          星期
start_period     开始节次
end_period       结束节次
classroom_id     教室
teacher_id       教师
class_id         班级
course_id        课程
```

候选位置必须经过硬约束检测，并计算候选评分。

---

### 4.4 修复范围

修复范围表示本次修复允许处理的数据边界。

修复范围可以是：

```text
单条风险
单个教学任务
某个班级
某个教师
某个教室
某一天
某个时间段
某个方案
当前正式课表
```

修复范围越大，生成结果越灵活，但风险和复杂度越高。

---

### 4.5 锁定课程

锁定课程表示用户明确要求保持不变的课表项。

锁定可以分为：

```text
完全锁定：时间、教室、教师、班级都不能变
时间锁定：只能更换教室，不能更换时间
教室锁定：只能更换时间，不能更换教室
软锁定：尽量不移动，但必要时可以提示用户确认
```

局部重排时必须先读取锁定信息。

---

### 4.6 试算方案

试算方案是 V5 的核心安全机制。

试算方案表示：

```text
系统根据修复建议或局部重排规则生成的新方案，但尚未应用为正式课表。
```

试算方案应保存为新的 `schedule_plan`，并通过 `plan_category = REPAIR_TRIAL` 或类似字段区分。

---

## 五、约束规则分层设计

V5 建议将排课规则分成四类：

```text
硬约束
软约束
偏好约束
修复约束
```

---

### 5.1 硬约束

硬约束是绝对不能违反的规则。

候选位置如果违反硬约束，应直接淘汰。

常见硬约束包括：

| 规则编码 | 规则名称 | 处理方式 |
|---|---|---|
| TEACHER_TIME_CONFLICT | 教师时间冲突 | 直接淘汰 |
| CLASS_TIME_CONFLICT | 班级时间冲突 | 直接淘汰 |
| ROOM_TIME_CONFLICT | 教室时间冲突 | 直接淘汰 |
| TEACHER_UNAVAILABLE | 教师禁排时间 | 直接淘汰 |
| ROOM_CAPACITY_NOT_ENOUGH | 教室容量不足 | 直接淘汰或高风险提示 |
| ROOM_TYPE_NOT_MATCH | 教室类型不匹配 | 直接淘汰或高风险提示 |
| SEMESTER_MISMATCH | 跨学期数据混用 | 直接拒绝 |

硬约束是 V5 修复建议可信度的基础。

---

### 5.2 软约束

软约束是尽量满足的规则。

违反软约束不会直接淘汰候选位置，但会降低候选评分。

常见软约束包括：

| 规则编码 | 规则名称 | 影响 |
|---|---|---|
| TEACHER_DAILY_LOAD | 教师每日负载 | 扣分 |
| CLASS_DAILY_BALANCE | 班级每日课程均衡 | 扣分 |
| CONTINUOUS_PERIOD_LIMIT | 连续上课限制 | 扣分 |
| COURSE_DISTRIBUTION | 课程分布均衡 | 扣分 |
| ROOM_USAGE_BALANCE | 教室使用均衡 | 扣分 |
| TIME_DENSITY_BALANCE | 时间段密度均衡 | 扣分 |

---

### 5.3 偏好约束

偏好约束用于优化用户体验。

偏好约束不影响合法性，但影响推荐顺序。

常见偏好约束包括：

| 规则编码 | 规则名称 | 说明 |
|---|---|---|
| MORNING_THEORY_PRIORITY | 理论课优先上午 | 上午候选加分 |
| LAB_ROOM_PRIORITY | 实验课优先实验室 | 匹配实验室加分 |
| AVOID_FRIDAY_AFTERNOON | 避免周五下午 | 周五下午扣分 |
| KEEP_ORIGINAL_TIME | 尽量保持原时间 | 时间不变加分 |
| KEEP_ORIGINAL_ROOM | 尽量保持原教室 | 教室不变加分 |

---

### 5.4 修复约束

修复约束是 V5 新增重点。

它决定局部重排时“哪些内容不能改、哪些内容尽量少改”。

常见修复约束包括：

| 规则编码 | 规则名称 | 说明 |
|---|---|---|
| LOCKED_ITEM_PROTECTED | 锁定课程保护 | 锁定课程不得移动 |
| CHANGE_SCOPE_LIMIT | 变更范围限制 | 只能改指定范围内课程 |
| MAX_MOVED_ITEM_LIMIT | 最大移动课程数限制 | 控制影响范围 |
| KEEP_APPLIED_PLAN_HISTORY | 保留已应用方案历史 | 不覆盖历史方案 |
| TRIAL_PLAN_ONLY | 只生成试算方案 | 不直接写正式课表 |
| MINIMIZE_CHANGE | 最小改动优先 | 修复越少越好 |

修复约束的优先级应高于软约束和偏好约束。

---

## 六、风险类型与修复策略映射

V5 应根据不同风险类型生成不同修复策略。

### 6.1 教师时间冲突

风险说明：同一教师在同一时间被安排多门课程。

推荐修复策略：

1. 移动其中一门课程到其他时间；
2. 保持时间不变，更换教师；
3. 若教师不可替换，则对冲突课程执行局部重排；
4. 如果课程已锁定，则优先移动未锁定课程。

修复优先级：

```text
优先移动未锁定课程
优先移动低优先级教学任务
优先选择不影响其他班级的时间段
```

---

### 6.2 班级时间冲突

风险说明：同一班级在同一时间被安排多门课程。

推荐修复策略：

1. 移动其中一门课程到班级空闲时间；
2. 若班级空闲时间不足，尝试更换教室和时间组合；
3. 对该班级当天或本周课程进行小范围重排；
4. 尽量保持教师和教室不变。

修复优先级：

```text
优先保持教师不变
优先保持教室类型不变
优先避免造成班级单日课程过多
```

---

### 6.3 教室时间冲突

风险说明：同一教室在同一时间被多门课程占用。

推荐修复策略：

1. 保持时间不变，更换其中一门课的教室；
2. 如果无可用教室，再尝试更换时间；
3. 如果教室有类型要求，优先找同类型教室；
4. 如果容量不足，优先找容量更接近班级人数的教室。

修复优先级：

```text
更换教室优先于更换时间
同类型教室优先
容量匹配度高的教室优先
```

---

### 6.4 教师禁排时间冲突

风险说明：课程安排在教师不可上课时间。

推荐修复策略：

1. 移动课程到教师可用时间；
2. 保持教室和班级不变，优先只换时间；
3. 如果教师可用时间不足，提示规则过严；
4. 如果禁排设置不合理，提示用户检查教师禁排时间。

修复优先级：

```text
教师可用时间优先
尽量保持教室不变
尽量保持课程所在星期不变
```

---

### 6.5 教室容量不足

风险说明：班级人数超过教室容量。

推荐修复策略：

1. 保持时间不变，更换更大容量教室；
2. 优先选择同类型且容量略大于班级人数的教室；
3. 如果同时间无合适教室，再尝试换时间；
4. 不建议拆分班级，除非系统明确支持。

修复优先级：

```text
更换教室优先
容量刚好匹配优先
避免占用过大教室
```

---

### 6.6 教室类型不匹配

风险说明：课程要求实验室、多媒体教室等，但实际教室类型不符合。

推荐修复策略：

1. 保持时间不变，更换符合类型的教室；
2. 若无同时间同类型教室，则更换到其他时间；
3. 对实验课优先寻找实验室；
4. 对普通理论课允许普通教室或多媒体教室。

---

### 6.7 教学任务未排满

风险说明：教学任务要求课时没有完全安排。

推荐修复策略：

1. 为未排课时生成候选位置；
2. 优先安排到教师、班级、教室均空闲的位置；
3. 若无法安排，分析具体阻塞原因；
4. 可创建局部重排任务，释放部分低优先级课程位置。

修复优先级：

```text
先尝试直接补排
再尝试局部重排
最后提示资源不足或规则过严
```

---

### 6.8 教师负载过高

风险说明：某教师一天课程过多或连续上课过多。

推荐修复策略：

1. 将该教师当天部分课程移动到其他日期；
2. 优先移动非锁定课程；
3. 优先移动软约束得分较低的课程；
4. 移动后不能造成其他教师、班级、教室冲突。

该类属于软性优化，不应牺牲硬约束。

---

### 6.9 班级单日课程过多

风险说明：某班级一天课程过满，影响课表均衡。

推荐修复策略：

1. 将部分课程移动到课程较少的日期；
2. 避免移动主课到不合适时段；
3. 避免产生教师禁排冲突；
4. 保持课程分布尽量均衡。

---

### 6.10 时间段课程密度过高

风险说明：某个时间段安排课程过多，导致教室或教师资源紧张。

推荐修复策略：

1. 将低优先级课程移动到低密度时间段；
2. 优先移动未锁定课程；
3. 不移动已应用且人工确认的课程；
4. 优先减少风险时间段的压力。

---

## 七、修复任务创建规则

### 7.1 创建来源

修复任务可以从以下入口创建：

1. 风险诊断页面；
2. 方案详情页面；
3. 正式课表页面；
4. 未排任务页面；
5. 质量分析页面；
6. 数据一致性检查页面。

---

### 7.2 创建前校验

创建修复任务前必须校验：

1. 所属学期是否存在；
2. 原方案或正式课表是否存在；
3. 风险记录是否仍然有效；
4. 关联课表项是否仍然存在；
5. 目标数据是否属于同一学期；
6. 修复对象是否已经被其他进行中的修复任务占用；
7. 已废弃方案是否允许修复。

建议规则：

```text
已废弃方案默认不允许创建修复任务
已应用方案允许创建试算修复任务
正式课表允许创建修复任务，但结果必须先生成试算方案
```

---

### 7.3 修复模式

V5 建议支持以下修复模式：

| 模式编码 | 名称 | 说明 |
|---|---|---|
| SINGLE_RISK_REPAIR | 单风险修复 | 针对一条风险记录生成建议 |
| UNSCHEDULED_TASK_REPAIR | 未排任务补排 | 针对未排教学任务寻找位置 |
| LOCAL_REARRANGE | 局部重排 | 对指定范围内课程重新安排 |
| QUALITY_OPTIMIZE | 质量优化 | 针对低分项进行优化 |
| DATA_FIX_PREVIEW | 数据修复预览 | 针对数据一致性问题生成修复预览 |

---

### 7.4 修复任务状态

修复任务建议状态如下：

```text
CREATED              已创建
SUGGESTION_GENERATED 已生成建议
TRIAL_GENERATED      已生成试算方案
COMPARED             已完成对比
APPLIED              已应用
CANCELLED            已取消
FAILED               失败
```

状态流转建议：

```text
CREATED
  ↓
SUGGESTION_GENERATED
  ↓
TRIAL_GENERATED
  ↓
COMPARED
  ↓
APPLIED
```

也允许：

```text
CREATED / SUGGESTION_GENERATED / TRIAL_GENERATED -> CANCELLED
任意执行失败节点 -> FAILED
```

---

## 八、候选位置生成规则

### 8.1 候选位置生成目标

候选位置生成的目标是：

> 在不违反硬约束和修复约束的前提下，为待修复课程找到若干可替代时间、教室或时间+教室组合。

---

### 8.2 候选时间范围

候选时间应来自系统已有时间段配置。

必须过滤：

1. 不属于当前学期的时间段；
2. 教师禁排时间；
3. 班级已占用时间；
4. 锁定课程占用时间；
5. 用户指定排除的时间；
6. 超出课程允许周次或节次的时间。

如果是修复单条冲突，可以优先尝试：

```text
原星期同一天其他节次
  ↓
同一周其他日期
  ↓
全周可用时间
```

---

### 8.3 候选教室范围

候选教室应来自启用状态的教室。

必须过滤：

1. 已停用教室；
2. 同一时间已被占用教室；
3. 容量明显不足教室；
4. 类型不匹配教室；
5. 用户指定排除教室；
6. 锁定课程占用教室。

如果是教室冲突或容量不足，优先保持原时间，只更换教室。

---

### 8.4 候选组合生成

候选组合由：

```text
候选时间 × 候选教室
```

组合生成后需要依次执行：

```text
硬约束过滤
修复约束过滤
软约束评分
偏好约束加减分
结果排序
数量截断
```

---

### 8.5 候选数量控制

为了避免前端展示过多、后端计算过慢，建议限制候选数量：

| 场景 | 最大候选数建议 |
|---|---:|
| 单条风险修复 | 10 |
| 教室替换 | 10 |
| 时间替换 | 15 |
| 时间 + 教室组合 | 20 |
| 未排任务补排 | 20 |
| 局部重排 | 每个任务 5 到 10 个候选 |

候选数量不足时，需要返回原因：

```text
无可用时间
无可用教室
锁定课程占用过多
教师禁排过多
班级时间已满
规则过于严格
```

---

### 8.6 候选位置评分公式

候选位置建议采用 100 分制。

示例公式：

```text
candidate_score = 100
                  - hard_penalty
                  - soft_penalty
                  - change_penalty
                  + preference_bonus
```

其中：

```text
hard_penalty：硬约束违规扣分。若大于 0，候选直接无效。
soft_penalty：软约束扣分。
change_penalty：改动成本扣分。
preference_bonus：偏好加分。
```

---

### 8.7 改动成本计算

V5 推荐加入“改动成本”，避免修复一个问题却大规模扰动课表。

改动成本建议如下：

| 改动类型 | 扣分建议 |
|---|---:|
| 保持原时间和原教室 | 0 |
| 只换教室 | -5 |
| 只换时间 | -8 |
| 时间和教室都变 | -12 |
| 影响其他课程移动 | 每条 -5 |
| 移动已人工调整课程 | -15 |
| 移动软锁定课程 | -20 或要求确认 |
| 移动完全锁定课程 | 不允许 |

---

## 九、修复建议生成规则

### 9.1 修复建议类型

V5 建议支持以下修复建议类型：

| 类型编码 | 名称 | 说明 |
|---|---|---|
| CHANGE_TIME | 更换时间 | 保持课程和教室，调整到其他时间 |
| CHANGE_ROOM | 更换教室 | 保持时间，调整到其他教室 |
| CHANGE_TIME_ROOM | 更换时间和教室 | 同时调整时间和教室 |
| MOVE_OTHER_ITEM | 移动其他课程 | 为当前课程腾出位置 |
| ADD_UNSCHEDULED_ITEM | 补排未排任务 | 为未排任务新增安排 |
| LOCAL_REARRANGE | 局部重排 | 对指定范围重新试算 |
| IGNORE_LOW_RISK | 忽略低风险 | 标记为暂不处理 |
| ADJUST_RULE | 调整规则 | 提示规则过严或资源不足 |

---

### 9.2 生成顺序

修复建议生成建议采用以下顺序：

```text
1. 根据风险类型判断可用修复策略
2. 读取待修复课程和关联对象
3. 读取锁定课程和修复范围
4. 生成候选时间
5. 生成候选教室
6. 组合候选位置
7. 过滤硬约束
8. 计算候选得分
9. 生成修复建议
10. 按推荐等级排序
```

---

### 9.3 推荐等级

修复建议推荐等级建议为：

```text
HIGH       强烈推荐
MEDIUM     推荐
LOW        可选
NOT_RECOMMENDED 不推荐
```

推荐等级判断示例：

| 条件 | 推荐等级 |
|---|---|
| 修复硬冲突且不产生新冲突，评分明显提升 | HIGH |
| 修复风险但有轻微软约束扣分 | MEDIUM |
| 只能部分改善问题 | LOW |
| 修复后产生新高风险 | NOT_RECOMMENDED |

---

### 9.4 建议摘要生成规则

每条修复建议应生成简洁摘要。

示例：

```text
建议将“高等数学-软件1班”从周一第1-2节调整到周三第3-4节，并更换至 A203 教室。该调整可消除教师时间冲突，预计总分提升 5.5 分。
```

摘要应包含：

1. 课程或教学任务；
2. 原位置；
3. 新位置；
4. 修复的问题；
5. 预计评分变化；
6. 是否影响其他课程。

---

### 9.5 不生成建议的情况

以下情况可以不生成修复建议，而是返回失败原因：

1. 所有可用时间都被占用；
2. 教师禁排时间覆盖过多；
3. 没有符合容量和类型的教室；
4. 待修复课程被完全锁定；
5. 修复范围为空；
6. 所属方案已废弃且不允许修复；
7. 数据存在严重不一致，无法判断原始状态。

---

## 十、局部重排规则

### 10.1 局部重排定义

局部重排是指：

> 在保持大部分课表不变的前提下，只对用户指定范围内的部分课程重新安排，并生成新的试算方案。

局部重排不是全量自动排课。

---

### 10.2 局部重排适用场景

适合使用局部重排的场景：

1. 单个班级课程过于集中；
2. 某个教师负载过高；
3. 某个教室利用异常；
4. 多条风险互相关联，单独修复无法解决；
5. 未排任务需要通过移动其他课程腾出位置；
6. 用户锁定满意课程后，希望优化剩余课程。

不适合使用局部重排的场景：

1. 基础数据严重缺失；
2. 教师、教室资源明显不足；
3. 用户希望完全重新生成新学期课表；
4. 需要跨学期调整；
5. 需要真实复杂选课、校历、单双周规则。

---

### 10.3 可移动课程选择规则

局部重排应先确定可移动课程集合。

可移动课程应满足：

1. 属于当前修复范围；
2. 未被完全锁定；
3. 不属于用户明确排除对象；
4. 不属于已废弃方案明细；
5. 不是系统标记为不可调整的课程；
6. 移动后不会跨学期。

可移动课程优先级建议：

| 优先级 | 课程类型 |
|---|---|
| 高 | 产生冲突或风险的课程 |
| 中高 | 软约束扣分严重的课程 |
| 中 | 未人工调整课程 |
| 低 | 已人工调整但未锁定课程 |
| 禁止 | 完全锁定课程 |

---

### 10.4 保留课程规则

以下课程默认保留不动：

1. 完全锁定课程；
2. 不在修复范围内的课程；
3. 已应用正式课表中用户不希望改变的课程；
4. 明确标记为人工确认的课程；
5. 作为修复任务排除对象的课程。

保留课程在候选位置检测时应视为已占用资源。

---

### 10.5 局部重排流程

推荐流程：

```text
选择修复对象或优化范围
  ↓
读取原方案或正式课表
  ↓
读取锁定课程
  ↓
划分保留课程和可移动课程
  ↓
清空试算内可移动课程的位置
  ↓
按优先级重新安排可移动课程
  ↓
生成试算方案明细
  ↓
重新计算评分和风险
  ↓
生成修复前后对比
```

注意：

```text
清空可移动课程的位置
```

只发生在内存或试算方案中，不能直接删除原方案或正式课表数据。

---

### 10.6 局部重排排序规则

可移动课程重新排序时建议优先安排难度高的任务。

排序规则可以参考：

```text
任务难度分 = 教师可用时间少
           + 可用教室少
           + 班级空闲时间少
           + 课程类型要求严格
           + 周课时要求多
           + 原风险等级高
```

排序建议：

```text
高风险任务
  ↓
未排任务
  ↓
可用候选位置少的任务
  ↓
课程类型要求高的任务
  ↓
普通任务
```

---

### 10.7 局部重排停止条件

局部重排应有明确停止条件，避免死循环。

建议停止条件：

1. 所有可移动课程都尝试完成；
2. 达到最大尝试轮数；
3. 连续多轮没有评分提升；
4. 候选位置为空；
5. 计算时间超过限制；
6. 用户取消任务。

建议默认参数：

```text
最大尝试轮数：3 到 5 轮
单任务最大候选数：10 个
局部重排最大课程数：50 条以内
```

毕业设计项目不建议做过大规模局部重排。

---

## 十一、试算方案生成规则

### 11.1 试算方案来源

试算方案可以来自：

1. 单条修复建议；
2. 某个候选位置；
3. 局部重排任务；
4. 未排任务补排；
5. 数据一致性修复预览。

---

### 11.2 试算方案保存规则

试算方案应保存为新的 `schedule_plan`。

建议字段：

```text
plan_category = REPAIR_TRIAL
source_plan_id = 原方案ID
repair_task_id = 修复任务ID
is_trial = 1
```

试算方案明细保存到 `schedule_plan_item`。

试算方案不得直接写入 `schedule` 正式课表。

---

### 11.3 试算方案命名规则

建议命名格式：

```text
原方案名称 + 局部修复试算 + 时间
```

示例：

```text
综合最优方案-局部修复试算-2026-05-19 10:30
软件1班课表优化试算-2026-05-19 10:30
教师冲突修复试算-张老师-2026-05-19
```

---

### 11.4 试算方案状态

试算方案状态仍然可以复用方案状态：

```text
DRAFT       草稿
APPLIED     已应用
ABANDONED   已废弃
```

也可以增加试算标识：

```text
is_trial = 1
```

推荐做法：

```text
status = DRAFT
plan_category = REPAIR_TRIAL
is_trial = 1
```

当用户确认应用后，再通过已有应用方案流程转为正式课表来源方案。

---

### 11.5 试算结果必须包含的信息

每个试算方案应展示：

1. 原方案；
2. 修复任务；
3. 移动课程数量；
4. 未移动课程数量；
5. 新增课程数量；
6. 删除或未排课程数量；
7. 修复后总分；
8. 修复后风险数量；
9. 修复前后对比；
10. 是否推荐应用。

---

## 十二、评分与对比规则

### 12.1 修复前后对比维度

V5 修复前后对比建议包含：

| 指标 | 说明 |
|---|---|
| total_score | 总评分变化 |
| high_risk_count | 高风险数量变化 |
| medium_risk_count | 中风险数量变化 |
| low_risk_count | 低风险数量变化 |
| conflict_count | 冲突数量变化 |
| unscheduled_count | 未排任务数量变化 |
| moved_item_count | 被移动课程数量 |
| teacher_balance_score | 教师均衡评分变化 |
| class_balance_score | 班级均衡评分变化 |
| room_usage_score | 教室利用评分变化 |
| time_distribution_score | 时间分布评分变化 |

---

### 12.2 推荐应用判断

试算方案是否推荐应用，可以按以下规则判断：

```text
推荐应用：高风险减少，且总分提升，且没有新增硬冲突
谨慎应用：风险减少，但移动课程较多，或总分提升较小
不推荐应用：新增高风险，或总分下降明显，或锁定课程被影响
```

示例判断条件：

| 条件 | 结论 |
|---|---|
| 高风险减少 >= 1 且总分提升 >= 3 | 推荐应用 |
| 高风险不变但软约束评分提升 >= 5 | 可选应用 |
| 总分下降但解决关键硬冲突 | 谨慎应用 |
| 新增高风险 | 不推荐应用 |
| 影响完全锁定课程 | 不允许应用 |

---

### 12.3 总分重新计算规则

V5 试算方案生成后，应重新计算总分。

总分计算建议继续复用 V3 / V4 的评分体系。

不要在 V5 中另起一套完全不同的评分体系。

可以增加 V5 特有扣分项：

| 扣分项 | 说明 |
|---|---|
| CHANGE_COST | 改动成本 |
| LOCK_WARNING | 影响软锁定课程 |
| REPAIR_SCOPE_OVERFLOW | 超出修复范围 |
| NEW_RISK_CREATED | 新增风险 |
| STABILITY_LOSS | 课表稳定性下降 |

---

### 12.4 改动成本不应压过硬冲突修复

如果一个方案虽然移动课程较多，但解决了严重硬冲突，可以允许总分提升。

但如果一个方案只是微弱提升软约束评分，却移动大量课程，则不应强烈推荐。

建议逻辑：

```text
硬冲突修复收益 > 改动成本扣分 > 软约束优化收益
```

---

## 十三、课程锁定保护规则

### 13.1 锁定类型

V5 建议支持以下锁定类型：

| 锁定类型 | 含义 | 是否允许移动 |
|---|---|---|
| FULL_LOCK | 完全锁定 | 不允许 |
| TIME_LOCK | 时间锁定 | 允许换教室，不允许换时间 |
| ROOM_LOCK | 教室锁定 | 允许换时间，不允许换教室 |
| SOFT_LOCK | 软锁定 | 默认不移动，必要时提示确认 |

---

### 13.2 锁定优先级

锁定优先级建议：

```text
FULL_LOCK > TIME_LOCK / ROOM_LOCK > SOFT_LOCK > 未锁定
```

FULL_LOCK 课程在任何自动修复和局部重排中都不能被移动。

---

### 13.3 锁定冲突处理

如果风险本身发生在锁定课程上，系统不应直接移动该课程。

应给出提示：

```text
该风险涉及已锁定课程，系统不能直接移动。请先解除锁定，或选择移动其他相关课程。
```

如果有其他未锁定冲突课程，应优先移动未锁定课程。

---

### 13.4 锁定课程作为资源占用

锁定课程即使不移动，也必须参与冲突检测。

它占用的教师、班级、教室和时间段，其他候选位置不能重复使用。

---

## 十四、未排任务补排规则

### 14.1 补排目标

未排任务补排的目标是：

> 在不破坏已有课表的前提下，为未排教学任务寻找可用位置。

---

### 14.2 补排优先级

未排任务补排建议按以下优先级处理：

1. 课程要求严格的任务优先；
2. 教师可用时间少的任务优先；
3. 班级空闲时间少的任务优先；
4. 需要特殊教室的任务优先；
5. 周课时要求多的任务优先。

---

### 14.3 无法补排时的处理

如果无法补排，应生成明确原因：

```text
无可用教师时间
无可用班级时间
无符合条件教室
教室容量不足
教室类型不匹配
锁定课程占用关键时间
规则过于严格
```

同时可以给出建议：

```text
增加可用教室
调整教师禁排时间
解除部分课程锁定
扩大局部重排范围
降低某些软约束权重
```

---

## 十五、数据一致性修复预览规则

### 15.1 数据一致性问题类型

V5 数据一致性检查可能发现：

1. 教学任务未绑定学期；
2. 正式课表未绑定来源方案；
3. 方案明细引用不存在的教师、班级、课程或教室；
4. 已删除对象仍被课表引用；
5. 评分明细和方案总分不一致；
6. 风险记录关联的方案明细不存在；
7. 锁定记录指向不存在课表项；
8. 同一学期存在多个当前应用方案。

---

### 15.2 自动修复边界

V5 可以给出数据修复建议，但不建议直接自动修改核心数据。

可自动修复或半自动修复的情况：

1. 缺少分析记录，可以重新分析生成；
2. 评分明细缺失，可以重新计算；
3. 风险记录状态过期，可以标记为失效；
4. 回归测试记录缺失，不影响业务。

不建议自动修复的情况：

1. 课表引用已删除教师；
2. 课表跨学期混用；
3. 正式课表来源方案缺失；
4. 多个方案同时标记为已应用；
5. 教学任务和课表之间关系不明。

这些问题应提示用户人工确认或让开发者处理。

---

## 十六、AI 修复解释规则

### 16.1 AI 可以做什么

AI 可以用于：

1. 解释某条修复建议为什么推荐；
2. 解释修复前后差异；
3. 总结试算方案优缺点；
4. 生成答辩展示用文字；
5. 将复杂风险转化为用户容易理解的说明。

---

### 16.2 AI 不能做什么

AI 不允许：

1. 直接修改正式课表；
2. 直接应用方案；
3. 直接删除方案；
4. 绕过后端冲突检测；
5. 绕过课程锁定规则；
6. 代替后端评分计算；
7. 生成未经验证的排课结果写入数据库。

---

### 16.3 AI 输入数据要求

AI 输入应为结构化摘要，不应直接传整张数据库。

推荐输入：

```text
修复任务摘要
风险类型和等级
原方案指标
试算方案指标
移动课程列表摘要
评分变化
风险变化
锁定课程影响
系统计算出的推荐等级
```

---

### 16.4 AI 输出格式建议

AI 输出建议包含：

```text
总体结论
主要改善点
仍然存在的问题
是否建议应用
人工确认注意事项
答辩说明版本
```

## 十七、核心算法建议

### 17.1 单风险修复算法

适用于教师冲突、班级冲突、教室冲突、容量不足、类型不匹配等单点问题。

推荐流程：

```text
读取风险记录
定位关联课程
判断锁定状态
生成可移动课程集合
为可移动课程生成候选位置
过滤硬约束
计算候选得分
生成修复建议
选择最高分建议生成试算方案
重新评分和诊断
生成对比结果
```

---

### 17.2 未排任务补排算法

适用于未排任务或课时未排满。

推荐流程：

```text
读取未排教学任务
生成候选时间
生成候选教室
组合候选位置
过滤硬约束
计算候选得分
若存在可用位置，生成补排建议
若不存在可用位置，生成原因和扩大范围建议
```

---

### 17.3 局部重排算法

适用于多个问题相关联的情况。

推荐流程：

```text
确定修复范围
读取原课表数据
读取锁定课程
划分保留集合和可移动集合
清空试算中的可移动课程位置
按任务难度排序可移动课程
依次生成候选位置并选择最佳位置
若无法安排，记录未排原因
生成试算方案
重新评分、诊断和对比
```

---

### 17.4 小范围回退机制

如果某个任务无法安排，可以尝试移动一个低优先级任务腾出位置。

但回退范围要受限。

建议规则：

```text
最多回退 1 到 2 层
不移动锁定课程
不移动高优先级课程
不造成更多高风险
```

毕业设计项目不建议做复杂深度搜索。

## 十八、伪代码示例

### 18.1 单风险修复伪代码

```text
function repairSingleRisk(riskId):
    risk = loadRisk(riskId)
    originPlan = loadPlan(risk.planId)
    targetItems = findRelatedItems(risk)

    movableItems = []
    for item in targetItems:
        if isFullLocked(item):
            continue
        movableItems.add(item)

    if movableItems is empty:
        return fail("风险涉及课程均已锁定，无法自动修复")

    suggestions = []
    for item in movableItems:
        candidates = generateCandidates(item, originPlan)
        validCandidates = filterHardConstraints(candidates)
        scoredCandidates = scoreCandidates(validCandidates)
        suggestions.add(toSuggestions(item, scoredCandidates))

    sort suggestions by recommendationLevel and score
    save suggestions
    return suggestions
```

---

### 18.2 候选位置生成伪代码

```text
function generateCandidates(item, plan):
    timeSlots = loadAvailableTimeSlots(item.teacherId, item.classId)
    rooms = loadAvailableRooms(item.courseType, item.classSize)
    candidates = []

    for time in timeSlots:
        for room in rooms:
            candidate = buildCandidate(item, time, room)
            if violatesHardConstraint(candidate, plan):
                continue
            if violatesLockConstraint(candidate, plan):
                continue
            candidate.score = calculateCandidateScore(candidate)
            candidates.add(candidate)

    return topN(candidates, 20)
```

---

### 18.3 局部重排伪代码

```text
function localRearrange(scope):
    originItems = loadItemsByScope(scope)
    lockedItems = loadLockedItems(scope)

    fixedItems = []
    movableItems = []

    for item in originItems:
        if item in lockedItems or outsideScope(item):
            fixedItems.add(item)
        else:
            movableItems.add(item)

    sort movableItems by difficulty desc

    trialItems = copy(fixedItems)
    unassigned = []

    for item in movableItems:
        candidates = generateCandidatesConsideringFixed(item, trialItems)
        if candidates is empty:
            unassigned.add(item)
        else:
            best = chooseBestCandidate(candidates)
            trialItems.add(applyCandidate(item, best))

    trialPlan = saveTrialPlan(trialItems, unassigned)
    recalculateScore(trialPlan)
    diagnoseRisk(trialPlan)
    compareWithOrigin(trialPlan, scope.originPlanId)

    return trialPlan
```

## 十九、开发阶段建议

### 19.1 第一阶段：规则和候选位置基础

目标：

1. 建立约束规则字典；
2. 实现候选时间生成；
3. 实现候选教室生成；
4. 实现硬约束过滤；
5. 返回候选位置列表。

验收：

```text
输入某条课程记录后，系统能返回若干合法候选位置，并说明每个位置的得分和原因。
```

---

### 19.2 第二阶段：单风险修复建议

目标：

1. 从风险记录创建修复任务；
2. 根据风险类型生成修复建议；
3. 展示推荐等级；
4. 保存修复建议；
5. 支持忽略或选择建议。

验收：

```text
针对教师冲突、教室冲突、容量不足等风险，系统能给出至少一种可执行修复建议。
```

---

### 19.3 第三阶段：试算方案生成

目标：

1. 根据修复建议生成试算方案；
2. 保存到 schedule_plan / schedule_plan_item；
3. 不修改正式课表；
4. 重新计算评分和风险；
5. 展示修复前后对比。

验收：

```text
用户选择修复建议后，系统生成一个新的试算方案，并能看到分数和风险变化。
```

---

### 19.4 第四阶段：局部重排

目标：

1. 支持选择修复范围；
2. 支持读取锁定课程；
3. 支持只重排未锁定课程；
4. 支持生成局部重排试算方案；
5. 支持未排原因记录。

验收：

```text
用户锁定部分课程后，系统只对未锁定课程进行局部重排，并生成新的试算方案。
```

---

### 19.5 第五阶段：数据一致性检查和 AI 解释

目标：

1. 实现数据一致性检查；
2. 检查方案、课表、学期、锁定、评分等数据；
3. 可选生成 AI 修复解释；
4. 可选生成答辩说明。

验收：

```text
系统可以检查排课核心数据是否一致，并能解释试算方案为什么推荐或不推荐。
```

## 二十一、答辩展示建议

V5 答辩展示可以按以下路线讲：

```text
先展示 V4 风险诊断，说明系统发现问题
  ↓
点击某条风险，创建 V5 修复任务
  ↓
系统生成多个修复建议
  ↓
选择一个建议生成试算方案
  ↓
展示修复前后评分、风险、课表变化
  ↓
展示锁定课程不会被移动
  ↓
确认后才应用为正式课表
```

可以重点强调：

1. 系统不是盲目重排，而是基于风险进行局部修复；
2. 系统不是黑盒优化，而是给出可解释建议；
3. 系统不会直接污染正式课表，而是先生成试算方案；
4. 用户可以锁定满意课程，系统只调整未锁定部分；
5. 修复前后有量化对比，方便决策。

答辩总结语可以使用：

> V5 版本在 V4 排课质量分析和风险诊断基础上，进一步实现了约束驱动的智能修复和局部重排能力。系统能够根据具体冲突生成候选修复建议，在保护锁定课程和正式课表安全的前提下生成试算方案，并通过修复前后评分、风险和变更对比帮助用户判断是否应用，从而使排课系统从“发现问题”升级为“辅助解决问题”。

## 二十二、不要过度实现的内容

V5 不建议实现以下内容：

1. 不直接集成大型求解器作为核心依赖；
2. 不实现真实高校复杂选课系统；
3. 不实现教师调课审批流；
4. 不实现复杂多角色权限；
5. 不做云端高并发部署；
6. 不做跨校区复杂资源调度；
7. 不允许 AI 直接写数据库；
8. 不允许局部重排直接覆盖正式课表；
9. 不允许为了修复建议删除历史方案；
10. 不允许绕过后端冲突检测。

## 二十四、总结

V5 局部重排与智能修复规则的核心是：

```text
以风险为入口
以约束为边界
以候选位置为基础
以试算方案为载体
以优化对比为依据
以用户确认作为最终应用条件
```

开发时必须始终坚持：

```text
不推翻 V3 方案机制
不破坏 V4 分析诊断能力
不直接覆盖正式课表
不移动锁定课程
不让 AI 直接做业务决策
```

只要这套规则落地，V5 就可以让排课系统从：

> 能排课、能分析、能解释

进一步升级为：

> 能发现问题、能给出修复建议、能局部试算、能对比优化结果、能安全应用修复方案。
