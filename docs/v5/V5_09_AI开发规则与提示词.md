# V5_09_AI开发规则与提示词

> 项目：高校排课管理系统 / 排课系统仿真  
> 版本：V5 约束驱动的局部重排与智能修复优化版  
> 文档类型：AI 开发规则与阶段提示词  
> 适用对象：Claude Code、Trae、CodeBuddy、Codex CLI、通用 AI 编程助手  
> 核心目标：让 AI 在开发 V5 时严格遵守 V1-V4 已有架构，不重构旧系统，不破坏正式课表，不绕过后端校验，按阶段稳步实现智能修复和局部重排能力。

---

## 一、文档说明

本文档用于指导 AI 开发工具继续实现排课系统 V5 版本。

V5 的核心方向是：

> **约束驱动的局部重排与智能修复优化版**

V5 不是重新开发排课系统，也不是推翻 V1、V2、V3、V4 的已有功能，而是在已有系统基础上继续增强：

1. 约束规则分层；
2. 修复任务管理；
3. 候选位置生成；
4. 智能修复建议；
5. 试算方案；
6. 局部重排；
7. 优化前后对比；
8. 数据一致性检查；
9. 回归测试记录；
10. AI 修复解释辅助。

AI 开发时必须始终围绕这一条主线：

```text
V4 发现问题、解释问题
        ↓
V5 生成修复建议
        ↓
V5 生成试算方案
        ↓
V5 对比优化前后效果
        ↓
用户确认后再应用
```

## 三、V5 AI 开发总规则

### 3.1 不允许推翻旧系统

AI 不允许为了实现 V5 功能而重写以下模块：

```text
教师管理
班级管理
课程管理
教室管理
教学任务管理
手动排课
自动排课
教师禁排时间
排课规则配置
学期管理
排课方案管理
方案详情
方案对比
方案应用
方案回滚
质量分析
风险诊断
局部调整
课程锁定
报告导出
AI 分析
```

正确做法是：

```text
阅读现有代码
理解已有表结构和接口
在现有代码旁边增量新增 V5 能力
必要时扩展字段或新增表
保留旧接口兼容
新增功能完成后回归测试旧功能
```

错误做法是：

```text
删除旧 Service
重命名旧接口
重写旧数据库表
改变旧页面路由
让新逻辑替代所有旧逻辑
为了 V5 把 V3/V4 推倒重来
```

---

### 3.2 修复结果必须先试算

V5 中任何自动修复、半自动修复、局部重排结果，都不能直接修改正式课表。

正确流程：

```text
创建修复任务
生成候选位置
生成修复建议
生成试算方案
展示优化前后对比
用户确认
应用试算方案或生成新方案
最终再写入正式课表
```

禁止流程：

```text
发现冲突
AI 或后端直接修改 schedule 正式课表
不生成试算方案
不展示对比
不让用户确认
```

---

### 3.3 后端校验是唯一可信结果

前端只能负责展示和交互，不能决定排课修复是否合法。

以下判断必须由后端完成：

1. 教师是否冲突；
2. 班级是否冲突；
3. 教室是否冲突；
4. 教师是否禁排；
5. 教室容量是否满足；
6. 教室类型是否匹配；
7. 课程是否被锁定；
8. 是否跨学期操作；
9. 方案状态是否允许修复；
10. 试算方案是否允许应用。

---

### 3.4 锁定课程必须优先保护

课程锁定是 V5 局部重排的重要约束。

被锁定课程：

1. 不能被候选位置生成逻辑移动；
2. 不能被修复建议静默修改；
3. 不能被局部重排覆盖；
4. 应用试算方案时必须保持原位置；
5. 如果必须移动锁定课程才能修复，应提示用户先解锁。

提示示例：

```text
当前风险涉及锁定课程，系统无法自动移动该课程。
请先解除锁定，或改为人工处理。
```

---

### 3.5 严格遵守学期边界

V5 所有查询、修复、试算、重排、对比、检查，都必须绑定学期。

禁止出现：

```text
读取 A 学期教学任务，却生成到 B 学期方案
使用历史学期课程参与当前学期修复
跨学期对比修复方案
跨学期应用试算方案
```

所有核心表和接口都应携带或自动推导：

```text
semester_id / term_id
```

如果项目中使用的是 `term_id`，不得强行改成 `semester_id`；如果项目中使用的是 `semester_id`，不得混用 `term_id`。必须以现有代码为准。

---

### 3.6 方案机制不能被破坏

V3 已经建立了排课方案机制。

AI 必须遵守：

```text
自动生成结果进入 schedule_plan / schedule_plan_item
正式课表 schedule 只在用户确认应用后写入
历史方案不能随意删除
已废弃方案不能直接应用
应用方案前必须校验状态
回滚必须保留来源信息
```

V5 的试算方案也应该遵守方案化原则。

建议方案类型可使用：

```text
REPAIR_TRIAL       修复试算方案
LOCAL_REARRANGE    局部重排方案
REPAIR_APPLIED     已应用修复方案
```

具体枚举以项目现有字段为准，不得随意混用中文和英文枚举。

---

## 四、V5 数据库开发规则

### 4.1 新增优先，不重构旧表

V5 数据库扩展应遵守：

```text
新增表为主
旧表少量加字段为辅
不删除旧表
不重命名旧字段
不改变旧字段含义
旧数据必须兼容
```

推荐新增表包括：

```text
schedule_repair_task
schedule_repair_suggestion
schedule_repair_candidate
schedule_repair_scope
schedule_repair_compare
schedule_constraint_rule
schedule_consistency_check
schedule_regression_test_record
schedule_ai_repair_explanation
```

如果项目中已经存在类似表，应优先复用或兼容扩展，不要重复建功能相同的表。

---

### 4.2 新增字段必须兼容旧数据

新增字段建议允许为空或给默认值。

例如：

```text
repair_status 默认 PENDING 或 NOT_REPAIRED
trial_flag 默认 0
repair_task_id 允许为空
source_repair_task_id 允许为空
```

禁止因为新增字段导致旧数据启动失败。

---

### 4.3 状态字段必须统一

状态字段建议统一使用英文枚举，前端负责转中文。

示例：

```text
PENDING
GENERATING
GENERATED
TRIAL_CREATED
APPLIED
FAILED
CANCELLED
```

禁止同一个字段同时出现：

```text
DRAFT / 草稿
APPLIED / 已应用
FAILED / 失败
```

混用会导致后端判断和前端展示混乱。

---

### 4.4 所有写操作必须考虑事务

以下操作必须使用事务或等价机制保证一致性：

1. 创建修复任务及修复范围；
2. 生成修复建议及候选位置；
3. 生成试算方案和方案明细；
4. 应用试算方案；
5. 局部重排生成新方案；
6. 写入优化前后对比结果；
7. 修改正式课表。

事务失败时必须回滚，不能留下半截数据。

---

## 五、后端开发规则

### 5.1 分层结构建议

后端建议保持现有 Spring Boot 分层，不要随意改变项目结构。

推荐新增：

```text
controller
  ScheduleRepairTaskController
  ScheduleRepairSuggestionController
  ScheduleRepairCandidateController
  ScheduleTrialPlanController
  ScheduleConsistencyCheckController

service
  ScheduleRepairTaskService
  ScheduleRepairSuggestionService
  ScheduleCandidateService
  ScheduleTrialPlanService
  ScheduleLocalRearrangeService
  ScheduleConsistencyCheckService
  ScheduleAiRepairExplanationService

dto / vo
  RepairTaskCreateDTO
  RepairSuggestionVO
  RepairCandidateVO
  TrialPlanVO
  RepairCompareVO
  ConsistencyCheckVO
```

具体命名以项目现有风格为准。

---

### 5.2 接口返回格式保持一致

如果项目已有统一返回结构，例如：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

V5 必须继续使用，不要另起一套返回结构。

分页、错误码、枚举值、时间格式都应保持一致。

---

### 5.3 修复建议必须可解释

每条修复建议至少应包含：

```text
建议类型
调整对象
调整前位置
调整后位置
影响教师
影响班级
影响教室
是否产生新冲突
评分变化
风险变化
推荐理由
不可行原因
```

不要只返回一个 ID 或一个分数。

---

### 5.4 候选位置必须过滤硬约束

候选位置生成时必须排除：

1. 教师时间冲突；
2. 班级时间冲突；
3. 教室时间冲突；
4. 教师禁排时间；
5. 教室容量不足；
6. 教室类型不匹配；
7. 锁定课程占用位置；
8. 跨学期数据；
9. 停用教师、班级、教室；
10. 超出教学任务课时要求的位置。

候选位置可以按照软约束和偏好约束排序，但不能牺牲硬约束合法性。

---

### 5.5 应用试算方案必须重新校验

即使试算方案生成时已经校验过，应用前仍需再次校验：

```text
方案状态是否允许应用
试算方案是否属于当前学期
是否存在硬冲突
是否移动锁定课程
正式课表是否仍然处于可应用状态
来源方案是否仍然存在
```

避免用户长时间停留页面后，底层数据已经变化，仍然应用旧试算结果。

## 六、前端开发规则

### 6.1 页面只做交互，不做核心判断

前端可以做：

1. 选择修复任务；
2. 展示候选位置；
3. 展示修复建议；
4. 展示试算方案；
5. 展示优化前后对比；
6. 展示数据一致性检查结果；
7. 提交用户确认操作。

前端不能做：

1. 自行判断候选是否合法；
2. 自行修改正式课表；
3. 直接拼接数据库字段写入；
4. 绕过后端校验；
5. 静默应用修复结果。

---

### 6.2 用户操作必须有明确提示

以下操作必须二次确认：

```text
应用试算方案
放弃修复任务
批量局部重排
解除课程锁定
覆盖当前正式课表
删除修复记录
```

确认文案应说明影响范围，例如：

```text
确认应用该试算方案吗？应用后将更新当前学期正式课表，但不会删除历史方案记录。
```

---

### 6.3 页面入口建议

V5 可新增一级菜单：

```text
智能修复中心
```

子菜单建议：

```text
修复任务
修复建议
候选位置
试算方案
局部重排
优化前后对比
数据一致性检查
回归测试记录
AI 修复解释
```

如果菜单过多，可以合并为：

```text
智能修复中心
  - 修复任务
  - 试算与对比
  - 局部重排
  - 数据检查
```

---

### 6.4 空状态和异常状态必须处理

前端必须处理：

1. 没有当前学期；
2. 当前学期没有方案；
3. 没有风险项；
4. 没有可用候选位置；
5. 修复建议生成失败；
6. 试算方案生成失败；
7. 试算方案已过期；
8. 应用失败；
9. 数据一致性检查无异常；
10. AI 分析接口不可用。

不要出现空白页面或无限加载。

## 七、AI 辅助功能边界

### 7.1 AI 可以做什么

AI 可以用于：

1. 生成修复建议的自然语言解释；
2. 总结优化前后变化；
3. 生成答辩展示用说明；
4. 解释为什么某些候选位置不可用；
5. 根据结构化结果生成报告文字；
6. 帮助开发者排查代码问题。

---

### 7.2 AI 不能做什么

AI 不允许：

1. 直接修改正式课表；
2. 直接应用方案；
3. 绕过后端冲突检测；
4. 绕过课程锁定；
5. 自行决定删除历史方案；
6. 代替规则引擎判断合法性；
7. 把数据库大表原文全部发送给 AI；
8. 输出不可追踪、不可验证的修复结果。

---

### 7.3 AI 输入必须结构化

AI 分析输入应是后端整理后的结构化数据。

推荐输入：

```json
{
  "taskName": "修复教师时间冲突",
  "semesterName": "2025-2026学年第二学期",
  "riskType": "TEACHER_CONFLICT",
  "beforeScore": 78.5,
  "afterScore": 86.0,
  "beforeRiskCount": 5,
  "afterRiskCount": 2,
  "changedItems": [
    {
      "courseName": "高等数学",
      "teacherName": "张老师",
      "beforeTime": "周一第1-2节",
      "afterTime": "周三第3-4节"
    }
  ]
}
```

禁止输入：

```text
整个数据库所有表
完整用户账号信息
无关日志文件
超大 SQL dump
敏感配置文件
API Key
```

## 十一、禁止事项总表

AI 开发 V5 时，明确禁止以下行为：

| 禁止事项 | 原因 |
|---|---|
| 重写 V1-V4 旧功能 | 容易破坏已有稳定功能 |
| 自动修复直接修改正式课表 | 违背试算优先原则 |
| 绕过后端冲突检测 | 数据安全风险高 |
| 移动锁定课程 | 破坏用户确认结果 |
| 跨学期读取或写入数据 | 破坏学期边界 |
| 删除历史方案 | 破坏方案回滚能力 |
| 已废弃方案直接应用 | 破坏方案状态机 |
| AI 直接应用方案 | AI 只能辅助解释 |
| 前端自行判断合法性 | 必须以后端为准 |
| 大规模重构数据库 | 易导致旧数据失效 |
| 引入大型求解器作为主线 | 超出 V5 范围 |
| 一次开发多个阶段 | 难以定位问题 |

## 十二、推荐开发节奏

V5 建议按以下节奏推进：

```text
每次只开发一个阶段
每个阶段先读文档
每个阶段先看现有代码
每个阶段只做最小必要改动
每个阶段完成后启动前后端
每个阶段完成后做最小回归测试
每个阶段记录问题和修复结果
确认稳定后再进入下一阶段
```

不建议：

```text
一次性让 AI 写完 V5 全部功能
一次性改数据库、后端、前端、算法、测试
不测试直接继续下一阶段
发现问题后让 AI 大规模重构
```

## 十四、总结

V5 的开发重点不是“让系统变得更复杂”，而是让系统在已有排课能力基础上具备更强的：

```text
问题修复能力
局部优化能力
试算验证能力
对比解释能力
数据稳定性检查能力
```

AI 开发时必须始终记住：

```text
V5 是增强，不是重写。
V5 是试算，不是直接覆盖。
V5 是辅助修复，不是 AI 替人决策。
V5 是保护旧功能，不是牺牲旧功能换新功能。
```

只要严格遵守本文档，V5 就可以在不破坏 V1-V4 的基础上，形成一个更适合毕业设计展示的高级排课优化版本。
