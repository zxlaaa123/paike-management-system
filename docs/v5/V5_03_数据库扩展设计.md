# V5_03_数据库扩展设计

> 版本：V5 版本  
> 文档类型：数据库扩展设计  
> 适用项目：排课系统仿真 / 高校排课管理系统  
> V5 定位：约束驱动的局部重排与智能修复优化版  
> 前置基础：V3 学期与排课方案机制、V4 排课质量分析与智能辅助优化机制  
> 重要原则：V5 是数据库扩展，不是数据库重构；所有自动修复和局部重排结果必须先生成试算方案，不允许直接覆盖正式课表。

---

## 一、文档目的

本文档用于说明排课系统 V5 版本需要新增或扩展的数据结构。

V5 的重点不是重新设计排课系统数据库，而是在 V3、V4 已有结构基础上，继续支持以下能力：

1. 约束规则分层管理；
2. 冲突修复建议生成；
3. 修复候选位置保存；
4. 局部重排试算；
5. 课程锁定保护；
6. 修复前后对比；
7. 修复方案管理；
8. 排课数据一致性检查；
9. 自动化回归测试结果记录；
10. AI 修复解释辅助。

V5 数据库设计的核心目标是：

```text
在不破坏 V3 方案机制和 V4 分析诊断机制的前提下，
增加“修复任务、修复建议、候选位置、试算方案、优化对比、数据检查”等支撑表。
```

---

## 二、V5 与 V3/V4 数据库的关系

### 2.1 V3 数据库提供的核心基础

V3 已经建立了排课系统非常关键的数据底座：

1. `semester`：学期表；
2. `teaching_task`：教学任务表，绑定学期；
3. `schedule`：正式课表表，绑定学期；
4. `schedule_plan`：排课方案表；
5. `schedule_plan_item`：排课方案明细表；
6. `schedule_rule_weight`：排课规则权重表；
7. `schedule_score_detail`：排课评分明细表；
8. `schedule_generate_log`：排课生成日志表；
9. `schedule_unassigned_task`：未排任务原因表；
10. `schedule_adjust_log`：手动调整日志表；
11. `schedule_compare_result`：方案对比结果表。

V5 必须继续遵守 V3 的两个核心原则：

```text
自动排课结果必须先进入 schedule_plan / schedule_plan_item。
正式课表 schedule 只能在用户明确应用方案后被写入或更新。
```

### 2.2 V4 数据库提供的分析与诊断基础

V4 已经围绕分析、解释、风险、锁定、导出设计了扩展结构，例如：

1. `schedule_plan_analysis`：排课方案分析汇总表；
2. `schedule_plan_score_detail`：排课方案评分明细表；
3. `schedule_plan_risk_issue`：排课方案风险诊断表；
4. `schedule_adjustment_log`：课表调整日志表；
5. `schedule_locked_item`：锁定排课项表；
6. `schedule_report_record`：排课报告导出记录表。

V5 要复用 V4 的风险诊断结果、课程锁定状态、分析汇总结果和评分明细结果。

V5 不是替代 V4，而是承接 V4 的结果继续做：

```text
风险诊断结果
  ↓
修复建议
  ↓
候选位置
  ↓
局部重排试算方案
  ↓
优化前后对比
  ↓
用户确认应用或放弃
```

## 三、V5 数据库设计原则

### 3.1 不重构已有核心表

V5 不允许为了实现智能修复而大规模重构以下表：

```text
teacher
class / class_group / school_class
course
classroom
teaching_task
schedule
schedule_plan
schedule_plan_item
schedule_rule_weight
schedule_plan_risk_issue
schedule_locked_item
```

如果需要新增能力，优先采用：

```text
新增字段
新增关联表
新增日志表
新增快照表
```

不采用：

```text
删除旧表
重命名旧字段
改变旧字段含义
把正式课表和试算方案混在一起
```

---

### 3.2 统一使用学期边界

V5 新增表必须继续绑定学期。

推荐统一使用字段：

```text
semester_id
```

说明：

1. 如果当前项目 V4 表中已经使用 `term_id`，不要强行重命名；
2. 可以在 V5 文档和新表中统一使用 `semester_id`；
3. 代码实现时可以根据项目实际表名进行映射；
4. 不允许同一张表里同时混用 `term_id` 和 `semester_id` 表示同一含义。

---

### 3.3 修复结果必须方案化

V5 的局部重排和智能修复不能直接修改正式课表。

推荐流程：

```text
用户选择风险或范围
  ↓
系统生成修复任务
  ↓
系统生成候选修复建议
  ↓
用户选择建议或执行局部重排
  ↓
系统生成试算方案 schedule_plan
  ↓
系统生成试算方案明细 schedule_plan_item
  ↓
系统生成优化前后对比
  ↓
用户确认后再应用为正式课表
```

也就是说，V5 的修复结果仍然应落到：

```text
schedule_plan
schedule_plan_item
```

而不是直接写入：

```text
schedule
```

---

### 3.4 试算模式优先

V5 应引入“试算方案”概念。

试算方案本质上仍然是一个排课方案，但它的来源不是全量自动排课，而是局部修复或局部重排。

建议通过 `schedule_plan` 的扩展字段区分：

```text
NORMAL_GENERATE      普通自动生成方案
LOCAL_REPAIR_TRIAL   局部修复试算方案
LOCAL_REPLAN_TRIAL   局部重排试算方案
MANUAL_ADJUST_PLAN   人工调整后保存的方案
```

---

### 3.5 锁定课程必须受保护

V5 中任何修复、试算、局部重排都必须读取课程锁定状态。

被锁定的课程不得被移动，除非用户明确解锁。

锁定数据优先复用 V4 的：

```text
schedule_locked_item
```

如果项目尚未实现该表，可在 V5 阶段补齐。

---

### 3.6 分析表不等于业务表

V5 新增的修复建议、候选位置、对比结果、数据检查结果都属于辅助数据。

它们不能替代核心业务表。

例如：

```text
schedule_repair_suggestion 不能替代 schedule_plan_item
schedule_repair_compare 不能替代 schedule_compare_result
schedule_data_check_result 不能替代真实业务数据
```

## 四、V5 推荐新增表总览

V5 建议新增以下 8 张表：

| 表名 | 中文名 | 作用 | 必要性 |
|---|---|---|---|
| schedule_repair_task | 排课修复任务表 | 记录一次修复或局部重排请求 | 必做 |
| schedule_repair_suggestion | 修复建议表 | 保存系统生成的修复建议 | 必做 |
| schedule_repair_candidate | 修复候选位置表 | 保存某条课程可替换的时间/教室候选 | 必做 |
| schedule_repair_scope | 修复范围表 | 记录本次修复涉及、排除或锁定的课程范围 | 建议做 |
| schedule_repair_compare | 修复前后对比表 | 保存修复前后评分、冲突、负载差异 | 必做 |
| schedule_constraint_rule | 约束规则字典表 | 统一维护硬约束、软约束、偏好约束、修复约束 | 建议做 |
| schedule_data_check_result | 数据一致性检查结果表 | 保存系统健康检查与数据一致性问题 | 建议做 |
| schedule_regression_test_record | 回归测试记录表 | 保存 V1-V5 主流程测试记录 | 可选 |

最小可用版建议先实现：

```text
1. schedule_repair_task
2. schedule_repair_suggestion
3. schedule_repair_candidate
4. schedule_repair_compare
```

增强版再实现：

```text
1. schedule_repair_scope
2. schedule_constraint_rule
3. schedule_data_check_result
4. schedule_regression_test_record
```

## 五、已有表字段扩展建议

## 5.1 schedule_plan 表扩展

### 5.1.1 扩展目的

V5 的局部修复和局部重排最终仍然应生成排课方案。

因此建议在 `schedule_plan` 中增加少量字段，用来标识方案来源、是否试算、对应修复任务和优化前后情况。

### 5.1.2 建议新增字段

| 字段名 | 类型建议 | 是否必填 | 说明 |
|---|---|---|---|
| plan_category | varchar(50) | 否 | 方案类别：普通生成、局部修复试算、局部重排试算等 |
| source_plan_id | bigint | 否 | 来源方案 ID，用于表示基于哪个方案修复 |
| source_schedule_id | bigint | 否 | 来源正式课表记录，通常用于单条修复场景，可选 |
| repair_task_id | bigint | 否 | 关联 V5 修复任务 ID |
| is_trial | tinyint | 否 | 是否试算方案：0 否，1 是 |
| before_score | decimal(6,2) | 否 | 修复前评分快照 |
| after_score | decimal(6,2) | 否 | 修复后评分快照 |
| improvement_score | decimal(6,2) | 否 | 评分提升值 |
| locked_item_count | int | 否 | 锁定课程数量 |
| moved_item_count | int | 否 | 被调整课程数量 |
| affected_item_count | int | 否 | 受影响课程数量 |
| repair_summary | varchar(1000) | 否 | 修复摘要 |

### 5.1.3 plan_category 建议枚举

```text
NORMAL_GENERATE        普通自动排课方案
MULTI_STRATEGY         多策略生成方案
LOCAL_REPAIR_TRIAL     局部修复试算方案
LOCAL_REPLAN_TRIAL     局部重排试算方案
MANUAL_ADJUST_PLAN     人工调整后方案
DATA_RECOVERY_PLAN     数据修复辅助方案
```

### 5.1.4 设计说明

1. `schedule_plan` 仍然是方案主表；
2. V5 不另建完整的 `trial_plan` 表，避免与 V3 方案体系割裂；
3. `is_trial=1` 的方案表示尚未应用，只用于对比和预览；
4. 试算方案应用后，可以将 `is_trial` 保留为历史标记，不需要改成普通方案；
5. 应用试算方案时仍必须走 V3 的“应用方案”流程。

---

## 5.2 schedule_plan_item 表扩展

### 5.2.1 扩展目的

局部修复和局部重排需要知道某条方案明细是否来自原方案、是否被移动、是否被锁定、移动原因是什么。

### 5.2.2 建议新增字段

| 字段名 | 类型建议 | 是否必填 | 说明 |
|---|---|---|---|
| source_item_id | bigint | 否 | 来源方案明细 ID |
| source_schedule_id | bigint | 否 | 来源正式课表 ID |
| is_locked | tinyint | 否 | 是否锁定快照 |
| is_moved | tinyint | 否 | 是否在本次修复中被移动 |
| move_type | varchar(50) | 否 | 移动类型：改时间、改教室、改时间和教室等 |
| repair_action | varchar(50) | 否 | 修复动作编码 |
| repair_reason | varchar(500) | 否 | 修复原因说明 |
| candidate_id | bigint | 否 | 来源候选位置 ID |

### 5.2.3 move_type 建议枚举

```text
KEEP_ORIGINAL       保持原安排
CHANGE_TIME         修改时间
CHANGE_ROOM         修改教室
CHANGE_TIME_ROOM    同时修改时间和教室
ADD_ITEM            新增安排
REMOVE_ITEM         移除安排
```

### 5.2.4 设计说明

1. 对于未被修复影响的课程，`is_moved=0`；
2. 对于从原方案复制而来的课程，记录 `source_item_id`；
3. 对于局部重排生成的新位置，可以记录 `candidate_id`；
4. `is_locked` 是生成试算方案时的锁定快照，真实锁定状态仍以 `schedule_locked_item` 为准；
5. 不建议直接修改历史方案明细，应生成新的方案明细。

---

## 5.3 schedule_plan_risk_issue 表扩展

### 5.3.1 扩展目的

V4 的风险诊断表主要记录风险和建议。

V5 需要进一步记录某条风险是否已经生成修复任务、是否已经解决、对应哪个修复建议。

### 5.3.2 建议新增字段

| 字段名 | 类型建议 | 是否必填 | 说明 |
|---|---|---|---|
| repair_status | varchar(50) | 否 | 修复状态 |
| repair_task_id | bigint | 否 | 关联修复任务 ID |
| selected_suggestion_id | bigint | 否 | 用户选择的修复建议 ID |
| resolved_plan_id | bigint | 否 | 解决该风险的试算方案 ID |
| resolved_at | datetime | 否 | 风险解决时间 |

### 5.3.3 repair_status 建议枚举

```text
NOT_REPAIRED        未修复
SUGGESTED           已生成建议
TRIAL_GENERATED     已生成试算方案
RESOLVED            已解决
IGNORED             已忽略
FAILED              修复失败
```

### 5.3.4 设计说明

1. 风险诊断仍不直接修改课表；
2. 修复状态只是记录风险处理进度；
3. 一条风险可以有多个修复建议；
4. 最终是否解决，应以试算方案重新诊断结果为准。

## 5.4 schedule_locked_item 表扩展

### 5.4.1 扩展目的

V4 的锁定表已经可以支持课程锁定。

V5 需要让锁定信息更适合局部重排。

### 5.4.2 建议新增字段

| 字段名 | 类型建议 | 是否必填 | 说明 |
|---|---|---|---|
| protect_level | varchar(50) | 否 | 保护级别 |
| lock_scope | varchar(50) | 否 | 锁定范围 |
| source_type | varchar(50) | 否 | 锁定来源 |
| repair_task_id | bigint | 否 | 如果是某次修复任务中的临时锁定，记录任务 ID |

### 5.4.3 protect_level 建议枚举

```text
STRICT      严格保护，不允许移动
NORMAL      普通保护，默认不移动
WEAK        弱保护，必要时提示用户确认
```

### 5.4.4 lock_scope 建议枚举

```text
TIME_ONLY       只锁定时间
ROOM_ONLY       只锁定教室
TIME_ROOM       锁定时间和教室
FULL_ITEM       完全锁定整条课表项
```

### 5.4.5 设计说明

1. V5 局部重排时必须读取有效锁定项；
2. `STRICT` 级别锁定项不能被局部重排改变；
3. 临时锁定可以绑定 `repair_task_id`；
4. 解锁时不建议删除记录，应设置 `is_active=0` 并记录 `unlocked_at`。

## 5.5 schedule_rule_weight 表扩展

### 5.5.1 扩展目的

V3 已有规则权重表，V5 需要把规则进一步分层。

如果不想新增独立的规则字典表，可以先扩展 `schedule_rule_weight`。

### 5.5.2 建议新增字段

| 字段名 | 类型建议 | 是否必填 | 说明 |
|---|---|---|---|
| constraint_category | varchar(50) | 否 | 约束分类 |
| severity_level | varchar(50) | 否 | 严重程度 |
| repair_enabled | tinyint | 否 | 是否参与修复建议生成 |
| preference_enabled | tinyint | 否 | 是否作为偏好约束参与排序 |
| check_scope | varchar(50) | 否 | 检查范围 |

### 5.5.3 constraint_category 建议枚举

```text
HARD          硬约束
SOFT          软约束
PREFERENCE    偏好约束
REPAIR        修复约束
```

### 5.5.4 设计说明

1. V5 可以先通过字段扩展实现规则分层；
2. 如果后续规则体系越来越复杂，再新增 `schedule_constraint_rule`；
3. 不建议删除 V3 已有 `rule_type` 字段；
4. 新字段可以为空，兼容旧数据。

## 六、V5 新增表设计

# 6.1 schedule_repair_task：排课修复任务表

## 6.1.1 表作用

用于记录一次修复、局部重排或试算操作。

一条修复任务代表用户基于某个方案或正式课表发起的一次修复过程。

例如：

```text
修复方案A中的高风险冲突
只重排软件1班周三下午课程
锁定当前满意课程后重新优化未锁定课程
修复某个教师时间冲突
```

## 6.1.2 建表 SQL

```sql
CREATE TABLE schedule_repair_task (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '修复任务ID',
    semester_id BIGINT NOT NULL COMMENT '所属学期ID',
    source_type VARCHAR(50) NOT NULL COMMENT '来源类型：PLAN正式方案、SCHEDULE正式课表',
    source_plan_id BIGINT NULL COMMENT '来源排课方案ID',
    source_schedule_id BIGINT NULL COMMENT '来源正式课表ID，单条修复时使用',
    source_risk_id BIGINT NULL COMMENT '来源风险ID',
    task_name VARCHAR(200) NOT NULL COMMENT '修复任务名称',
    repair_mode VARCHAR(50) NOT NULL COMMENT '修复模式',
    repair_scope_type VARCHAR(50) NOT NULL COMMENT '修复范围类型',
    status VARCHAR(50) NOT NULL DEFAULT 'CREATED' COMMENT '任务状态',
    before_score DECIMAL(6,2) NULL COMMENT '修复前评分',
    after_score DECIMAL(6,2) NULL COMMENT '修复后评分',
    generated_plan_id BIGINT NULL COMMENT '生成的试算方案ID',
    locked_item_count INT NOT NULL DEFAULT 0 COMMENT '锁定项数量',
    affected_item_count INT NOT NULL DEFAULT 0 COMMENT '影响项数量',
    moved_item_count INT NOT NULL DEFAULT 0 COMMENT '移动项数量',
    description VARCHAR(1000) NULL COMMENT '任务说明',
    error_message TEXT NULL COMMENT '失败原因',
    created_by VARCHAR(100) NULL COMMENT '创建人',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间'
) COMMENT='排课修复任务表';
```

## 6.1.3 字段说明

| 字段名 | 说明 |
|---|---|
| semester_id | 所属学期，必须绑定 |
| source_type | 修复来源，可以是方案或正式课表 |
| source_plan_id | 基于某个方案进行修复时填写 |
| source_schedule_id | 修复正式课表中某一条记录时填写 |
| source_risk_id | 基于 V4 风险诊断结果修复时填写 |
| repair_mode | 修复模式，例如单点修复、局部重排、批量优化 |
| repair_scope_type | 修复范围类型，例如单条课程、班级范围、教师范围 |
| status | 修复任务状态 |
| generated_plan_id | 修复完成后生成的试算方案 |

## 6.1.4 repair_mode 建议枚举

```text
SINGLE_ISSUE_REPAIR     单风险修复
SINGLE_ITEM_REPAIR      单课程修复
CLASS_LOCAL_REPLAN      班级局部重排
TEACHER_LOCAL_REPLAN    教师局部重排
ROOM_LOCAL_REPLAN       教室局部重排
TIME_RANGE_REPLAN       时间范围局部重排
MULTI_RISK_REPAIR       多风险批量修复
```

## 6.1.5 repair_scope_type 建议枚举

```text
RISK_ONLY       仅修复指定风险
ITEM_ONLY       仅修复指定课表项
CLASS_SCOPE     班级范围
TEACHER_SCOPE   教师范围
ROOM_SCOPE      教室范围
TIME_SCOPE      时间范围
```

## 九、关键约束设计

### 9.1 试算方案不直接应用

试算方案必须满足：

```text
is_trial = 1
status = DRAFT 或 草稿
plan_category = LOCAL_REPAIR_TRIAL / LOCAL_REPLAN_TRIAL
```

只有用户明确点击“应用试算方案”后，才能进入 V3 方案应用流程。

---

### 9.2 锁定课程不可移动

局部重排时，必须检查：

```text
schedule_locked_item.is_active = 1
```

如果锁定项为：

```text
protect_level = STRICT
```

则不允许移动。

如果系统尝试移动严格锁定课程，应直接中断任务，并记录失败原因。

---

### 9.3 同一修复任务只能有一个最终试算方案

建议一个 `schedule_repair_task` 只绑定一个最终 `generated_plan_id`。

如果用户多次生成试算，可以采用两种方式：

```text
方式一：每次重新生成一个新的 repair_task
方式二：同一 repair_task 下允许多个试算方案，但 generated_plan_id 指向当前选中的方案
```

毕业设计项目建议采用方式一，降低复杂度。

---

### 9.4 修复建议不能绕过后端校验

所有修复建议必须由后端执行规则检查。

前端不能自己判断：

```text
可用时间
可用教室
是否冲突
是否违反锁定
是否满足容量
```

---

### 9.5 正式课表修改仍走原应用流程

V5 不能新增一个“直接把修复建议写入 schedule”的捷径。

正确流程是：

```text
修复建议 → 试算方案 → 对比确认 → 应用方案 → 写入 schedule
```

## 十六、开发注意事项

### 16.1 不要重复建设 V4 表

如果 V4 已经有：

```text
schedule_plan_risk_issue
schedule_locked_item
schedule_plan_analysis
schedule_plan_score_detail
```

V5 不要重复建类似表。

应优先复用和扩展。

---

### 16.2 不要让修复建议直接改正式课表

错误做法：

```text
点击修复建议 → 直接 update schedule
```

正确做法：

```text
点击修复建议 → 生成试算方案 → 对比 → 用户确认 → 应用方案
```

---

### 16.3 试算方案必须可废弃

用户不满意试算结果时，应可以废弃该试算方案。

废弃试算方案不能影响：

```text
原正式课表
原排课方案
历史方案
锁定状态
```

---

### 16.4 数据检查不能自动乱修

数据一致性检查模块可以发现问题，但不应自动修复复杂数据。

对于可能影响正式课表的数据修复，必须让用户确认。

---

### 16.5 JSON 字段使用建议

本文档部分字段建议使用 `TEXT` 保存 JSON，例如：

```text
conflict_result
check_detail
before_data
after_data
```

如果项目使用 MySQL 5.7+ 且团队熟悉 JSON 类型，可以使用 `JSON`。

如果只是毕业设计项目，为了兼容简单，使用 `TEXT` 更稳。

```text
1. V5 是数据库扩展，不是数据库重构；
2. 不要删除 V1、V2、V3、V4 已有表；
3. 不要重命名已有核心字段；
4. 不要改变 schedule_plan / schedule_plan_item / schedule 的核心语义；
5. 修复和局部重排结果必须先生成 schedule_plan；
6. 不允许修复建议直接 update schedule；
7. 课程锁定必须被局部重排识别和保护；
8. 新增字段必须兼容旧数据；
9. 如果项目已有 term_id 命名，不要强行与 semester_id 混用；
10. JSON 字段可以用 TEXT 简化实现；
11. 先实现最小闭环，再扩展数据检查和回归测试；
12. 每次数据库迁移前必须备份。
```

## 二十、总结

V5 数据库扩展的核心不是“另起炉灶”，而是在 V3 的方案机制和 V4 的分析诊断机制之上，补齐“修复过程”的数据支撑。

V5 的数据库主线可以概括为：

```text
风险诊断结果
  ↓
修复任务
  ↓
修复建议
  ↓
候选位置
  ↓
试算方案
  ↓
修复前后对比
  ↓
用户确认应用
```

开发时一定要记住：

```text
V5 可以辅助修复，不能直接污染正式课表；
V5 可以生成试算方案，不能绕过 V3 应用方案流程；
V5 可以检查数据一致性，不能自动乱改核心业务数据。
```
