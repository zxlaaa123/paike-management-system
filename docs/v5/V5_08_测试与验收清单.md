# V5_08_测试与验收清单

> 项目：高校排课管理系统 / 排课系统仿真  
> 版本：V5 约束驱动的局部重排与智能修复优化版  
> 文档类型：测试与验收清单  
> 适用阶段：V5 开发完成后、进入最终联调前、毕业设计演示前  
> 核心目标：确认 V5 新增功能稳定可用，同时保证 V1-V4 已有功能未被破坏。

---

## 一、文档说明

本文档用于指导 V5 版本完成后的系统测试、回归测试、接口测试、页面测试和最终验收。

V5 是建立在 V1、V2、V3、V4 基础上的深化版本，其核心不是推翻已有排课系统，而是在已有排课方案、质量分析、风险诊断、局部调整、课程锁定等能力基础上，进一步增加：

1. 约束规则分层；
2. 冲突智能修复建议；
3. 候选位置生成；
4. 试算方案；
5. 局部重排；
6. 优化前后对比；
7. 数据一致性检查；
8. 回归测试记录；
9. AI 修复解释辅助。

本测试文档的重点是确认：

```text
V5 能不能在不破坏旧系统的前提下，完成“发现问题 → 生成修复建议 → 试算优化 → 对比结果 → 用户确认应用”的完整闭环。
```

---

## 二、V5 测试总目标

V5 测试应覆盖以下目标：

1. 验证 V1-V4 核心功能未被 V5 改坏；
2. 验证 V5 新增数据库结构与旧数据兼容；
3. 验证智能修复建议能够基于风险诊断生成；
4. 验证候选位置生成逻辑符合硬约束；
5. 验证试算方案不会直接污染正式课表；
6. 验证局部重排能够跳过锁定课程；
7. 验证优化前后对比数据准确；
8. 验证数据一致性检查能发现异常；
9. 验证 AI 解释只做文字辅助，不直接修改业务数据；
10. 验证前端页面操作闭环清晰、提示明确、不会误导用户。

## 五、V5 测试主流程

V5 最核心的测试主流程如下：

```text
准备当前学期数据
↓
生成或选择一个已有排课方案
↓
执行 V4 质量分析和风险诊断
↓
选择一个风险项
↓
创建 V5 修复任务
↓
生成候选位置
↓
生成修复建议
↓
选择建议并生成试算方案
↓
查看优化前后对比
↓
确认试算方案没有覆盖正式课表
↓
选择是否应用为新方案或正式课表
↓
执行数据一致性检查
↓
保存测试结果
```

只要这条流程跑通，说明 V5 的主线基本成立。

## 六、V5 功能测试清单

# 6.1 约束规则分层管理测试

## 6.1.1 测试目标

确认系统能够区分不同类型的约束规则，并在修复、候选位置生成、局部重排过程中正确使用。

## 6.1.2 测试点

- [ ] 能查看约束规则列表；
- [ ] 能区分硬约束、软约束、偏好约束、修复约束；
- [ ] 硬约束默认启用；
- [ ] 硬约束不允许随意关闭，或关闭时有明确提示；
- [ ] 软约束可以调整权重；
- [ ] 偏好约束可以影响推荐排序；
- [ ] 修复约束可以约束局部重排范围；
- [ ] 锁定课程作为修复约束时能被正确识别。

## 6.1.3 重点验收标准

```text
系统必须保证硬约束优先级最高。
任何违反教师时间冲突、班级时间冲突、教室时间冲突、教师禁排时间、教室容量、教室类型等硬约束的候选位置，不应作为推荐修复结果。
```

# 6.2 修复任务管理测试

## 6.2.1 测试目标

确认系统可以围绕某个风险、某条课表记录或某个未排任务创建修复任务。

## 6.2.2 测试点

- [ ] 能从风险诊断页面创建修复任务；
- [ ] 能从方案详情页面创建修复任务；
- [ ] 能从正式课表页面创建修复任务；
- [ ] 修复任务能绑定学期；
- [ ] 修复任务能绑定方案或正式课表；
- [ ] 修复任务能绑定相关风险项；
- [ ] 修复任务能记录问题类型；
- [ ] 修复任务能记录处理状态；
- [ ] 修复任务能查看详情；
- [ ] 修复任务能取消或关闭。

## 6.2.3 状态流转测试

| 初始状态 | 操作 | 期望状态 |
|---|---|---|
| 待分析 | 生成候选位置 | 候选已生成 |
| 候选已生成 | 生成修复建议 | 建议已生成 |
| 建议已生成 | 创建试算方案 | 试算中 / 试算完成 |
| 试算完成 | 用户确认应用 | 已应用 |
| 任意未完成状态 | 用户取消 | 已取消 |
| 修复失败 | 查看错误原因 | 修复失败 |

## 6.2.4 重点验收标准

```text
修复任务必须只是一个辅助流程，不允许创建任务时直接修改正式课表。
```

# 6.3 候选位置生成测试

## 6.3.1 测试目标

确认系统能为待修复课程生成可用时间和教室候选位置。

## 6.3.2 测试点

- [ ] 能根据教学任务生成候选时间段；
- [ ] 能根据课程类型筛选教室；
- [ ] 能根据班级人数过滤容量不足教室；
- [ ] 能避开教师已有课程；
- [ ] 能避开班级已有课程；
- [ ] 能避开教室已有占用；
- [ ] 能避开教师禁排时间；
- [ ] 能避开锁定课程占用位置；
- [ ] 能显示候选位置评分；
- [ ] 能显示候选位置推荐理由；
- [ ] 无候选位置时能给出原因。

## 6.3.3 异常场景测试

- [ ] 所有教室容量不足时，候选列表为空并提示原因；
- [ ] 教师所有时间都禁排时，候选列表为空并提示原因；
- [ ] 班级所有时间都有课时，候选列表为空并提示原因；
- [ ] 课程类型要求实验室但没有实验室时，候选列表为空并提示原因；
- [ ] 目标课程被锁定时，不允许生成移动候选或需要先解锁。

## 6.3.4 重点验收标准

```text
候选位置不能只靠前端过滤，必须由后端进行完整冲突检测。
```

# 6.4 智能修复建议测试

## 6.4.1 测试目标

确认系统能根据候选位置和风险类型生成多个可选修复建议。

## 6.4.2 测试点

- [ ] 能生成更换教室建议；
- [ ] 能生成更换时间建议；
- [ ] 能生成同时更换时间和教室建议；
- [ ] 能生成保留当前安排但标记风险建议；
- [ ] 能根据评分变化排序建议；
- [ ] 能显示每条建议的优缺点；
- [ ] 能显示建议影响对象；
- [ ] 能显示建议是否引入新风险；
- [ ] 能选择某条建议进入试算；
- [ ] 无建议时能给出原因。

## 6.4.3 推荐评分测试

修复建议推荐分应至少考虑：

- 是否解决原风险；
- 是否产生新风险；
- 是否提升总评分；
- 是否影响锁定课程；
- 是否影响教师负载；
- 是否影响班级负载；
- 是否提升教室利用率；
- 是否减少未排任务。

## 6.4.4 重点验收标准

```text
智能修复建议必须可解释。
系统不能只显示“推荐方案一”，而应说明为什么推荐。
```

# 6.5 试算方案测试

## 6.5.1 测试目标

确认系统可以基于修复建议生成试算方案，并且试算方案不直接覆盖正式课表。

## 6.5.2 测试点

- [ ] 能基于某个方案生成试算方案；
- [ ] 能基于正式课表生成试算方案；
- [ ] 试算方案有独立状态；
- [ ] 试算方案能查看课表明细；
- [ ] 试算方案能查看评分；
- [ ] 试算方案能查看风险变化；
- [ ] 试算方案能废弃；
- [ ] 试算方案能转为正式候选方案；
- [ ] 试算方案不会自动修改 schedule 正式课表；
- [ ] 试算失败时不会产生脏数据。

## 6.5.3 状态测试

| 状态 | 说明 | 是否允许应用 |
|---|---|---:|
| 试算中 | 后端正在计算 | 否 |
| 试算完成 | 可查看结果 | 可转候选方案 |
| 试算失败 | 有错误原因 | 否 |
| 已废弃 | 用户放弃 | 否 |
| 已转方案 | 已生成正式候选方案 | 按方案状态处理 |

## 6.5.4 重点验收标准

```text
试算方案必须和正式课表隔离。
任何试算动作都不能直接覆盖当前正式课表。
```

# 6.6 局部重排测试

## 6.6.1 测试目标

确认系统能在指定范围内进行局部重排，并保护锁定课程不被修改。

## 6.6.2 测试点

- [ ] 能选择局部重排范围；
- [ ] 能按教师范围重排；
- [ ] 能按班级范围重排；
- [ ] 能按教室范围重排；
- [ ] 能按时间范围重排；
- [ ] 能按风险项范围重排；
- [ ] 已锁定课程不会被移动；
- [ ] 未选中范围外课程不会被移动；
- [ ] 重排结果生成新方案；
- [ ] 重排结果不直接覆盖正式课表；
- [ ] 重排后能重新评分；
- [ ] 重排后能重新诊断风险。

## 6.6.3 锁定保护测试

- [ ] 锁定时间和教室后，局部重排不得改变该课程时间和教室；

## 6.6.4 重点验收标准

```text
局部重排必须仍然遵守 V3 的方案机制：生成新方案，不直接覆盖正式课表。
```

# 6.8 数据一致性检查测试


# 6.10 AI 修复解释测试

## 6.10.1 测试目标

确认 AI 只用于文字解释和建议，不直接执行排课修改。

## 6.10.2 测试点

- [ ] AI 能基于结构化数据生成修复解释；
- [ ] AI 能说明推荐理由；
- [ ] AI 能总结优化前后变化；
- [ ] AI 能生成答辩展示用文字；
- [ ] AI 不能直接修改正式课表；
- [ ] AI 不能直接应用方案；
- [ ] AI 不能绕过后端冲突检测；
- [ ] AI 不能删除方案；
- [ ] AI 结果页面明确标注“仅供参考”。

## 6.10.3 重点验收标准

```text
AI 输出只能作为解释性文本，不允许作为系统唯一决策依据。
```

## 十、核心业务闭环验收

### 10.1 闭环一：风险修复闭环

```text
风险诊断 → 创建修复任务 → 生成候选位置 → 生成修复建议 → 生成试算方案 → 查看对比 → 用户确认
```

验收项：

- [ ] 整个流程可以连续完成；
- [ ] 每一步都有清晰页面反馈；
- [ ] 后端数据状态正确；
- [ ] 不直接污染正式课表；
- [ ] 可以回到上一步查看原因。

---

### 10.2 闭环二：锁定课程后局部重排

```text
锁定已确认课程 → 选择重排范围 → 执行局部重排 → 生成试算方案 → 对比优化效果
```

验收项：

- [ ] 锁定课程保持不变；
- [ ] 未锁定课程可以被调整；
- [ ] 重排结果保存为新方案；
- [ ] 原方案仍然保留；
- [ ] 对比结果准确。

---

### 10.3 闭环三：试算转正式方案

```text
生成试算方案 → 查看优化效果 → 转为候选方案 → 应用方案 → 查看正式课表
```

验收项：

- [ ] 试算方案不会自动应用；
- [ ] 用户确认后才能转为候选方案；
- [ ] 应用方案前校验状态；
- [ ] 已废弃试算不允许应用；
- [ ] 应用后正式课表来源记录正确。

---

### 10.4 闭环四：数据一致性检查闭环

```text
执行检查 → 查看异常 → 定位数据 → 手动处理 → 再次检查
```

验收项：

- [ ] 检查结果可读；
- [ ] 异常可以定位到具体对象；
- [ ] 异常等级合理；
- [ ] 修复后再次检查结果变化正确；
- [ ] 系统不会私自自动修改数据。

## 十九、总结

V5 测试的核心不是单独验证某个按钮能不能点，而是验证完整的智能修复闭环：

```text
风险发现
  ↓
修复任务
  ↓
候选位置
  ↓
修复建议
  ↓
试算方案
  ↓
优化对比
  ↓
用户确认
  ↓
数据一致性检查
```

同时，V5 必须继续遵守整个项目的核心原则：

```text
不推翻旧系统
不破坏历史方案
不直接覆盖正式课表
不绕过后端校验
不让 AI 直接改数据
不把试算结果当正式结果
```

只要 V5 能做到“发现问题、解释问题、辅助修复、试算对比、安全应用”，这个版本就具备明显的毕业设计展示价值和系统深化意义。
