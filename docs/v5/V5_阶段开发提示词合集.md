# V5_阶段开发提示词合集

> 适用项目：高校排课管理系统 / 排课系统仿真项目  
> 适用版本：V5：约束驱动的局部重排与智能修复优化版  
> 文档用途：把 V5 每个阶段的开发提示词整理成可直接复制给 AI 编程工具使用的版本。  
> 使用方式：每次只复制一个阶段提示词给 AI，不要一次性把所有阶段都丢给 AI。每完成一个阶段，先运行、测试、提交，再进入下一阶段。

---

## 一、V5 开发总原则提示词

```text
你正在开发一个基于 Spring Boot + Vue 的高校排课管理系统。当前版本是 V5：约束驱动的局部重排与智能修复优化版。

本阶段必须建立在 V1、V2、V3、V4 已有功能基础上继续开发，不允许推翻重写旧系统。

已有版本边界如下：
V1：基础数据管理、教学任务、手动排课、冲突检测、课表查询。
V2：规则化自动排课、教师禁排时间、排课规则、未排任务、冲突报告、课表评分、Excel 导出。
V3：学期管理、排课方案、多方案生成、评分明细、方案对比、应用方案、历史回滚、排课日志。
V4：排课质量分析、评分解释、冲突风险诊断、可视化图表、局部调整、课程锁定、报告导出、AI 辅助分析。
V5：智能修复建议、候选位置推荐、试算方案、局部重排、优化前后对比、数据一致性检查、回归测试增强。

开发必须遵守以下规则：
1. 不允许重写 V1-V4 已经稳定运行的功能。
2. 不允许让自动排课或局部重排直接覆盖正式课表。
3. 所有新生成的修复结果、试算结果、重排结果必须先生成排课方案或试算方案。
4. 应用到正式课表必须由用户明确触发，并经过后端校验。
5. 课程锁定必须被严格保护，锁定项不能被局部重排修改。
6. 风险诊断、AI 分析、修复建议都只能辅助决策，不能直接修改数据库中的正式课表。
7. 涉及正式课表修改时必须使用事务，并记录调整或修复日志。
8. 所有新功能必须兼容当前学期、排课方案、正式课表来源方案等已有机制。
9. 所有接口必须后端校验，前端校验只作为体验增强。
10. 每个阶段完成后都必须进行自测，确认旧功能没有被破坏。

请在开始编码前先阅读项目现有代码结构，确认已有实体、接口、表结构、路由、页面和工具方法，优先复用已有代码，不要重复造轮子。
```

## 二、阶段 0：V1-V4 回归确认提示词

```text
现在开始 V5 阶段 0：V1-V4 回归确认与开发前基线检查。

目标：在正式开发 V5 之前，确认 V1、V2、V3、V4 的核心功能仍然可用，避免 V5 开发建立在不稳定基础上。

请重点检查：
1. V1 基础数据管理是否正常：教师、班级、课程、教室、教学任务、手动排课、课表查询。
2. V2 自动排课是否正常：教师禁排时间、规则配置、自动排课、未排任务、冲突报告、课表评分、Excel 导出。
3. V3 方案机制是否正常：学期管理、当前学期切换、多方案生成、方案详情、方案对比、应用方案、回滚方案、排课日志。
4. V4 分析能力是否正常：质量分析、评分解释、风险诊断、可视化图表、局部调整、课程锁定、报告导出、AI 分析。
5. 正式课表是否仍然能追踪来源方案。
6. 已废弃方案是否不能直接应用。
7. 应用方案是否仍然需要状态校验。
8. 局部调整是否仍然经过后端冲突检测。

执行要求：
1. 不要开发新功能。
2. 不要修改业务逻辑，除非发现明显 bug。
3. 发现问题时先记录问题、复现步骤、影响模块和严重程度。
4. 对阻塞 V5 的问题优先修复。
5. 修复完成后重新运行相关功能。

输出要求：
1. 给出 V1-V4 回归检查结论。
2. 列出发现的问题和修复情况。
3. 明确是否可以进入 V5 正式开发。
```

## 三、阶段 1：数据库扩展与实体准备提示词

```text
现在开始 V5 阶段 1：数据库扩展与实体准备。

目标：为 V5 的智能修复、候选位置、试算方案、局部重排、优化对比、数据一致性检查准备数据库结构和后端实体。

请基于现有 V3/V4 数据库继续扩展，不允许重构旧表。

重点新增或扩展以下数据能力：
1. 修复任务记录：用于记录一次风险修复或局部重排任务。
2. 修复建议记录：用于保存系统生成的候选修复方案。
3. 候选位置记录：用于保存某条课程可调整到的候选时间和教室。
4. 试算方案记录：用于标记某个排课方案是试算生成，不能直接当正式课表。
5. 优化前后对比记录：用于保存修复前后评分、风险数量、未排任务数量等差异。
6. 数据一致性检查记录：用于保存系统健康检查结果。
7. 回归测试记录：用于记录 V5 开发过程中的测试结果。

开发要求：
1. 先检查项目是否已有相同或相近表，避免重复建表。
2. 新增字段应尽量允许为空或设置默认值，保证旧数据兼容。
3. 不允许删除 V1-V4 已有表。
4. 不允许重命名旧字段。
5. 不允许改变 schedule、schedule_plan、schedule_plan_item 的已有语义。
6. 所有新表必须包含必要的 created_at / updated_at 字段。
7. 所有与学期有关的数据必须绑定 semester_id 或项目实际使用的学期字段。
8. 所有与方案有关的数据必须能追溯 plan_id。
9. 所有与正式课表有关的数据必须能追溯 schedule_id 或 source_plan_id。

代码要求：
1. 新增实体类、DTO、VO、Repository/Mapper、Service 基础结构。
2. 枚举值统一使用后端枚举，不要前后端混用中文和英文状态。
3. 添加必要索引，重点包括 plan_id、semester_id、task_id、status、created_at。
4. 如果项目使用 Flyway/Liquibase，生成迁移脚本；如果没有，生成独立 SQL 文件。

完成后请自测：
1. 项目能正常启动。
2. 旧功能页面仍能访问。
3. 数据库迁移不破坏旧数据。
4. 新增实体和表结构字段一致。
```

## 四、阶段 2：约束规则分层与修复规则准备提示词

```text
现在开始 V5 阶段 2：约束规则分层与修复规则准备。

目标：在已有 V3/V4 规则和评分体系基础上，进一步整理 V5 的修复规则，让系统能够区分硬约束、软约束、偏好约束和修复约束。

请实现或整理以下规则分类：
1. 硬约束：教师时间冲突、班级时间冲突、教室时间冲突、教师禁排、教室容量、教室类型。
2. 软约束：教师日负载、班级日负载、课程分布、连续上课、教室利用率、时间段分布。
3. 偏好约束：上午优先、实验课优先实验室、体育课避免晚间、教师偏好时间段。
4. 修复约束：锁定课程不可移动、只修复指定范围、只生成试算方案、不直接覆盖正式课表。

开发要求：
1. 优先复用已有冲突检测、评分规则和风险诊断代码。
2. 不要重写整个自动排课算法。
3. 把规则判断逻辑尽量封装成可复用方法，供候选位置、修复建议、局部重排共同使用。
4. 每个规则需要有 rule_code、rule_name、rule_type、description、enabled、weight 等基本信息。
5. 硬约束默认不能关闭。
6. 软约束和偏好约束可以影响评分，但不能导致系统直接报错。
7. 修复约束必须在局部重排和修复建议中强制执行。

输出能力：
1. 能根据一条课程安排判断是否违反硬约束。
2. 能计算软约束扣分或加分。
3. 能解释某个候选位置为什么可用或不可用。
4. 能给修复建议提供评分依据。

完成后请自测：
1. 原有自动排课仍可运行。
2. 原有风险诊断仍可运行。
3. 规则分层不会导致旧评分接口异常。
4. 锁定课程在规则层能被识别为不可移动。
```

## 五、阶段 3：修复任务管理提示词

```text
现在开始 V5 阶段 3：修复任务管理。

目标：实现“修复任务”概念，用于承载一次针对排课风险、未排任务或局部课表问题的修复流程。

修复任务用于记录：用户想修复哪个方案、哪个正式课表、哪些风险、哪些课程范围、当前修复状态是什么。

请实现以下功能：
1. 创建修复任务。
2. 查询修复任务列表。
3. 查看修复任务详情。
4. 更新修复任务状态。

2. 支持从风险诊断页面创建修复任务。
3. 支持从方案详情页面创建修复任务。
4. 修复任务详情页展示任务范围、状态、关联风险和后续操作按钮。

完成后请自测：
1. 能创建修复任务。
2. 能查看任务列表和详情。
3. 状态流转正确。
4. 不会影响原有方案应用和回滚功能。
```

## 六、阶段 4：候选位置生成提示词

```text
现在开始 V5 阶段 4：候选位置生成。

目标：针对某一条存在问题的课程安排，系统自动寻找可替代的时间段和教室，生成候选位置列表。

候选位置要回答的问题是：
这节课还能移动到哪些时间和教室？哪些位置没有硬冲突？哪些位置更推荐？

请实现以下能力：
1. 根据 schedule_id 或 plan_item_id 读取原课程安排。
2. 遍历可用时间段。
3. 遍历可用教室。
4. 检查教师时间冲突。
5. 检查班级时间冲突。
6. 检查教室时间冲突。
7. 检查教师禁排时间。
8. 检查教室容量。
9. 检查教室类型。
10. 检查锁定课程影响。
11. 计算候选位置评分。
12. 返回候选位置列表，并说明推荐理由。

候选位置返回信息建议包括：
1. weekday：星期。
2. start_period / end_period：节次。
3. classroom_id / classroom_name：教室。
4. available：是否可用。
5. hard_conflict_count：硬冲突数量。
6. soft_score：软约束评分。
7. total_score：综合评分。
8. reason：推荐或不可用原因。
9. affected_items：受影响课程。

开发要求：
1. 候选位置生成只读，不修改数据库。
2. 不允许返回会违反硬约束的位置作为可用位置。
3. 可选允许展示不可用位置，但必须明确标记原因。
4. 锁定课程不能被候选算法移动。
5. 候选位置必须限制在同一学期内。
6. 不同学期的数据不能混用。

前端要求：
1. 在风险详情或课程详情中提供“查看候选位置”按钮。
2. 候选位置用表格展示。
3. 支持按推荐度、星期、节次、教室筛选或排序。
4. 点击候选位置后，可以进入修复建议生成或试算流程。

完成后请自测：
1. 教师冲突能被识别。
2. 班级冲突能被识别。
3. 教室冲突能被识别。
4. 教师禁排能被识别。
5. 教室容量和类型能被识别。
6. 候选列表不修改正式课表。
```

## 七、阶段 5：智能修复建议生成提示词

```text
现在开始 V5 阶段 5：智能修复建议生成。

目标：基于风险诊断和候选位置，系统生成多个可选修复建议，帮助用户选择如何修复课表问题。

修复建议不是直接执行修复，而是给出可选择的方案。

请实现以下建议类型：
1. KEEP_TIME_CHANGE_ROOM：保持时间不变，只更换教室。
2. KEEP_ROOM_CHANGE_TIME：保持教室不变，只更换时间。
3. CHANGE_TIME_AND_ROOM：同时更换时间和教室。
4. MANUAL_REVIEW：建议人工处理。
5. PARTIAL_RESCHEDULE：建议进入局部重排。

每条修复建议需要包含：
1. 建议类型。
2. 关联风险。
3. 原课程安排。
4. 建议后的时间和教室。
5. 是否解决原风险。
6. 是否产生新风险。
7. 影响对象。
8. 评分变化预估。
9. 推荐等级。
10. 建议说明。

开发要求：
1. 修复建议必须基于后端规则检测生成。
2. 修复建议不能绕过硬约束。
3. 修复建议不能修改正式课表。
4. 修复建议需要绑定修复任务。
5. 对于无可用候选位置的风险，应生成人工处理建议。
6. 对于涉及多条课程的问题，可以建议进入局部重排。

推荐等级建议：
1. HIGH：强烈推荐。
2. MEDIUM：可考虑。
3. LOW：不推荐但可选。
4. MANUAL：需要人工判断。

前端要求：
1. 修复任务详情页展示修复建议列表。
2. 支持查看建议详情。
3. 支持对比多个建议。
4. 支持选择某条建议生成试算方案。

完成后请自测：
1. 单个教室冲突能生成换教室建议。
2. 单个教师禁排冲突能生成换时间建议。
3. 无候选位置时能生成人工处理建议。
4. 建议生成后不修改正式课表。
```

## 八、阶段 6：试算方案生成提示词

```text
现在开始 V5 阶段 6：试算方案生成。

目标：用户选择某个修复建议后，系统生成一个“试算方案”，用于预览修复效果。试算方案不能直接覆盖正式课表。

试算方案的意义是：
先模拟修复结果，让用户看到优化前后变化，再决定是否应用。

请实现以下功能：
1. 根据修复建议生成试算方案。
2. 将原方案或正式课表复制为试算基础。
3. 在试算副本中应用修复建议。
4. 对试算方案重新进行冲突检测。
5. 对试算方案重新评分。
6. 生成试算方案风险列表。
7. 生成优化前后对比数据。
8. 标记试算方案状态。

试算方案建议状态：
1. SIMULATION：试算中或试算方案。
2. CONFIRMED：用户确认可应用。
3. DISCARDED：已放弃。
4. APPLIED：已应用。

开发要求：
1. 试算方案必须写入 schedule_plan / schedule_plan_item 或专门的试算表，但不能直接写 schedule 正式课表。
2. 试算方案必须标记 source_plan_id 或 source_schedule_id。
3. 试算方案必须绑定修复任务。
4. 试算失败不能污染原方案和正式课表。
5. 试算方案默认不能被当成正式课表展示，除非进入试算详情页。
6. 试算方案应用前必须再次校验。

前端要求：
1. 修复建议列表中提供“生成试算方案”按钮。
2. 试算生成后跳转到试算方案详情页。
3. 试算详情页展示课表、评分、风险、对比结果。
4. 提供“应用试算方案”和“放弃试算方案”按钮。

完成后请自测：
1. 生成试算方案不会修改正式课表。
2. 原方案明细不被覆盖。
3. 试算方案能重新评分。
4. 试算失败能正确回滚。
```

## 九、阶段 7：优化前后对比提示词

```text
现在开始 V5 阶段 7：优化前后对比。

目标：对比原方案和试算方案，展示修复或局部重排到底带来了哪些变化。

请实现以下对比维度：
1. 总评分变化。
2. 已排任务数量变化。
3. 未排任务数量变化。
4. 高风险数量变化。
5. 中风险数量变化。
6. 低风险数量变化。
7. 教师负载变化。
8. 班级负载变化。
9. 教室利用率变化。
10. 课程变动数量。
11. 被锁定课程是否保持不变。
12. 新增风险列表。
13. 已解决风险列表。

开发要求：
1. 对比结果必须基于后端统计计算。
2. 对比结果只读，不修改课表。
3. 对比对象必须属于同一学期。
4. 原方案和试算方案必须能追溯。
5. 如果试算方案导致新硬冲突，必须明确标记为不推荐应用。

前端要求：
1. 试算详情页展示优化前后对比卡片。
2. 用表格展示关键指标变化。
```

## 十、阶段 8：局部重排提示词

```text

局部重排适用场景：
1. 某几个风险无法通过单条修复建议解决。

1. 选择局部重排范围。
2. 读取锁定课程。
3. 保留锁定课程不变。
4. 只重排未锁定且在范围内的课程。
5. 检查所有硬约束。
6. 根据软约束评分选择较优位置。
7. 生成局部重排试算方案。
8. 生成重排日志。
9. 生成优化前后对比。

重排范围可以支持：
1. 按班级。
2. 按教师。
3. 按教室。
4. 按时间段。
5. 按风险项。
6. 按用户勾选课程。

开发要求：
1. 局部重排必须遵守课程锁定。
2. 局部重排不能直接写入正式课表。
3. 局部重排生成的是试算方案或新方案。
4. 原方案和正式课表必须保留。
5. 重排失败时必须给出原因。
6. 不要引入大型求解器，先用规则遍历和评分排序实现。

前端要求：
1. 提供局部重排入口。
2. 支持选择重排范围。
3. 展示锁定课程数量和可重排课程数量。
4. 展示重排结果。
5. 展示重排前后对比。
6. 用户确认后才能应用。

完成后请自测：
1. 锁定课程不会被移动。
2. 未锁定课程可以被调整。
3. 重排结果不会产生硬冲突。
4. 重排结果不会直接覆盖正式课表。
5. 失败时有清晰原因。
```

## 二十、总结

V5 的开发重点不是把系统做得无限复杂，而是让已有排课系统具备更强的“问题修复能力”。

V5 的核心主线是：

```text
发现风险
  ↓
创建修复任务
  ↓
生成候选位置
  ↓
生成修复建议
  ↓
生成试算方案
  ↓
优化前后对比
  ↓
用户确认应用
  ↓
数据一致性检查
```

开发过程中必须始终坚持：

```text
先试算，后应用；
先校验，后保存；
先保护旧功能，再开发新功能；
AI 只解释，不决策；
正式课表安全优先。
```
