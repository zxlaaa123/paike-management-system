# V4 版本阶段提示词合集

## 一、文档说明

本文档用于“排课系统仿真”V4 版本开发阶段中，直接复制给 AI 编程工具使用。

适用工具包括但不限于：

```text
Claude Code
Trae
CodeBuddy
Cursor
Codex CLI
其他 AI 编程助手
```

V4 版本定位为：

> 排课质量分析与智能辅助优化版。

V4 的目标不是继续强行提升自动排课算法复杂度，而是在 V3 已有多方案排课、方案详情、方案对比、应用方案、回滚方案和正式课表来源追踪的基础上，增加排课质量分析、评分解释、风险诊断、可视化图表、局部调整、课程锁定、局部重排、报告导出和 AI 辅助分析能力。

# V4 阶段 0 提示词：开发前检查与数据衔接

```text
现在开始开发 V4 阶段 0：开发前检查与数据衔接。

本阶段目标不是开发复杂功能，而是检查 V3 已有数据结构和接口是否能够支撑 V4 后续的排课质量分析、评分解释、风险诊断、图表展示、局部调整、课程锁定、局部重排、报告导出和 AI 辅助分析。

请先阅读并遵守以下文档：
1. V4_01_版本需求说明.md；
2. V4_03_数据库扩展设计.md；
3. V4_06_开发阶段计划.md；
4. V4_07_AI开发规则.md。

本阶段重点检查：

一、数据库结构检查

请检查以下表是否存在，并确认字段是否满足 V4 后续开发需要。

1. schedule_plan

重点检查字段语义：

- id；
- term_id；
- plan_name；
- strategy_code；
- status；
- total_score；
- scheduled_count；
- unscheduled_count；
- conflict_count；
- created_at；
- applied_at；
- is_current。

如果 is_current 不存在，请判断当前系统是否可以通过 schedule.source_plan_id 反查当前正式课表来源方案。

2. schedule_plan_item

重点检查字段语义：

- id；
- plan_id；
- teaching_task_id；
- course_id；
- teacher_id；
- class_id；
- room_id；
- week_day；
- period_start；
- period_end；
- is_scheduled；
- unscheduled_reason。

字段名可以不同，但语义必须能对应。

3. schedule 正式课表表

重点检查是否具备来源字段：

- source_plan_id；
- source_plan_item_id。

如果没有，请评估是否需要补充字段。

注意：
schedule 表代表当前正式课表。
生成方案不能写入 schedule。
只有 V3 apply、V3 rollback 或后续明确的 V4 正式课表局部调整功能才允许修改 schedule。

二、V3 接口检查

请检查以下 V3 接口是否存在且可用：

- GET /api/v3/schedule-plans；
- GET /api/v3/schedule-plans/{id}；
- POST /api/v3/schedule-plans/compare；
- POST /api/v3/schedule-plans/{id}/apply；
- POST /api/v3/schedule-plans/{id}/rollback。

如果接口路径和项目实际不一致，请以项目已有实现为准，不要强行改坏已有接口。

三、V4 基础目录准备

如项目尚未有 V4 目录，可按现有项目规范新增：

后端建议：

- controller/v4；
- service/v4；
- dto/v4；
- vo/v4；
- mapper/v4；
- entity/v4。

前端建议：

- frontend/src/views/v4；
- frontend/src/components/v4；
- frontend/src/api；
- frontend/src/types。

如果项目已有更合适的目录规范，请优先遵守现有规范。

四、正式课表来源检查

请实现或检查一个只读能力，用于判断当前正式课表来源方案。

如果 V3 已经实现，可以复用。
如果没有，可以先准备后续 V4 阶段 5 要用的数据查询逻辑。

五、本阶段限制

1. 不要开发质量分析页面；
2. 不要开发评分详情；
3. 不要开发风险诊断；
4. 不要开发图表；
5. 不要开发局部调整；
6. 不要开发局部重排；
7. 不要修改 V3 自动排课算法；
8. 不要删除历史方案；
9. 不要删除历史方案明细；
10. 不要让任何检查逻辑修改正式课表。

六、完成后请输出

1. 当前数据库表检查结果；
2. 当前 V3 接口检查结果；
3. 是否需要新增 source_plan_id；
4. 是否需要新增 source_plan_item_id；
5. 是否新增了 V4 基础目录；
6. 是否影响 V3 原有功能；
7. 本阶段修改文件清单；
8. 下一阶段开发建议。
```

- 满分；

本阶段目标是基于排课方案明细，对教师冲突、班级冲突、教室冲突、未排任务和潜在风险进行集中诊断和展示。

请严格遵守：
1. 风险诊断只做检测和提示；
2. 风险诊断不能自动修复课表；
3. 风险诊断不能修改正式课表；
4. 风险诊断不能删除历史方案；
5. 风险诊断不能删除方案明细；
6. 风险建议仅作为提示，不直接执行。

一、后端开发目标

请实现接口：

GET /api/v4/schedule-risks/plans/{planId}

支持查询参数：

- riskType；
- level；
- onlyUnresolved。

返回内容包括：

- planId；
- riskCount；
- risks。

每条 risk 至少包括：

- id；
- riskType；
- riskTypeName；
- level；
- title；
- description；
- relatedTeacherId；
- relatedTeacherName；
- relatedClassId；
- relatedClassName；
- relatedRoomId；
- relatedRoomName；
- weekDay；
- period；
- suggestion；
- resolved。

请实现或预留接口：

POST /api/v4/schedule-risks/plans/{planId}/refresh

用于重新扫描并刷新风险记录。

风险类型至少支持：

- TEACHER_CONFLICT：教师时间冲突；
- CLASS_CONFLICT：班级时间冲突；
- ROOM_CONFLICT：教室时间冲突；
- ROOM_CAPACITY：教室容量不足；
- ROOM_TYPE：教室类型不匹配；
- TEACHER_UNAVAILABLE：教师禁排时间冲突；
- UNSCHEDULED_TASK：教学任务未排；

- CLASS_DAILY_OVERLOAD：班级单日课程过多；
- ROOM_LOW_UTILIZATION：教室利用率偏低；
- ROOM_HIGH_UTILIZATION：教室利用率偏高。

风险等级：

- HIGH；
- MEDIUM；
- LOW。

- detectClassConflicts；

- detectTeacherUnavailableRisks；
- detectUnscheduledTasks；
- detectTeacherOverload；
- detectClassDailyOverload；
- detectRoomUtilizationRisks。

不要把所有检测逻辑写在一个几百行大方法里。

三、前端开发目标

新增页面：

frontend/src/views/v4/ScheduleRiskCenter.vue

新增或完善 API 封装：

frontend/src/api/v4ScheduleRiskApi.ts

建议路由：

/v4/schedule-analysis/:planId/risks

页面至少包括：

- 风险统计卡片；
- 风险类型筛选；
- 风险等级筛选；
- 是否已处理筛选；
- 风险列表表格；
- 风险详情弹窗或抽屉；
- 刷新风险按钮；
- 尝试调整入口。

注意：
“尝试调整”只是打开后续局部调整弹窗或预留入口，不要在本阶段直接自动修复。

四、本阶段禁止事项

1. 不要自动调整课程；
2. 不要自动修改教室；
3. 不要修改正式课表；

6. 不要只在前端检测风险；
7. 不要跳过后端校验；
8. 不要破坏 V3 方案详情页。

五、完成后请输出

1. 本阶段完成内容；
2. 新增风险类型；
3. 新增后端接口；
