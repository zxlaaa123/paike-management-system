# V4_02_功能模块设计

> 版本：V4 版本  
> 文档类型：功能模块设计  
> 适用项目：排课系统仿真  
> V4 定位：排课质量分析与智能辅助优化版  
> 前置基础：V1 / V2 基础排课系统、V3 多方案自动排课与方案应用回滚能力  

---

## 一、文档目的

本文档用于说明 V4 版本的功能模块划分、模块职责、模块之间的数据关系和开发边界。

V4 不再以“继续堆复杂自动排课算法”为主线，而是在 V3 已有能力基础上，围绕以下目标增强系统：

1. 能分析排课方案质量；
2. 能解释方案评分来源；
3. 能诊断课表冲突和风险；
4. 能通过图表展示排课数据；
5. 能支持局部调整和实时冲突检测；
6. 能支持课程锁定和局部重排；
7. 能导出排课分析报告；
8. 可选支持 AI 辅助生成分析建议。

本文档重点解决：

- V4 要做哪些模块；
- 每个模块的功能边界是什么；
- 每个模块依赖哪些 V3 数据；
- 哪些地方不能破坏 V3 已有逻辑；
- 后续 API、数据库、前端页面文档如何展开。

---

## 二、V4 与 V3 的关系

### 2.1 V3 已经负责的能力

V3 版本主要负责：

1. 自动生成单个排课方案；
2. 一次生成多个排课方案；
3. 将结果保存到 `schedule_plan` 和 `schedule_plan_item`；
4. 对方案进行评分；
5. 支持方案详情查看；
6. 支持多方案对比；
7. 支持应用某个方案为正式课表；
8. 支持回滚历史方案；
9. 正式课表记录来源方案 `source_plan_id`。

### 2.2 V4 不推翻 V3

V4 不能破坏以下规则：

1. 不重写 V3 自动排课算法；
2. 不删除历史方案；
3. 不删除历史方案明细；
4. 不让生成方案接口直接写入正式课表；
5. 不改变 V3 中“方案生成”和“应用方案”的分离设计；
6. 不把复杂求解器作为 V4 必选项；
7. 不让 AI 直接决定正式课表结果；
8. 不让 V4 分析功能影响 V1 / V2 / V3 的基础数据管理流程。

### 2.3 V4 的增强方式

V4 主要读取和分析以下数据：

- `schedule_plan`：方案主表；
- `schedule_plan_item`：方案明细；
- `schedule`：正式课表；
- 教师信息；
- 班级信息；
- 课程信息；
- 教室信息；
- 教学任务信息；
- 学期信息；
- 禁排时间和规则配置。

V4 的核心不是重新生成所有课表，而是围绕已有方案和正式课表进行：

```text
分析 → 解释 → 诊断 → 可视化 → 局部调整 → 报告导出
```

## 三、V4 功能模块总览

V4 建议划分为以下 8 个核心模块：

| 模块编号 | 模块名称 | 是否必做 | 难度 | 说明 |
|---|---|---:|---:|---|
| V4-M01 | 排课质量分析总览 | 必做 | 中 | 对方案和正式课表进行整体质量分析 |
| V4-M02 | 评分详情与规则解释 | 必做 | 中 | 拆解 total_score，解释分数来源 |
| V4-M03 | 冲突风险诊断中心 | 必做 | 中 | 诊断冲突、未排、负载过高等风险 |
| V4-M04 | 可视化图表分析 | 必做 | 中 | 用图表展示教师、教室、班级、时间段数据 |
| V4-M05 | 局部调整与实时冲突检测 | 建议做 | 中高 | 支持手动调整课程并检测冲突 |
| V4-M06 | 课程锁定与局部重排 | 建议做 | 高 | 锁定部分课程，只重排未锁定课程 |
| V4-M07 | 排课报告导出 | 建议做 | 中 | 导出分析报告、统计表、风险报告 |
| V4-M08 | AI 辅助分析建议 | 可选 | 中 | 用 AI 生成文字分析，不直接改课表 |

# 四、模块一：排课质量分析总览

## 4.1 模块定位

排课质量分析总览是 V4 的入口模块，用于从整体上展示某个排课方案或当前正式课表的质量情况。

该模块要回答的问题是：

> 当前课表整体排得怎么样？有没有明显问题？哪些指标比较好，哪些指标比较差？

## 4.2 数据来源

主要读取：

- `schedule_plan`
- `schedule_plan_item`
- `schedule`
- 教师表
- 班级表
- 教室表
- 课程表
- 教学任务表

## 4.3 核心功能

### 4.3.1 方案质量概览

展示内容包括：

1. 方案名称；
2. 所属学期；
3. 方案状态；
4. 生成策略；
5. 总评分；
6. 已排数量；
7. 未排数量；
8. 冲突数量；
9. 应用状态；
10. 是否当前正式课表来源。

### 4.3.2 关键指标统计

建议展示以下指标：

1. 排课完成率；
2. 未排任务率；
3. 冲突风险数量；
4. 教师平均课时；
5. 教师最大课时；
6. 教师最小课时；
7. 教室使用数量；
8. 教室平均利用率；
9. 班级日均课程数；
10. 时间段课程密度。

### 4.3.3 质量等级判断

可以根据分数和风险数量给出简单等级：

| 等级 | 条件建议 | 显示文案 |
|---|---|---|
| 优秀 | total_score >= 90 且无冲突 | 排课质量优秀 |
| 良好 | total_score >= 80 且冲突较少 | 排课质量良好 |
| 一般 | total_score >= 60 | 排课质量一般，建议优化 |
| 较差 | total_score < 60 或冲突较多 | 排课质量较差，建议重新调整 |

注意：质量等级只是辅助展示，不影响 V3 的应用和回滚逻辑。

## 4.4 模块边界

本模块只做分析和展示，不负责：

1. 生成新方案；
2. 应用方案；
3. 回滚方案；
4. 删除方案；
5. 直接修改正式课表。

# 五、模块二：评分详情与规则解释

## 5.1 模块定位

V3 阶段已经有 `total_score`，但单独显示总分不够清楚。

V4 需要把总评分拆解成多个维度，让用户知道：

> 这个方案为什么是这个分数？扣分扣在哪里？哪些地方还有优化空间？

## 5.2 评分维度建议

评分详情建议拆为以下维度：

| 评分维度 | 说明 |
|---|---|
| 硬约束评分 | 教师、班级、教室是否存在硬冲突 |
| 教师均衡评分 | 教师课时是否过度集中或差距过大 |
| 教室利用率评分 | 教室是否被合理使用 |
| 班级负载评分 | 班级每天课程是否过满或过空 |
| 时间分布评分 | 课程是否过度集中在某些时间段 |
| 教室匹配评分 | 教室容量和类型是否匹配课程需求 |
| 未排任务评分 | 是否存在未排或部分未排教学任务 |

## 5.3 展示内容

每个评分项建议展示：

1. 评分项名称；
2. 当前得分；
3. 满分；
4. 扣分原因；
5. 影响对象；
6. 优化建议。

示例：

```text
教师均衡评分：82 / 100
原因：部分教师课时明显高于平均值。
影响对象：张老师、李老师。
建议：适当分散高负载教师的课程，或调整部分教学任务分配。
```

## 5.4 数据保存建议

V4 可以先采用“实时计算评分详情”的方式，不一定立刻新增复杂表。

如果后续需要保存历史评分明细，可以在 V4 数据库扩展设计中考虑新增：

```text
schedule_plan_score_detail
```

但 V4 初期建议先不要强依赖该表，避免数据库改动过大。

## 5.5 模块边界

本模块只解释评分，不重新计算和覆盖 V3 的 `total_score`。

如果需要重新计算评分，应通过单独的评分分析接口返回结果，不直接改写历史方案分数。

# 六、模块三：冲突风险诊断中心

## 6.1 模块定位

冲突风险诊断中心用于集中展示方案或正式课表中的问题。

它要回答的问题是：

> 当前课表有哪些风险？风险在哪里？严重程度如何？应该怎么处理？

## 6.2 风险类型

建议支持以下风险类型：

| 风险类型 | 说明 | 严重程度 |
|---|---|---|
| 教师时间冲突 | 同一教师同一时间被安排多门课 | 高 |
| 班级时间冲突 | 同一班级同一时间被安排多门课 | 高 |
| 教室时间冲突 | 同一教室同一时间被重复占用 | 高 |
| 教师禁排冲突 | 安排在教师禁排时间 | 高 |
| 教室容量不足 | 教室容量小于班级人数 | 中高 |
| 教室类型不匹配 | 实验课安排到普通教室等 | 中高 |
| 教学任务未排满 | 课程要求课时没有完全安排 | 中高 |
| 教师负载过高 | 某教师课时明显偏高 | 中 |
| 班级日负载过高 | 某班级一天课程过多 | 中 |
| 时间段过度集中 | 大量课程集中在同一时间段 | 中 |
| 教室利用率过低 | 部分教室长期未使用 | 低中 |

## 6.3 风险信息字段

每条风险建议包含：

1. 风险 ID；
2. 风险类型；
3. 风险等级；
4. 所属学期；
5. 所属方案；
6. 影响教师；
7. 影响班级；
8. 影响教室；
9. 影响课程；
10. 周几；
11. 节次；
12. 风险说明；
13. 建议处理方式。

## 6.4 诊断方式

V4 初期建议采用“按需实时诊断”：

```text
用户打开诊断页面 → 后端根据方案明细或正式课表实时扫描 → 返回风险列表
```

暂时不建议一开始就做复杂的风险缓存表，避免增加维护成本。

## 6.5 页面功能

冲突风险诊断页面建议支持：

1. 按风险等级筛选；
2. 按风险类型筛选；
3. 按教师筛选；
4. 按班级筛选；
5. 按教室筛选；
6. 查看风险详情；
7. 从风险跳转到对应课表位置；
8. 查看建议处理方式。

## 6.6 模块边界

本模块只负责诊断和提示，不直接修改课表。

如果用户要处理风险，应跳转到“局部调整与实时冲突检测”模块。

# 七、模块四：可视化图表分析

## 7.1 模块定位

可视化图表模块用于提升 V4 的展示效果，让用户更直观看到排课结果和质量问题。

该模块适合用于毕业设计展示和答辩演示。

## 7.2 图表类型建议

### 7.2.1 教师课时分布柱状图

展示每位教师在当前方案或正式课表中的总课时。

用途：

- 查看教师负载是否均衡；
- 发现课时过高或过低的教师。

### 7.2.2 教室使用率排行图

展示教室使用次数或使用率。

用途：

- 查看哪些教室使用频繁；
- 查看哪些教室利用率过低。

### 7.2.3 班级每日课程负载图

展示每个班级周一到周日的课程数量。

用途：

- 判断班级每天课程是否过满；
- 避免课程集中在少数几天。

### 7.2.4 时间段课程密度热力图

以“星期 + 节次”为维度，展示课程密度。

用途：

- 发现高峰时间段；
- 发现空闲时间段；
- 辅助后续局部调整。

### 7.2.5 方案评分维度雷达图

展示不同评分维度的得分。

用途：

- 快速判断方案短板；
- 对比不同方案的优劣。

### 7.2.6 多方案对比折线图或柱状图

对比多个方案的总分、未排数量、冲突数量等。

用途：

- 辅助选择最优方案；
- 展示 V3 多方案机制的价值。

## 7.3 前端实现建议

前端可以使用现有 Vue3 技术栈，图表库可选：

1. ECharts；
2. AntV G2Plot；
3. 其他轻量图表库。

如果项目当前没有图表库，建议优先使用 ECharts，资料多、效果好、适合毕业设计展示。

## 7.4 模块边界

本模块只负责展示图表，不负责：

1. 应用方案；
2. 回滚方案；
3. 直接修改课表；
4. 改写评分规则。

# 八、模块五：局部调整与实时冲突检测

## 8.1 模块定位

局部调整模块用于解决自动排课后仍需人工微调的问题。

V4 不追求“一键全局最优”，而是提供更真实、更稳的能力：

> 用户手动调整某一节课，系统实时检查是否可行。

## 8.2 适用场景

1. 某教师临时不方便某个时间上课；
2. 某教室需要调整；
3. 某班级当天课程过满，需要调到其他时间；
4. 某节课程虽然不冲突，但排课体验不好；
5. 管理员希望对正式课表进行微调。

## 8.3 基本功能

局部调整至少支持：

1. 选择一条课表记录；
2. 修改上课时间；
3. 修改上课教室；
4. 检查教师冲突；
5. 检查班级冲突；
6. 检查教室冲突；
7. 检查教师禁排；
8. 检查教室容量；
9. 检查教室类型；
10. 保存调整结果。

## 8.4 冲突检测结果

检测结果建议返回：

```json
{
  "available": false,
  "conflicts": [
    {
      "type": "TEACHER_CONFLICT",
      "level": "HIGH",
      "message": "张老师在该时间已有课程安排"
    }
  ]
}
```

## 8.5 数据安全要求

局部调整属于 V4 新增能力，必须独立于 V3 的 apply / rollback 逻辑。

要求：

1. 只允许通过专门的局部调整接口修改正式课表；
2. 修改前必须做完整冲突检测；
3. 修改后不能删除来源方案；
4. 修改后正式课表可以保留原 `source_plan_id`；
5. 建议增加“已人工调整”标记，避免用户误以为正式课表仍完全等同于原方案。

建议字段：

```text
is_manually_adjusted
adjusted_at
adjusted_reason
```

如果 V4 初期不想改太多表，可以先只做冲突检测预览，不直接保存调整。

## 8.6 最小可用版

为了降低难度，V4 初期可以先实现：

```text
只检测，不保存
```

即用户选择新时间和新教室后，系统返回是否冲突。

后续阶段再实现保存调整。

# 九、模块六：课程锁定与局部重排

## 9.1 模块定位

课程锁定与局部重排是 V4 的高级能力。

它解决的问题是：

> 有些课程已经人工确认，不希望自动重排时被改变；系统只调整未锁定部分。

## 9.2 课程锁定功能

用户可以对某些课表项设置锁定状态。

锁定后：

1. 该课程不能被局部重排改变；
2. 该课程在课表中显示锁定标识；
3. 局部重排时必须避开锁定课程；
4. 用户可以手动解锁。

## 9.3 局部重排功能

局部重排不是重新生成整个课表，而是：

1. 保留锁定课程；
2. 保留用户指定不变的课程；
3. 只重新安排未锁定课程；
4. 生成一个新的排课方案；
5. 不直接覆盖正式课表；
6. 用户确认后才能应用新方案。

## 9.4 与 V3 的关系

局部重排生成的新结果仍然应该进入：

```text
schedule_plan
schedule_plan_item
```

不能直接写入：

```text
schedule
```

也就是说，局部重排仍然遵守 V3 的核心规则：

> 生成方案和应用方案必须分离。

## 9.5 难度控制

本模块难度较高，建议不要作为 V4 第一阶段开发。

建议放在：

```text
V4 中后期或可选增强阶段
```

如果 AI 开发能力不足，可以只实现“课程锁定标记”，暂不实现真正局部重排。

# 十、模块七：排课报告导出

## 10.1 模块定位

排课报告导出用于将 V4 的分析结果输出成文件，便于毕业设计展示和实际管理使用。

## 10.2 报告类型

建议支持以下报告：

1. 排课方案分析报告；
2. 多方案对比报告；
3. 教师课时统计表；
4. 教室使用率统计表；
5. 班级课程负载统计表；
6. 冲突风险诊断报告；
7. 正式课表导出；
8. 教师个人课表导出；
9. 班级课表导出；
10. 教室课表导出。

## 10.3 导出格式建议

V4 初期建议优先实现：

```text
Excel 导出
```

原因：

1. 实现难度低于 PDF；
2. 适合表格数据；
3. 教务系统中 Excel 使用频率高；
4. 方便用户二次编辑。

PDF 导出可以作为后续增强。

## 10.4 报告内容建议

方案分析报告至少包括：

1. 方案基本信息；
2. 方案总评分；
3. 评分维度拆解；
4. 已排和未排统计；
5. 教师课时统计；
6. 教室使用统计；
7. 班级负载统计；
8. 冲突风险列表；
9. 优化建议。

## 10.5 模块边界

报告导出只读取数据，不修改数据。

# 十一、模块八：AI 辅助分析建议

## 11.1 模块定位

AI 辅助分析是 V4 的可选亮点，不是核心依赖。

AI 的作用是：

> 根据系统已经计算好的排课统计数据，生成自然语言分析和优化建议。

## 11.2 AI 可以做什么

AI 可以用于：

1. 生成方案分析摘要；
2. 解释某个方案为什么得分高或低；
3. 总结冲突风险；
4. 给出人工调整建议；
5. 生成适合毕业答辩展示的说明文字；
6. 生成排课报告中的文字部分。

## 11.3 AI 不能做什么

AI 不允许：

1. 直接修改 `schedule` 正式课表；
2. 直接修改 `schedule_plan`；
3. 直接修改 `schedule_plan_item`；
4. 代替后端冲突检测；
5. 代替后端评分计算；
6. 绕过应用方案和回滚机制；
7. 作为唯一判断依据。

## 11.4 推荐实现方式

推荐流程：

```text
后端统计结构化数据 → 拼接 AI 分析提示词 → AI 返回文字建议 → 前端展示 → 用户自行判断
```

AI 输入必须是系统已经计算好的结构化数据，不要把数据库原始大表全部丢给 AI。

## 11.5 最小可用版

V4 可以先不接真实 AI，只做一个 mock 分析接口：

```text
根据评分和风险数量返回固定模板建议
```

后续再接入真实 AI 接口。

# 十二、模块之间的关系

## 12.1 主流程关系

V4 推荐主流程：

```text
选择方案或正式课表
        ↓
查看质量分析总览
        ↓
查看评分详情
        ↓
查看冲突风险诊断
        ↓
查看可视化图表
        ↓
必要时进行局部调整或课程锁定
        ↓
导出排课分析报告
        ↓
可选生成 AI 分析建议
```

## 12.2 与 V3 应用流程的关系

V3 负责：

```text
生成方案 → 对比方案 → 应用方案 → 回滚方案
```

V4 负责：

```text
分析方案 → 解释方案 → 诊断风险 → 辅助调整 → 导出报告
```

两者关系是增强关系，不是替代关系。

# 十五、不要做的功能

8. 不建议为了图表展示大量复制冗余数据；
9. 不建议让分析模块直接修改正式课表；
10. 不建议让局部重排直接覆盖正式课表。

# 十六、给 AI 开发工具的模块开发原则

后续让 AI 开发 V4 时，应明确告诉 AI：

```text
1. 本阶段是在 V3 已有多方案排课、方案应用、方案回滚基础上继续开发；
2. 不允许重写 V3 自动排课算法；
3. 不允许破坏 schedule_plan / schedule_plan_item / schedule 的既有语义；
4. V4 主要做分析、解释、诊断、可视化、局部调整和报告导出；
5. 任何生成新方案的功能都必须写入 schedule_plan 和 schedule_plan_item；
6. 任何正式课表变更都必须有明确接口、冲突检测和数据追踪；
7. 分析类接口只读，不允许修改数据；
8. AI 辅助分析只能生成文字建议，不能直接改数据库；
9. 优先保证系统稳定，不追求复杂算法；
10. 新增功能必须兼容 V1 / V2 / V3 旧页面。
```

# 十八、总结

V4 的核心不是“继续让自动排课算法更复杂”，而是让系统具备更强的解释能力和展示能力。

V4 应围绕以下主线展开：

```text
排课质量分析
评分详情解释
冲突风险诊断
可视化图表展示
局部调整检测
课程锁定与局部重排
报告导出
AI 辅助分析建议
```

其中，前四个模块是 V4 的核心必做内容，后四个模块可以根据开发进度逐步实现。

V4 最重要的开发原则是：

> 不推翻 V3，不硬刚复杂算法，而是在已有排课方案基础上，把系统做得更会分析、更会解释、更适合展示。
