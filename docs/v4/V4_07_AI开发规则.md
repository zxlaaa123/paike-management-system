# V4 版本 AI 开发规则

## 一、文档说明

本文档用于约束 AI 编程工具在开发“排课系统仿真”V4 版本时的行为。

适用对象包括但不限于：

```text
Claude Code
Trae
CodeBuddy
Cursor
Codex CLI
其他 AI 编程助手
```

V4 版本定位为：

> 排课质量分析与智能辅助优化版。

V4 的核心不是重写自动排课算法，而是在 V3 已有多方案排课、方案对比、应用和回滚基础上，增加质量分析、评分解释、风险诊断、图表展示、局部调整、课程锁定、报告导出和 AI 辅助分析能力。

本规则文件优先级很高。开发 V4 时，AI 必须优先遵守本文档约束。

---

## 二、V4 总体开发原则

### 2.1 不推翻已有版本

V4 是在 V1、V2、V3 基础上的增量版本。

AI 禁止把 V4 写成一个全新的系统。

必须遵守：

```text
V1/V2 提供基础业务数据；
V3 提供多方案自动排课、方案对比、应用和回滚；
V4 提供质量分析、风险诊断、可视化、辅助优化和报告。
```

不要为了实现 V4 而重构整个项目。

---

### 2.2 不重写 V3 自动排课

V3 已经完成或正在完成：

```text
多方案自动排课
方案详情
方案对比
应用方案
回滚历史方案
正式课表来源方案
```

V4 不能重写这些主流程。

如果需要生成局部重排新方案，必须复用或轻量调用已有 V3 方案生成思想，不能新建一个完全独立的大型排课框架。

---

### 2.3 先读后写

V4 前期功能应尽量只读。

优先开发：

```text
排课质量分析
评分详情解释
冲突风险诊断
可视化图表
正式课表来源展示
```

这些功能不能修改正式课表。

后期再开发：

```text
局部调整
课程锁定
局部重排
报告生成
AI 分析记录
```

凡是写操作，必须有事务、校验和日志。

---

## 三、V4 与 V3 的边界

### 3.1 V3 负责什么

V3 主要负责：

```text
1. 生成单个排课方案；
2. 一次生成多个排课方案；
3. 保存 schedule_plan；
4. 保存 schedule_plan_item；
5. 方案详情；
6. 方案对比；
7. 应用方案为正式课表；
8. 回滚历史方案；
9. 正式课表记录来源 plan_id。
```

V4 不替代这些功能。

---

### 3.2 V4 负责什么

V4 主要负责：

```text
1. 分析方案质量；
2. 拆解评分明细；
3. 诊断冲突和风险；
4. 提供图表统计；
5. 展示正式课表来源；
6. 支持局部调整前的冲突检测；
7. 支持课程锁定；
8. 基于锁定状态生成局部重排新方案；
9. 生成排课分析报告；
10. 使用 AI 生成文字建议。
```

---

### 3.3 明确禁止跨边界行为

AI 禁止：

```text
在 V4 分析接口中重新生成方案；
在 V4 图表接口中修改 schedule；
在 V4 AI 接口中直接修改课表；
在 V4 局部重排后自动应用正式课表；
在 V4 页面中绕过 V3 apply 接口；
在 V4 中删除 V3 历史方案。
```

---

## 四、数据库开发规则

### 4.1 只做扩展，不做推翻

V4 数据库设计必须是扩展式的。

允许新增表：

```text
schedule_analysis_summary
schedule_score_detail
schedule_risk
schedule_adjustment_log
schedule_lock
schedule_report
ai_analysis_record
```

允许给旧表增加必要字段：

```text
source_plan_id
source_plan_item_id
manual_adjusted
```

但是禁止：

```text
删除 V1/V2/V3 已有核心表；
重命名已有核心字段；
大规模重构 schedule_plan；
大规模重构 schedule_plan_item；
大规模重构 schedule；
破坏旧接口依赖的字段。
```

---

### 4.2 历史方案不能删除

以下表中的历史数据必须保留：

```text
schedule_plan
schedule_plan_item
```

V4 中任何功能都不能删除历史方案和历史方案明细。

局部重排必须生成新方案，而不是覆盖原方案。

---

### 4.3 正式课表修改必须谨慎

`schedule` 表代表当前正式课表。

允许修改 `schedule` 的情况：

```text
V3 apply
V3 rollback
V4 明确的正式课表局部调整功能
```

不允许修改 `schedule` 的情况：

```text
质量分析
评分详情
风险诊断
图表统计
AI 分析
报告预览
课程锁定
```

---

### 4.4 写操作必须使用事务

以下操作必须使用事务：

```text
刷新分析汇总
刷新风险诊断
保存局部调整
锁定课程
取消锁定
局部重排生成新方案
生成报告记录
```

事务要求：

```text
任意一步失败，全部回滚；
不能出现只保存一半的状态；
调整数据和日志记录必须在同一事务；
局部重排的新方案和新方案明细必须在同一事务。
```

---

### 4.5 旧数据兼容

AI 必须兼容旧数据。

例如：

```text
source_plan_id 为空时，正式课表页面应显示“暂无来源方案”；
旧方案没有评分明细时，V4 可以重新计算或显示暂无；
旧方案没有风险记录时，可以通过刷新风险生成；
旧数据不能因为新增字段为空而导致页面崩溃。
```

---

## 五、后端开发规则

### 5.1 接口命名规则

V4 新接口建议统一使用：

```http
/api/v4/...
```

不要混在 V3 路径里。

例如：

```http
GET  /api/v4/schedule-analysis/plans/{planId}/summary
GET  /api/v4/schedule-analysis/plans/{planId}/score-details
GET  /api/v4/schedule-risks/plans/{planId}
GET  /api/v4/schedule-charts/plans/{planId}/teacher-hours
POST /api/v4/schedule-adjustments/check
POST /api/v4/schedule-adjustments/apply
POST /api/v4/schedule-locks/lock
POST /api/v4/schedule-locks/unlock
POST /api/v4/schedule-replan/plans/{planId}
POST /api/v4/schedule-reports/plans/{planId}/generate
POST /api/v4/ai/schedule-analysis/plans/{planId}
```

---

### 5.2 接口职责必须单一

不要把多个职责写进一个接口。

错误示例：

```text
一个接口既分析方案，又生成图表，又调整课表，又生成报告。
```

正确拆分：

```text
分析归分析；
风险归风险；
图表归图表；
调整归调整；
报告归报告；
AI 建议归 AI 建议。
```

---

### 5.3 后端必须做完整校验

前端校验不能替代后端校验。

后端必须校验：

```text
方案是否存在；
方案所属学期是否正确；
方案状态是否允许操作；
方案明细是否属于该方案；
课程是否已经锁定；
目标时间是否冲突；
目标教室容量是否满足；
目标教室类型是否匹配；
教师禁排时间是否冲突；
操作是否会影响正式课表；
是否需要二次确认。
```

---

### 5.4 状态校验规则

方案状态建议：

```text
GENERATED     已生成，未应用
APPLIED       已应用为正式课表
ABANDONED     已废弃
FAILED        生成失败
```

AI 必须遵守：

| 状态 | 可分析 | 可调整 | 可锁定 | 可局部重排 | 可应用 |
|---|---:|---:|---:|---:|---:|
| GENERATED | 是 | 是 | 是 | 是 | 走 V3 apply |
| APPLIED | 是 | 谨慎 | 是 | 是 | 走 V3 apply |
| ABANDONED | 是 | 否 | 否 | 否 | 否 |
| FAILED | 部分 | 否 | 否 | 否 | 否 |

---

### 5.5 风险确认规则

以下操作如果存在风险，必须返回确认提示：

```text
应用有冲突的方案；
应用有未排任务的方案；
保存有冲突的局部调整；
强制调整正式课表；
局部重排失败但仍生成部分方案。
```

建议返回：

```json
{
  "needConfirm": true,
  "message": "存在风险，是否继续？",
  "riskCount": 2,
  "risks": []
}
```

不要直接强制执行。

---

## 六、前端开发规则

### 6.1 不重写 V3 页面主体

V4 可以在 V3 页面增加入口，但不能重写 V3 页面主体。

允许增加：

```text
质量分析按钮
风险诊断按钮
图表分析按钮
报告按钮
AI 分析按钮
局部调整入口
课程锁定入口
```

禁止：

```text
重写 V3 方案详情页全部逻辑；
重写 V3 方案对比页全部逻辑；
重写 V3 应用和回滚按钮逻辑；
破坏 V3 已有课表显示。
```

---

### 6.2 V4 页面目录建议

建议新增：

```text
frontend/src/views/v4/
```

建议新增页面：

```text
ScheduleAnalysisOverview.vue
ScheduleAnalysisDetail.vue
ScheduleScoreDetail.vue
ScheduleRiskCenter.vue
ScheduleCharts.vue
ScheduleLockManage.vue
ScheduleAdjustmentLogs.vue
ScheduleReports.vue
ScheduleAiAnalysis.vue
```

建议新增组件：

```text
frontend/src/components/v4/
```

建议新增 API 封装：

```text
frontend/src/api/v4ScheduleAnalysisApi.ts
frontend/src/api/v4ScheduleRiskApi.ts
frontend/src/api/v4ScheduleChartApi.ts
frontend/src/api/v4ScheduleAdjustmentApi.ts
frontend/src/api/v4ScheduleLockApi.ts
frontend/src/api/v4ScheduleReportApi.ts
frontend/src/api/v4ScheduleAiApi.ts
```

如果项目已有命名规范，应优先遵守现有规范。

---

### 6.3 前端不能直接调用 AI 服务商

禁止在前端写：

```text
OpenAI API Key
Claude API Key
DeepSeek API Key
小米 API Key
任何模型供应商 Key
```

AI 分析必须走后端接口。

前端只调用：

```http
POST /api/v4/ai/schedule-analysis/plans/{planId}
```

---

### 6.4 页面必须处理空数据

所有 V4 页面必须处理：

```text
没有方案；
没有方案明细；
没有评分详情；
没有风险记录；
没有图表数据；
没有报告；
AI 分析失败；
source_plan_id 为空；
接口请求失败；
接口返回空数组。
```

不能出现白屏或未捕获错误。

---

### 6.5 修改操作必须二次确认

前端必须二次确认：

```text
保存有冲突的调整；
锁定课程；
取消锁定；
生成局部重排方案；
调整正式课表；
生成报告；
调用 AI 分析。
```

对于正式课表调整，应提示：

```text
你正在调整正式课表。保存后，正式课表可能与原来源方案不完全一致，系统将记录本次调整日志。
```

---

### 6.6 局部重排必须提示

局部重排前必须提示：

```text
局部重排会基于当前方案生成一个新方案，不会覆盖原方案，也不会直接修改正式课表。新方案生成后，需要手动应用后才会成为正式课表。
```

---

## 七、局部调整开发规则

### 7.1 检测和保存必须分离

局部调整必须有两个动作：

```text
检测冲突
保存调整
```

对应接口：

```http
POST /api/v4/schedule-adjustments/check
POST /api/v4/schedule-adjustments/apply
```

不要一个接口既检测又无条件保存。

---

### 7.2 保存前必须再次校验

即使前端已经调用过检测接口，保存接口也必须重新检测。

原因：

```text
前端数据可能过期；
用户可能绕过前端；
其他操作可能已经改变课表；
后端才是最终安全边界。
```

---

### 7.3 必须记录调整日志

所有调整必须记录日志。

日志至少包括：

```text
target_type
plan_id
plan_item_id
schedule_id
operation_type
before_week_day
before_period_start
before_period_end
before_room_id
after_week_day
after_period_start
after_period_end
after_room_id
remark
created_at
```

没有日志的调整不允许保存。

---

### 7.4 调整范围要清楚

`targetType` 建议：

```text
PLAN      调整方案明细
SCHEDULE  调整正式课表
```

AI 必须明确区分：

```text
调整方案项不会直接影响正式课表；
调整正式课表会影响当前正式课表；
正式课表调整必须提示来源方案可能不一致。
```

---

## 八、课程锁定开发规则

### 8.1 锁定的含义

课程锁定表示：

```text
该课程安排已人工确认，后续局部重排不得修改它的时间和教室。
```

锁定不是应用方案。

锁定不是正式发布课表。

锁定不会自动修改正式课表。

---

### 8.2 锁定必须后端保存

不要只在前端维护锁定状态。

锁定记录必须保存在数据库中。

建议表：

```text
schedule_lock
```

---

### 8.3 局部重排必须尊重锁定

局部重排时：

```text
锁定课程必须保持原时间；
锁定课程必须保持原教室；
锁定课程必须复制到新方案；
锁定课程不能被算法重新安排。
```

---

## 九、局部重排开发规则

### 9.1 局部重排生成新方案

局部重排必须生成新方案。

正确逻辑：

```text
读取原方案；
读取锁定课程；
复制锁定课程；
重排未锁定课程；
保存为新的 schedule_plan；
保存新的 schedule_plan_item；
返回 newPlanId。
```

错误逻辑：

```text
直接覆盖原方案；
直接修改正式课表；
删除原方案；
删除原方案明细；
生成后自动应用为正式课表。
```

---

### 9.2 不引入复杂求解器

V4 不以复杂排课算法作为主线。

禁止为了局部重排强行引入：

```text
OR-Tools
Timefold Solver
OptaPlanner
复杂遗传算法框架
复杂模拟退火框架
```

如果确实要参考，只能参考思想，不能把整个项目变成求解器项目。

---

### 9.3 最小可用版允许复制方案

如果算法实现难度太大，允许先实现最小可用版：

```text
基于原方案复制一个新方案；
保留锁定信息；
标记为局部重排来源；
暂不做真正复杂重排。
```

但 AI 必须在完成说明中明确：

```text
当前局部重排是最小可用版，后续可继续优化未锁定课程重新安排逻辑。
```

---

## 十、报告导出开发规则

### 10.1 报告类型

V4 支持的报告类型建议：

```text
方案质量分析报告
方案对比报告
冲突风险报告
教师课时统计报告
教室使用率报告
```

---

### 10.2 导出格式

V4 初期优先支持：

```text
HTML
EXCEL
```

PDF 可以作为后续扩展，不要一开始强制实现。

---

### 10.3 文件保存位置

报告文件不要保存到前端源码目录。

建议：

```text
data/reports/
uploads/reports/
backend/data/reports/
```

具体路径按项目已有规范确定。

---

### 10.4 报告不能修改课表

报告生成只读取数据。

禁止报告接口：

```text
修改方案；
修改正式课表；
应用方案；
回滚方案；
触发重排。
```

---

## 十一、AI 辅助分析开发规则

### 11.1 AI 只做文字建议

AI 可以做：

```text
生成方案整体分析；
解释评分结果；
总结风险问题；
给出优化建议；
生成答辩说明；
生成报告摘要。
```

AI 不可以做：

```text
直接修改课表；
直接写入 schedule；
直接写入 schedule_plan_item；
直接调用 apply；
直接调用 rollback；
直接决定最终课表。
```

---

### 11.2 AI 输入必须是结构化统计数据

给 AI 的输入应是：

```text
方案基础信息
评分明细
风险列表摘要
教师课时统计
教室利用率统计
班级负载统计
未排任务摘要
```

不要把整个数据库原始数据无脑塞给 AI。

---

### 11.3 AI 失败不能影响主功能

如果 AI 接口失败：

```text
页面提示 AI 分析失败；
基础分析、评分、风险和图表功能仍然可用；
不要导致整个页面崩溃。
```

---

### 11.4 API Key 安全

AI API Key 必须：

```text
放在后端环境变量；
不写死在代码中；
不传给前端；
不提交到 Git。
```

---

## 十二、代码结构规则

### 12.1 后端代码结构建议

可以按模块新增：

```text
controller/v4
service/v4
dto/v4
vo/v4
mapper/v4
entity/v4
```

或按项目现有结构命名。

重点是：

```text
V4 代码和 V3 代码边界清晰；
不要把所有 V4 逻辑塞进 V3 Service；
不要写超大 Controller；
不要写超大 Service 方法。
```

---

### 12.2 前端代码结构建议

建议：

```text
views/v4
components/v4
api/v4...
types/v4...
stores/v4...
```

不要把所有 V4 页面和组件塞进一个文件。

---

### 12.3 方法拆分规则

复杂逻辑必须拆分方法。

例如风险诊断服务应拆成：

```text
detectTeacherConflicts()
detectClassConflicts()
detectRoomConflicts()
detectRoomCapacityRisks()
detectRoomTypeRisks()
detectTeacherUnavailableRisks()
detectUnscheduledTasks()
detectTeacherOverload()
detectClassDailyOverload()
detectRoomUtilizationRisks()
```

不要写一个几百行的 `analyze()` 大方法。

---

## 十三、错误处理规则

### 13.1 后端错误处理

后端必须返回明确错误信息。

例如：

```text
方案不存在；
方案已废弃，不能调整；
方案生成失败，不能锁定；
目标教室不存在；
目标时间段冲突；
教师禁排时间冲突；
该课程已锁定；
报告文件不存在；
AI 分析失败。
```

不要只返回：

```text
系统异常
```

---

### 13.2 前端错误处理

前端必须提示用户：

```text
加载失败；
保存失败；
检测冲突失败；
生成报告失败；
AI 分析失败；
暂无数据；
无权限或状态不允许。
```

不要让用户只看到控制台报错。

---

## 十四、测试规则

每完成一个阶段，必须测试：

```text
后端能否启动；
前端能否启动；
接口能否调用；
页面能否打开；
空数据是否正常；
异常数据是否提示；
是否影响 V3 方案生成；
是否影响 V3 方案应用；
是否影响 V3 方案回滚；
是否影响正式课表展示。
```

---

### 14.1 分析类测试

必须确认：

```text
分析接口不会修改 schedule；
评分接口不会修改 schedule_plan；
风险接口不会修改正式课表；
图表接口不会写数据库；
AI 分析不会修改课表。
```

---

### 14.2 写操作测试

必须确认：

```text
局部调整有事务；
局部调整有日志；
锁定有数据库记录；
取消锁定能生效；
局部重排生成新方案；
原方案没有被删除；
新方案不会自动应用；
报告生成不影响课表。
```

---

## 十五、完成后输出规则

AI 每完成一个阶段后，必须输出：

```text
1. 本阶段完成内容；
2. 新增接口；
3. 修改接口；
4. 新增页面；
5. 修改页面；
6. 新增数据库表或字段；
7. 修改文件清单；
8. 测试步骤；
9. 是否影响 V3 原有功能；
10. 未完成事项；
11. 后续建议。
```

如果某功能只做了最小可用版，必须明确说明。

---

## 十六、禁止事项总表

开发 V4 时，AI 必须严格禁止：

1. 不要重写 V3 自动排课算法；
2. 不要重写 V3 多方案生成接口；
3. 不要重写 V3 应用方案接口；
4. 不要重写 V3 回滚方案接口；
5. 不要删除历史方案；
6. 不要删除历史方案明细；
7. 不要让分析接口修改正式课表；
8. 不要让图表接口修改数据库；
9. 不要让 AI 直接修改课表；
10. 不要让局部重排直接应用为正式课表；
11. 不要绕过 V3 apply 接口；
12. 不要只靠前端做冲突检测；
13. 不要让写操作缺少事务；
14. 不要破坏旧课表页面；
15. 不要引入复杂求解器作为 V4 主线；
16. 不要为了 V4 大规模重构整个项目；
17. 不要把导出文件放进前端源码目录；
18. 不要在前端保存 AI API Key；
19. 不要忽略旧数据兼容；
20. 不要一次性开发所有阶段；
21. 不要把所有 V4 功能写在一个大文件；
22. 不要在没有测试的情况下声称完成；
23. 不要隐藏未完成事项；
24. 不要用假数据冒充真实接口联调成功；
25. 不要为了页面好看而牺牲数据安全。

---

## 十七、推荐开发顺序

AI 开发 V4 时，推荐严格按以下顺序：

```text
1. V4 阶段 0：开发前检查与数据衔接
2. V4 阶段 1：排课质量分析总览
3. V4 阶段 2：评分详情解释
4. V4 阶段 3：冲突风险诊断中心
5. V4 阶段 4：可视化图表分析
6. V4 阶段 5：正式课表来源与应用日志增强
7. V4 阶段 6：局部调整与实时冲突检测
8. V4 阶段 7：课程锁定管理
9. V4 阶段 8：局部重排生成新方案
10. V4 阶段 9：排课报告导出
11. V4 阶段 10：AI 辅助分析建议
```

不要跳过前置阶段直接做局部重排。

---

## 十八、V4 成功标准

V4 完成后，系统应该从：

```text
能生成排课方案
```

升级为：

```text
能分析方案质量；
能解释评分来源；
能诊断冲突风险；
能用图表展示结果；
能安全辅助人工调整；
能锁定课程并局部优化；
能导出分析报告；
能用 AI 生成辅助建议。
```

同时必须保证：

```text
V3 的多方案生成、应用方案、回滚方案、正式课表来源追踪全部正常。
```

---

## 十九、给 AI 的执行提醒

开发 V4 时，请始终先问自己：

```text
这个功能是否会修改正式课表？
如果会，是否真的应该由 V4 修改？
是否需要事务？
是否需要日志？
是否需要二次确认？
是否会删除历史方案？
是否会破坏 V3 apply / rollback？
是否能兼容旧数据？
```

如果答案不确定，优先选择保守实现。

---

## 二十、总结

V4 的开发核心不是“更复杂的算法”，而是：

```text
更清楚的分析；
更安全的调整；
更直观的展示；
更完整的追溯；
更适合毕业设计答辩的说明能力。
```

AI 在开发 V4 时，必须始终遵守：

```text
V3 负责生成、应用、回滚；
V4 负责分析、解释、诊断、展示、辅助优化；
历史方案必须保留；
正式课表修改必须谨慎；
AI 只做建议，不做最终决策。
```
