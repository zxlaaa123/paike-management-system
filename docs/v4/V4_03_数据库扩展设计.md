# V4_03_数据库扩展设计

> 版本：V4 排课质量分析与智能辅助优化版  
> 适用项目：排课系统仿真 / 毕业设计项目  
> 文档定位：在 V1、V2、V3 已有数据库基础上，说明 V4 需要新增或扩展的数据结构。  
> 重要原则：V4 不重构旧数据库，不推翻 V3 的多方案自动排课、方案对比、应用回滚机制，只在其基础上做分析、解释、可视化、局部调整、课程锁定和报告导出能力扩展。

---

## 一、V4 数据库设计目标

V4 的数据库设计目标不是重新设计排课系统，而是围绕 V3 已有的排课方案数据，补充以下能力：

1. 保存排课质量分析结果；
2. 保存评分明细，解释 `total_score` 的来源；
3. 保存冲突与风险诊断结果；
4. 保存人工局部调整记录；
5. 支持课程锁定，防止局部重排时被修改；
6. 保存报告导出记录；
7. 为 AI 辅助分析预留报告摘要字段；
8. 不破坏已有正式课表和历史方案数据。

V4 数据库扩展的核心思想是：

```text
V3 负责生成和应用课表；
V4 负责分析、解释、辅助调整和记录过程。
```

---

## 二、和 V3 数据库的关系

V3 应已经具备或计划具备以下核心表：

| 表名 | 作用 | V4 是否重写 |
|---|---|---|
| term | 学期表 | 不重写 |
| teacher | 教师表 | 不重写 |
| class_group / class | 班级表 | 不重写 |
| course | 课程表 | 不重写 |
| classroom | 教室表 | 不重写 |
| teaching_task | 教学任务表 | 不重写 |
| schedule_plan | 排课方案表 | 不重写，只允许小字段扩展 |
| schedule_plan_item | 排课方案明细表 | 不重写，只读取为主 |
| schedule | 正式课表表 | 不重写，只允许必要字段扩展 |

V4 不允许做以下事情：

1. 不允许删除 V3 的 `schedule_plan`；
2. 不允许删除 V3 的 `schedule_plan_item`；
3. 不允许改变 V3 apply / rollback 的基本逻辑；
4. 不允许让分析表直接替代正式 `schedule` 表；
5. 不允许为了统计方便，把正式课表和方案明细混在一起；
6. 不允许在 V4 分析阶段自动覆盖正式课表。

## 三、V4 推荐新增表总览

V4 建议新增以下 6 张表：

| 表名 | 中文名 | 作用 | 必要性 |
|---|---|---|---|
| schedule_plan_analysis | 排课方案分析汇总表 | 保存方案整体分析结果 | 必做 |
| schedule_plan_score_detail | 排课方案评分明细表 | 保存各维度评分解释 | 必做 |
| schedule_plan_risk_issue | 排课方案风险诊断表 | 保存冲突、风险、建议 | 必做 |
| schedule_adjustment_log | 课表调整日志表 | 保存人工调整记录 | 建议做 |
| schedule_locked_item | 锁定排课项表 | 支持课程锁定和局部重排 | 建议做 |
| schedule_report_record | 排课报告导出记录表 | 保存报告导出历史 | 可选 |

其中前三张表是 V4 的核心表，建议优先实现。

## 四、已有表字段扩展建议

### 4.1 schedule_plan 表扩展

V3 的 `schedule_plan` 表已经是排课方案主表，V4 不重写该表，只建议补充少量分析相关字段。

建议扩展字段：

| 字段名 | 类型建议 | 说明 |
|---|---|---|
| analysis_status | varchar(32) | 分析状态，如 NOT_ANALYZED / ANALYZED / ANALYSIS_FAILED |
| analysis_time | datetime | 最近一次分析时间 |
| quality_level | varchar(32) | 质量等级，如 EXCELLENT / GOOD / NORMAL / RISKY |
| ai_summary | text | AI 辅助分析摘要，可选 |

状态建议：

```text
NOT_ANALYZED      未分析
ANALYZED          已分析
ANALYSIS_FAILED   分析失败
```

质量等级建议：

```text
EXCELLENT   优秀
GOOD        良好
NORMAL      一般
RISKY       存在风险
```

注意：

1. `total_score` 仍然保留在 `schedule_plan` 中；
2. V4 的评分明细放入 `schedule_plan_score_detail`；
3. 不要把所有分析指标都堆进 `schedule_plan`；
4. `ai_summary` 只是摘要，不作为核心判断依据。

---

### 4.2 schedule 表扩展

V3 阶段 6 已经要求正式课表记录来源方案。

如果尚未实现，V4 继续建议补充：

| 字段名 | 类型建议 | 说明 |
|---|---|---|
| source_plan_id | bigint | 来源排课方案 ID |
| source_plan_item_id | bigint | 来源方案明细 ID |
| is_manual_adjusted | tinyint / boolean | 是否经过人工调整 |
| adjusted_at | datetime | 最近人工调整时间 |

说明：

1. `source_plan_id` 用于追踪正式课表来自哪个方案；
2. `source_plan_item_id` 用于追踪正式课表来自哪条方案明细；
3. `is_manual_adjusted` 用于标记正式课表是否被人工改动过；
4. 如果暂时不做人工调整，`is_manual_adjusted` 可以先不加。

注意：

```text
schedule 表仍然只表示当前正式课表。
它不是历史方案表，也不是分析结果表。
```

## 5.1 schedule_plan_analysis：排课方案分析汇总表

### 5.1.1 表作用

用于保存某个排课方案的整体质量分析结果。

它是 V4 分析面板的数据来源之一。

### 5.1.2 建议字段

| 字段名 | 类型建议 | 是否必填 | 说明 |
|---|---:|---:|---|
| id | bigint | 是 | 主键 |
| plan_id | bigint | 是 | 关联 schedule_plan.id |
| term_id | bigint | 是 | 所属学期 ID |
| total_score | decimal(6,2) | 是 | 总评分快照 |
| completion_rate | decimal(6,2) | 是 | 排课完成率 |
| scheduled_count | int | 是 | 已排数量 |
| unscheduled_count | int | 是 | 未排数量 |
| conflict_count | int | 是 | 冲突数量 |
| teacher_avg_hours | decimal(6,2) | 否 | 教师平均课时 |
| teacher_max_hours | decimal(6,2) | 否 | 教师最大课时 |
| teacher_min_hours | decimal(6,2) | 否 | 教师最小课时 |
| classroom_usage_rate | decimal(6,2) | 否 | 教室整体利用率 |
| overloaded_teacher_count | int | 否 | 课时过高教师数量 |
| overloaded_class_count | int | 否 | 负载过高班级数量 |
| high_risk_count | int | 否 | 高风险项数量 |
| medium_risk_count | int | 否 | 中风险项数量 |
| low_risk_count | int | 否 | 低风险项数量 |
| quality_level | varchar(32) | 否 | 质量等级 |
| generated_at | datetime | 是 | 分析生成时间 |
| created_at | datetime | 是 | 创建时间 |
| updated_at | datetime | 是 | 更新时间 |

### 5.1.3 设计说明

该表保存的是分析结果快照。

即使后续评分算法调整，也可以重新生成分析记录，或者覆盖当前方案的最新分析结果。

建议做法：

```text
同一个 plan_id 只保留一条最新分析记录。
重新分析时更新该记录。
```

也可以扩展为保留历史分析版本，但 V4 不建议做复杂。

### 5.1.4 关联关系

```text
schedule_plan_analysis.plan_id -> schedule_plan.id
schedule_plan_analysis.term_id -> term.id
```

## 5.2 schedule_plan_score_detail：排课方案评分明细表

### 5.2.1 表作用

用于保存排课方案的各项评分明细，让 `total_score` 有解释来源。

V4 的“评分详情解释页面”主要读取此表。

### 5.2.2 建议字段

| 字段名 | 类型建议 | 是否必填 | 说明 |
|---|---:|---:|---|
| id | bigint | 是 | 主键 |
| plan_id | bigint | 是 | 关联 schedule_plan.id |
| score_code | varchar(64) | 是 | 评分项编码 |
| score_name | varchar(100) | 是 | 评分项名称 |
| score_value | decimal(6,2) | 是 | 实际得分 |
| max_score | decimal(6,2) | 是 | 满分 |
| weight | decimal(6,2) | 否 | 权重 |
| description | varchar(500) | 否 | 评分说明 |
| deduction_reason | text | 否 | 扣分原因 |
| sort_order | int | 否 | 排序 |
| created_at | datetime | 是 | 创建时间 |
| updated_at | datetime | 是 | 更新时间 |

### 5.2.3 评分项建议

| score_code | score_name | 说明 |
|---|---|---|
| HARD_CONFLICT | 硬冲突评分 | 教师、班级、教室冲突等 |
| COMPLETION | 排课完成率评分 | 教学任务是否排满 |
| TEACHER_BALANCE | 教师课时均衡评分 | 教师工作量是否均衡 |
| CLASS_LOAD | 班级负载评分 | 班级每日课程是否过多 |
| ROOM_USAGE | 教室利用率评分 | 教室使用是否合理 |
| TIME_DISTRIBUTION | 时间分布评分 | 上午、下午、晚上分布是否合理 |
| ROOM_MATCH | 教室匹配评分 | 容量、类型匹配程度 |

### 5.2.4 设计说明

V3 阶段 5 已经有 `total_score`，V4 不需要推翻它。

V4 只是把总分拆成多个维度：

```text
total_score = 多个评分项综合后的结果
```

注意：

1. 评分明细用于解释，不一定要完全重新计算 V3 的算法分数；
2. 如果 V3 已有规则权重，可复用 V3 权重；
3. 不要为了评分详情重写自动排课算法；
4. 评分详情可以在方案生成后或点击分析时生成。

## 5.3 schedule_plan_risk_issue：排课方案风险诊断表

### 5.3.1 表作用

用于保存排课方案中的冲突、风险和优化建议。

V4 的“冲突风险诊断中心”主要读取此表。

### 5.3.2 建议字段

| 字段名 | 类型建议 | 是否必填 | 说明 |
|---|---:|---:|---|
| id | bigint | 是 | 主键 |
| plan_id | bigint | 是 | 关联 schedule_plan.id |
| term_id | bigint | 是 | 所属学期 ID |
| risk_type | varchar(64) | 是 | 风险类型 |
| risk_level | varchar(32) | 是 | 风险等级 |
| object_type | varchar(64) | 否 | 影响对象类型 |
| object_id | bigint | 否 | 影响对象 ID |
| object_name | varchar(100) | 否 | 影响对象名称快照 |
| related_item_id | bigint | 否 | 关联方案明细 ID |
| title | varchar(200) | 是 | 风险标题 |
| description | text | 是 | 风险描述 |
| suggestion | text | 否 | 处理建议 |
| status | varchar(32) | 是 | 处理状态 |
| created_at | datetime | 是 | 创建时间 |
| updated_at | datetime | 是 | 更新时间 |

### 5.3.3 风险类型建议

| risk_type | 说明 |
|---|---|
| TEACHER_CONFLICT | 教师时间冲突 |
| CLASS_CONFLICT | 班级时间冲突 |
| ROOM_CONFLICT | 教室时间冲突 |
| ROOM_CAPACITY_NOT_ENOUGH | 教室容量不足 |
| ROOM_TYPE_NOT_MATCH | 教室类型不匹配 |
| TEACHER_UNAVAILABLE | 教师禁排时间冲突 |
| UNSCHEDULED_TASK | 教学任务未排满 |
| TEACHER_OVERLOAD | 教师课时过高 |
| CLASS_DAY_OVERLOAD | 班级单日课程过多 |
| ROOM_LOW_USAGE | 教室利用率过低 |
| ROOM_HIGH_USAGE | 教室利用率过高 |
| TIME_DISTRIBUTION_UNBALANCED | 时间分布不均衡 |

### 5.3.4 风险等级建议

```text
HIGH      高风险
MEDIUM    中风险
LOW       低风险
INFO      提示
```

### 5.3.5 状态建议

```text
OPEN       未处理
IGNORED    已忽略
RESOLVED   已解决
```

### 5.3.6 设计说明

V3 阶段 5 的自动排课算法应该尽量避免硬冲突。

但是 V4 仍然可以分析：

1. 是否存在未排任务；
2. 是否存在软性风险；
3. 是否存在工作量不均衡；
4. 是否存在教室利用不合理；
5. 是否存在课表分布不合理。

注意：

```text
风险诊断表不直接修改课表。
它只负责记录问题和建议。
```

### 5.4.1 表作用

用于记录正式课表或方案课表中的人工调整过程。

V4 如果实现“局部调整与实时冲突检测”，建议新增该表。

### 5.4.2 建议字段

|---|---:|---:|---|
| id | bigint | 是 | 主键 |
| term_id | bigint | 是 | 学期 ID |
| plan_id | bigint | 否 | 关联方案 ID，调整方案时使用 |
| schedule_id | bigint | 否 | 正式课表记录 ID，调整正式课表时使用 |
| plan_item_id | bigint | 否 | 方案明细 ID，调整方案时使用 |
| adjustment_type | varchar(64) | 是 | 调整类型 |
| before_data | text / json | 是 | 调整前数据 |
| after_data | text / json | 是 | 调整后数据 |
| conflict_checked | tinyint / boolean | 是 | 是否已做冲突检测 |
| conflict_result | text / json | 否 | 冲突检测结果 |
| operator_name | varchar(100) | 否 | 操作人名称 |
| remark | varchar(500) | 否 | 备注 |
| created_at | datetime | 是 | 创建时间 |

### 5.4.3 调整类型建议

```text
CHANGE_TIME       修改时间
CHANGE_ROOM       修改教室
CHANGE_TEACHER    修改教师
CHANGE_CLASS      修改班级
MANUAL_ADD        手动新增
MANUAL_DELETE     手动删除
LOCK_ITEM         锁定课程
UNLOCK_ITEM       解锁课程
```

### 5.4.4 设计说明

调整日志用于追踪人工修改，不参与核心排课算法。

如果项目暂时没有登录用户，可以先用：

```text
operator_name = '系统管理员'
```

不要为了这个日志表引入复杂权限系统。

## 5.5 schedule_locked_item：锁定排课项表

### 5.5.1 表作用

用于支持“课程锁定”和“局部重排”。

被锁定的课程，在局部重排时不能被修改。

### 5.5.2 建议字段

| 字段名 | 类型建议 | 是否必填 | 说明 |
|---|---:|---:|---|
| id | bigint | 是 | 主键 |
| term_id | bigint | 是 | 学期 ID |
| plan_id | bigint | 否 | 所属方案 ID |
| schedule_id | bigint | 否 | 正式课表记录 ID |
| plan_item_id | bigint | 否 | 方案明细 ID |
| lock_type | varchar(64) | 是 | 锁定类型 |
| lock_reason | varchar(500) | 否 | 锁定原因 |
| locked_by | varchar(100) | 否 | 锁定人 |
| locked_at | datetime | 是 | 锁定时间 |
| is_active | tinyint / boolean | 是 | 是否有效 |
| unlocked_at | datetime | 否 | 解锁时间 |
| created_at | datetime | 是 | 创建时间 |
| updated_at | datetime | 是 | 更新时间 |

### 5.5.3 锁定类型建议

```text
TIME_ROOM_LOCK     锁定时间和教室
TIME_LOCK          只锁定时间
ROOM_LOCK          只锁定教室
FULL_LOCK          完全锁定，不允许修改
```

### 5.5.4 设计说明

V4 不建议一开始就做复杂局部重排。

但是如果后续要做“锁定已确认课程，只重排未锁定课程”，该表是必要基础。

注意：

1. 锁定表只表示哪些课不能改；
2. 它不直接保存完整课表；
3. 局部重排时必须读取该表；
4. 解锁时建议保留历史记录，通过 `is_active=false` 表示失效。

## 六、字段命名与兼容要求

### 6.1 命名规则

建议统一使用下划线命名：

```text
source_plan_id
analysis_status
risk_type
score_code
created_at
updated_at
```

后端实体类可以使用驼峰：

```java
sourcePlanId
analysisStatus
riskType
scoreCode
createdAt
updatedAt
```

### 6.2 时间字段

建议每张新增表至少包含：

```text
created_at
updated_at
```

日志类表可以只保留：

```text
created_at
```

### 6.3 旧数据兼容

如果 V1/V2/V3 已经存在正式课表数据，新增字段后必须允许为空。

例如：

```text
source_plan_id 可以为空
source_plan_item_id 可以为空
is_manual_adjusted 默认 false
```

页面显示时：

```text
如果 source_plan_id 为空，则显示：暂无来源方案
```

## 八、V4 数据生成逻辑

V4 新增数据主要来自以下几个动作。

### 8.1 分析方案

触发方式：

1. 用户点击“分析方案”；
2. 进入方案详情自动分析；
3. 应用方案后自动分析当前方案。

生成数据：

```text
schedule_plan_analysis
schedule_plan_score_detail
schedule_plan_risk_issue
```

注意：

分析方案不能修改正式课表。

---

### 8.2 局部调整

触发方式：

1. 用户手动修改某一节课时间；
2. 用户手动修改某一节课教室；
3. 用户手动新增或删除课表项。

生成数据：

```text
schedule_adjustment_log
```

可能修改：

```text
schedule 或 schedule_plan_item
```

但修改前必须完成冲突检测。

---

### 8.3 锁定课程

触发方式：

1. 用户点击锁定某节课；
2. 用户批量锁定已确认课程；
3. 局部重排前设置锁定项。

生成数据：

```text
schedule_locked_item
```

注意：

锁定本身不等于重排。

---

### 8.4 导出报告

触发方式：

1. 用户导出方案分析报告；
2. 用户导出教师课时统计；
3. 用户导出教室使用率统计；
4. 用户导出风险诊断报告。

生成数据：

```text
schedule_report_record
```

## 十、数据库迁移建议

如果项目当前使用 Spring Boot + MySQL，建议按以下方式处理：

1. 新建 V4 数据库迁移 SQL 文件；
2. 不直接修改旧初始化文件，避免破坏已有数据；
3. 先备份数据库；
4. 再执行新增表和新增字段 SQL；
5. 新增字段尽量允许为空或设置默认值；
6. 执行后检查旧页面是否还能正常访问。

迁移文件命名建议：

```text
v4_database_extension.sql
V4__database_extension.sql
2026xxxx_v4_database_extension.sql
```

如果项目没有使用 Flyway / Liquibase，也可以放在：

```text
backend/src/main/resources/db/v4_database_extension.sql
```

或：

```text
docs/sql/v4_database_extension.sql
```

## 十二、AI 开发注意事项

给 AI 开发工具阅读本文件时，必须强调以下规则：

```text
1. V4 是数据库扩展，不是数据库重构；
2. 不要删除 V1、V2、V3 已有表；
3. 不要重命名已有核心字段；
4. 不要改变 V3 的方案生成、应用、回滚主流程；
5. 新增表优先服务分析、解释、风险、调整日志、锁定和导出；
6. 分析表不能直接替代 schedule 正式课表；
7. 风险诊断表不能直接修改课表；
8. 课程锁定表只表示锁定规则，不保存完整课表；
9. 旧数据必须兼容，新增字段尽量允许为空；
10. 任何涉及 schedule 正式课表的修改都必须走明确的接口和事务；
11. 不要为了 V4 引入复杂权限系统；
12. 不要为了 V4 引入复杂求解器。
```

## 十五、总结

V4 数据库扩展的核心是：

```text
围绕 V3 排课方案做分析，围绕正式课表做追踪，围绕人工优化做记录。
```

本阶段不追求复杂算法，也不重构旧系统。

优先保证：

1. 数据结构清晰；
2. 和 V3 不冲突；
3. 旧功能可继续运行；
4. 分析数据可解释；
5. 后续页面和接口有稳定数据来源。
