# V4 版本开发阶段计划

## 一、文档说明

本文档用于指导“排课系统仿真”V4 版本的阶段化开发。

V4 版本定位为：

> 排课质量分析与智能辅助优化版。

V4 不推翻 V1、V2、V3 的功能基础，不重新设计自动排课主流程，不替代 V3 已有的多方案生成、方案对比、应用方案和回滚方案功能。

V4 的开发重点是：

1. 基于 V3 已有排课方案做质量分析；
2. 对排课评分进行拆解和解释；
3. 对冲突、未排任务和潜在风险进行诊断；
4. 用图表展示排课质量；
5. 提供安全的局部调整能力；
6. 支持课程锁定和局部重排；
7. 支持排课报告导出；
8. 可选支持 AI 辅助分析建议。

---

## 二、V4 开发总原则

### 2.1 先只读，后写入

V4 前期优先做只读分析功能：

```text
质量分析
评分解释
风险诊断
图表展示
正式课表来源展示
```

这些功能即使有问题，也不会破坏正式课表。

后期再做写入型功能：

```text
局部调整
课程锁定
局部重排
报告生成
AI 分析记录
```

这样开发风险更低。

---

### 2.2 不一开始做复杂重排

局部重排属于 V4 中难度较高的功能。

不建议第一阶段就做。

推荐顺序：

```text
先能分析
再能解释
再能诊断
再能手动调整
最后再局部重排
```

---

### 2.3 每个阶段都要能独立验收

每个阶段完成后，都要能单独测试。

不要写到一半依赖下一个阶段才能运行。

---

### 2.4 不破坏 V3

V4 每个阶段都必须遵守：

1. 不重写 V3 自动排课算法；
2. 不破坏 V3 多方案生成；
3. 不破坏 V3 方案应用；
4. 不破坏 V3 回滚方案；
5. 不删除历史方案；
6. 不删除历史方案明细；
7. 不让分析接口修改正式课表；
8. 不让 AI 直接修改课表。

---

## 三、V4 阶段总览

建议 V4 拆分为 10 个阶段：

```text
V4 阶段 0：开发前检查与数据衔接
V4 阶段 1：排课质量分析总览
V4 阶段 2：评分详情解释
V4 阶段 3：冲突风险诊断中心
V4 阶段 4：可视化图表分析
V4 阶段 5：正式课表来源与应用日志增强
V4 阶段 6：局部调整与实时冲突检测
V4 阶段 7：课程锁定管理
V4 阶段 8：局部重排生成新方案
V4 阶段 9：排课报告导出
V4 阶段 10：AI 辅助分析建议
```

如果开发时间紧张，建议至少完成：

```text
阶段 0
阶段 1
阶段 2
阶段 3
阶段 4
阶段 5
```

这样 V4 已经具备明显展示亮点。

# V4 阶段 0：开发前检查与数据衔接

## 0.1 阶段目标

在正式开发 V4 前，先确认 V3 的核心数据已经具备 V4 分析基础。

本阶段不开发复杂页面，重点是检查数据结构、接口可用性和历史兼容问题。

---

## 0.2 重点检查内容

### 1. V3 方案表

确认 `schedule_plan` 是否具备：

```text
id
term_id
plan_name
strategy_code
status
total_score
scheduled_count
unscheduled_count
conflict_count
created_at
applied_at
is_current
```

如果没有 `is_current`，需要确认是否能通过正式课表 `source_plan_id` 反查当前方案。

---

### 2. V3 方案明细表

确认 `schedule_plan_item` 是否具备：

```text
id
plan_id
teaching_task_id
course_id
teacher_id
class_id
room_id
week_day
period_start
period_end
is_scheduled
unscheduled_reason
```

字段名可以不同，但语义必须能对应。

---

### 3. 正式课表表

确认 `schedule` 是否具备来源字段：

```text
source_plan_id
source_plan_item_id
```

如果没有，至少应有能表示来源方案的字段。

---

### 4. V3 方案接口

确认以下接口能正常使用：

```http
GET  /api/v3/schedule-plans
GET  /api/v3/schedule-plans/{id}
POST /api/v3/schedule-plans/compare
POST /api/v3/schedule-plans/{id}/apply
POST /api/v3/schedule-plans/{id}/rollback
```

---

## 0.3 本阶段后端任务

1. 检查 V3 数据表；
2. 检查 V3 方案接口；
3. 如有必要，补充 `source_plan_id`；
4. 如有必要，补充 `source_plan_item_id`；
5. 确认 V4 可以读取 V3 方案数据；
6. 不要修改 V3 自动排课算法。

---

## 0.4 本阶段前端任务

1. 检查 V3 方案列表页面；
2. 检查 V3 方案详情页面；
3. 检查 V3 正式课表页面；
4. 预留 V4 分析入口；
5. 不要重写 V3 页面主体。

---

## 0.5 验收标准

- [ ] 可以查询已有排课方案；
- [ ] 可以查询方案明细；
- [ ] 可以判断当前正式课表来源方案；
- [ ] 可以确认生成方案不会自动覆盖正式课表；
- [ ] 可以确认 V4 分析功能具备数据基础。

# V4 阶段 2：评分详情解释

## 2.1 阶段目标

实现方案评分详情解释功能。

V3 只有总评分时，展示效果不够好。V4 要把评分拆解成多个维度，让用户知道方案为什么得这个分。

---

## 2.2 后端任务

### 2.2.1 新增评分详情接口

```http
GET /api/v4/schedule-analysis/plans/{planId}/score-details
```

返回评分项：

```text
硬性冲突评分
教师课时均衡评分
教室利用率评分
班级负载评分
时间分布评分
总评分
```

每个评分项包括：

```text
score_key
score_name
score_value
max_score
weight
description
```

### 2.2.2 评分计算说明

如果 V3 已经保存规则权重，则优先复用。

如果 V3 没有保存评分明细，V4 可以基于方案明细重新计算。

不要求本阶段评分算法非常复杂，重点是：

```text
结构清晰
能解释
能展示
不影响 V3 总评分逻辑
```

---

## 2.3 前端任务

### 2.3.1 新增页面

```text
frontend/src/views/v4/ScheduleScoreDetail.vue
```

### 2.3.2 新增路由

```text
/v4/schedule-analysis/:planId/score
```

### 2.3.3 页面内容

```text
顶部方案信息
总评分展示
评分明细表格
评分雷达图
评分规则说明
```

---

## 2.4 本阶段禁止事项

1. 不要允许前端修改评分；
2. 不要让评分详情接口修改方案；
3. 不要重写 V3 自动排课评分逻辑；
4. 不要强行要求评分明细总和完全等于旧 total_score；
5. 不要隐藏评分计算来源。

---

## 2.5 验收标准

- [ ] 可以查看方案评分详情；
- [ ] 评分项至少包含 5 个维度；
- [ ] 每个评分项有说明；
- [ ] 页面可以展示总评分；
- [ ] 页面可以展示评分雷达图或表格；

本阶段是 V4 从“只读分析”进入“安全辅助优化”的关键阶段。

---

## 6.2 后端任务

### 6.2.1 新增冲突检测接口

```http
POST /api/v4/schedule-adjustments/check
```

请求内容：

```text
targetType
planId
planItemId
scheduleId
newWeekDay
newPeriodStart
newPeriodEnd

教室容量
教室类型
```

### 6.2.2 新增保存调整接口

```http
POST /api/v4/schedule-adjustments/apply
```

要求：

1. 保存前再次检测冲突；

# V4 阶段 7：课程锁定管理

## 7.1 阶段目标

实现课程锁定功能，为后续局部重排打基础。

课程锁定的含义是：

> 某些课程已经人工确认，后续局部重排时不能改变这些课程的时间和教室。

---

## 7.2 后端任务

实现接口：

```http
POST /api/v4/schedule-locks/lock
POST /api/v4/schedule-locks/unlock
GET  /api/v4/schedule-locks/plans/{planId}
```

锁定记录应包括：

```text
target_type
plan_id
plan_item_id
schedule_id
lock_reason
created_at
```

---

## 7.3 前端任务

### 7.3.1 新增页面

```text
frontend/src/views/v4/ScheduleLockManage.vue
```

### 7.3.2 页面内容

```text
方案信息
已锁定课程数量
已锁定课程列表
锁定原因
取消锁定按钮
```

### 7.3.3 入口

可以从：

```text
方案详情页
质量分析详情页
局部重排弹窗
```

进入。

---

## 7.4 本阶段禁止事项

1. 锁定不是应用方案；
2. 锁定不应该修改正式课表；
3. 不要只在前端保存锁定状态；
4. 不要允许锁定已废弃方案；
5. 不要让锁定功能直接触发重排；
6. 不要删除锁定日志。

---

## 7.5 验收标准

- [ ] 可以锁定方案中的课程；
- [ ] 可以填写锁定原因；
- [ ] 可以取消锁定；
- [ ] 可以查看锁定列表；
- [ ] 锁定状态刷新后仍存在；
- [ ] 后端能返回锁定状态；
- [ ] 锁定不会影响正式课表。

# V4 阶段 8：局部重排生成新方案

## 8.1 阶段目标

基于已有方案，保留锁定课程，只对未锁定课程进行局部重排，并生成一个新的排课方案。

注意：

> 局部重排生成的是新方案，不是直接修改正式课表。

---

## 8.2 后端任务

### 8.2.1 新增局部重排接口

```http
POST /api/v4/schedule-replan/plans/{planId}
```

请求：

```text
newPlanName
keepLocked
strategyCode
forceGenerate
```

返回：

```text
newPlanId
sourcePlanId
scheduledCount
unscheduledCount
conflictCount
totalScore
```

### 8.2.2 处理逻辑

```text
1. 校验原方案存在；
2. 校验原方案状态；
3. 查询锁定课程；
4. 复制锁定课程到新方案；
5. 对未锁定课程执行简化重排；
6. 写入新的 schedule_plan；
7. 写入新的 schedule_plan_item；
8. 计算新方案评分；
9. 返回新方案 ID。
```

### 8.2.3 最小可用策略

如果重排算法复用困难，可以先实现：

```text
复制原方案为新方案
保留锁定标记
允许后续再做真正重排
```

但必须在完成说明中明确当前是最小可用版。

---

## 8.3 前端任务

### 8.3.1 新增局部重排弹窗

建议组件：

```text
frontend/src/components/v4/LocalReplanDialog.vue
```

### 8.3.2 弹窗内容

```text
来源方案信息
已锁定课程数量
可重排课程数量
新方案名称
策略选择
确认提示
```

### 8.3.3 成功后行为

生成成功后：

```text
跳转到新方案详情页
提示用户：新方案不会自动应用，需要手动应用
```

---

## 8.4 本阶段禁止事项

1. 不要覆盖原方案；
2. 不要删除原方案；
3. 不要修改正式课表；
4. 不要绕过 V3 apply；
5. 不要让局部重排结果直接成为正式课表；
6. 不要修改锁定课程；
7. 不要引入复杂求解器；
8. 不要把局部重排写成全量重写系统。

---

## 8.5 验收标准

- [ ] 可以基于旧方案生成新方案；
- [ ] 新方案有独立 plan_id；
- [ ] 原方案仍然存在；
- [ ] 原方案明细没有被删除；
- [ ] 锁定课程在新方案中保持不变；
- [ ] 新方案不会自动写入正式课表；
- [ ] 新方案可以通过 V3 apply 应用；
- [ ] 生成失败时有明确提示。

## 十二、总结

V4 的开发顺序应坚持：

```text
先分析
再解释
再诊断
再展示
再辅助调整
最后智能建议
```

V4 的核心价值不是继续堆排课算法，而是让 V3 已经生成的排课方案变得：

```text
看得懂
比得清
查得出问题
能辅助优化
能导出报告
能用于答辩展示
```

只要严格遵守阶段计划，V4 可以在不破坏 V3 的前提下，显著提升系统完整度和毕业设计展示效果。
