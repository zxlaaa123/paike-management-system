# 未来前瞻计划：距离真正可商用排课系统还差什么

## 0. 结论

当前项目已经不是简单 demo。它具备一套较完整的高校排课业务闭环：基础数据、教学任务、自动排课、手动调整、多方案、冲突检测、评分、导出、审计、治理中心、V8/V9 引擎演进和较厚的测试网。

但它距离“真正可商用”还有明显距离。差距不主要在“能不能排出课表”，而在：

- 真实学校数据复杂度。
- 多角色协作和权限。
- 批量导入、教务系统集成、数据治理。
- 可部署、可监控、可备份、可升级。
- 产品体验、实施工具和售后运营能力。
- 大规模场景下的性能、稳定性、可解释性和可恢复性。

当前更准确的位置：**强技术原型 / 校内试点前置版本**。完成 V10 连续周段后，可接近“单校小规模内部试用”。要到商业交付，还需要至少 3-5 个大版本的产品化和工程化工作。

## 1. 调查依据

### 1.1 本地代码实证

| 项目 | 当前规模 / 事实 |
|---|---|
| 后端 Controller | 43 个 |
| 后端实体 | 32 个 |
| 前端页面 | 50 个 Vue 页面 |
| 前端 API 模块 | 39 个 |
| 数据库脚本 | 32 个 SQL 脚本 |
| CI | `.github/workflows/backend-ci.yml`、`frontend-ci.yml` 已存在 |
| E2E | 根目录 `package.json` 有 stage6/stage7/stage9/v8/v9 Playwright 脚本 |
| 认证 | JWT httpOnly Cookie + CSRF + 登录限流 + 安全响应头 |
| 权限 | 后端写操作粗粒度 ADMIN；前端静态菜单，无细粒度权限点 |
| 生产观测 | 有 `/api/health`，无 Spring Boot Actuator / metrics / tracing |
| 交付 | 无 Dockerfile / docker-compose；已有 backend/frontend `.env.example` |
| 批量导入 | 未发现真正的上传、批量导入、模板校验入口 |
| 迁移 | 使用 `spring.sql.init` + 自定义脚本列表；未引入 Flyway/Liquibase |

### 1.2 外部参照

- OWASP ASVS：用于衡量 Web 应用安全验证覆盖面。
- Spring Boot Actuator：生产环境健康、指标、审计、管理端点参照。
- UniTime：成熟高校排课系统参照，覆盖 university timetabling、constraint solver、文档、demo、下载和支持。

这些参照说明：商用排课系统不是只包含算法，还包含安全、运维、实施、集成、文档、支持体系。

## 2. 当前已经比较强的部分

### 2.1 核心排课链路

已具备：

- 学期、教师、班级、教室、课程、教学任务。
- 自动排课、手动排课、多方案生成、方案对比、方案应用。
- 冲突检测、未排任务、课表查询、Excel 导出。
- V8 引擎：内存冲突检测、回溯、模拟退火、增量评分。
- V9 周型：`ALL / ODD / EVEN` 单双周支持。
- V10 文档已开始规划连续周段。

评价：核心“排课系统”主线已经成立。

### 2.2 质量治理

已具备：

- 审计日志。
- 回归测试中心。
- 一致性检查。
- 性能基线。
- 数据库迁移状态。
- 错误码中心。
- 后端全量测试和前端类型检查流程。

评价：这部分超过普通课程设计水平，说明项目有工程治理意识。

### 2.3 安全基础

已具备：

- JWT 强密钥启动校验。
- httpOnly Cookie。
- CSRF 双 token 校验。
- 登录限流。
- 安全响应头。
- CORS 配置。
- JSON 请求体大小限制。
- 管理员默认密码随机化。

评价：安全基础不是空白，但还不是商用安全体系。

## 3. 商用差距总览

| 方向 | 当前状态 | 商用要求 | 缺口等级 |
|---|---|---|---|
| 周次模型 | V9 单双周，V10 规划连续周段 | 任意周段、节假日、停调课、补课 | 高 |
| 权限 | 粗粒度 ADMIN 写权限 | 多角色、多部门、字段/操作级权限 | 高 |
| 数据导入 | 基本靠页面录入 | Excel 模板导入、校验、回滚、批量修复 | 高 |
| 系统集成 | 未见正式 SIS/SSO 对接 | 教务系统、统一认证、组织架构同步 | 高 |
| 生产部署 | 本地启动为主 | 容器化、配置分层、发布回滚 | 高 |
| 可观测性 | 简单 health | metrics、日志、trace、告警、容量水位 | 中高 |
| 数据安全 | 有认证和审计 | 备份恢复、脱敏、保留策略、权限审计 | 高 |
| 产品体验 | 功能页齐全 | 实施向导、批量操作、异常修复、帮助文档 | 中高 |
| 算法能力 | 已有 V8/V9 | 大规模、偏好、解释、稳定重跑、局部锁定更细 | 中高 |
| 商业运营 | 无 | 版本、租户、授权、SLA、支持流程 | 高 |

## 4. 关键差距详解

### 4.1 真实教务模型还不够复杂

当前模型覆盖常见基础排课，但真实学校常见问题更多：

- 连续周段、停课周、节假日、补课、临时调课。
- 合班课、拆班课、单双教师、主讲+助教。
- 多校区、楼间移动时间、跨校区不可连续排。
- 实验分组、轮转实验、单双周之外的 1-4/5-8/9-12 周切换。
- 课程计划、培养方案、年级、专业方向、行政班和教学班分离。
- 学生选课后形成个人课表，不能只按班级排。
- 考试排程、监考、考场容量、试卷保密等独立场景。

当前 V10 连续周段是第一块关键拼图，但不是终点。

### 4.2 权限体系不够商用

当前事实：

- `AuthInterceptor.requiresAdmin` 对所有状态变更接口要求 ADMIN。
- 读接口基本只要求登录。
- 前端 `BaseLayout.vue` 菜单静态展示。
- 路由没有角色或权限点控制。

商用需要：

- 教务管理员、院系管理员、教师、教室管理员、只读审计员等角色。
- 权限点：`schedule:read`、`schedule:write`、`plan:apply`、`rule:admin`、`governance:read` 等。
- 数据范围：只能看本院系、本校区、本学期或授权班级。
- 前端菜单、按钮、路由和后端接口一致控制。
- 权限变更审计。

这不是小修，建议单独版本做。

### 4.3 缺少批量导入和实施工具

目前未发现真正的批量上传/导入入口。

商用实施中，客户不会手工录入几百个教师、几百个教室、几千条教学任务。必须有：

- 教师、班级、课程、教室、教学任务 Excel 模板。
- 导入预检查：重复、缺字段、非法枚举、容量不匹配。
- 错误报告下载。
- 部分成功 / 全部回滚策略。
- 导入批次记录和审计。
- 数据清洗工具。

没有导入能力，系统很难从“能演示”进入“能实施”。

### 4.4 缺少外部系统集成

真实学校已有教务系统、统一身份认证、组织架构、人事系统、选课系统。

商用需要：

- SSO：CAS / OAuth2 / LDAP / SAML 至少选一种。
- 组织架构同步：学院、系、专业、班级、教师。
- 课程计划和教学任务同步。
- 课表结果回写教务系统。
- 标准 API 文档或 OpenAPI。
- 同步失败重试、差异对账、接口审计。

当前项目更像独立系统，还没有作为学校 IT 生态中的一环。

### 4.5 生产运维能力不足

当前事实：

- 有 `/api/health`。
- 无 `spring-boot-starter-actuator`。
- 无 Dockerfile / docker-compose。
- 无统一日志采集、指标、trace。
- 迁移使用 `spring.sql.init` 配脚本列表，未用 Flyway/Liquibase。

商用至少需要：

- Docker 镜像。
- 一键部署或 compose。
- 环境变量模板和配置说明。
- Actuator health / metrics。
- 日志格式规范。
- 数据库迁移版本化。
- 备份恢复手册。
- 升级回滚方案。
- 容量和性能压测报告。

否则客户现场出问题，难以定位和恢复。

### 4.6 数据安全与合规不完整

已有认证、CSRF、安全头、审计基础，但商用还需要：

- 完整 RBAC。
- 密码策略、账号锁定、重置流程。
- 登录历史和异常登录告警。
- 操作审计覆盖所有关键写操作。
- 数据脱敏、导出权限控制。
- 备份加密、恢复演练。
- 安全测试基线，至少可参考 OWASP ASVS 做自查。

排课系统涉及教师、班级、教室资源，不一定是强隐私系统，但一旦接学生选课和个人课表，就会涉及更高的数据保护要求。

### 4.7 产品体验还偏工程后台

当前页面多，功能全，但商用还需要“实施者友好”：

- 首次初始化向导。
- 数据完整性看板。
- 排课前准备清单。
- 一键发现阻塞项。
- 冲突原因可解释、可定位、可批量修复。
- 导出模板可配置。
- 教师/院系确认流程。
- 操作帮助和内置说明。
- 更强的空状态、加载状态、错误恢复。

很多商用价值不在算法，而在用户能否顺利把数据准备好，并理解为什么排不出来。

## 5. 建议未来路线

### 阶段 A：核心排课真实化

目标：从“能排一张课表”到“能覆盖真实高校常见规则”。

建议内容：

1. 完成 V10 连续周段。
2. 增加节假日 / 停课 / 补课模型。
3. 支持合班、拆班、实验分组。
4. 支持多校区和移动时间约束。
5. 强化局部调课：保留锁定、只重排局部、变更影响分析。

完成后定位：单校内部试用版。

### 阶段 B：数据实施能力

目标：让系统能接真实学校数据。

建议内容：

1. Excel 模板导入：教师、班级、课程、教室、教学任务。
2. 导入预检和错误报告。
3. 导入批次审计和回滚。
4. 数据质量评分。
5. OpenAPI 文档。

完成后定位：可实施原型。

### 阶段 C：权限与协作

目标：从单管理员系统变成多角色协作系统。

建议内容：

1. 权限点模型。
2. 角色管理。
3. 用户管理。
4. 数据范围控制。
5. 前端菜单和按钮权限。
6. 关键审批流：方案确认、调课申请、院系确认。

完成后定位：真实学校多人使用。

### 阶段 D：生产交付

目标：从开发环境项目变成能部署、监控、升级的系统。

建议内容：

1. Dockerfile + docker-compose。
2. Nginx 示例配置。
3. Actuator + metrics。
4. 结构化日志。
5. 数据库迁移版本化。
6. 备份恢复手册。
7. 发布包和升级说明。
8. CI 增加后端、前端、E2E、镜像构建、制品归档。

完成后定位：可交付版本。

### 阶段 E：高级排课能力

目标：对标成熟排课系统的技术深度。

建议内容：

1. 学生个人课表冲突。
2. 选课容量和多教学班。
3. 考试排程。
4. 教师偏好、院系偏好、软约束权重可解释。
5. 排课结果解释：为什么某课被排在这里，为什么某课排不出。
6. what-if 模拟：调整规则后对课表影响。
7. 大规模 benchmark 和稳定性报告。

完成后定位：有竞争力的专业排课产品。

### 阶段 F：商业运营能力

目标：如果未来做 SaaS 或对外售卖，需要补这一层。

建议内容：

1. 多租户或多学校隔离。
2. 授权 / License。
3. 租户级配置。
4. 客户数据隔离和备份。
5. SLA、日志留存、问题工单。
6. 用户手册、管理员手册、部署手册。
7. 演示数据包和初始化脚本。

这阶段不建议近期做，除非目标明确变成产品化创业或长期项目。

## 6. 优先级建议

### 6.1 近期最值得做

| 优先级 | 事项 | 原因 |
|---|---|---|
| P0 | V10 连续周段 | 直接补真实排课刚需 |
| P0 | 批量导入设计 | 没有导入就很难实施 |
| P1 | RBAC 设计稿 | 商用必须有，但先写设计，别急着全改 |
| P1 | Docker/部署手册 | 让别人能跑起来 |
| P1 | Actuator/metrics 方案 | 生产运维入口 |
| P2 | OpenAPI/接口文档 | 对接教务系统前置 |

### 6.2 暂时不建议做

| 暂缓项 | 原因 |
|---|---|
| 多租户 SaaS | 当前单校能力还没完全商用化 |
| 计费/License | 太早，和当前核心能力无关 |
| 大规模 UI 改版 | 先补真实数据和部署能力 |
| 任意周集合 | V10 连续周段先落地，避免模型过度复杂 |
| 移动端 App | 排课系统核心用户主要在桌面端 |

## 7. 如果按“商用程度”分级

| 等级 | 标准 | 当前状态 |
|---|---|---|
| L1 演示系统 | 能展示主流程 | 已超过 |
| L2 技术原型 | 有核心算法和测试 | 已达到 |
| L3 校内试点 | 能导入真实数据、权限基本可用、可部署 | 未达到 |
| L4 单校交付 | 可监控、可备份、可升级、有实施文档 | 未达到 |
| L5 专业产品 | 多角色协同、系统集成、高级约束、稳定支持 | 距离较远 |

完成 V10 + 批量导入 + Docker/部署 + 基础 RBAC 后，可尝试冲 L3。
