# V6 阶段 6 错误码与提示中心现状调查

调查日期：2026-06-08

## 一、现状结论

后端已有统一响应结构 `Result<T>`，失败响应包含数值型 `code` 和 `message`。`BusinessException` 支持自定义数值错误码，全局异常处理器会把 401、403、404、409、429 等业务码映射到对应 HTTP 状态。

前端 `request` 拦截器已统一处理非 200 响应并展示 `message`，401 会跳转登录页。阶段 6 最小版在不改变响应结构的前提下，补齐错误码目录、只读页面，并让前端错误提示显示数值 `code`。

## 二、错误分类

当前错误码目录按以下分类维护：

1. `AUTH`
2. `VALIDATION`
3. `BUSINESS`
4. `CONFLICT`
5. `SYSTEM`

## 三、本阶段交付

后端：

1. `SystemErrorCode` 枚举。
2. `GET /api/v6/error-codes`
3. `GET /api/v6/error-codes/{code}`
4. `ErrorCodeCatalogService`

前端：

1. `/v6/error-codes`
2. V6 系统治理菜单新增“错误码中心”。
3. 错误码列表、分类筛选、详情弹窗。
4. request 拦截器错误提示格式调整为 `[code] message`。

## 四、约束

1. 不改变现有 `Result` 响应结构。
2. 不强制替换所有历史 `BusinessException` 调用。
3. 字符串错误码先作为目录展示使用，接口实际失败响应继续沿用数值 `code`。

## 五、后续增强

1. 为高频业务异常逐步接入语义化字符串错误码。
2. 在审计日志和错误码中心之间建立跳转关系。
3. 为前端页面级异常增加错误码筛选和统计。
