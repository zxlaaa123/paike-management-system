# V6_01_版本需求说明

## 一、版本名称

V6：稳定化与工程化治理版

## 二、背景

V1-V5 已经形成完整排课业务链路：

1. V1 提供基础数据、教学任务、手动排课、课表查询。
2. V2 提供规则化自动排课、禁排、评分、冲突报告。
3. V3 提供学期、方案、评分明细、方案应用、回滚。
4. V4 提供质量分析、风险诊断、局部调整、锁定、报告。
5. V5 提供智能修复建议、候选位置、试算方案、优化对比。

系统下一阶段主要风险不是功能不足，而是功能边界复杂后带来的回归成本、数据一致性、性能波动、部署升级和问题追踪困难。

## 三、当前实现校准（2026-05-26）

本需求说明是早期 V6 草案，进入开发前必须按当前代码重新校准：

1. 当前产品功能线做到 V1-V5，尚无 `/api/v6` 接口层。
2. V5 已经实现修复任务、候选位置、试算方案、优化对比，并已有一致性检查相关能力。
3. V5 已存在 `schedule_regression_test` 和 `schedule_consistency_check` 等基础表，不应在 V6 里重复建设同语义表。
4. V6 仍应保留治理方向，但第一阶段建议从 `system_audit_log` 审计日志最小闭环开始。
5. 数据库脚本文件名里的 `v6_*.sql` 不是产品 V6 版本完成标志，只代表历史迁移编号。

## 四、V6 核心目标

V6 目标是建立长期维护能力：

1. 建立 V1-V5 自动化回归体系。
2. 固化正式课表写入、学期隔离、方案隔离、锁定课程保护边界。
3. 建立自动排课、局部重排、智能修复的性能基线。
4. 引入数据库迁移和版本化升级机制。
5. 增加审计日志，追踪关键排课操作。
6. 统一后端错误码和前端失败提示。
7. 提供治理类前端页面，方便检查系统健康状态。

## 五、用户角色

| 角色 | 关注点 |
|---|---|
| 管理员 | 系统是否稳定、数据是否安全、操作是否可追踪 |
| 教务人员 | 排课、调整、应用方案是否可靠 |
| 测试人员 | V1-V5 功能是否可快速回归 |
| 开发人员 | 数据库升级、接口错误、性能问题是否可定位 |

## 六、功能范围

V6 包含：

1. 回归测试中心。
2. 数据一致性检查中心。
3. 排课性能基线中心。
4. 审计日志中心。
5. 数据库迁移状态查看。
6. 错误码与接口失败提示规范。
7. 前端危险操作状态增强。

V6 不包含：

1. 新一代自动排课算法重写。
2. 大模型直接自动改课表。
3. 推翻 V3 方案机制。
4. 绕过 V5 试算方案机制。
5. 对 V1-V5 接口做破坏性重命名。

## 七、关键业务边界

### 6.1 正式课表边界

自动排课、局部重排、智能修复仍然只能生成方案或试算方案。正式课表必须由用户显式应用，并经过后端二次校验。

### 6.2 学期边界

所有新增治理接口必须支持 `semesterId`，不能跨学期聚合关键业务数据，除非接口明确是全局统计。

### 6.3 方案边界

评分、风险、修复建议、性能指标、审计日志必须能追踪到 `planId` 或明确标记为正式课表级操作。

### 6.4 锁定边界

锁定课程是硬约束。V6 的一致性检查必须能发现锁定课程被误改的情况。

## 八、验收目标

V6 完成后应达到：

1. 一键运行 V1-V5 核心回归。
2. 可查看最近一次回归结果和失败原因。
3. 可查看正式课表关键写操作审计日志。
4. 可运行学期、方案、锁定、试算数据一致性检查。
5. 可查看自动排课和局部重排性能基线。
6. 数据库升级有明确版本记录。
