# V6_06_回归自动化与性能治理规则设计

## 一、设计目标

本文档定义 V6 的回归自动化、数据一致性检查和性能治理规则。

目标：

1. 每次新增功能后能快速确认 V1-V5 没有被破坏。
2. 每个关键写操作能被审计。
3. 每个关键排课操作有性能基线。
4. 每个关键数据边界有一致性检查。

## 二、回归自动化规则

### 2.1 用例分层

| 层级 | 说明 |
|---|---|
| P0 | 登录、基础数据、自动排课、方案应用、正式课表查询 |
| P1 | V1-V5 各模块成功路径和失败路径 |
| P2 | 页面交互、导出、图表、AI 解释 |

### 2.2 P0 最小集合

1. 登录成功。
2. 创建教师、班级、课程、教室、时间段。
3. 创建教学任务。
4. 执行自动排课生成方案。
5. 查看方案详情。
6. 应用方案到正式课表。
7. 查询正式课表。
8. 创建锁定项。
9. 执行局部重排生成试算方案。
10. 运行智能修复建议。

### 2.3 失败路径必须覆盖

1. 教师同时间冲突。
2. 班级同时间冲突。
3. 教室同时间冲突。
4. 教室容量不足。
5. 教师禁排冲突。
6. 跨学期应用方案。
7. 应用已废弃方案。
8. 修改锁定课程。
9. 未登录访问。
10. CSRF 缺失。

## 三、数据一致性规则

### 3.1 学期一致性

所有核心业务数据必须能追踪到学期。

检查规则：

1. `teaching_task.semester_id` 不能为空。
2. `schedule.semester_id` 必须和来源任务一致。
3. `schedule_plan.semester_id` 必须和方案明细一致。
4. 跨学期方案不能应用到当前学期。

### 3.2 方案一致性

检查规则：

1. 正式课表来源方案必须存在。
2. 已废弃方案不能应用。
3. 试算方案不能被当作正式方案直接应用。
4. 评分、风险、修复建议必须绑定有效方案。

### 3.3 锁定一致性

检查规则：

1. 锁定课程不能被移动。
2. 锁定课程不能被删除。
3. 锁定课程不能被替换教师、时间或教室。
4. 局部重排结果不能覆盖锁定项。

## 四、性能治理规则

### 4.1 监控范围

必须记录耗时的操作：

1. 自动排课。
2. 冲突检测。
3. 方案评分。
4. 风险诊断。
5. 候选位置生成。
6. 局部重排。
7. 试算方案生成。

### 4.2 性能记录维度

每次记录至少包含：

1. 操作类型。
2. 学期 ID。
3. 方案 ID。
4. 教学任务数量。
5. 课表记录数量。
6. 候选位置数量。
7. 耗时毫秒。
8. 成功状态。
9. 错误码。

### 4.3 性能退化判断

建议规则：

1. 同类操作平均耗时增长超过 30%，标记为警告。
2. 同类操作最大耗时增长超过 50%，标记为风险。
3. P0 操作连续 3 次失败，标记为阻塞。

## 五、审计规则

必须审计的操作：

1. 应用方案。
2. 回滚方案。
3. 手动排课。
4. 手动调整。
5. 锁定课程。
6. 解除锁定。
7. 应用试算方案。
8. 修改规则权重。

审计日志必须记录成功和失败，不能只记录成功操作。

## 六、禁止事项

1. 禁止为了回归测试直接清空业务表。
2. 禁止测试数据污染正式学期。
3. 禁止性能统计阻塞主业务流程。
4. 禁止一致性检查自动修复正式课表。
5. 禁止前端把失败操作展示为成功。
