# 高校排课系统手动测试流程

## 1. 文档目的

这份文档用于指导你对当前系统做一轮完整的手动测试。

适用场景：

- 版本发布前做人工回归
- 自动化测试结果异常，需要人工复核
- 新功能开发完成后做冒烟测试
- 第一次接手项目，不清楚该从哪里开始点

本文默认测试对象为本地开发环境：

- 前端：`http://127.0.0.1:5173`
- 后端：`http://127.0.0.1:8090`
- 默认账号：`admin / 123456`

---

## 2. 测试目标

本轮手动测试的目标不是“把每个按钮都点一遍”，而是确认下面 5 类核心能力：

1. 登录和权限流程正常
2. 基础数据管理正常
3. 教学任务与排课流程正常
4. 排课分析与课表查询正常
5. 页面没有明显异常、报错、错乱、卡死

---

## 3. 测试前准备

### 3.1 环境准备

开始测试前，先确认：

- 前端能正常打开
- 后端接口可访问
- 数据库已连接
- 浏览器建议使用 Chrome 或 Edge 最新版

建议先手动访问：

- `http://127.0.0.1:5173/login`
- `http://127.0.0.1:8090/api/health`

### 3.2 浏览器准备

正式测试前建议：

- 清空浏览器缓存或用无痕窗口
- 打开浏览器开发者工具
- 切到 `Console`
- 切到 `Network`

测试过程中重点观察：

- 是否出现红色报错
- 是否出现接口 401、403、500
- 是否出现页面空白、按钮无响应、弹窗无法关闭

### 3.3 测试数据准备

建议每次手测都使用唯一标识，避免和旧数据混淆。

推荐命名规则：

- 教师编号：`T-MANUAL-日期序号`
- 课程编号：`C-MANUAL-日期序号`
- 班级名称：`手测班级-日期序号`
- 教室名称：`手测教室-日期序号`

例如：

- `T-MANUAL-0514-01`
- `C-MANUAL-0514-01`
- `手测班级-0514-01`
- `手测教室-0514-01`

---

## 4. 建议测试顺序

手动测试建议按下面顺序执行：

1. 登录
2. 首页
3. 基础数据管理
4. 教学任务管理
5. 手动排课
6. 自动排课
7. 排课分析
8. 课表查询
9. 退出登录

原因：

- 基础数据是后续流程的前置条件
- 教学任务依赖教师、班级、课程
- 排课依赖教学任务和教室
- 分析和课表依赖排课结果

---

## 5. 冒烟测试清单

如果你时间很少，至少先跑这一组冒烟测试：

### 5.1 登录

- 打开登录页
- 输入正确账号密码
- 点击“登录”
- 预期：
  - 登录成功
  - 跳转到首页
  - 左侧菜单显示完整

### 5.2 首页

- 查看首页统计卡片
- 预期：
  - 不再显示 `--`
  - 显示教师、班级、教室、课程数量

### 5.3 基础数据

- 教师管理：新增 1 条教师
- 班级管理：新增 1 条班级
- 教室管理：新增 1 条教室
- 课程管理：新增 1 条课程
- 预期：
  - 新增成功
  - 搜索能搜到
  - 列表显示正确

### 5.4 教学任务

- 新增 1 条教学任务
- 预期：
  - 可在弹窗内正常选择课程、教师、班级
  - 保存成功
  - 列表显示 `已排/需排`

### 5.5 手动排课

- 新增 1 条排课
- 预期：
  - 保存成功
  - 列表能看到排课记录

### 5.6 冲突检测

- 用同一教师、同一时间重复排课
- 预期：
  - 系统拦截
  - 出现冲突提示
  - 不产生重复记录

### 5.7 课表查询

- 查询班级课表
- 预期：
  - 能看到刚才新增的排课

### 5.8 自动排课

- 执行一次自动排课
- 预期：
  - 生成批次记录
  - 状态、成功数、失败数有结果

## 6. 详细测试步骤

## 6.1 登录与退出

### 用例 1：正确登录

步骤：

1. 打开 `/login`
2. 输入用户名 `admin`
3. 输入密码 `123456`
4. 点击“登录”

预期：

- 页面跳转到 `/dashboard`
- 顶部显示“当前登录：管理员”
- 左侧菜单正常显示

### 用例 2：空表单校验

步骤：

1. 不输入任何内容
2. 点击“登录”

预期：

- 提示必须输入用户名和密码
- 不跳转

### 用例 3：错误密码

步骤：

1. 输入正确用户名
2. 输入错误密码
3. 点击“登录”

预期：

- 登录失败提示
- 不跳转

### 用例 4：退出登录

步骤：

1. 登录后点击右上角“退出登录”

预期：

- 返回登录页
- 再访问受保护页面会被拦截到登录页

### 用例 1：首页统计正常展示

步骤：

- 列表查询

- 状态切换
- 删除

## 6.3.1 教师管理

入口：`基础数据管理 -> 教师管理`

建议字段：

- 教师编号：`T-MANUAL-0514-01`
- 教师姓名：`手测教师01`
- 所属部门：`计算机学院`

2. 用教师编号搜索，确认筛选正常

- 列表数据即时刷新

## 6.4 教学管理

## 6.4.1 教学任务管理

入口：`教学管理 -> 教学任务管理`

前置条件：

- 至少已有 1 名教师
- 至少已有 1 个班级
- 至少已有 1 门课程

建议字段：

- 课程：选择刚新增课程
- 教师：选择刚新增教师
- 班级：选择刚新增班级
- 每周课时：`4`
- 连续排课：默认关闭

重点：

- 这是本系统最核心的前置流程之一
- 弹窗里的 3 个下拉必须都能正常选中

用例：

1. 打开页面，确认列表和分页正常
2. 点击“新增教学任务”
3. 选择课程、教师、班级
4. 填写每周课时
5. 保存
6. 用课程名、教师名、班级名搜索

预期：

- 新增成功
- 列表可查到
- `已排/需排` 正常显示，如 `0/2大节`

## 6.4.2 教师禁排时间

入口：`教学管理 -> 教师禁排时间`

建议字段：

- 教师：选择已存在教师
- 时间段：例如 `周一 第1-2节`
- 禁排原因：`参加会议`
- 状态：`启用`

用例：

1. 新增一条禁排时间
2. 查询列表确认显示
3. 编辑禁排原因
4. 删除记录

预期：

- 教师和时间段下拉可正常操作
- 状态单选正常
- 列表显示正确

## 6.4.3 排课规则配置

入口：`教学管理 -> 排课规则配置`

用例：

1. 打开页面，确认当前规则正常加载
2. 修改“教师每天最多课程大节数”
3. 修改“班级每天最多课程大节数”
4. 切换“优先安排上午课程”
5. 切换“避免周五下午排课”
6. 点击“保存配置”
7. 点击“恢复默认配置”

预期：

- 保存成功提示
- 刷新页面后规则仍能正确显示
- 恢复默认后值恢复

## 6.5 排课管理

## 6.5.1 手动排课

入口：`教学管理 -> 手动排课`

前置条件：

- 已有教学任务
- 已有教室
- 已有时间段

建议操作：

1. 点击“新增排课”
2. 选择教学任务
3. 选择时间段
4. 选择教室
5. 保存

预期：

- 新增成功
- 列表中能看到课程、教师、班级、时间段、教室、排课来源

### 冲突检测专项

在同一页面继续做：

1. 再次点击“新增排课”
2. 选择相同教师或相同班级或相同教室
3. 选择相同时间段
4. 保存

预期：

- 系统拒绝保存
- 出现明确冲突提示
- 列表记录数不增加

建议至少验证 3 类冲突中的 1 类：

- 教师冲突
- 班级冲突
- 教室冲突

### 删除排课

步骤：

1. 找到刚新增的排课记录
2. 点击“删除”
3. 二次确认

预期：

- 删除成功
- 列表中消失

## 6.5.2 自动排课

入口：`教学管理 -> 自动排课`

用例 1：全部未排满任务

步骤：

1. 进入自动排课页面
2. 观察“全部未排满任务”数量
3. 点击“一键自动排课”

预期：

- 生成新的批次
- 出现执行结果弹层
- 显示批次号、成功数、失败数、生成记录数

用例 2：手动选择任务

步骤：

1. 切换到“手动选择任务”
2. 勾选 1 条任务
3. 点击“一键自动排课”

预期：

- 仅处理已选任务
- 批次记录显示任务数量正确

用例 3：批次记录

步骤：

1. 查看“最近批次记录”
2. 观察状态、开始时间、结束时间、操作列
3. 点击“清空结果”

预期：

- 批次列表正常刷新
- 清空后相关自动排课结果被移除

## 7. 每个页面都要顺手检查什么

不管你在测哪个页面，都建议顺手看下面这些点：

### 7.1 页面展示

- 标题是否正确
- 文案是否明显错误
- 表格是否错位
- 弹窗是否遮挡
- 分页是否显示异常

### 7.2 表单交互

- 必填校验是否生效
- 数字输入框能否正常输入
- 下拉能否展开、选择、关闭
- 保存后弹窗是否自动关闭

### 7.3 接口反馈

- 成功时有无提示
- 失败时有无提示
- 控制台是否报错
- Network 中是否出现 500

### 7.4 数据一致性

- 新增后能否查到
- 修改后是否立即刷新
- 删除后是否真正消失
- 查询结果是否和输入条件匹配

## 9. 一轮手测结束后建议做什么

完成测试后建议执行：

1. 清理你新增的测试数据
2. 导出或保存错误截图
3. 整理测试结论
4. 记录：
   - 通过项
   - 失败项
   - 未测项
   - 阻塞项

建议最终结论用这 4 类状态：

- `通过`
- `失败`
- `部分通过`
- `未执行`

## 11. git 状态提醒

如果你测试完准备提测或提交流程，建议顺手执行：

```bash
git status
git diff --stat
```

如果改动确认没问题，再做：

```bash
git add .
git commit -m "你的提交说明"
```

如果你不确定哪些文件该提交，先不要 `git add .`，而是先看：

```bash
git status --short
```

按文件逐个判断更安全。
