# 排课系统 V3 开发阶段任务

## 一、文档说明

本文档用于指导排课系统 V3 版本的分阶段开发。

V3 版本名称：

```text
智能排课优化与学期方案管理版
```

V3 核心目标：

```text
以学期为数据边界
以排课方案为核心对象
以多方案生成、评分明细、方案对比、排课日志、未排原因和版本回滚作为主要亮点
```

本文档适合用于：

1. 给 AI 编程助手分阶段开发；
2. 作为 Claude Code、Trae、CodeBuddy、Codex CLI 等工具的开发路线；
3. 防止 AI 一次性修改太多文件导致项目失控；
4. 开发前确认每个阶段的目标、范围和验收标准。

---

## 二、V3 开发总原则

## 2.1 不推翻 V1/V2

V3 是在 V1、V2 基础上的增强版本，不是重写项目。

禁止：

```text
重建整个项目
删除 V1/V2 已有核心功能
随意改动已有接口返回结构
随意删除已有数据库表
随意清空已有业务数据
把原来的手动排课和自动排课全部推翻重写
```

允许：

```text
新增 V3 表
新增 V3 接口
新增 V3 页面
给旧表增加 semester_id 等必要字段
在不破坏旧功能的基础上增强查询条件
```

---

## 2.2 先稳定，再扩展

V3 开发前必须先检查当前 V1/V2 状态。

如果现有项目存在明显问题，应先修复：

```text
后端无法启动
前端无法启动
数据库连接失败
已有页面报错
自动排课接口异常
冲突检测结果不准确
```

不要在系统不稳定时直接加 V3 大功能。

---

## 2.3 每次只做一个阶段

AI 开发时必须按阶段推进。

禁止一次性要求 AI 完成整个 V3。

建议流程：

```text
完成一个阶段
启动项目
测试接口
测试页面
提交或保存当前版本
再进入下一个阶段
```

---

## 2.4 自动排课不能直接覆盖正式课表

V3 的重要规则：

```text
自动排课先生成排课方案
排课方案经过查看、评分、对比后
由用户点击应用
再写入正式课表
```

禁止：

```text
自动排课接口直接清空正式课表
自动排课接口直接覆盖 schedule 表
生成方案时误删历史课表
```

---

## 2.5 所有核心数据必须绑定学期

V3 中以下数据必须考虑 `semester_id`：

```text
教学任务
正式课表
排课方案
方案明细
规则权重
评分明细
排课日志
未排任务
手动调整记录
统计分析
```

---

## 三、V3 推荐开发阶段总览

V3 建议拆成 9 个阶段：

```text
阶段 0：V1/V2 代码体检与备份
阶段 1：学期管理基础能力
阶段 2：核心数据绑定学期
阶段 3：排课方案管理
阶段 4：评分明细与规则权重
阶段 5：多方案自动排课
阶段 6：方案详情、方案对比与应用回滚
阶段 7：排课日志、未排原因与手动调整
阶段 8：统计分析与首页增强
阶段 9：最终联调、演示数据与答辩包装
```

# 阶段 0：V1/V2 代码体检与备份

## 0.1 阶段目标

在正式开发 V3 前，先检查当前项目状态，确认 V1/V2 功能可运行，避免在不稳定基础上继续叠加功能。

---

## 0.2 主要任务

### 0.2.1 检查项目启动

确认：

```text
后端可以正常启动
前端可以正常启动
数据库可以正常连接
浏览器可以正常访问系统
```

---

### 0.2.2 检查 V1/V2 主要功能

检查以下功能是否正常：

```text
教师管理
班级管理
课程管理
教室管理
教学任务管理
手动排课
自动排课
冲突检测
课表查询
Excel 导入导出
```

如果某些功能暂时不可用，需要记录问题，不要盲目继续开发。

---

### 0.2.3 检查数据库结构

重点检查是否已经存在类似表：

```text
semester
term
schedule_plan
schedule_version
schedule_log
score_detail
```

如果已有类似表，V3 不要重复建表，需要基于现有结构调整。

---

### 0.2.4 备份数据库

开发 V3 前必须备份数据库。

建议命名：

```text
backup_before_v3.sql
backup_before_v3_日期.sql
```

---

### 0.2.5 备份代码或提交 Git

建议在 V3 开发前创建 Git 提交：

```text
git add .
git commit -m "backup: before v3 development"
```

如果暂时不用 Git，也至少复制一份项目目录备份。

---

## 0.3 输出结果

阶段 0 完成后，应得到：

```text
1. 当前 V1/V2 可运行状态确认
2. 数据库结构检查结果
3. 数据库备份文件
4. Git 提交或项目备份
5. V3 开发风险清单
```

---

## 0.4 验收标准

```text
后端启动成功
前端启动成功
数据库连接正常
V1/V2 主要功能未明显异常
已完成数据库备份
已完成代码备份或 Git 提交
已确认是否存在 V3 相关旧表
```

---

## 0.5 给 AI 的阶段提示词

```text
请你先不要开发 V3 新功能。请检查当前排课系统 V1/V2 的项目结构、数据库结构、后端启动方式、前端启动方式和已有功能模块，重点确认是否已经存在 semester、term、schedule_plan、schedule_log、score_detail 等类似表或模块。

请输出：
1. 当前项目结构概览；
2. V1/V2 已有功能清单；
3. 数据库已有表清单；
4. V3 开发前需要注意的兼容点；
5. 不能随意改动的文件和模块；
6. 下一阶段开发学期管理的建议。

注意：本阶段只做检查和分析，不要修改业务代码。
```


### 1.2.2 新增后端实体类


如果系统没有学期，可以初始化一个默认学期：

```text

```

```text

is_current = 1
```

### 1.3.1 新增学期管理页面

页面路径建议：

```text

```

功能包括：

```text

编辑学期

设置当前学期

```

---

### 1.3.2 顶部显示当前学期

在系统顶部或明显位置显示：

```text
当前学期：2025-2026学年第二学期
```

---

### 1.3.3 当前学期切换

支持从下拉框切换当前学期。

切换后提醒：

```text
切换学期后，教学任务、课表、排课方案和统计数据将按新学期展示。
```

---

## 1.4 验收标准

```text
可以新增学期
可以编辑学期
可以删除未使用学期
可以设置当前学期
同一时间只有一个当前学期
页面顶部可以显示当前学期
切换当前学期后，前端状态能刷新
```

# 阶段 2：核心数据绑定学期

## 2.1 阶段目标

让 V3 的核心数据按学期隔离。

本阶段重点处理：

```text
教学任务绑定学期
正式课表绑定学期
教学任务页面按学期筛选
课表页面按学期筛选
```

---

## 2.2 后端任务

### 2.2.1 teaching_task 表增加 semester_id

如果教学任务表尚无学期字段，需要增加：

```text
semester_id
```

---

### 2.2.2 schedule 表增加 semester_id

如果正式课表表尚无学期字段，需要增加：

```text
semester_id
```

可选增加：

```text
plan_id
```

用于记录正式课表来源方案。

---

### 2.2.3 旧数据迁移

将旧教学任务和旧课表绑定到默认当前学期。

迁移逻辑：

```text
如果 teaching_task.semester_id 为空，则设置为当前学期 ID
如果 schedule.semester_id 为空，则设置为当前学期 ID
```

---

### 2.2.4 改造教学任务查询接口

教学任务查询默认按当前学期过滤。

规则：

```text
如果传 semesterId，按传入学期查
如果不传 semesterId，按当前学期查
```

---

### 2.2.5 改造课表查询接口

课表查询默认按当前学期过滤。

包括：

```text
班级课表
教师课表
教室课表
课程课表
总课表
```

---

## 2.3 前端任务

### 2.3.1 教学任务页面增加学期感知

要求：

```text
页面显示当前学期
列表默认查询当前学期教学任务
新增教学任务默认绑定当前学期
支持按学期筛选历史任务
```

---

### 2.3.2 课表页面增加学期感知

要求：

```text
页面显示当前学期
课表默认查询当前学期
支持按学期查看历史课表
显示正式课表来源方案
```

---

## 2.4 注意事项

### 2.4.1 不要破坏旧接口

如果旧页面依赖旧接口，建议保留旧接口，新增 V3 参数或 V3 接口。

---

### 2.4.2 没有当前学期时的处理

如果没有当前学期：

```text
教学任务页面提示先设置当前学期
课表页面提示先设置当前学期
自动排课相关功能暂不可用
```

---

## 2.5 验收标准

```text
teaching_task 表有 semester_id
schedule 表有 semester_id
旧教学任务已绑定默认学期
旧课表已绑定默认学期
教学任务列表可以按学期隔离
课表查询可以按学期隔离
新增教学任务自动绑定当前学期
切换学期后教学任务和课表数据发生变化
V1/V2 原有功能不报错
```

---

## 2.6 给 AI 的阶段提示词

```text
现在开始开发 V3 阶段 2：核心数据绑定学期。

请在不破坏 V1/V2 已有功能的前提下，为教学任务和正式课表增加学期维度。

本阶段只做：

3. 旧数据迁移到当前学期；
4. 教学任务查询默认按当前学期过滤；
5. 课表查询默认按当前学期过滤；
6. 前端教学任务页面和课表页面显示当前学期并支持学期筛选。

注意：
1. 不要开发排课方案；
2. 不要开发评分明细；
3. 不要重写原有教学任务和课表模块；
4. 如果没有当前学期，页面必须提示用户先设置当前学期；
5. 所有修改要兼容原有 V1/V2 功能。

完成后请给出数据库变更、接口变更和测试步骤。
```

# 七、V3 开发风险提醒

## 7.1 最大风险：改乱旧功能

V3 修改涉及教学任务、课表、自动排课，容易影响 V1/V2。

必须避免：

```text
旧课表页面突然不能用
旧教学任务页面查不到数据
旧自动排课被破坏
旧冲突检测失效
```

---

## 7.2 最大风险：学期字段没贯穿

如果只给部分表加学期，会导致数据混乱。

必须确保：

```text
教学任务有 semester_id
正式课表有 semester_id
排课方案有 semester_id
方案明细有 semester_id
评分、日志、未排、统计都能按 semester_id 查询
```

---

## 7.3 最大风险：自动排课覆盖正式课表

V3 绝对不能让自动排课直接覆盖正式课表。

正确流程：

```text
自动排课 -> 生成方案 -> 用户应用方案 -> 写入正式课表
```

---

## 7.4 最大风险：一次性开发太多

V3 功能较多，不要一次性全部交给 AI。

必须分阶段：

```text
一阶段一提示词
一阶段一测试
一阶段一提交
```

---

# 八、V3 最终完成标准

V3 最终完成后，系统应具备以下能力：

```text
1. 可以按学期管理教学任务和课表；
2. 可以为一个学期生成多个排课方案；
3. 每个方案有独立明细；
4. 每个方案有总分和评分明细；
5. 每个方案有生成日志；
6. 每个方案有未排任务原因；
7. 多个方案可以对比；
8. 用户可以选择方案应用为正式课表；
9. 用户可以回滚到历史方案；
10. 用户可以手动调整方案并重新评分；
11. 系统可以展示教师工作量统计；
12. 系统可以展示教室利用率统计；
13. 系统可以展示班级课表均衡度；
14. V1/V2 原功能不被破坏。
```

# 结语

V3 开发的核心原则是：

```text
不要重写系统
不要一次性开发全部
不要破坏旧功能
不要让自动排课直接覆盖正式课表
```

正确开发路线是：

```text
先学期
再绑定数据
再方案管理
再评分规则
再自动排课
再方案对比
再日志调整
最后统计和答辩包装
```

只要按阶段推进，V3 就能形成一个非常完整、适合毕业设计展示的高级版本。
