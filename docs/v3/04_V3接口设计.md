# 排课系统 V3 接口设计

## 一、文档说明

本文档用于说明排课系统 V3 版本的前后端接口设计。

V3 版本接口设计必须与以下文档保持一致：

```text
01_V3版本需求说明.md
02_V3功能模块设计.md
03_V3数据库设计.md
```

V3 接口主要围绕以下能力展开：

1. 学期管理；
2. 当前学期切换；
3. 教学任务按学期查询；
4. 正式课表按学期查询；
5. 排课方案管理；
6. 多方案自动排课；
7. 规则权重配置；
8. 评分明细查询；
9. 方案对比；
10. 排课过程日志；
11. 未排任务原因分析；
12. 手动调整后重新评分；
13. 教师工作量统计；
14. 教室利用率统计；
15. 班级课表均衡度分析。

本文档主要面向后端接口开发、前端页面联调、AI 辅助开发和后续测试验收。

---

## 二、接口设计总原则

### 2.1 不破坏 V1/V2 已有接口

V3 是增量升级版本，不应随意删除或大改 V1/V2 已有接口。

已有接口如果需要支持学期筛选，优先采用以下方式：

```text
新增 semesterId 查询参数
新增 currentSemester 参数
新增 V3 专用接口路径
```

不建议直接改变旧接口返回结构，避免前端已有页面报错。

---

### 2.2 所有核心业务接口必须考虑学期

以下接口必须支持按学期处理数据：

```text
教学任务
正式课表
排课方案
方案明细
评分明细
排课日志
未排任务
统计分析
```

默认规则：

```text
如果前端传 semesterId，则按指定学期查询
如果前端不传 semesterId，则默认使用当前学期
```

---

### 2.3 自动排课不能直接覆盖正式课表

V3 自动排课接口只能生成排课方案：

```text
schedule_plan
schedule_plan_item
```

不能直接写入正式课表：

```text
schedule
```

只有调用“应用方案接口”后，才能把方案写入正式课表。

---

### 2.4 接口路径建议

V3 新增接口建议统一使用：

```text
/api/v3/...
```

例如：

```text
/api/v3/semesters
/api/v3/schedule-plans
/api/v3/schedule-rules
/api/v3/schedule-statistics
```

如果项目原来已经统一使用 `/api`，也可以继续沿用，但建议 V3 新接口单独分组，方便维护。

---

### 2.5 请求与响应格式统一

所有接口建议统一返回格式：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {}
}
```

分页接口建议统一返回：

```json
{
  "code": 200,
  "message": "查询成功",
  "data": {
    "records": [],
    "total": 100,
    "pageNum": 1,
    "pageSize": 10
  }
}
```

## 三、通用接口规范

## 3.1 通用成功响应

```json
{
  "code": 200,
  "message": "操作成功",
  "data": null
}
```

---

## 3.2 通用失败响应

```json
{
  "code": 400,
  "message": "请求参数错误",
  "data": null
}
```

---

## 3.3 常见状态码建议

| code | 含义 |
|---:|---|
| 200 | 成功 |
| 400 | 请求参数错误 |
| 401 | 未登录或无权限，如果项目无登录可不用 |
| 404 | 数据不存在 |
| 409 | 业务冲突 |
| 500 | 系统内部错误 |

---

## 3.4 分页参数

分页查询统一使用：

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|---|---|---|---|---|
| pageNum | number | 否 | 1 | 当前页 |
| pageSize | number | 否 | 10 | 每页数量 |
| keyword | string | 否 | 空 | 搜索关键词 |

---

## 3.5 学期参数

涉及学期的数据查询统一支持：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| semesterId | number | 否 | 指定学期 ID，不传则默认当前学期 |

---

## 3.6 时间字段格式

日期格式：

```text
yyyy-MM-dd
```

日期时间格式：

```text
yyyy-MM-dd HH:mm:ss
```


```json
{
```

```json
  "endDate": "2027-01-15",
```

```text
学期名称不能为空
学年不能为空

结束日期不能早于开始日期

```

### 接口地址

```http
DELETE /api/v3/semesters/{id}
```

### 业务限制

以下情况不允许删除：

```text
当前学期不能直接删除
已关联教学任务的学期不能删除
已关联正式课表的学期不能删除
已关联排课方案的学期不能删除
```

## 4.7 设置当前学期

### 接口地址

```http
PUT /api/v3/semesters/{id}/current
```

### 业务规则

```text

同一时间只能有一个当前学期
切换当前学期后，前端应刷新教学任务、课表、方案等页面数据
```

## 7.3 删除草稿方案

### 接口地址

```http
DELETE /api/v3/schedule-plans/{id}
```

### 业务规则

```text
只有草稿方案可以删除
已应用方案不能直接删除
已废弃方案建议保留，也可以根据系统需求允许删除
删除方案时需要同时删除方案明细、评分明细、日志、未排任务记录
```

---

## 7.4 废弃方案

### 接口地址

```http
PUT /api/v3/schedule-plans/{id}/abandon
```

### 业务规则

```text
草稿方案可以废弃
已应用方案可以废弃，但需要确认是否已有新方案应用
废弃方案不参与默认对比和应用
```

---

## 7.5 应用方案为正式课表

### 接口地址

```http
POST /api/v3/schedule-plans/{id}/apply
```

### 请求体

```json
{
  "replaceCurrentSchedule": true,
  "remark": "采用综合最优方案作为当前学期正式课表"
}
```

### 业务规则

```text
只能应用当前学期或指定学期下的方案
方案必须存在
方案不能是已废弃状态
应用方案前必须检查冲突
应用方案前建议检查未排任务数量
应用方案时，将 schedule_plan_item 写入 schedule
应用成功后，当前方案状态改为已应用
同一学期其他已应用方案可改为已废弃或保留历史状态
```

### 响应示例

```json
{
  "code": 200,
  "message": "方案已应用为正式课表",
  "data": {
    "planId": 11,
    "semesterId": 1,
    "appliedCount": 48,
    "appliedAt": "2026-05-14 16:00:00"
  }
}
```

---

# 八、自动排课接口

## 8.1 生成单个排课方案

### 接口地址

```http
POST /api/v3/schedule-generate
```

### 请求体

```json
{
  "semesterId": 1,
  "strategyType": "COMPREHENSIVE",
  "planName": "综合最优方案-001",
  "overwriteDraft": false
}
```

### 请求参数说明

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| semesterId | number | 否 | 学期 ID，不传默认当前学期 |
| strategyType | string | 是 | 策略类型 |
| planName | string | 否 | 方案名称 |
| overwriteDraft | boolean | 否 | 是否覆盖同名草稿方案 |

### 业务流程

```text
1. 获取目标学期
2. 读取该学期教学任务
3. 读取基础数据
4. 读取规则权重
5. 根据策略执行自动排课
6. 写入 schedule_plan
7. 写入 schedule_plan_item
8. 写入 schedule_score_detail
9. 写入 schedule_generate_log
10. 写入 schedule_unassigned_task
11. 返回方案摘要
```

### 响应示例

```json
{
  "code": 200,
  "message": "排课方案生成成功",
  "data": {
    "planId": 11,
    "semesterId": 1,
    "planName": "综合最优方案-001",
    "strategyType": "COMPREHENSIVE",
    "totalScore": 88.5,
    "scheduledCount": 48,
    "unscheduledCount": 2,
    "conflictCount": 0
  }
}
```

```text

2. 检查方案是否允许调整
3. 检查新时间和新教室是否合法
4. 重新检测教师、班级、教室冲突
5. 更新方案明细
6. 写入手动调整日志
7. 重新计算方案评分
8. 返回调整结果
```

### 响应示例

```json
{
  "code": 200,
  "message": "调整成功",
  "data": {
    "itemId": 10001,
    "planId": 11,
    "beforeScore": 88.5,
    "afterScore": 87.0,
    "conflictFlag": false
  }
}
```

# 二十一、接口验收标准

V3 接口开发完成后，需要满足以下标准：

```text
1. 可以新增、编辑、删除、查询学期；
2. 可以设置唯一当前学期；
3. 不传 semesterId 时，接口默认使用当前学期；
4. 教学任务列表能按学期隔离；
5. 正式课表能按学期隔离；
6. 自动排课接口只生成方案，不直接覆盖正式课表；
7. 一个学期可以生成多个排课方案；
8. 每个方案可以查看明细；
9. 每个方案可以查看评分明细；
10. 每个方案可以查看生成日志；
11. 每个方案可以查看未排任务原因；
12. 可以应用某个方案为正式课表；
13. 可以对多个方案进行对比；
14. 可以手动调整方案明细并重新评分；
15. 可以查看教师工作量统计；
16. 可以查看教室利用率统计；
17. 可以查看班级课表均衡度统计；
18. 所有 V3 接口不破坏 V1/V2 原有接口。
```

# 二十二、开发注意事项

## 22.1 不要让接口功能发散

V3 接口只围绕以下核心做：

```text
学期
方案
评分
对比
日志
统计
```

不要在 V3 中突然加入：

```text
学生选课
复杂审批
真实教务系统同步
多学校多租户
手机端接口
支付接口
```

---

## 22.2 自动排课接口必须有日志

生成方案时，必须写入排课日志。

否则 V3 的“可解释排课”亮点无法体现。

---

## 22.3 应用方案前必须校验

应用方案前至少检查：

```text
方案是否存在
方案是否属于当前学期
方案是否已废弃
方案是否有严重冲突
方案是否有未排任务
```

未排任务不一定阻止应用，但必须提示。

---

## 22.4 前端切换学期后必须刷新数据

切换当前学期后，前端应重新请求：

```text
教学任务
课表
排课方案
统计概览
```

否则页面可能显示旧学期数据。

---

## 22.5 状态值必须统一

后端、前端、数据库必须统一以下状态值：

```text
学期状态
排课方案状态
策略类型
规则类型
日志类型
未排原因编码
```

不允许同一个状态在不同地方写成不同值。

---

# 结语

V3 接口设计的核心是：

```text
所有核心数据都围绕学期查询
自动排课先生成方案
方案可以评分、对比、解释、应用和回滚
正式课表不能被自动排课直接覆盖
```

后续开发时，必须先完成学期与方案接口，再继续开发评分、对比、日志和统计分析接口。
