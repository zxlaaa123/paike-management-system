# 排课系统 V3 数据库设计

## 一、文档说明

本文档用于说明排课系统 V3 版本的数据库设计方案。

V3 版本的核心目标是引入：

1. 学期管理；
2. 当前学期切换；
3. 排课方案管理；
4. 多方案自动排课；
5. 规则权重配置；
6. 评分明细；
7. 方案对比；
8. 排课日志；
9. 未排任务原因分析；
10. 手动调整记录；
11. 统计分析支撑。

本文档重点说明 V3 需要新增哪些表、已有表需要增加哪些字段、表之间如何关联，以及开发时需要注意哪些数据库约束。

---

## 二、设计原则

### 2.1 不推翻 V1/V2 已有结构

V3 是在 V1/V2 基础上的增强版本，不应大规模重构已有数据库。

原则上采用：

```text
新增表为主
旧表少量加字段为辅
不删除原有核心字段
不随意修改原有字段含义
不直接覆盖正式课表数据
```

---

### 2.2 以学期作为数据边界

V3 引入 `semester_id` 作为核心数据边界。

以下数据必须绑定学期：

```text
教学任务
正式课表
排课方案
方案明细
评分明细
排课日志
手动调整记录
统计分析结果
```

这样可以避免不同学期的数据混在一起。

---

### 2.3 以排课方案作为 V3 核心对象

V2 的自动排课可能是“直接生成课表结果”。

V3 要调整为：

```text
自动排课先生成排课方案
用户查看方案
用户对比方案
用户应用某个方案
被应用的方案再写入正式课表
```

也就是说：

```text
schedule_plan 是 V3 的核心表
schedule_plan_item 是 V3 的核心明细表
schedule 是正式课表表
```

---

### 2.4 正式课表与方案课表分离

V3 不允许自动排课直接覆盖正式课表。

应该先写入：

```text
schedule_plan
schedule_plan_item
```

当用户点击“应用方案”后，再同步到正式课表表：

```text
schedule
```

这样可以支持：

1. 多方案生成；
2. 方案对比；
3. 草稿方案查看；
4. 历史方案回滚；
5. 正式课表保护。

---

### 2.5 数据库字段命名保持统一

建议字段命名统一使用下划线风格：

```text
semester_id
plan_id
teacher_id
class_id
course_id
classroom_id
time_slot_id
created_at
updated_at
```

如果项目现有字段已经使用驼峰或其他风格，以现有项目风格为准，但同一个项目内必须保持一致。

---

## 三、V3 推荐新增数据表总览

V3 推荐新增以下表：

```text
semester                    学期表
schedule_plan               排课方案表
schedule_plan_item          排课方案明细表
schedule_rule_weight        排课规则权重表
schedule_score_detail       排课评分明细表
schedule_generate_log       排课生成日志表
schedule_unassigned_task    未排任务原因表
schedule_adjust_log         手动调整日志表
schedule_compare_result     方案对比结果表
```

已有表建议增加字段：

```text
teaching_task 增加 semester_id
schedule 增加 semester_id
```

如果 V1/V2 中已经存在类似的学期字段、方案字段或日志字段，则不要重复建表，需要在开发前先检查现有数据库结构。

---

## 四、已有表改造设计

## 4.1 teaching_task 教学任务表改造

### 4.1.1 改造目的

教学任务必须归属于某一个学期。

自动排课时，系统只读取当前学期的教学任务，避免把不同学期的任务混在一起排。

---

### 4.1.2 新增字段

```sql
ALTER TABLE teaching_task
ADD COLUMN semester_id BIGINT NULL COMMENT '所属学期ID';
```

后续数据稳定后，可以将该字段改为非空：

```sql
ALTER TABLE teaching_task
MODIFY COLUMN semester_id BIGINT NOT NULL COMMENT '所属学期ID';
```

---

### 4.1.3 字段说明

| 字段名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| semester_id | BIGINT | 是 | 所属学期 ID |

---

### 4.1.4 关联关系

```text
teaching_task.semester_id -> semester.id
```

---

### 4.1.5 开发要求

1. 新增教学任务时，必须绑定当前学期；
2. 查询教学任务时，默认只查当前学期；
3. 自动排课时，只读取当前学期的教学任务；
4. 切换学期后，教学任务列表应随之变化；
5. 历史学期的教学任务不应参与当前学期排课。

---

## 4.2 schedule 正式课表表改造

### 4.2.1 改造目的

正式课表也必须归属于某个学期。

这样系统可以保存多个学期的历史课表。

---

### 4.2.2 新增字段

```sql
ALTER TABLE schedule
ADD COLUMN semester_id BIGINT NULL COMMENT '所属学期ID';
```

如果需要记录正式课表来自哪个方案，可以增加：

```sql
ALTER TABLE schedule
ADD COLUMN plan_id BIGINT NULL COMMENT '来源排课方案ID';
```

---

### 4.2.3 字段说明

| 字段名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| semester_id | BIGINT | 是 | 所属学期 ID |
| plan_id | BIGINT | 否 | 来源排课方案 ID |

---

### 4.2.4 关联关系

```text
schedule.semester_id -> semester.id
schedule.plan_id -> schedule_plan.id
```

---

### 4.2.5 开发要求

1. 正式课表必须绑定学期；
2. 查询课表时，默认查询当前学期；
3. 应用排课方案时，将方案明细写入正式课表；
4. 应用新方案前，需要明确处理旧正式课表；
5. 建议保留旧方案，不建议直接删除历史方案。

---

## 五、V3 新增表设计

# 5.1 semester 学期表

## 5.1.1 表作用

用于管理系统中的学年学期。

V3 中所有核心业务数据都需要围绕学期进行隔离。

---

## 5.1.2 建表 SQL

```sql
CREATE TABLE semester (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '学期ID',
    name VARCHAR(100) NOT NULL COMMENT '学期名称，例如：2025-2026学年第一学期',
    school_year VARCHAR(30) NOT NULL COMMENT '学年，例如：2025-2026',
    term VARCHAR(30) NOT NULL COMMENT '学期，例如：第一学期、第二学期',
    start_date DATE NULL COMMENT '学期开始日期',
    end_date DATE NULL COMMENT '学期结束日期',
    is_current TINYINT NOT NULL DEFAULT 0 COMMENT '是否当前学期：0否，1是',
    status VARCHAR(20) NOT NULL DEFAULT '未开始' COMMENT '状态：未开始、进行中、已结束',
    remark VARCHAR(255) NULL COMMENT '备注',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间'
) COMMENT='学期表';
```

---

## 5.1.3 字段说明

| 字段名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| id | BIGINT | 是 | 学期 ID |
| name | VARCHAR(100) | 是 | 学期名称 |
| school_year | VARCHAR(30) | 是 | 学年 |
| term | VARCHAR(30) | 是 | 学期 |
| start_date | DATE | 否 | 开始日期 |
| end_date | DATE | 否 | 结束日期 |
| is_current | TINYINT | 是 | 是否当前学期 |
| status | VARCHAR(20) | 是 | 学期状态 |
| remark | VARCHAR(255) | 否 | 备注 |
| created_at | DATETIME | 是 | 创建时间 |
| updated_at | DATETIME | 是 | 更新时间 |

---

## 5.1.4 状态说明

```text
未开始
进行中
已结束
```

---

## 5.1.5 约束建议

1. 同一时间只能有一个当前学期；
2. 学期名称不建议重复；
3. 删除学期前必须检查是否有关联数据；
4. 已被教学任务、课表、方案引用的学期不允许直接删除。

---

## 5.1.6 推荐索引

```sql
CREATE INDEX idx_semester_current ON semester(is_current);
CREATE INDEX idx_semester_school_year ON semester(school_year);
```

---

# 5.2 schedule_plan 排课方案表

## 5.2.1 表作用

用于保存一次自动排课生成的方案。

一个学期可以有多个排课方案。

例如：

```text
教师优先方案
班级均衡方案
教室利用率方案
综合最优方案
```

---

## 5.2.2 建表 SQL

```sql
CREATE TABLE schedule_plan (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '排课方案ID',
    semester_id BIGINT NOT NULL COMMENT '所属学期ID',
    name VARCHAR(100) NOT NULL COMMENT '方案名称',
    strategy_type VARCHAR(50) NOT NULL COMMENT '方案策略类型',
    status VARCHAR(20) NOT NULL DEFAULT '草稿' COMMENT '方案状态：草稿、已应用、已废弃',
    total_score DECIMAL(6,2) NULL COMMENT '方案总分',
    scheduled_count INT NOT NULL DEFAULT 0 COMMENT '已排任务数量',
    unscheduled_count INT NOT NULL DEFAULT 0 COMMENT '未排任务数量',
    conflict_count INT NOT NULL DEFAULT 0 COMMENT '冲突数量',
    description VARCHAR(500) NULL COMMENT '方案说明',
    generated_by VARCHAR(50) NULL COMMENT '生成方式或生成人',
    generated_at DATETIME NULL COMMENT '生成时间',
    applied_at DATETIME NULL COMMENT '应用时间',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间'
) COMMENT='排课方案表';
```

---

## 5.2.3 字段说明

| 字段名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| id | BIGINT | 是 | 方案 ID |
| semester_id | BIGINT | 是 | 所属学期 |
| name | VARCHAR(100) | 是 | 方案名称 |
| strategy_type | VARCHAR(50) | 是 | 方案策略类型 |
| status | VARCHAR(20) | 是 | 方案状态 |
| total_score | DECIMAL(6,2) | 否 | 方案总分 |
| scheduled_count | INT | 是 | 已排数量 |
| unscheduled_count | INT | 是 | 未排数量 |
| conflict_count | INT | 是 | 冲突数量 |
| description | VARCHAR(500) | 否 | 方案说明 |
| generated_by | VARCHAR(50) | 否 | 生成方式 |
| generated_at | DATETIME | 否 | 生成时间 |
| applied_at | DATETIME | 否 | 应用时间 |
| created_at | DATETIME | 是 | 创建时间 |
| updated_at | DATETIME | 是 | 更新时间 |

---

## 5.2.4 strategy_type 建议值

```text
TEACHER_PRIORITY        教师优先
CLASS_BALANCE           班级均衡
CLASSROOM_UTILIZATION   教室利用率优先
COMPREHENSIVE           综合最优
CUSTOM                  自定义权重
```

如果前端直接展示中文，也可以存中文，但后端枚举建议使用英文编码。

---

## 5.2.5 status 建议值

```text
草稿
已应用
已废弃
```

或使用英文枚举：

```text
DRAFT
APPLIED
ABANDONED
```

二者选择一种即可。建议后端用英文枚举，前端负责显示中文。

---

## 5.2.6 推荐索引

```sql
CREATE INDEX idx_plan_semester ON schedule_plan(semester_id);
CREATE INDEX idx_plan_status ON schedule_plan(status);
CREATE INDEX idx_plan_strategy ON schedule_plan(strategy_type);
```

---

# 5.3 schedule_plan_item 排课方案明细表

## 5.3.1 表作用

用于保存某个排课方案下的具体课程安排。

一条记录表示某个教学任务在某个时间、某个教室的安排结果。

---

## 5.3.2 建表 SQL

```sql
CREATE TABLE schedule_plan_item (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '方案明细ID',
    plan_id BIGINT NOT NULL COMMENT '排课方案ID',
    semester_id BIGINT NOT NULL COMMENT '所属学期ID',
    teaching_task_id BIGINT NOT NULL COMMENT '教学任务ID',
    teacher_id BIGINT NOT NULL COMMENT '教师ID',
    class_id BIGINT NOT NULL COMMENT '班级ID',
    course_id BIGINT NOT NULL COMMENT '课程ID',
    classroom_id BIGINT NOT NULL COMMENT '教室ID',
    weekday INT NOT NULL COMMENT '星期几：1-7',
    start_period INT NOT NULL COMMENT '开始节次',
    end_period INT NOT NULL COMMENT '结束节次',
    week_type VARCHAR(20) NOT NULL DEFAULT 'ALL' COMMENT '周次类型：ALL、ODD、EVEN',
    score DECIMAL(6,2) NULL COMMENT '该安排得分',
    conflict_flag TINYINT NOT NULL DEFAULT 0 COMMENT '是否存在冲突：0否，1是',
    conflict_reason VARCHAR(500) NULL COMMENT '冲突原因',
    source_type VARCHAR(20) NOT NULL DEFAULT 'AUTO' COMMENT '来源：AUTO自动、MANUAL手动',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间'
) COMMENT='排课方案明细表';
```

---

## 5.3.3 字段说明

| 字段名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| id | BIGINT | 是 | 明细 ID |
| plan_id | BIGINT | 是 | 所属方案 |
| semester_id | BIGINT | 是 | 所属学期 |
| teaching_task_id | BIGINT | 是 | 教学任务 |
| teacher_id | BIGINT | 是 | 教师 |
| class_id | BIGINT | 是 | 班级 |
| course_id | BIGINT | 是 | 课程 |
| classroom_id | BIGINT | 是 | 教室 |
| weekday | INT | 是 | 星期几 |
| start_period | INT | 是 | 开始节次 |
| end_period | INT | 是 | 结束节次 |
| week_type | VARCHAR(20) | 是 | 周次类型 |
| score | DECIMAL(6,2) | 否 | 单项安排得分 |
| conflict_flag | TINYINT | 是 | 是否冲突 |
| conflict_reason | VARCHAR(500) | 否 | 冲突原因 |
| source_type | VARCHAR(20) | 是 | 来源类型 |
| created_at | DATETIME | 是 | 创建时间 |
| updated_at | DATETIME | 是 | 更新时间 |

---

## 5.3.4 关联关系

```text
schedule_plan_item.plan_id -> schedule_plan.id
schedule_plan_item.semester_id -> semester.id
schedule_plan_item.teaching_task_id -> teaching_task.id
schedule_plan_item.teacher_id -> teacher.id
schedule_plan_item.class_id -> class.id
schedule_plan_item.course_id -> course.id
schedule_plan_item.classroom_id -> classroom.id
```

如果项目实际表名是 `clazz`、`school_class`、`room` 等，以实际表名为准。

---

## 5.3.5 推荐索引

```sql
CREATE INDEX idx_plan_item_plan ON schedule_plan_item(plan_id);
CREATE INDEX idx_plan_item_semester ON schedule_plan_item(semester_id);
CREATE INDEX idx_plan_item_teacher_time ON schedule_plan_item(teacher_id, weekday, start_period, end_period);
CREATE INDEX idx_plan_item_class_time ON schedule_plan_item(class_id, weekday, start_period, end_period);
CREATE INDEX idx_plan_item_room_time ON schedule_plan_item(classroom_id, weekday, start_period, end_period);
```

---

## 5.3.6 冲突检测建议

在同一个方案内，需要检测：

```text
同一教师同一时间不能重复
同一班级同一时间不能重复
同一教室同一时间不能重复
教师禁排时间不能排课
教室容量不能小于班级人数
教室类型必须满足课程要求
```

# 5.4 schedule_rule_weight 排课规则权重表

## 5.4.1 表作用

用于保存排课评分规则及其权重。

V3 中不同方案可以使用不同权重。

例如：

```text
教师优先方案：教师禁排权重更高
班级均衡方案：班级每天课程分布权重更高
教室利用率方案：教室使用率权重更高
综合最优方案：各项权重相对均衡
```

---

## 5.4.2 建表 SQL

```sql
CREATE TABLE schedule_rule_weight (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '规则权重ID',
    semester_id BIGINT NOT NULL COMMENT '所属学期ID',
    strategy_type VARCHAR(50) NOT NULL COMMENT '方案策略类型',
    rule_code VARCHAR(100) NOT NULL COMMENT '规则编码',
    rule_name VARCHAR(100) NOT NULL COMMENT '规则名称',
    rule_type VARCHAR(20) NOT NULL COMMENT '规则类型：HARD硬约束、SOFT软约束',
    weight DECIMAL(6,2) NOT NULL DEFAULT 1.00 COMMENT '规则权重',
    enabled TINYINT NOT NULL DEFAULT 1 COMMENT '是否启用：0否，1是',
    description VARCHAR(500) NULL COMMENT '规则说明',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间'
) COMMENT='排课规则权重表';
```

---

## 5.4.3 字段说明

| 字段名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| id | BIGINT | 是 | 规则权重 ID |
| semester_id | BIGINT | 是 | 所属学期 |
| strategy_type | VARCHAR(50) | 是 | 策略类型 |
| rule_code | VARCHAR(100) | 是 | 规则编码 |
| rule_name | VARCHAR(100) | 是 | 规则名称 |
| rule_type | VARCHAR(20) | 是 | 硬约束或软约束 |
| weight | DECIMAL(6,2) | 是 | 权重 |
| enabled | TINYINT | 是 | 是否启用 |
| description | VARCHAR(500) | 否 | 说明 |
| created_at | DATETIME | 是 | 创建时间 |
| updated_at | DATETIME | 是 | 更新时间 |

---

## 5.4.4 rule_type 建议值

```text
HARD    硬约束
SOFT    软约束
```

---

## 5.4.5 rule_code 建议值

### 硬约束

```text
TEACHER_TIME_CONFLICT          教师时间冲突
CLASS_TIME_CONFLICT            班级时间冲突
CLASSROOM_TIME_CONFLICT        教室时间冲突
TEACHER_UNAVAILABLE            教师禁排时间
CLASSROOM_CAPACITY             教室容量不足
CLASSROOM_TYPE_MISMATCH        教室类型不匹配
```

### 软约束

```text
TEACHER_DAILY_LOAD             教师每日课程负载
CLASS_DAILY_BALANCE            班级每日课程均衡
COURSE_DISTRIBUTION            课程分布均衡
CONTINUOUS_PERIOD_LIMIT        连续上课节次限制
MORNING_THEORY_PRIORITY        理论课优先上午
LAB_CLASSROOM_PRIORITY         实验课优先实验室
CLASSROOM_UTILIZATION          教室利用率
```

---

## 5.4.6 推荐索引

```sql
CREATE INDEX idx_rule_weight_semester ON schedule_rule_weight(semester_id);
CREATE INDEX idx_rule_weight_strategy ON schedule_rule_weight(strategy_type);
CREATE INDEX idx_rule_weight_rule_code ON schedule_rule_weight(rule_code);
```

# 5.5 schedule_score_detail 排课评分明细表

## 5.5.1 表作用

用于保存某个排课方案的评分明细。

V2 如果只有总分，V3 要拆成多项评分。

---

## 5.5.2 建表 SQL

```sql
CREATE TABLE schedule_score_detail (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '评分明细ID',
    plan_id BIGINT NOT NULL COMMENT '排课方案ID',
    semester_id BIGINT NOT NULL COMMENT '所属学期ID',
    rule_code VARCHAR(100) NOT NULL COMMENT '规则编码',
    rule_name VARCHAR(100) NOT NULL COMMENT '规则名称',
    score DECIMAL(6,2) NOT NULL DEFAULT 0 COMMENT '该项得分或扣分',
    max_score DECIMAL(6,2) NULL COMMENT '该项最高分',
    violation_count INT NOT NULL DEFAULT 0 COMMENT '违规次数',
    detail_message VARCHAR(1000) NULL COMMENT '评分说明',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间'
) COMMENT='排课评分明细表';
```

---

## 5.5.3 字段说明

| 字段名 | 类型 | 是否必填 | 说明 |
|---|---|---|---|
| id | BIGINT | 是 | 评分明细 ID |
| plan_id | BIGINT | 是 | 排课方案 |
| semester_id | BIGINT | 是 | 所属学期 |
| rule_code | VARCHAR(100) | 是 | 规则编码 |
| rule_name | VARCHAR(100) | 是 | 规则名称 |
| score | DECIMAL(6,2) | 是 | 得分或扣分 |

## 八、关键约束设计

## 8.1 当前学期唯一约束

业务上必须保证：

```text
同一时间只能有一个 is_current = 1 的学期
```

数据库层面可以通过代码控制，也可以使用唯一索引实现。

如果使用 MySQL，可以先通过业务代码控制，不强制建复杂唯一索引，降低开发难度。

---

## 8.2 同一方案内时间冲突约束

同一方案内不应出现：

```text
同一教师 + 同一星期 + 同一节次 重复
同一班级 + 同一星期 + 同一节次 重复
同一教室 + 同一星期 + 同一节次 重复
```

由于节次存在区间重叠问题，数据库唯一索引不太适合直接解决，建议在后端业务层检测。

---

## 8.3 删除约束

建议规则：

```text
已有关联教学任务的学期不能删除
已有关联课表的学期不能删除
已应用的排课方案不能随意删除
已应用方案只能废弃或保留历史
草稿方案可以删除
```

---

## 8.4 状态流转约束

### 排课方案状态流转

```text
草稿 -> 已应用
草稿 -> 已废弃
已应用 -> 已废弃
```

不建议：

```text
已废弃 -> 已应用
```

除非系统明确支持恢复废弃方案。

## 十三、开发注意事项

### 13.1 不要直接覆盖正式课表

自动排课结果必须先进入：

```text
schedule_plan
schedule_plan_item
```

用户应用方案后，才能写入：

```text
schedule
```

---

### 13.2 所有 V3 查询默认带 semester_id

涉及以下数据查询时，必须考虑当前学期：

```text
教学任务
课表
排课方案
评分明细
排课日志
未排任务
统计分析
```

---

### 13.3 不要重复建表

开发前必须检查 V1/V2 是否已经存在类似表。

如果已有：

```text
term
semester
schedule_version
schedule_log
score_detail
```

应优先复用或改造，不要重复创建功能相同的表。

---

### 13.4 枚举值保持统一

后端、前端、数据库必须统一状态值。

例如排课方案状态只能选一种风格：

```text
DRAFT / APPLIED / ABANDONED
```

或：

```text
草稿 / 已应用 / 已废弃
```

不允许混用。

---

### 13.5 历史数据不能丢

V3 升级时，不能导致 V1/V2 已有数据丢失。

所有迁移操作必须先备份数据库。

```text
04 接口设计必须与本数据库表结构对应
05 前端页面设计必须能展示本数据库支撑的数据
06 自动排课与评分规则设计必须使用本数据库中的规则、评分、日志和方案表
07 开发阶段任务必须按本数据库改造顺序推进
08 测试验收必须覆盖本数据库核心关系
09 AI 开发规则必须强调禁止破坏 V1/V2 数据
```

---

# 结语

V3 数据库设计的核心是：

```text
以学期为边界
以方案为核心
以评分和日志为解释能力
以方案应用和回滚保护正式课表
```

开发时一定要记住：

```text
自动排课不是直接生成正式课表
自动排课先生成方案
用户选择方案后再应用为正式课表
所有核心数据必须绑定学期
```
