# 排课系统 V3 AI 开发规则与提示词

## 一、文档说明

本文档用于指导 AI 编程助手开发排课系统 V3 版本。

V3 版本名称：

```text
智能排课优化与学期方案管理版
```

V3 开发目标：

```text
在 V1 基础管理和 V2 自动排课的基础上，引入学期管理、多方案排课、约束权重、评分明细、方案对比、版本回滚、排课日志、未排原因和统计分析，使系统从“能排课”升级为“能生成、评估、对比、解释和管理排课方案”。
```

本文档适合给以下 AI 工具阅读：

```text
Claude Code
Trae
CodeBuddy
Codex CLI
Cursor
其他 AI 编程助手
```

本文档重点不是业务介绍，而是约束 AI 的开发行为，防止 AI：

```text
随意重构项目
破坏 V1/V2 已有功能
跳过阶段乱开发
重复建表
覆盖正式课表
忽略学期隔离
接口和数据库不一致
前端页面和接口不一致
```

---

## 二、V3 开发总规则

## 2.1 不允许重写整个项目

V3 是增量升级，不是重写系统。

禁止：

```text
重新创建一个新项目
删除原有前端目录
删除原有后端目录
重写所有路由
重写所有数据库表
推翻 V1/V2 原有功能
把已有代码全部替换成新架构
```

允许：

```text
新增 V3 模块
新增 V3 数据表
新增 V3 接口
新增 V3 页面
在兼容旧功能的前提下改造旧模块
```

---

## 2.2 不允许破坏 V1/V2 已有功能

V1/V2 已有功能必须保留。

重点保护：

```text
教师管理
班级管理
课程管理
教室管理
教学任务管理
手动排课
课表查询
冲突检测
V2 自动排课
教师禁排时间
规则配置
Excel 导入导出
```

如果必须修改旧代码，必须遵守：

```text
先说明为什么要修改
尽量小范围修改
保留旧接口兼容性
修改后测试旧功能
```

---

## 2.3 每次只开发一个阶段

V3 必须分阶段开发。

禁止一次性完成全部 V3。

推荐阶段：

```text
阶段 0：V1/V2 代码体检与备份
阶段 1：学期管理基础能力
阶段 2：核心数据绑定学期
阶段 3：排课方案管理
阶段 4：评分明细与规则权重
阶段 5：多方案自动排课
阶段 6：方案详情、方案对比与应用回滚
阶段 7：排课日志、未排原因与手动调整
阶段 8：统计分析与首页增强
阶段 9：最终联调、演示数据与答辩包装
```

开发时必须：

```text
完成当前阶段
启动项目测试
确认无明显错误
再进入下一个阶段
```

---

## 2.4 自动排课不能直接覆盖正式课表

这是 V3 最重要的规则之一。

V3 自动排课正确流程：

```text
自动排课 -> 生成排课方案 -> 查看方案 -> 对比方案 -> 用户应用方案 -> 写入正式课表
```

禁止：

```text
自动排课接口直接清空 schedule 表
自动排课接口直接覆盖正式课表
生成草稿方案时影响正式课表
重新生成方案时删除正式课表
```

正确写入位置：

```text
自动排课结果先写入 schedule_plan
自动排课明细先写入 schedule_plan_item
应用方案时才写入 schedule
```

---

## 2.5 所有核心数据必须绑定学期

V3 中以下数据必须绑定 `semester_id`：

```text
教学任务
正式课表
排课方案
方案明细
规则权重
评分明细
排课日志
未排任务
手动调整记录
统计分析
```

查询这些数据时必须遵守：

```text
如果传 semesterId，则按传入学期查询
如果不传 semesterId，则默认使用当前学期
```

---

## 2.6 不允许重复建表

开发前必须检查当前数据库是否已有类似表。

如果已有：

```text
semester
term
schedule_plan
schedule_version
schedule_log
score_detail
rule_weight
```

则应优先复用或改造，不要重复创建功能相同的表。

---

## 2.7 状态值必须统一

以下状态值必须统一：

```text
学期状态
排课方案状态
策略类型
规则类型
日志类型
未排原因编码
```

建议使用英文枚举，前端显示中文。

例如：

```text
DRAFT      草稿
APPLIED    已应用
ABANDONED  已废弃
```

禁止同一个状态在不同地方混写：

```text
草稿 / draft / DRAFT / 待应用
```

---

## 2.8 接口返回格式保持统一

建议统一格式：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {}
}
```

分页格式：

```json
{
  "code": 200,
  "message": "查询成功",
  "data": {
    "records": [],
    "total": 0,
    "pageNum": 1,
    "pageSize": 10
  }
}
```

如果项目已有统一响应格式，以项目现有格式为准，不要另起一套。

---

## 2.9 前端页面不要过度设计

V3 前端重点是功能清晰，不是炫酷大屏。

优先保证：

```text
页面能打开
数据能显示
操作能完成
错误有提示
空状态清晰
loading 清晰
```

不强制引入复杂图表库。

---

## 2.10 不要引入过重依赖

V3 不建议随意引入：

```text
大型求解器
复杂低代码框架
重量级大屏框架
不必要的 UI 框架
新的数据库
新的后端框架
```

尤其不要在 V3 主线中强行引入 Timefold Solver。

V3 算法建议：

```text
贪心算法 + 候选评分 + 局部重试 + 评分明细 + 多方案对比
```

## 三、V3 核心业务规则

## 3.1 学期规则

```text
1. 同一时间只能有一个当前学期；
2. 当前学期用于默认查询教学任务、课表、方案和统计；
3. 已有关联数据的学期不能直接删除；
4. 切换当前学期后，前端必须刷新相关数据；
5. 没有当前学期时，V3 排课功能应提示用户先设置学期。
```

---

## 3.2 教学任务规则

```text
1. 新增教学任务默认绑定当前学期；
2. 查询教学任务默认按当前学期过滤；
3. 历史学期教学任务不参与当前学期自动排课；
4. 修改教学任务学期前，需要考虑是否已有排课结果；
5. 自动排课只读取目标学期的教学任务。
```

---

## 3.3 正式课表规则

```text
1. 正式课表必须绑定学期；
2. 正式课表可以记录来源方案 plan_id；
3. 自动排课不能直接写入正式课表；
4. 应用方案后才写入正式课表；
5. 回滚历史方案本质是重新应用历史方案。
```

---

## 3.4 排课方案规则

```text
1. 一个学期可以有多个排课方案；
2. 每个方案必须绑定 semester_id；
3. 每个方案有 strategy_type；
4. 每个方案有 status；
5. 每个方案有 total_score；
6. 每个方案有 scheduled_count、unscheduled_count、conflict_count；
7. 草稿方案可以删除；
8. 已应用方案不能直接删除；
9. 已废弃方案不能直接应用；
10. 应用方案前必须进行业务校验。
```

---

## 3.5 自动排课规则

```text
1. 自动排课只生成方案；
2. 自动排课必须进行教师冲突检测；
3. 自动排课必须进行班级冲突检测；
4. 自动排课必须进行教室冲突检测；
5. 自动排课必须考虑教师禁排时间；
6. 自动排课必须考虑教室容量；
7. 自动排课必须考虑教室类型；
8. 自动排课应生成评分明细；
9. 自动排课应生成排课日志；
10. 自动排课失败的任务应记录未排原因。
```

---

## 3.6 评分规则

```text
1. 评分不能只有总分；
2. 必须有评分明细；
3. 评分明细必须绑定 plan_id；
4. 评分明细必须绑定 semester_id；
5. 硬约束违规应严重扣分；
6. 软约束用于优化方案质量；
7. 手动调整后必须重新评分；
8. 重新评分后要更新方案总分。
```

---

## 3.7 日志规则

```text
1. 自动排课必须记录关键日志；
2. 日志不能只写“成功”或“失败”；
3. 日志应包含排课过程；
4. 未排任务应说明失败原因；
5. 手动调整应记录调整前后信息。
```

## 五、V3 数据库开发规则

## 5.1 新增表

V3 推荐新增：

```text
semester
schedule_plan
schedule_plan_item
schedule_rule_weight
schedule_score_detail
schedule_generate_log
schedule_unassigned_task
schedule_adjust_log
schedule_compare_result
```

如果项目已有类似表，不要重复建表。

---

## 5.2 旧表改造

推荐给旧表增加：

```text
teaching_task.semester_id
schedule.semester_id
schedule.plan_id
```

其中 `schedule.plan_id` 可选，但建议保留，用于记录正式课表来源方案。

---

## 5.3 数据迁移规则

旧数据迁移必须安全。

建议流程：

```text
1. 备份数据库；
2. 创建默认当前学期；
3. 为 teaching_task 增加 semester_id；
4. 为 schedule 增加 semester_id；
5. 将旧教学任务绑定默认学期；
6. 将旧课表绑定默认学期；
7. 确认无误后再进行非空约束处理。
```

---

## 5.4 删除规则

```text
1. 已有关联数据的学期不能删除；
2. 已应用方案不能直接删除；
3. 删除草稿方案时，应同步删除方案明细、评分明细、日志和未排任务；
4. 不允许误删正式课表；
5. 不允许误删历史方案。
```

## 七、V3 前端开发规则

前端应在顶部或明显位置显示：

```text
当前学期：2025-2026学年第二学期
```

并支持切换当前学期。

切换当前学期后，应刷新：

```text

统计分析

```

不能继续显示旧学期数据。

以下页面必须有空状态提示：

```text
暂无学期
暂无教学任务
暂无排课方案
暂无评分明细
暂无排课日志
暂无未排任务
暂无统计数据
```

以下操作必须弹窗确认：

```text
删除学期
切换当前学期
删除方案
废弃方案
应用方案
回滚方案
生成演示数据
清理演示数据
```

如果方案存在未排任务，应提示：

## 八、V3 自动排课开发规则

## 8.1 算法选择

V3 主线推荐：

```text
贪心算法 + 候选位置评分 + 硬约束过滤 + 软约束扣分 + 多方案权重差异
```

暂不建议：

```text
直接引入复杂优化求解器
直接调用大模型决定课表
写过于复杂的全局最优算法
```

---

## 8.2 教学任务排序

优先安排更难排的任务：

```text
特殊教室课程优先
周课时多的课程优先
教师禁排时间多的任务优先
可用教室少的任务优先
普通理论课后排
```

---

## 8.3 硬约束

必须检测：

```text
教师时间冲突
班级时间冲突
教室时间冲突
教师禁排时间
教室容量不足
教室类型不匹配
```

硬约束不满足时，候选位置应直接排除。

---

## 8.4 软约束

建议考虑：

```text
班级每日课程均衡
教师每日负载均衡
连续上课限制
课程分布均衡
理论课优先上午
实验课优先实验室
教室利用率
```

软约束用于计算候选得分和方案总分。

---

## 8.5 多方案策略

V3 至少支持：

```text
教师优先方案
班级均衡方案
教室利用率方案
综合最优方案
```

不同策略的差异来自规则权重不同。

---

## 8.6 未排任务必须有原因

如果任务无法安排，不能只写：

```text
排课失败
```

必须写：

```text
reason_code
reason_message
suggestion
```

示例：

```text
reason_code: CLASSROOM_TYPE_MISMATCH
reason_message: 当前学期没有可用实验室满足该课程要求
suggestion: 请新增实验室，或调整课程教室类型要求
```

---


```text

```

# 十六、答辩表述参考

如果需要向老师解释 V3，可以这样说：

```text
本系统 V1 主要实现基础排课数据管理和手动排课功能。
V2 在 V1 基础上增加了规则驱动的自动排课、冲突检测和基础评分能力。
V3 进一步引入了学期管理和排课方案机制。

在 V3 中，自动排课不会直接覆盖正式课表，而是先生成多个排课方案。
每个方案都有独立的课表明细、评分明细、生成日志和未排任务原因。
用户可以对多个方案进行对比，选择最合适的方案应用为正式课表。
系统还支持方案回滚、手动调整后重新评分，以及教师工作量、教室利用率和班级课表均衡度统计。

因此，V3 不只是能自动排课，而是能对排课方案进行生成、评估、对比、解释和管理。
```
