# 排课系统 V3 自动排课与评分规则设计

## 一、文档说明

本文档用于说明排课系统 V3 版本的自动排课逻辑、约束规则、评分规则、多方案生成策略、未排任务原因分析和手动调整后重新评分机制。

V3 自动排课不是单纯“把课程塞进课表”，而是要实现：

```text
能生成多个方案
能说明为什么这样排
能判断方案好坏
能展示评分明细
能分析未排原因
能支持手动调整后重新评分
```

本文档需要与以下文档保持一致：

```text
01_V3版本需求说明.md
02_V3功能模块设计.md
03_V3数据库设计.md
04_V3接口设计.md
05_V3前端页面设计.md
```

---

## 二、V3 自动排课总体目标

V3 自动排课的总体目标是：

> 在当前学期范围内，根据教学任务、教师、班级、课程、教室、时间段、教师禁排时间和规则权重，自动生成一个或多个排课方案，并对每个方案进行评分、记录日志、分析未排任务原因，最终供用户对比和选择。

---

## 三、V3 自动排课与 V2 的区别

## 3.1 V2 自动排课特点

V2 主要解决：

```text
系统能不能根据规则自动生成课表
系统能不能检测基本冲突
系统能不能给出简单评分
系统能不能查看未排任务
```

V2 的重点是“能自动排”。

---

## 3.2 V3 自动排课特点

V3 要升级为：

```text
按学期排课
先生成方案，不直接覆盖正式课表
一次可以生成多个方案
不同方案使用不同策略和权重
每个方案有评分明细
每个方案有生成日志
每个未排任务有具体原因
方案可以对比
方案可以手动调整并重新评分
方案可以应用和回滚
```

V3 的重点是“能优化、能对比、能解释”。

---

## 四、核心概念说明

## 4.1 学期

V3 所有自动排课都必须基于某一个学期。

自动排课时只读取当前学期或指定学期的数据：

```text
当前学期教学任务
当前学期排课规则权重
当前学期已有方案
当前学期教师禁排时间
当前学期正式课表
```

---

## 4.2 教学任务

教学任务是自动排课的输入数据。

一条教学任务通常包括：

```text
课程
教师
班级
周课时
课程类型
所需教室类型
所属学期
```

例如：

```text
高等数学 / 张老师 / 软件工程1班 / 每周4课时 / 理论课 / 普通教室 / 2025-2026第二学期
```

---

## 4.3 时间段

自动排课需要把教学任务安排到具体时间段。

时间段可以由以下字段组成：

```text
weekday       星期几
startPeriod   开始节次
endPeriod     结束节次
weekType      周次类型
```

V3 初期建议先使用简单模式：

```text
周一到周五
每天 1-8 节或 1-10 节
默认全周
暂不做复杂单双周
```

如果 V2 已经支持单双周，可以保留，但 V3 不强制扩展。

---

## 4.4 教室

教室是自动排课的资源。

教室需要考虑：

```text
教室容量
教室类型
是否可用
同一时间是否被占用
```

---

## 4.5 排课方案

V3 自动排课的输出不是正式课表，而是排课方案。

自动排课结果先写入：

```text
schedule_plan
schedule_plan_item
```

用户应用方案后，才写入正式课表：

```text
schedule
```

---

## 4.6 评分

评分用于衡量方案质量。

V3 不只保存总分，还要保存评分明细：

```text
总分
硬约束违规情况
软约束扣分情况
每个规则的扣分原因
每个规则的违规次数
```

---

## 五、自动排课总体流程

V3 自动排课建议采用以下流程：

```text
1. 获取目标学期
2. 读取当前学期教学任务
3. 读取教师、班级、课程、教室基础数据
4. 读取教师禁排时间
5. 读取规则权重
6. 初始化排课方案
7. 对教学任务进行排序
8. 为每个教学任务寻找候选时间和教室
9. 检查硬约束
10. 计算软约束评分
11. 选择得分最高的候选位置
12. 写入方案明细
13. 处理未排任务
14. 计算方案总分
15. 写入评分明细
16. 写入排课生成日志
17. 返回方案结果
```

---

## 六、教学任务排序规则

自动排课时，教学任务的处理顺序会影响排课结果。

建议优先安排“更难排”的任务。

## 6.1 推荐排序优先级

排序优先级建议如下：

```text
1. 需要特殊教室的课程优先
2. 周课时多的课程优先
3. 教师禁排时间多的任务优先
4. 可用教室少的课程优先
5. 班级任务较多的班级优先
6. 普通理论课后排
```

---

## 6.2 示例

优先排：

```text
大学物理实验 / 需要实验室 / 周课时4
计算机网络实验 / 需要机房 / 周课时4
```

后排：

```text
大学英语 / 普通教室 / 周课时2
形势与政策 / 普通教室 / 周课时2
```

---

## 6.3 排序评分公式建议

可以为每个教学任务计算一个难度分：

```text
任务难度分 = 特殊教室权重 + 周课时权重 + 教师禁排权重 + 可用教室稀缺权重
```

示例：

```text
特殊教室课程 +30
周课时 >= 4 +20
教师禁排时间较多 +20
可用教室数量 <= 2 +30
```

任务难度分越高，越优先安排。

---

## 七、候选位置生成规则

对每个教学任务，需要生成多个候选排课位置。

一个候选位置包括：

```text
星期几
开始节次
结束节次
教室
```

例如：

```text
周一 第1-2节 A101
周二 第3-4节 A102
周三 第5-6节 实验室B201
```

---

## 7.1 候选时间范围

初期建议使用：

```text
周一到周五
第1节到第8节或第10节
默认每次安排连续2节
```

如果某课程周课时为 4，可以拆成两次：

```text
一次第1-2节
一次第3-4节
```

---

## 7.2 候选教室范围

候选教室需要满足：

```text
教室可用
教室容量满足班级人数
教室类型满足课程要求
同一时间没有被占用
```

---

## 7.3 候选位置过滤

候选位置生成后，先过滤硬约束不满足的位置。

如果硬约束不满足，不进入评分阶段。

---

## 八、硬约束设计

硬约束是必须满足的规则。

如果违反硬约束，该候选位置应直接被排除，或者给予极高扣分并标记严重违规。

V3 初期建议硬约束直接排除。

---

## 8.1 教师时间冲突

规则编码：

```text
TEACHER_TIME_CONFLICT
```

规则说明：

```text
同一教师在同一时间段不能同时教授两门课程。
```

检测条件：

```text
同一 plan_id
同一 teacher_id
weekday 相同
节次区间存在重叠
```

示例违规：

```text
张老师 周一第1-2节 已安排高等数学
又尝试安排 张老师 周一第1-2节 数据结构
```

处理方式：

```text
候选位置排除
记录日志
```

---

## 8.2 班级时间冲突

规则编码：

```text
CLASS_TIME_CONFLICT
```

规则说明：

```text
同一班级在同一时间段不能同时上两门课程。
```

检测条件：

```text
同一 plan_id
同一 class_id
weekday 相同
节次区间存在重叠
```

处理方式：

```text
候选位置排除
记录日志
```

---

## 8.3 教室时间冲突

规则编码：

```text
CLASSROOM_TIME_CONFLICT
```

规则说明：

```text
同一教室在同一时间段不能安排多门课程。
```

检测条件：

```text
同一 plan_id
同一 classroom_id
weekday 相同
节次区间存在重叠
```

处理方式：

```text
候选位置排除
记录日志
```

---

## 8.4 教师禁排时间

规则编码：

```text
TEACHER_UNAVAILABLE
```

规则说明：

```text
教师设置为不可上课的时间段，不应安排课程。
```

检测条件：

```text
teacher_id 匹配
weekday 匹配
节次区间存在重叠
```

处理方式：

```text
候选位置排除
记录日志
```

---

## 8.5 教室容量不足

规则编码：

```text
CLASSROOM_CAPACITY
```

规则说明：

```text
教室容量必须大于或等于班级人数。
```

检测条件：

```text
classroom.capacity < class.student_count
```

处理方式：

```text
候选教室排除
记录日志
```

---

## 8.6 教室类型不匹配

规则编码：

```text
CLASSROOM_TYPE_MISMATCH
```

规则说明：

```text
课程要求的教室类型必须与实际教室类型匹配。
```

示例：

```text
实验课需要实验室
机房课需要机房
普通理论课可以使用普通教室
```

处理方式：

```text
候选教室排除
记录日志
```

---

## 8.7 同一课程过度拆分限制

规则编码：

```text
COURSE_SPLIT_LIMIT
```

规则说明：

```text
同一教学任务的周课时拆分次数不应过多。
```

V3 初期建议：

```text
每次安排 2 节
周课时 2 -> 安排 1 次
周课时 4 -> 安排 2 次
周课时 6 -> 安排 3 次
```

不建议将 4 课时拆成 4 个单节，避免课表太碎。

---

## 九、软约束设计

软约束不是绝对禁止，而是用于优化课表质量。

软约束通过扣分或加分影响候选位置选择。

---

## 9.1 班级每日课程均衡

规则编码：

```text
CLASS_DAILY_BALANCE
```

规则说明：

```text
同一班级每天课程数量尽量均衡，不要某一天过满、某一天过空。
```

建议规则：

```text
班级某天课程超过 6 节，扣分
班级某天课程为 0，轻微扣分
班级一周课程分布越均匀，得分越高
```

扣分示例：

```text
某班周三已有 6 节课，再安排新课，扣 5 分
某班周一到周五分布为 8、2、2、2、2，整体均衡度扣分
```

---

## 9.2 教师每日负载均衡

规则编码：

```text
TEACHER_DAILY_LOAD
```

规则说明：

```text
教师每天上课数量尽量合理，不要集中在某一天。
```

建议规则：

```text
教师某天超过 6 节课，扣分
教师连续上课节次过长，扣分
教师课程过度集中在一天，扣分
```

---

## 9.3 连续上课限制

规则编码：

```text
CONTINUOUS_PERIOD_LIMIT
```

规则说明：

```text
教师或班级连续上课时间不宜过长。
```

建议规则：

```text
连续 4 节以内正常
连续 6 节轻微扣分
连续 8 节严重扣分
```

---

## 9.4 课程分布均衡

规则编码：

```text
COURSE_DISTRIBUTION
```

规则说明：

```text
同一课程不要集中在连续几天或同一天。
```

示例：

```text
高等数学每周 4 节，建议分布在两天
不建议周一第1-4节全部排完
```

---

## 9.5 理论课优先上午

规则编码：

```text
MORNING_THEORY_PRIORITY
```

规则说明：

```text
理论课尽量安排在上午，便于学习效果展示。
```

建议：

```text
理论课排上午加分
理论课排晚上扣分
```

如果系统没有晚上节次，可以只作为轻量加分项。

---

## 9.6 实验课优先实验室

规则编码：

```text
LAB_CLASSROOM_PRIORITY
```

规则说明：

```text
实验课应优先安排实验室。
```

如果硬约束已经要求实验课必须使用实验室，该规则可以不用重复扣分。

如果允许实验课临时使用普通教室，则可作为软约束扣分。

---

## 9.7 教室利用率优化

规则编码：

```text
CLASSROOM_UTILIZATION
```

规则说明：

```text
尽量提高教室利用率，避免大教室长期空闲或小班占用大教室。
```

建议规则：

```text
班级人数与教室容量匹配度越高，得分越高
小班占用超大教室，扣分
热门教室过度集中使用，轻微扣分
```

示例：

```text
30 人班级使用 40 人教室，得分较高
30 人班级使用 200 人报告厅，扣分
```

---

## 9.8 教师偏好时间

规则编码：

```text
TEACHER_PREFERENCE
```

规则说明：

```text
如果系统支持教师偏好时间，则优先满足教师偏好。
```

V3 初期如果没有教师偏好功能，可以暂不实现。

## 十一、候选位置评分规则

每一个候选位置都可以计算一个候选得分。

推荐初始分：

```text
candidateScore = 100
```

然后根据软约束扣分或加分。

示例：

```text
candidateScore = 100
- 班级当天课程过多扣分
- 教师当天课程过多扣分
- 连续上课过多扣分
- 小班占用大教室扣分
+ 理论课排上午加分
+ 教室容量匹配度高加分
```

---

## 11.1 候选得分示例

```text
课程：高等数学
教师：张老师
班级：软件工程1班
候选位置：周二第3-4节，A101

初始分：100
教师当天已有 2 节课：不扣分
班级当天已有 4 节课：扣 5 分
教室容量匹配较好：加 3 分
理论课安排在上午：加 2 分

最终候选得分：100 - 5 + 3 + 2 = 100
```

如果得分超过 100，可以限制为 100。

---

## 11.2 候选位置选择

对同一个教学任务，生成多个候选位置后：

```text
选择得分最高的候选位置
如果得分相同，选择节次更靠前的位置
如果仍相同，选择教室容量更匹配的位置
```

---

## 十二、方案总分计算规则

方案总分用于整体评价一个排课方案。

建议初始总分：

```text
totalScore = 100
```

然后根据硬约束和软约束进行扣分。

---

## 12.1 硬约束扣分

正常情况下，硬约束不应该违反。

如果系统允许生成带冲突方案，则硬约束违规应严重扣分。

建议：

| 违规项 | 单次扣分 |
|---|---:|
| 教师时间冲突 | -30 |

## 十五、未排任务原因分析

## 15.1 常见未排原因

| 原因编码 | 原因说明 |
|---|---|
| NO_AVAILABLE_CLASSROOM | 无可用教室 |
| TEACHER_TIME_CONFLICT | 教师时间全部冲突 |
| CLASS_TIME_CONFLICT | 班级时间全部冲突 |

| PERIOD_NOT_ENOUGH | 可用节次不足 |
| UNKNOWN_REASON | 未知原因 |

## 15.2 未排原因判断顺序

建议按以下顺序判断：

```text

4. 班级是否存在可用时间
5. 教室是否存在可用时间
6. 是否存在连续节次满足周课时
7. 是否因为多个约束组合导致失败
```

## 15.3 未排任务建议生成

示例：

| 原因 | 建议 |
|---|---|
| 无可用教室 | 新增教室或调整课程教室类型要求 |
| 教室容量不足 | 更换更大容量教室或拆分班级 |
| 教师时间冲突 | 调整教师禁排时间或更换教师 |
| 班级时间冲突 | 调整同班级其他课程时间 |
| 可用节次不足 | 增加可排节次或减少周课时 |

## 二十、基础算法建议

V3 不建议一开始引入复杂求解器。

推荐采用：

```text
贪心算法 + 候选评分 + 局部重试 + 评分对比
```

这套算法更适合毕业设计：

```text
好实现
好调试
好解释
不容易失控
答辩时讲得清楚
```

---

## 20.1 贪心排课算法说明

基本思想：

```text
先排更难排的任务
每个任务选择当前最优的位置
排完后统计整体结果
```

优点：

```text
实现简单
运行速度快
容易输出日志
容易说明原因
```

缺点：

```text
不一定全局最优
前面的选择可能影响后面的任务
```

V3 可以通过多策略和重试来弥补。

---

## 20.2 局部重试机制

当某个任务排不进去时，可以尝试：

```text
换一个候选位置
换一个教室
调整同班级低优先级课程
调整同教师低优先级课程
重新排序后再排一次
```

V3 初期可以只做简单重试：

```text
最多重试 3 次
重试失败则记录未排原因
```

---

## 20.3 多方案生成机制

多方案本质上是：

```text
同一批教学任务
不同策略权重
生成不同候选评分结果
得到不同排课方案
```

示例：

```text
教师优先策略更倾向选择教师负载低的位置
班级均衡策略更倾向选择班级课程较少的日期
教室利用率策略更倾向选择容量匹配度高的教室
综合最优策略综合计算
```

## 二十一、伪代码示例

## 21.1 单方案生成伪代码

```text
function generateSchedulePlan(semesterId, strategyType):

    semester = getSemester(semesterId)
    tasks = getTeachingTasks(semesterId)
    teachers = getTeachers()
    classes = getClasses()
    classrooms = getClassrooms()
    rules = getRuleWeights(semesterId, strategyType)

    plan = createSchedulePlan(semesterId, strategyType)

    sortedTasks = sortTasksByDifficulty(tasks)

    for task in sortedTasks:
        writeLog(plan, task, "开始为教学任务生成候选位置")

        candidates = generateCandidates(task, classrooms)

        validCandidates = []

        for candidate in candidates:
            hardCheckResult = checkHardConstraints(task, candidate, plan)

            if hardCheckResult.passed:
                score = calculateCandidateScore(task, candidate, plan, rules)
                validCandidates.add(candidate, score)
            else:
                writeLog(plan, task, hardCheckResult.reason)

        if validCandidates is not empty:
            bestCandidate = selectBestCandidate(validCandidates)
            savePlanItem(plan, task, bestCandidate)
            writeLog(plan, task, "排课成功")
        else:
            reason = analyzeUnassignedReason(task)
            saveUnassignedTask(plan, task, reason)
            writeLog(plan, task, "排课失败：" + reason)

    scoreDetails = calculatePlanScore(plan)
    saveScoreDetails(plan, scoreDetails)
    updatePlanSummary(plan)

    return plan
```

## 21.2 候选评分伪代码

```text
function calculateCandidateScore(task, candidate, plan, rules):

    score = 100

    if classDailyHoursTooMuch(task.class, candidate.weekday):
        score -= getWeight(rules, "CLASS_DAILY_BALANCE")

    if teacherDailyHoursTooMuch(task.teacher, candidate.weekday):
        score -= getWeight(rules, "TEACHER_DAILY_LOAD")

    if continuousPeriodsTooLong(task, candidate):
        score -= getWeight(rules, "CONTINUOUS_PERIOD_LIMIT")

    if classroomCapacityTooLarge(task.class, candidate.classroom):
        score -= getWeight(rules, "CLASSROOM_UTILIZATION") * 0.3

    if theoryCourseInMorning(task, candidate):
        score += 2

    return limit(score, 0, 100)
```

# 结语

V3 自动排课与评分规则的核心是：

```text
以学期为范围
以排课方案为输出
以硬约束保证基本正确
以软约束优化课表质量
以评分明细解释方案优劣
以生成日志解释排课过程
以未排原因说明失败原因
以多方案对比辅助最终决策
```

开发时必须牢记：

```text
自动排课先生成方案
方案评分要有明细
排课失败要有原因
手动调整要重新评分
应用方案后才写入正式课表
```
