# 排课系统 V3 版本需求说明

## 一、文档说明

本文档用于说明排课系统 V3 版本的建设目标、功能范围、版本边界、核心模块和验收标准。

V3 版本是在 V1、V2 已完成的基础上继续升级，不推翻已有系统，不重写项目，不改变原有技术路线，而是在现有排课系统基础上增加“学期管理、排课方案、多方案自动排课、评分明细、方案对比、版本回滚、排课日志和统计分析”等能力。

本文档主要用于：

1. 明确 V3 版本做什么；
2. 明确 V3 版本不做什么；
3. 防止开发过程中功能发散；
4. 作为后续数据库设计、接口设计、前端页面设计、算法规则设计的总纲；
5. 作为 AI 辅助开发时的需求依据。

---

## 二、项目版本背景

本项目是一个本地运行的排课系统仿真项目，主要用于毕业设计、课程设计或教学管理系统模拟场景。

系统以学校排课业务为背景，围绕教师、班级、课程、教室、教学任务和课表结果进行管理，实现基础排课、冲突检测、自动排课和排课方案优化等功能。

本项目的整体发展路线如下：

```text
V1：基础排课系统
V2：规则自动排课系统
V3：智能排课优化与学期方案管理系统
```

V3 的目标不是做成真实高校教务系统，也不是追求复杂企业级平台，而是在毕业设计范围内，让系统具备更完整、更清晰、更容易答辩展示的排课优化能力。

## 三、已有版本概述

### 3.1 V1 版本定位

V1 版本定位为：

> 基础排课系统。

V1 主要解决“系统能不能管理基础数据、能不能手动排课、能不能查看课表”的问题。

V1 主要能力包括：

1. 教师管理；
2. 班级管理；
3. 课程管理；
4. 教室管理；
5. 教学任务管理；
6. 手动排课；
7. 基础课表查询；
8. 基础冲突检测；
9. 基础数据增删改查。

V1 的核心目标是让系统具备最基本的排课业务闭环。

---

### 3.2 V2 版本定位

V2 版本定位为：

> 规则自动排课系统。

V2 主要解决“系统能不能根据一定规则自动生成课表”的问题。

V2 主要能力包括：

1. 自动排课；
2. 教师禁排时间；
3. 排课规则配置；
4. 课表评分；
5. 冲突报告；
6. 未排任务查看；
7. Excel 导入导出；
8. 课表查询增强；
9. 自动排课结果调整。

V2 的核心目标是让系统从“手动排课”升级为“规则驱动的自动排课”。

---

## 四、V3 版本定位

V3 版本正式定位为：

> 智能排课优化与学期方案管理版。

V3 版本不是简单增加几个页面，也不是继续堆普通增删改查，而是围绕“学期、方案、评分、对比、日志、回滚、统计”进行系统升级。

V3 的核心目标是：

> 在 V1 基础管理和 V2 自动排课的基础上，引入学期管理、多方案排课、约束权重、评分明细、方案对比、版本回滚和排课过程解释，让系统从“能排课”升级为“能生成、评估、对比、解释和管理排课方案”。

V3 重点体现以下能力：

1. 按学期管理教学任务与课表；
2. 自动生成多个排课方案；
3. 对每个方案进行多维评分；
4. 支持不同方案之间对比；
5. 支持将某个方案应用为正式课表；
6. 支持历史方案查看与回滚；
7. 支持查看排课过程日志；
8. 支持分析未排任务原因；
9. 支持手动微调后重新评分；
10. 支持教师、班级、教室维度的统计分析。

---

## 五、V3 版本核心思想

V3 版本的设计重点有三个。

### 5.1 以学期为数据边界

V3 引入“学期”概念。

系统中的教学任务、排课方案、正式课表、评分结果、排课日志和统计分析，都应当归属于某一个具体学期。

例如：

```text
2025-2026学年第一学期
2025-2026学年第二学期
2026-2027学年第一学期
```

引入学期后，可以避免不同学期的数据混在一起，也方便后续查看历史课表、历史方案和历史统计结果。

V3 中的学期不需要做得过于复杂，主要承担以下作用：

1. 区分不同学期的教学任务；
2. 区分不同学期的排课方案；
3. 区分不同学期的正式课表；
4. 支持当前学期切换；
5. 支持历史学期查询。

---

### 5.2 以排课方案为核心对象

V1 和 V2 更关注“课表结果”，V3 要引入“排课方案”的概念。

自动排课时，系统不应直接覆盖正式课表，而是先生成一个或多个排课方案。

排课方案可以有不同状态：

```text
草稿
已应用
已废弃
```

用户可以查看方案、比较方案、应用方案，也可以回滚到历史方案。

这样可以避免自动排课结果直接覆盖正式数据，提高系统安全性和可操作性。

---

### 5.3 以评分和日志解释排课质量

V3 不仅要生成课表，还要告诉用户：

1. 为什么这样排；
2. 这个方案好不好；
3. 哪些地方扣分；
4. 哪些规则没有满足；
5. 哪些教学任务没有排进去；
6. 未排任务的具体原因是什么；
7. 手动调整后方案质量是否变化。

因此，V3 要加入评分明细、排课日志和未排原因分析，让系统具备一定的“可解释性”。

---

## 六、V3 必做功能范围

### 6.1 学期管理

V3 必须新增学期管理能力。

学期管理用于维护系统中的学年学期信息。

功能包括：

1. 新增学期；
2. 编辑学期；
3. 删除未使用学期；
4. 设置当前学期；
5. 查看学期列表；
6. 查看学期状态；
7. 按当前学期筛选相关业务数据。

建议学期字段包括：

```text
id                  学期ID
name                学期名称
school_year         学年，例如 2025-2026
term                学期，例如 第一学期 / 第二学期
start_date          开始日期
end_date            结束日期
is_current          是否当前学期
status              状态：未开始 / 进行中 / 已结束
created_at          创建时间
updated_at          更新时间
```

学期管理只做基础版本，不做复杂校历、不做节假日调休、不做单双周高级规则。

---

### 6.2 当前学期切换

系统应支持当前学期切换。

系统顶部或首页应显示当前学期，例如：

```text
当前学期：2025-2026学年第二学期
```

切换当前学期后，以下数据应跟随变化：

1. 教学任务；
2. 课表结果；
3. 排课方案；
4. 评分记录；
5. 排课日志；
6. 冲突报告；
7. 统计分析结果。

当前学期是 V3 的重要数据过滤条件，不能只做成页面展示。

---

### 6.3 教学任务绑定学期

V3 中，教学任务必须绑定学期。

每个教学任务都应明确属于哪个学期。

例如：

```text
高等数学 - 软件工程1班 - 张老师 - 2025-2026学年第二学期
```

自动排课时，只读取当前学期的教学任务，不应读取其他学期的数据。

如果已有 teaching_task 表，需要增加：

```text
semester_id
```

---

### 6.4 课表结果绑定学期

正式课表结果也必须绑定学期。

如果已有 schedule 表，需要增加：

```text
semester_id
```

这样可以实现：

1. 查看当前学期课表；
2. 查看历史学期课表；
3. 防止不同学期课表混在一起；
4. 为方案应用和历史回滚提供数据基础。

---

### 6.5 排课方案管理

V3 需要新增排课方案管理。

自动排课生成的结果应先进入排课方案，而不是直接覆盖正式课表。

排课方案功能包括：

1. 创建排课方案；
2. 查看方案列表；
3. 查看方案详情；
4. 查看方案状态；
5. 应用方案为正式课表；
6. 废弃方案；
7. 删除未使用草稿方案；
8. 回滚到历史方案。

排课方案建议包含以下基础信息：

```text
方案名称
所属学期
方案类型
方案状态
生成时间
总分
已排任务数
未排任务数
创建人或创建方式
备注说明
```

---

### 6.6 多方案自动排课

V3 自动排课不应只生成一个结果，而应支持生成多个方案。

建议至少支持以下方案类型：

```text
教师优先方案
班级均衡方案
教室利用率方案
综合最优方案
```

不同方案使用不同的规则权重或排课策略。

例如：

1. 教师优先方案：优先满足教师禁排时间和教师上课习惯；
2. 班级均衡方案：优先让班级每天课程分布更均匀；
3. 教室利用率方案：优先提高教室使用效率；
4. 综合最优方案：综合考虑教师、班级、教室和课程分布等因素。

多方案排课是 V3 的核心亮点之一。

---

### 6.7 约束权重配置

V3 要对排课规则进行更清晰的分类和权重配置。

规则分为两类：

#### 6.7.1 硬约束

硬约束是必须满足的规则。

例如：

```text
同一教师同一时间不能上两门课
同一班级同一时间不能上两门课
同一教室同一时间不能安排两门课
教师禁排时间不能安排课程
教室容量必须满足班级人数
课程类型应匹配教室类型
```

硬约束一般不允许违反。

#### 6.7.2 软约束

软约束是尽量满足的规则。

例如：

```text
教师一天课程不要过多
班级一天课程不要过满
课程分布尽量均匀
同一课程不要过度集中
理论课尽量安排在上午
实验课优先安排实验室
体育课尽量避免晚上
```

软约束可以通过权重影响评分结果。

---

### 6.8 评分明细

V3 应将 V2 中可能已有的总分评分升级为评分明细。

评分不应只显示一个总分，而应显示每个评分项的得分或扣分原因。

示例：

| 评分项 | 扣分 |
| --- | ---: |
| 教师冲突 | 0 |
| 班级冲突 | 0 |
| 教室冲突 | 0 |
| 教师禁排违规 | -10 |
| 班级课程不均衡 | -6 |
| 教室利用率偏低 | -4 |
| 连续上课过多 | -5 |
| 总分 | 75 |

评分明细用于解释不同方案之间的质量差异。

---

### 6.9 方案对比

V3 应支持排课方案对比。

用户可以选择两个或多个方案进行比较。

对比维度包括：

```text
总分
已排课程数
未排课程数
教师冲突数
班级冲突数
教室冲突数
教师禁排违规数
教室利用率
班级均衡度
教师工作量均衡度
```

方案对比页面可以先采用表格方式实现，不要求一开始就做复杂图表。

---

### 6.10 排课过程日志

V3 应记录自动排课过程日志。

排课日志用于说明系统是如何生成课表方案的。

日志内容可以包括：

```text
开始生成排课方案
读取当前学期教学任务
检测教师可用时间
检测教室可用时间
筛选可用时间段
计算候选位置评分
选择最优时间与教室
生成课表明细
计算方案总分
生成未排任务原因
```

日志可以分为两类：

1. 整体生成日志；
2. 单个教学任务排课日志。

---

### 6.11 未排任务原因分析

V3 中，自动排课失败时不能只显示“未排”。

系统应给出未排任务的原因。

常见原因包括：

```text
无可用教室
教师时间全部冲突
班级时间全部冲突
课程要求的教室类型不存在
教室容量不足
周课时过多无法安排
教师禁排时间过多
当前规则过于严格
```

未排任务原因分析可以帮助用户调整教学任务、教室资源或规则权重。

---

### 6.12 手动微调后重新评分

V3 应支持用户对某个排课方案进行手动调整。

调整后，系统应重新检测：

1. 是否存在教师冲突；
2. 是否存在班级冲突；
3. 是否存在教室冲突；
4. 是否违反教师禁排时间；
5. 是否影响课程分布；
6. 是否导致方案总分变化。

手动微调后重新评分，可以将 V1 的手动排课、V2 的冲突检测、V3 的评分体系连接起来。

---

## 七、V3 选做功能范围

以下功能可以作为 V3 后期增强内容，不要求第一阶段全部完成。

### 7.1 教师工作量统计

统计每个教师在当前学期的授课情况。

包括：

```text
总课时
每周课时
每天课程分布
最多连续上课节数
课程数量
班级数量
```

---

### 7.2 教室利用率统计

统计当前学期教室使用情况。

包括：

```text
教室使用次数
空闲时间段
利用率百分比
最常使用教室
长期空闲教室
不同类型教室使用情况
```

---

### 7.3 班级课表均衡度分析

分析班级课表是否合理。

包括：

```text
每天课程数量
上午/下午/晚上分布
是否某一天课程过多
是否某一天课程过少
是否连续上课过多
```

---

### 7.4 冲突热力图

可以用星期和节次展示冲突集中区域。

例如：

```text
周一第1-2节冲突较多
周三第5-6节教室资源紧张
周五下午课程安排较少
```

该功能可以后期再做，不作为 V3 必须完成内容。

---

### 7.5 答辩演示数据生成

可以提供一个“生成演示数据”功能，用于快速创建适合展示的样例数据。

示例数据包括：

```text
学院
专业
班级
教师
课程
教室
教学任务
教师禁排时间
排课方案
评分结果
```

该功能有助于毕业设计演示，但不影响核心业务闭环。

---

## 八、V3 暂不实现功能

为了控制开发范围，V3 暂不实现以下功能：

```text
不做真实教务系统对接
不做复杂审批流
不做学生选课
不做手机端
不做小程序
不做在线支付
不做多学校多租户
不做复杂校历节假日调休
不做单双周复杂排课
不做真实 AI 大模型自动排课
不强行引入 Timefold Solver
不做分布式高并发架构
不做复杂权限审批体系
```

V3 应优先保证现有系统稳定升级，而不是追求过度复杂的真实教务系统能力。

## 九、V3 主要业务流程

### 9.1 当前学期初始化流程

```text
进入系统
查看当前学期
如果没有当前学期，则创建学期
设置某个学期为当前学期
后续业务默认基于当前学期执行
```

---

### 9.2 教学任务准备流程

```text
选择当前学期
维护教师、班级、课程、教室等基础数据
创建当前学期教学任务
设置教师禁排时间
配置排课规则和权重
准备自动排课
```

---

### 9.3 多方案自动排课流程

```text
选择当前学期
点击生成排课方案
系统读取当前学期教学任务
系统读取教师、班级、教室、规则等数据
按照不同策略生成多个排课方案
计算每个方案的评分
记录排课日志
生成未排任务原因
保存方案结果
```

---

### 9.4 方案对比与应用流程

```text
进入排课方案列表
选择多个方案进行对比
查看方案总分和评分明细
查看冲突数量和未排任务数量
选择较优方案
应用为当前学期正式课表
原正式课表进入历史记录
```

---

### 9.5 手动调整与重新评分流程

```text
进入方案详情或正式课表页面
选择某节课进行调整
系统检测新位置是否冲突
保存调整结果
重新计算方案评分
记录调整日志
展示评分变化
```

---

## 十、V3 数据边界要求

V3 必须保证以下数据边界清晰：

1. 不同学期的教学任务不能混用；
2. 不同学期的课表结果不能混用；
3. 不同学期的排课方案不能混用；
4. 方案草稿不能直接当作正式课表；
5. 应用方案时需要明确覆盖的是当前学期正式课表；
6. 历史方案应保留，不能随意丢失；
7. 评分记录和日志应绑定具体方案；
8. 手动调整记录应绑定具体方案或正式课表。

---

## 十一、V3 与 V1/V2 的关系

V3 不重写 V1/V2。

V3 应建立在 V1/V2 的基础上进行升级。

### 11.1 保留 V1 能力

以下能力必须继续可用：

1. 教师管理；
2. 班级管理；
3. 课程管理；
4. 教室管理；
5. 教学任务管理；
6. 手动排课；
7. 课表查询；

## 十五、V3 开发原则

V3 开发必须遵守以下原则：

### 15.1 不推翻已有系统

不得为了开发 V3 重写 V1/V2 已经稳定运行的功能。

应尽量采用增量升级方式。

---

### 15.2 不直接覆盖正式课表

自动排课结果必须先生成排课方案。

只有用户明确点击“应用方案”后，方案才能成为正式课表。

---

### 15.3 所有核心数据必须绑定学期

V3 中以下数据必须能够明确归属到学期：

```text
教学任务
课表结果
排课方案
评分记录
排课日志
统计结果
```

---

### 15.4 先保证硬约束，再优化软约束

排课算法应优先满足硬约束。

软约束用于优化评分和方案质量。

---

### 15.5 评分必须可解释

不能只显示一个总分。

应尽量显示评分项、扣分原因和影响因素。

---

### 15.6 日志必须有业务意义

排课日志不能只是程序调试日志，而应尽量表达业务过程。

例如：

```text
教师张老师在周一第1-2节存在禁排时间，因此跳过该时间段。
A101教室容量不足，无法安排软件工程1班。
最终选择周二第3-4节和B202教室，候选评分为90分。
```

---

## 十六、V3 验收标准

V3 完成后，应至少满足以下验收标准。

### 16.1 学期管理验收

1. 能新增学期；
2. 能编辑学期；
3. 能设置当前学期；
4. 切换学期后，教学任务和课表数据随之变化；
5. 不同学期数据不会混在一起。

---

### 16.2 排课方案验收

1. 自动排课生成的是方案，而不是直接覆盖正式课表；
2. 能查看方案列表；
3. 能查看方案详情；
4. 能应用方案为正式课表；
5. 能查看历史方案；
6. 能回滚或重新应用历史方案。

---

### 16.3 多方案排课验收

1. 能生成多个不同策略的方案；
2. 不同方案有不同评分；
3. 不同方案可以进行对比；
4. 每个方案能查看已排任务和未排任务。

---

### 16.4 评分明细验收

1. 每个方案有总分；
2. 每个方案有评分明细；
3. 能显示扣分项；
4. 能解释扣分原因；
5. 手动调整后能重新计算评分。

---

### 16.5 排课日志验收

1. 自动排课时能生成日志；
2. 能查看整体生成日志；
3. 能查看部分教学任务的排课过程；
4. 日志内容具有业务意义；
5. 未排任务能显示原因。

---

### 16.6 统计分析验收

1. 能查看教师工作量；
2. 能查看教室利用率；
3. 能查看班级课表均衡情况；
4. 统计数据能按当前学期筛选。

## 十七、V3 答辩展示重点

1. 系统支持学期化管理，不同学期数据隔离；

3. 系统可以生成多个不同策略的排课方案；
4. 每个方案都有评分明细，可以解释优劣；
5. 多个方案可以进行横向对比；
6. 方案可以应用、废弃和回滚；
7. 系统可以记录排课过程日志；
8. 未排任务可以显示具体原因；

答辩时可以用一句话概括：

## 二十、总结

V3 版本是排课系统从“自动排课”走向“排课优化与方案决策”的关键版本。

V1 解决基础管理问题，V2 解决规则自动排课问题，V3 进一步解决学期化管理、方案化管理、评分解释、方案对比和历史回滚问题。

V3 不追求真实教务系统的全部复杂功能，而是围绕毕业设计和本地仿真系统的实际需求，做出一个结构清晰、功能完整、技术含量明显、容易展示和答辩的排课系统升级版本。
