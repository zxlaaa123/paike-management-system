# 高校排课管理系统 — 代码设计问题全面审查报告

> 审查日期：2026-05-14
> 审查范围：后端全部 73 个 Java 文件、前端全部 18 个 Vue 文件、17 个 TS API 文件、3 个 SQL 脚本及所有配置文件

---

## 🔴 严重问题（可能导致功能缺陷或数据不一致）

### 1. ScheduleController.list() — 全量查询 + 内存分页，严重性能问题

- **位置**：`backend/src/main/java/com/paike/scheduler/controller/ScheduleController.java`
- **问题**：`list()` 方法用 `selectList()` 查出**所有**排课记录，然后在 Java 内存中过滤和截取分页。当排课数据量大时（如数千条），每次查询都会全量加载到内存。
- **建议**：应该用 MyBatis-Plus 的 `Page` 分页查询 + SQL WHERE 条件过滤，而不是内存分页。

### 2. TeachingTaskController.list() — 同样的全量查询 + 内存分页

- **位置**：`backend/src/main/java/com/paike/scheduler/controller/TeachingTaskController.java`
- **问题**：与 ScheduleController 相同的问题，全量 `selectList()` 后内存过滤分页。

### 3. UnscheduledTaskService.list() — 全量查询 + 内存分页

- **位置**：`backend/src/main/java/com/paike/scheduler/service/UnscheduledTaskService.java`
- **问题**：同上，`selectList()` 全量加载后手动分页。

### 4. CORS 配置：`allowedOriginPatterns("*")` + `allowCredentials=false` 矛盾且不安全

- **位置**：`backend/src/main/java/com/paike/scheduler/config/CorsConfig.java`
- **问题**：`setAllowedOriginPatterns(List.of("*"))` 允许所有源，但 `setAllowCredentials(false)` 禁止凭证。前端 Vite 代理走 localhost 时不影响，但如果前后端分离部署，这个配置要么不安全（允许所有源），要么不工作（带 cookie 时不能用通配符）。
- **建议**：明确指定前端域名，如 `http://localhost:5173`。

### 5. ScheduleConflictService.checkConflict() — N+1 查询问题

- **位置**：`backend/src/main/java/com/paike/scheduler/service/ScheduleConflictService.java`
- **问题**：在 `for (Schedule s : existingSchedules)` 循环中，每条 `s` 都会执行一次 `teachingTaskMapper.selectById(s.getTeachingTaskId())`。如果有 1000 条排课记录，就会产生 1000 次额外 SQL 查询。
- **建议**：先批量查出所有 teachingTask，放入 Map，再循环检查。

### 6. ScheduleController.fillRelation() — 也是 N+1 查询

- **位置**：`backend/src/main/java/com/paike/scheduler/controller/ScheduleController.java`
- **问题**：单条记录查询时，连续调用 `timeSlotMapper.selectById`、`classroomMapper.selectById`、`teachingTaskMapper.selectById`、`courseMapper.selectById`、`teacherMapper.selectById`、`classInfoMapper.selectById`、`autoScheduleBatchMapper.selectById`，共 **7 次 SQL** 查一条记录。
- **建议**：虽然单条记录影响不大，但应统一用批量查询优化。

### 7. AutoScheduleService.run() — 无事务保护的大批量操作

- **位置**：`backend/src/main/java/com/paike/scheduler/service/AutoScheduleService.java`
- **问题**：`run()` 方法标注了 `@Transactional`，但在循环中每次排课都会调用 `conflictService.checkConflict()`，且 `saveSchedule()` 也在同一事务中。如果排课过程中间失败，前面已排的课**全部回滚**，但 `batchService.createBatch()` 的批次记录可能已经提交（取决于事务传播行为）。更严重的是，`@Transactional` 在 Spring AOP 代理下，**同类方法调用会失效**。
- **建议**：考虑分批提交，或者将冲突检测抽取到事务外部预检。

### 8. AutoScheduleService 内部 DTO 类使用 `@Data` 而非不可变对象

- **位置**：`backend/src/main/java/com/paike/scheduler/service/AutoScheduleService.java` 末尾
- **问题**：`AutoScheduleRequest` 和 `AutoScheduleResult` 作为内部静态类放在 Service 层，且用 `@Data`（可 set），违反了 DTO 的不可变原则。
- **建议**：抽取到 `dto` 包，使用 `record` 或 `@Value`。

## 🟠 中等问题（设计不规范，影响可维护性）

### 9. Controller 层直接注入 Mapper，绕过 Service 层

- **位置**：`ScheduleController.java`、`TeacherController.java`、`ClassInfoController.java`、`ClassroomController.java`、`CourseController.java`、`TeachingTaskController.java`
- **问题**：所有 CRUD 控制器都**直接注入 XXMapper**，在 Controller 中手写查询逻辑、分页逻辑、关联数据填充逻辑。这违反了分层架构原则——Controller 应该只调用 Service。
- **建议**：创建对应的 `TeacherService`、`ClassInfoService`、`ClassroomService`、`CourseService`、`TeachingTaskService`，将业务逻辑从 Controller 移到 Service。

### 10. TimetableVo 放在 controller 包中但实际是 VO

- **位置**：`controller/TimetableVo.java`
- **问题**：`TimetableVo.java` 文件放在 `controller` 包下但实际是一个 VO（View Object），命名和位置都不规范。
- **建议**：放到 `controller/vo/` 子包或 `vo/` 包中。

### 11. TimetableVo 缺少完整的 Lombok 注解

- **位置**：`TimetableVo.java`
- **问题**：与 Entity 不同，VO 没有使用 `@NoArgsConstructor` / `@AllArgsConstructor`，只有 `@Data`。如果框架需要无参构造器，可能出问题。

### 12. TimetableController 中查询方法大量重复逻辑

- **位置**：`TimetableController.java`
- **问题**：`queryByClassId()` 和 `queryByTeacherId()` 几乎完全相同的代码（先通过 task 查，再直接查 schedule 表，然后合并去重），存在大量重复。
- **建议**：抽取通用方法。

### 13. 多处硬编码字符串常量未提取为枚举

- **问题**：`"EXPERIMENT"`、`"LAB"`、"`COMPUTER`"、`"NORMAL"`、`"AUTO"`、`"MANUAL"` 等字符串在代码中大量硬编码，如 `ScheduleConflictService` 中 `courseType` 判断、`AutoScheduleService` 中 `sourceType` 设置。
- **建议**：定义枚举类 `CourseType`、`RoomType`、`ScheduleSourceType`、`ConflictType` 等。

### 14. ScheduleRuleConfig 使用字符串存储所有规则值

- **位置**：`ScheduleRuleConfig` 实体 + `ScheduleRuleService`
- **问题**：整数（如 `TEACHER_MAX_DAILY_SLOTS=3`）和布尔值（如 `PRIORITIZE_MORNING=true`）都用 `VARCHAR` 存储，在 Service 中手动 `parseInt` / `parseBoolean`。类型不安全，容易因拼写错误导致运行时异常。
- **建议**：增加 `value_type` 字段区分类型，或使用专门的规则解析器。

### 15. ScheduleScoreReport 的 gradeName 不会被持久化

- **位置**：`ScheduleScoreReport.java`
- **问题**：`gradeName` 用 `@TableField(exist = false)` 标注为不存在字段，在 Service 中设置了值但不会保存到数据库。后续查询需要显示等级名称时必须再次转换。
- **建议**：要么在实体表中增加 `grade_name` 列，要么在前端转换。

### 16. Schedule 实体类混合了持久化字段和展示字段

- **位置**：`Schedule.java`
- **问题**：`courseName`、`teacherName`、`className`、`timeLabel`、`dayOfWeek`、`periodNo`、`roomName`、`building`、`sourceTypeName`、`batchNo` 等用 `@TableField(exist = false)` 标注。一个实体类同时承担 DB 映射和前端展示两种职责。
- **建议**：创建独立的 VO 类用于返回前端，Entity 只保留数据库字段。

### 17. 前端 API 类型定义与后端不一致

- **位置**：前端 `api/` 目录
- **问题**：
  - 后端 `Result<T>` 的 `code` 是 `Integer`，前端 `ApiResponse<T>` 的 `code` 是 `number` —— 前端没有处理 `null` 情况
  - `PageResult<T>` 定义了 `current` 字段，但后端 `Page` 对象用的是 `page`
  - 后端分页参数名是 `page`，前端传的也是 `page`，但 `PageResult` 字段名叫 `current` —— 命名不统一

### 18. 前端 ID 类型混用 `number` 和实际可能的 `Long`

- **位置**：所有前端 `.vue` 和 `.ts` 文件
- **问题**：前端所有 ID 都定义为 `number` 类型，但后端是 `Long`（64位）。JavaScript 的 `number` 只能安全表示到 `2^53-1`。
- **建议**：在注释中标明范围，或使用 `bigint`。

### 19. 前端 request.ts 拦截器与调用方重复处理错误

- **位置**：`request.ts`
- **问题**：响应拦截器在 `payload.code !== 200` 时已经 `ElMessage.error()` 并 `Promise.reject()`，但每个 API 函数的调用方又有 `catch (_e)` 注释说"错误由拦截器显示"。这种双重错误处理模式容易导致错误被吞掉或重复提示。

### 20. 前端大量空 catch 块静默吞掉错误

- **位置**：几乎所有 `.vue` 文件
- **问题**：`catch (_e) { /* 错误由拦截器处理 */ }` 的模式导致**真正的业务错误被静默吞掉**。如果拦截器没有正确处理某种错误类型，用户和开发者都无法感知。
- **建议**：至少记录日志 `console.error(_e)`。

### 21. TimeSlot 实体缺少审计字段，与其他实体不一致

- **位置**：`TimeSlot.java`
- **问题**：其他所有实体都有 `deleted`、`createTime`、`updateTime` 字段，但 `TimeSlot` 只有 `id`、`dayOfWeek`、`periodNo`、`timeLabel`、`sortOrder`。
- **建议**：至少保持一致性，即使预置数据不需要软删除。

### 22. v2_alter_schedule.sql 存储过程不可重复执行

- **位置**：`backend/src/main/resources/db/v2_alter_schedule.sql`
- **问题**：存储过程用 `DELIMITER //` 包裹，但每次执行都会尝试 `CREATE PROCEDURE`，第二次执行会报"PROCEDURE 已存在"错误。
- **建议**：使用 `DROP PROCEDURE IF EXISTS` 或改用简单的 `ALTER TABLE` 语句。

## 🟡 轻微问题（代码风格、命名、可维护性）

### 23. 所有 Controller 的内部 Form 类用 `@Data` 而非按需注解

- **位置**：所有 `Controller` 中的 `XxxForm` 内部类
- **问题**：Form 类只需要 getter（用于校验），不需要 setter（除了框架绑定）。使用 `@Data` 暴露了不必要的 setter。
- **建议**：使用 `@Getter` + `@Setter` 按需添加，或使用 record。

### 24. 前端 API 文件缺少空值检查

- **位置**：所有 `api/*.ts` 文件
- **问题**：`.then((r) => r.data.data)` 假设 `r.data` 一定存在且 `r.data.data` 一定存在。如果后端返回的 `data` 为 `null`，前端会拿到 `null` 而不报错，后续访问属性时会出运行时错误。

### 25. BaseLayout.vue 中两个子菜单使用相同的 DataLine 图标

- **位置**：`frontend/src/layout/BaseLayout.vue`
- **问题**："教学管理"和"排课分析"两个子菜单都使用 `<DataLine />` 图标，视觉上无法区分。
- **建议**：使用不同图标区分不同模块。

### 26. HelloWorld.vue 组件未被使用但保留在项目中

- **位置**：`frontend/src/components/HelloWorld.vue`
- **问题**：Vite 脚手架生成的示例文件，没有被任何路由引用，属于无用代码。
- **建议**：删除。

### 27. PlaceholderView.vue 路由从未被使用

- **位置**：`frontend/src/views/PlaceholderView.vue`
- **问题**：路由定义了 `/placeholder/:module` 但菜单中没有入口，属于死代码。

### 28. HealthController 可能不存在但配置中排除了拦截

- **位置**：`WebMvcConfig.java`
- **问题**：代码中排除了 `/api/health` 的拦截，但项目中未发现对应的 Controller 类。如果该 Controller 不存在，这个排除配置是无意义的。

### 29. TeacherController.updateStatus 方法没有参数校验

- **位置**：`TeacherController.java`
- **问题**：`@RequestBody StatusForm form` 没有加 `@Valid`，而 `StatusForm` 内部也没有校验注解，与其他 Controller 的风格不一致。

### 30. 部分 Controller 手动实现软删除而非使用 deleteById

- **位置**：`ClassInfoController`、`ClassroomController`、`CourseController`
- **问题**：这些 Controller 手动 `setDeleted(1)` + `updateById()` 实现软删除，而 `ScheduleController.delete()` 使用 `deleteById()`（触发 `@TableLogic`）。两种方式风格不统一。
- **建议**：统一使用 `deleteById()` 让 `@TableLogic` 自动处理。

### 31. TeacherUnavailableTime 实体上加了无意义的校验注解

- **位置**：`TeacherUnavailableTime.java`
- **问题**：实体类上加了 `@NotNull` 校验注解，但这些校验只在 Controller 层通过 `@Valid` 触发，在 Service 层直接 `new` 创建对象时不会校验。
- **建议**：校验注解应放在 Controller 层的 Form/DTO 上。

### 32. application.yml 中 JWT 密钥硬编码默认值

- **位置**：`backend/src/main/resources/application.yml`
- **问题**：`secret: ${JWT_SECRET:replace_with_a_strong_secret_key_for_stage3_v1_auth}` 默认密钥是公开的低强度字符串。
- **建议**：生产环境必须通过环境变量设置，或启动时检查密钥强度。

### 33. AdminUserInitializer 硬编码弱密码

- **位置**：`backend/src/main/java/com/paike/scheduler/config/AdminUserInitializer.java`
- **问题**：默认管理员密码是 `123456`，虽然有 BCrypt 加密，但仍然存在安全隐患。
- **建议**：首次登录强制修改密码，或生成随机密码打印到日志。

### 34. ClassTimetableView.vue 中加载状态与空状态混淆

- **位置**：`frontend/src/views/timetable/ClassTimetableView.vue`
- **问题**：`v-else-if="selectedClassId && !loading"` 条件意味着当用户选择了班级但正在加载时，既不显示表格也不显示空状态，而是直接跳到 `v-else` 显示"请先选择班级"——加载中和未选择的状态混淆。

### 35. TimetableGrid.vue 中 highlight 注释与实际逻辑不一致

- **位置**：`frontend/src/components/TimetableGrid.vue`
- **问题**：注释说 `class=课程/教师/教室`，但代码中 `props.highlight !== 'teacher'` 控制是否显示教师名。逻辑是"高亮模式下隐藏某些字段"，但注释描述的是"高亮显示某些字段"，容易误解。

### 36. ScheduleConflictReportService 内部 Context 类字段访问修饰符不规范

- **位置**：`ScheduleConflictReportService.java`
- **问题**：`private static class Context` 的所有字段都是默认访问修饰符（无 `private`），不符合 Java 编码规范。

### 37. 前端 clearBatchSchedules 返回类型声明不准确

- **位置**：`frontend/src/api/autoSchedule.ts`
- **问题**：`request.delete(...)` 没有 `.then()` 链，返回的是 `Promise<AxiosResponse>` 而非 `void`，类型声明不准确。

### 38. v2_schema.sql 中 ON DUPLICATE KEY UPDATE 依赖唯一索引

- **位置**：`backend/src/main/resources/db/v2_schema.sql`
- **问题**：`INSERT INTO schedule_rule_config ... ON DUPLICATE KEY UPDATE` 依赖 `uk_rule_key` 唯一键。如果表已存在且 `rule_key` 值被修改过，则不会匹配到重复，会插入新记录而不是更新。

### 39. TeacherView.vue 中表单字段缺少 prop 属性

- **位置**：`frontend/src/views/teacher/TeacherView.vue`
- **问题**：`rules` 对象只定义了 `teacherNo` 和 `name` 的校验规则，但模板中 `department`、`phone`、`remark` 字段没有 `prop` 属性，即使定义了规则也不会触发校验。

### 40. Schedule 表中冗余字段无一致性保证

- **位置**：`Schedule.java` + `ScheduleController.java`
- **问题**：`Schedule` 表中有 `teacherId`、`classId`、`courseId` 冗余字段（可以从 `teaching_task_id` 关联查出）。这些冗余字段在插入时需要手动同步，但**没有任何机制保证冗余字段与 teaching_task 的一致性**。如果 teaching_task 的 teacherId 被修改了，schedule 表的 teacherId 不会自动更新。
- **建议**：要么通过数据库触发器保证一致性，要么去掉冗余字段改为 JOIN 查询。

## 🎯 优先修复建议

以下是最需要优先修复的问题：

| 优先级 | 问题 | 原因 |
|--------|------|------|
| P0 | 全量查询 + 内存分页（问题 1、2、3） | 数据量增大后必然导致 OOM |
| P0 | N+1 查询（问题 5、6） | 排课冲突检测是核心功能，性能影响直接 |
| P0 | Controller 直接操作 Mapper（问题 9） | 违反分层原则，导致大量逻辑无法复用和测试 |
| P1 | 硬编码魔法字符串（问题 13） | 维护时极易出错，应使用枚举 |
| P1 | CORS 配置不安全（问题 4） | 部署后存在安全隐患 |
| P1 | Schedule 冗余字段无一致性保证（问题 40） | 可能导致数据不一致 |
| P2 | 前端空 catch 块（问题 20） | 错误被静默吞掉，难以调试 |
| P2 | AutoScheduleService 内部 DTO（问题 8） | 影响代码可维护性 |
