# 20260528 M-05 冲突状态刷新复杂度调查

## 结论

`M-05` 部分成立，不建议当前改生产代码。

原因：

- `SchedulePlanService.refreshPlanConflictState()` 确实会遍历方案明细并逐项计算冲突原因。
- 当前实现已批量加载教学任务、课程、教师、班级、教室和时间段，不存在按明细 N+1 查询。
- 当前实现只在明细的 `conflictFlag` 或 `conflictReason` 变化时调用 `planItemMapper.updateById(item)`。
- 200 条无冲突且状态不变的样本已验证不会触发任何明细更新。
- 方法最后仍会更新一次 `SchedulePlan.conflictCount/updatedAt`，这是单条方案汇总更新，不是按明细循环写库。

## 源码证据

目标文件：

- `backend/src/main/java/com/paike/scheduler/service/SchedulePlanService.java`

关键方法：

- `refreshPlanConflictState()`：先 `selectList` 取方案明细，再按 ID 批量加载关联数据。
- `buildPeerConflictReasons()`：按 `weekday_startPeriod` 分组，给同一时间点的教师、班级、教室冲突生成原因。
- `buildConflictReasons()`：合并同伴冲突、教师禁排、容量、教室类型等原因。

更新条件：

```java
if (!Objects.equals(item.getConflictFlag(), conflictFlag)
        || !Objects.equals(item.getConflictReason(), conflictReason)) {
    item.setConflictFlag(conflictFlag);
    item.setConflictReason(conflictReason);
    item.setUpdatedAt(LocalDateTime.now());
    planItemMapper.updateById(item);
}
```

这说明原报告里“按项目循环处理”的现象存在，但不能直接等价为“每个项目都会写库”。

## 风险判断

可确认：

- 计算仍是内存内逐明细扫描。
- 每次调用都会更新一次方案汇总记录。

暂未确认：

- 没有证据表明当前真实数据量下该方法会超时。
- 没有证据表明批量更新能带来足够收益抵消回归风险。

## 建议

`M-05` 从“性能缺陷”调整为“已验证，部分成立，暂不修复生产代码”。

后续只有在真实接口压测或大数据导入场景证明 `refreshPlanConflictState()` 成为瓶颈时，再考虑优化：

1. 给无冲突且方案 `conflictCount` 未变化的场景跳过方案汇总更新。
2. 对变化明细较多的场景引入批量更新。
3. 将同时间冲突检测从当前分组逻辑进一步压缩成按资源键聚合。
