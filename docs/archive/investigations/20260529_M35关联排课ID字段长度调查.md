# M-35 关联排课 ID 字段长度调查

## 结论

已修复。

原问题成立：`schedule_conflict_report.related_schedule_ids` 用逗号分隔字符串保存关联排课记录 ID，但历史 SQL 将字段定义为 `VARCHAR(255)`。

当前写入路径集中在 `ScheduleConflictReportService`：

- `detectTeacherConflicts()` / `detectClassConflicts()` / `detectClassroomConflicts()` 会把同一资源同一时间段的冲突排课 ID 拼接写入。
- `detectTeacherDailyOverload()` / `detectClassDailyOverload()` 会把同一教师或班级同一天的排课 ID 拼接写入。
- `detectUnfinishedTasks()` 会把同一教学任务已经排出的排课 ID 拼接写入。

拼接逻辑 `joinScheduleIds()` 没有长度保护。`BIGINT` ID 在极限情况下每个 ID 最多 19 位，再加逗号分隔，`VARCHAR(255)` 只能容纳十几个 ID。对大规模冲突组或异常重复数据，字段存在截断风险。

## 本轮处理

保留现有接口和实体类型，不改变 `relatedScheduleIds` 的前后端表现，单独放宽数据库字段：

- `db/v2_schema.sql`：新库初始化改为 `TEXT NULL`。
- `db/migration/V1__baseline.sql`：baseline 同步改为 `TEXT NULL`。
- 新增 `db/v20_schedule_conflict_related_ids_text.sql`：已有库若字段仍不是 `text`，幂等执行 `MODIFY COLUMN related_schedule_ids TEXT NULL`。
- `application.yml`：把 `v20_schedule_conflict_related_ids_text.sql` 追加到 `schema-locations`。
- `docs/v2/V2_03_数据库设计.md`：字段类型同步为 `text`。

本轮不改为 JSON。原因是当前读写逻辑、前端类型和历史数据都已经使用逗号分隔字符串；本问题核心是容量不足，先用最小迁移解除截断风险。

## 本轮验证

新增 `M35RelatedScheduleIdsColumnLengthTest` 锁定当前事实：

- `v2_schema.sql` 和 `V1__baseline.sql` 不再使用 `VARCHAR(255)`。
- `v20_schedule_conflict_related_ids_text.sql` 会在旧字段类型不是 `text` 时执行放宽迁移。
- `application.yml` 已注册 `v20_schedule_conflict_related_ids_text.sql`。
