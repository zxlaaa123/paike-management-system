# M-25 时间字段命名调查

## 结论

部分成立，已做低风险整理；本次复核收口未发现新增迁移点。

项目中确实存在两套时间字段命名：

- 老核心表多使用 `create_time` / `update_time`，Java 字段为 `createTime` / `updateTime`。
- V4/V5、日志、报告类表多使用 `created_at` / `updated_at`，Java 字段为 `createdAt` / `updatedAt`。

这两套命名在当前表内没有混用；MyBatis-Plus 驼峰下划线映射和局部 `@TableField` 能覆盖当前字段，不构成直接运行故障。

## 本轮处理

调查时发现 `AutoScheduleBatch.updateTime` 映射 `update_time`，而 `auto_schedule_batch` 的基线建表只包含 `create_time`，依赖后续 `v9_auto_schedule_batch_update_time.sql` 补列。

本轮做低风险收口：

- `db/v2_schema.sql` 的 `auto_schedule_batch` 建表补 `update_time`。
- `db/migration/V1__baseline.sql` 的 `auto_schedule_batch` 建表补 `update_time`。
- 保留 `v9_auto_schedule_batch_update_time.sql`，继续为已有旧库做幂等补列。

本次复核补强测试覆盖：所有实体中显式 `@TableField` 标注的时间字段，都能在现有 `CREATE TABLE` 定义中找到对应列。

## 判断

不建议本轮机械统一所有时间字段命名。统一会牵涉实体、SQL、前端类型、导出字段、历史数据迁移和接口兼容，收益低于回归风险。

后续如果要统一命名，应单独立迁移任务，先选定 `create_time/update_time` 或 `created_at/updated_at` 作为标准，再逐表迁移。

## 本轮验证

新增 `M25TimestampNamingInvestigationTest` 锁定当前事实：

- `auto_schedule_batch` 基线建表包含实体映射需要的 `update_time`。
- v9 迁移继续保留旧库补列兜底。
- 实体显式时间字段映射均能匹配建表脚本中的列定义。
- 建表语句不在同一张表内混用两套时间字段命名。
