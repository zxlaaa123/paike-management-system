# M-43 试算放弃顺序调查

## 结论

M-43 不成立，已验证，暂不修改生产代码。

原报告认为 `V5SimulationService.discard()` 存在“先改状态再获取详情”的顺序问题。当前实现确实先把方案状态改为 `DISCARDED`，再调用 `detail(taskId, planId)`，但这不会导致详情获取失败：

- `requireSimulationPlan()` 明确允许 `DISCARDED` 状态。
- `discard()` 在清理 `SchedulePlanItem` / 锁定项 / 评分明细之前先生成详情快照。
- 前端 `SimulationPlanDetailView` 使用 `discardSimulation(...)` 的返回详情刷新页面。

因此，当前顺序是有意设计：返回放弃后的方案详情，同时避免清理明细后再生成详情导致空明细风险。

## 现状证据

- `discard()` 先校验 `APPLIED` 与重复 `DISCARDED`，再设置 `DISCARDED`。
- `requireSimulationPlan()` 允许 `SIMULATION` / `CONFIRMED` / `DISCARDED` / `APPLIED`。
- `discard()` 中 `V5SimulationPlanDetailVo result = detail(taskId, planId)` 位于 `planItemMapper.delete(...)`、`lockedItemMapper.update(...)`、`scoreDetailMapper.delete(...)` 之前。
- 前端 `discardPlan()` 将接口返回值赋给 `detail.value`。

  - 用 Mockito `InOrder` 验证 `planMapper.updateById(...)` 之后先构建详情，再进入明细清理。
