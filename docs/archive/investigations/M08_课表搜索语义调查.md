# M-08 课表搜索语义调查

## 结论

`M-08` 的原始证据成立：`ScheduleMapper.xml` 对课程、教师、班级、教室 4 个字段使用 `LIKE CONCAT('%', #{...}, '%')`，普通 BTree 索引无法高效支持前导通配符。

当前不建议直接把 SQL 改为前缀匹配。原因是前端提供的是 4 个独立名称筛选框，现有行为是“包含匹配”；改成 `keyword%` 会改变用户可见搜索语义。

本分支先做不改变语义的收敛：新增 `idx_schedule_semester_deleted_created (semester_id, deleted, create_time, id)`，优化默认按学期加载课表列表时的过滤和排序路径。

## 当前链路

- 前端入口：`frontend/src/views/schedule/ScheduleView.vue`
  - `searchForm.courseName`
  - `searchForm.teacherName`
  - `searchForm.className`
  - `searchForm.roomName`
  - 直接传给 `getScheduleList(params)`
- API：`GET /api/schedules`
- 后端入口：`ScheduleController.list(...)`
  - 已对 4 个名称参数做 `trimToNull`
  - 未传 `semesterId` 时默认当前学期
- SQL：`ScheduleMapper.selectFilteredSchedulePage`
  - `c.course_name LIKE CONCAT('%', #{courseName}, '%')`
  - `t.name LIKE CONCAT('%', #{teacherName}, '%')`
  - `cl.class_name LIKE CONCAT('%', #{className}, '%')`
  - `cr.room_name LIKE CONCAT('%', #{roomName}, '%')`
  - `ORDER BY s.create_time DESC`

## 方案比较

| 方案 | 语义变化 | 性能收益 | 风险 |
|---|---:|---:|---|
| 保留包含匹配，仅补排序索引 | 无 | 优化默认学期列表和分页排序 | 名称筛选仍无法吃普通 BTree |
| 改为前缀匹配 `keyword%` | 有 | 名称字段可考虑普通索引 | 用户搜中间片段会查不到 |
| 引入全文/搜索字段 | 可保持近似包含搜索 | 取决于分词和数据量 | 中文分词、维护成本、排序相关性需设计 |

## 产品确认点

1. 课表筛选是否必须支持“输入中间片段也能搜到”？
2. 是否允许改为“从名称开头匹配”？
3. 是否需要新增一个全局关键字框，跨课程/教师/班级/教室统一搜索？
4. 数据量规模是多少：单学期课表记录是千级、万级还是更高？

## 推荐

短期：保留包含匹配，合入排序索引，避免破坏现有体验。

中期：拿真实数据执行 `EXPLAIN`，分别看无名称筛选、单字段筛选、多字段筛选场景。

长期：如课表规模达到万级以上且名称搜索频繁，再单独设计搜索字段或全文索引方案。
