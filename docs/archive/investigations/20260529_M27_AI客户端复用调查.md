# M-27 AI HTTP client 重复程度复核

## 结论

M-27 部分成立，暂不修复生产代码。

原条目中“HttpClient 实例重复”的描述不够精确。当前远程 AI 调用只分布在两个服务：

- `V4ScheduleAiAnalysisService`
- `V5RepairExplanationService`

两者都已经使用 `private static final HttpClient HTTP_CLIENT`，不存在每次 AI 请求都创建 `HttpClient` 的运行时问题。

真正成立的是可维护性重复：两个服务各自注入同一组 `app.ai.*` 配置，并分别实现 OpenAI chat completion 请求、响应 JSON 提取、prompt 字段清洗和远程失败后的本地兜底。

## 现状证据

- `application.yml` 只有一组 AI 配置：`app.ai.api-key`、`app.ai.base-url`、`app.ai.model`、`app.ai.timeout-ms`。
- `V4ScheduleAiAnalysisService` 和 `V5RepairExplanationService` 均重复注入上述 4 个配置项。
- 两个服务均持有静态 `HTTP_CLIENT`，并通过 `HTTP_CLIENT.send(...)` 发起请求。
- 两个服务均保留自己的 `extractJson(...)` 与 `sanitizeForPrompt(...)`，但输出结构不同：
  - V4 返回 `analysisText` / `suggestions`
  - V5 返回 `overallEvaluation` / `recommendationReason` / `improvedMetrics` / `remainingIssues` / `applyAdvice` / `recommendApply` / `defenseSummary`

## 判断

当前不建议为了两处调用立即抽公共远程 AI 客户端。

原因：

- 运行时资源问题已经通过静态 `HttpClient` 缓解。
- 两个服务的 prompt、响应字段、兜底逻辑不同，强行抽象容易把业务 schema 混进通用客户端。
- 远程 AI 功能目前规模很小，抽象收益有限。

如果后续出现第三个远程 AI 调用，或需要统一重试、超时、日志脱敏、模型切换、错误码处理，再抽：

- `AiChatProperties`：集中承载 `app.ai.*` 配置。
- `RemoteAiChatClient`：只负责 chat completion HTTP envelope、鉴权、超时和原始 content 提取。
- 各业务服务继续保留 prompt 组装、业务 JSON schema 解析和本地兜底。

## 本轮验证

- 新增 `M27AiHttpClientDuplicationInvestigationTest`，锁定：
  - 当前只有两个远程 AI 服务直接使用 `java.net.http.HttpClient`。
  - 两个服务均使用静态 `HTTP_CLIENT`，没有 `HttpClient.newHttpClient()`。
  - 两个服务仍重复注入 `app.ai.*` 配置。
  - 两个服务仍各自实现 prompt 清洗和 JSON 提取。
