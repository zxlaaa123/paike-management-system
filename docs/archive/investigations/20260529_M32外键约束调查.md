# M-32 外键约束调查

## 结论

部分成立，暂不修复生产 SQL。

当前 SQL 初始化脚本确实没有声明数据库级外键：

- 未检出 `FOREIGN KEY`
- 未检出 `REFERENCES`

但这不是“没有表关系”。本轮扫描到大量关系型 ID 列，例如：

- `semester_id`
- `plan_id`
- `teaching_task_id`
- `teacher_id`
- `course_id`
- `class_id`
- `time_slot_id`
- `classroom_id`

其中 `schedule` 表同时保存教学任务、课程、教师、班级、时间段、教室等多个关联 ID。项目当前实际采用的是“业务层关系校验 + MyBatis-Plus 逻辑删除 + 索引/唯一约束”的模式，而不是数据库外键模式。

## 判断

M-32 指出的事实成立：数据库脚本没有外键约束。

但不建议本轮直接补外键，原因：

- 主数据大量使用 `@TableLogic` / `deleteById` 软删除，数据库外键无法直接表达“只约束未删除记录”。
- 部分删除流程在业务层清理子数据，例如排课方案删除会先删方案明细和解释产物，再删方案。
- 历史脚本采用多段初始化/补列/补索引方式，直接补外键会引入既有数据清洗、迁移顺序、级联策略和软删除语义问题。
- 关系列数量多，若补外键需要逐表确认 `RESTRICT` / `CASCADE` / `SET NULL` 策略，不适合机械批量修改。

## 本轮验证

新增 `M32ForeignKeyConstraintInvestigationTest` 锁定当前事实：

- SQL 脚本不包含 `FOREIGN KEY` / `REFERENCES`。
- SQL 中仍存在大量 `*_id` 关系列。
- `schedule` 等核心表确实通过 ID 列表达业务关系。

后续如要推进外键，应单独立设计任务：先定义每张表的删除语义，再补数据清洗脚本、迁移顺序和回归测试。
