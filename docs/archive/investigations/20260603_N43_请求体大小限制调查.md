# N-43 请求体大小限制调查

> 调查对象：`20260527bug验证报告.md` N-43（`application.yml` 未检出请求体大小限制配置）
> 调查日期：2026-06-03
> 分支：`fix/n43-request-body-size-limit`
> 结论：**部分成立 → 已修复**。补一个按 `Content-Length` 拦截的轻量过滤器作为应用层兜底。

---

## 1. 背景与原始结论

`20260527bug验证报告.md` N-43 状态为 `确认`：「`application.yml` 未检出请求体大小限制配置」。
本次按"调查 → 改代码 → 测试 → 更新文档 → 合并"的流程核实并收口。

## 2. 调查发现（源码静态核验）

| 核验点 | 结果 |
|---|---|
| `application.yml` 是否有请求体大小配置 | **无**：无 `spring.servlet.multipart.*`、无 `server.tomcat.*`，仅 `server.port: 8090`。 |
| 是否存在文件上传端点 | **无**：全后端 `MultipartFile` / `multipart` 零命中（`backend/src` Grep）。 |
| 请求体形态 | 全部为 JSON（`@RequestBody`）。 |
| Spring 是否对裸 JSON 请求体设默认上限 | **否**：`spring.servlet.multipart.max-request-size`（默认 10MB）只作用于 multipart/表单；`server.tomcat.max-http-form-post-size` 只作用于 `x-www-form-urlencoded`/表单。两者都**不拦** JSON 请求体。 |
| 生产部署是否有外层兜底 | **有**：`app.cors` 注释表明生产走 nginx 反代，nginx 默认 `client_max_body_size 1MB` 会在入口先拦一层。 |

**判定**：原结论 N-43「无请求体大小限制」**部分成立**——multipart 维度因为没有上传端点本就无关紧要；真正的缺口是 **JSON 请求体在应用层没有任何上限**，理论上存在超大 body 导致内存压力（OOM/DoS）的风险。生产环境由 nginx 兜底，故严重度为 Minor，但应用层补一层防御（defense-in-depth）是合理且低风险的收口。

## 3. 改造方案

新增 `RequestBodySizeLimitFilter`（`com.paike.scheduler.config`）：

- `implements Filter` + `@Component` + `@Order(HIGHEST_PRECEDENCE + 10)`，在鉴权与 body 读取之前尽早拦截。
- 读取 `request.getContentLengthLong()`，超过阈值即直接返回 `413`，响应体复用项目统一信封 `Result.fail(413, ...)`，不进入 DispatcherServlet（`GlobalExceptionHandler` 在过滤器层之外，接不住，必须由过滤器自行写响应）。
- 阈值走项目既有 `app.security.*` 命名空间：`app.security.max-request-body-size`，默认 **2097152（2MB）**，与 `cookie-secure` 一致用 `@Value` 注入。
- 默认值取舍：当前所有端点的请求体均为小体量 JSON（ID / 小 DTO，重活在服务端），2MB 已是约 10 倍冗余；如未来出现大批量导入类端点，调高该配置即可。

`application.yml` 同步补 `spring.servlet.multipart.max-file-size` / `max-request-size`，作为将来万一引入文件上传时的护栏（当前无上传端点，属预置）。

## 4. 已知局限（已在代码注释与本报告中说明）

- 过滤器按 `Content-Length` 拦截。对**显式 chunked（`Transfer-Encoding: chunked`，无 Content-Length）**的请求无法预判大小，会放行；该路径由外层 nginx `client_max_body_size` 兜底。浏览器 / axios / fetch 发 JSON 时均带 `Content-Length`，故覆盖绝大多数真实流量。
- 若需对 chunked 也强约束，可后续追加按字节计数的 `HttpServletRequestWrapper`（本次按 Minor 比例不做，列为可选 follow-up）。

## 5. 验证

- 新增单测 `RequestBodySizeLimitFilterTest`（仿 `SecurityHeadersFilterTest`，纯 `MockHttpServletRequest/Response`，不依赖 Spring context，规避 `contextLoads` 因 `JWT_SECRET`/DB 缺失而失败的已知问题）：
  - 超限请求 → 状态 413、响应体 `code=413`、`chain.doFilter` 未被调用；
  - 阈值内请求 → 放行（`chain.doFilter` 被调用）；
  - 无 `Content-Length`（如 GET）→ 放行。
- 命令：`cd D:\paike\backend; mvn -Dtest=RequestBodySizeLimitFilterTest test`
