> 评估方式：源码静态核验 + Entity × SQL × Mapper × Service × Controller × Frontend 端到端追踪

## 3. 风险评估

### 3.1 风险矩阵

| 风险点 | 等级 | 触发条件 | 缓解措施 |
|---|---|---|---|
| 列重命名导致 MyBatis 反射写错列 | **高** | `ALTER TABLE ... RENAME COLUMN` 写错或顺序错 | 实施时严格 1 表 1 步 1 验证 |
| 数据丢失/截断 | **高** | RENAME COLUMN 在某些 MySQL 版本有限制 | 先备份表 + 验证回滚路径 |
| Service `setXxxTime` 与 Entity 字段名不同步 | **极高** | 改 Java 字段名后漏改 Service | 必须全量 grep + 测试覆盖 |
| Mapper XML 引用未更新 | 中 | MyBatis XML 用 `${...}` 拼接时间字段名 | 当前 XML 不引用，但需 grep 验证 |
| Frontend `interface X { createTime: string }` 漏改 | 中 | 26 张表对应 ~25 个 TS 接口 | 同步 PR 改前端 |
| InvestigationTest 不变量被破坏 | 低 | 3 个不变量会先红 | 改造时更新测试 |
| `AutoScheduleBatch.updateTime` 历史数据迁移 | 中 | v9 迁移逻辑需调整 | 已有 v9 幂等补列兜底 |
| V3/V4/V5 流程审计 | 高 | 排课/试算/修复全链路依赖时间字段 | 排课/试算全流程回归测试 |
| 时间字段与 `@TableLogic` 软删除交互 | 低 | 时间字段非软删除字段，独立 | 无影响 |
| MyBatis-Plus 隐式映射被破坏 | **高** | 5 个无 `@TableField` Entity 时间字段改动 | 必须显式加 `@TableField` |
| 分页响应中时间字段缺失 | 中 | 大表 100w+ 行 `update_time` 默认值 | 迁移脚本需 `BATCH UPDATE` |
| `v3_semester` 兜底逻辑 | 低 | 已有 `is_current` 兜底迁移 | 无影响 |
| 多环境数据迁移一致性 | 高 | dev/staging/prod 三套数据迁移同步 | 写一份 Runbook + 演练 |

### 3.2 影响面（机械统一到任一命名后）

#### 方案 X：统一到 `create_time/update_time`
- **SQL 迁移**：17 张 at 表 → legacy 命名（17 个 ALTER TABLE）
- **Entity 改动**：17 个 Entity 改 `@TableField("created_at")` → `@TableField("create_time")`，Java 字段 `createdAt` → `createTime`（17 文件 × 2 字段 = 34 改）
- **Service 改动**：16 个 Service 文件 58 处 `setCreatedAt`/`setUpdatedAt` → `setCreateTime`/`setUpdateTime`（仅 at 族子集，见 §7.6.1）
- **Mapper 改动**：0（XML 不引用）
- **Frontend 改动**：10 个 TS 文件 `createdAt`/`updatedAt` → `createTime`/`updateTime`（at 族，见 §7.6.2）
- **Controller VO 改动**：部分 VO 复制 `createdAt` 字段需改 `createTime`
- **测试改动**：`M25 InvestigationTest` 不变量改写 + 各 Entity 单测字段名

#### 方案 Y：统一到 `created_at/updated_at`
- **SQL 迁移**：13 张 legacy 表 → at 命名（13 个 ALTER TABLE，含 v9 迁移脚本；`TimeSlot` 无时间列不计）
- **Entity 改动**：13 个 Entity（9 个改 `@TableField` + 4 个隐式实体**新增** `@TableField`；`TimeSlot` 无字段），Java `createTime` → `createdAt`
- **Service 改动**：15 个 Service 文件 38 处 `setCreateTime`/`setUpdateTime` → `setCreatedAt`/`setUpdatedAt`（仅 legacy 族子集，见 §7.6.1）
- **Mapper 改动**：0
- **Frontend 改动**：11 个 TS 文件 `createTime`/`updateTime` → `createdAt`/`updatedAt`（legacy 族，见 §7.6.2）
- **Controller VO 改动**：部分 VO 复制 `createTime` 字段需改 `createdAt`
- **测试改动**：同上

#### 量化总成本

| 维度 | 方案 X | 方案 Y |
|---|---:|---:|
| SQL 脚本 | 17 | 13 |
| Entity 文件 | 17 | 13 |
| Service 文件 | 16 | 15 |
| Mapper XML | 0 | 0 |
| Frontend TS | 10 | 11 |
| VO 类 | 5+ | 5+ |
| 测试 | 改 3 个 + 25+ 个回归 | 改 3 个 + 25+ 个回归 |
| **预估总改文件** | **~65** | **~55** |
| **预估工期（仅开发改动）** | **7-10 人日** | **6-8 人日** |
| **回归测试** | 全量 backend test + 关键路径 E2E | 同 |
| **数据迁移** | 17 张表 DDL + DML 演练 | 13 张表 DDL + DML 演练 |

> 注：上表"预估工期"为**开发改动**估算，**不含**生产演练 / 灰度 / DBA 演练；含完整 runbook（演练 + 维护窗口）的端到端工期见 §4.3 的 **9-11 人日**。

### 3.3 不可逆点

- **数据迁移 ALTER TABLE**：执行后无法回滚（除非有完整 DDL 备份）
- **Service 编译失败**：单向转换涉及的 setter（at 族 58 / legacy 族 38，见 §7.6.1）漏改会导致 backend 启动失败
- **Frontend 编译失败**：24 处 TS 接口漏改会导致 vue-tsc 0 错误失败
- **存量数据**：已软删除的 `created_at=NULL` 记录迁移后可能显示空值

### 3.4 测试覆盖现状

| 测试类 | 当前 | 改造后 |
|---|---|---|
| `M25TimestampNamingInvestigationTest` | 锁定 3 不变量 | 重写或删除 |
| 26 个 Entity 单测（间接） | 通过 Service 隐式覆盖 | 必须全量回归 |
| 前端构建 | 通过 | 应继续通过 |

### 3.5 性能影响

- **运行**：MyBatis 反射写列名、Jackson 序列化字段名——纯字符串替换
- **数据库**：ALTER TABLE 在大表上耗时长，需要 `pt-online-schema-change` 或维护窗口
- **应用启动**：MyBatis-Plus 启动时元数据扫描会重读 `@TableField` 注解，量级不变

### 3.6 安全影响

- **无**：纯字段名重命名不影响认证/输入校验
- **风险点**：数据迁移脚本如写错，可能误删数据

## 4. 改造方案（不推荐执行）

### 4.1 为什么"机械统一"不可取

| 反对理由 | 说明 |
|---|---|
| **零业务收益** | 当前混用**不引发任何运行故障**，纯粹是代码风格不统一 |
| **回归面极大** | 70+ 文件改动 + 数据迁移 + 全链路测试 ≈ 1.5-2 sprint |
| **存在数据迁移风险** | 任何 ALTER COLUMN 都可能引发历史数据丢失或索引失效 |
| **与 ORM 框架绑定** | MyBatis-Plus 隐式映射依赖 Java 字段名与 SQL 列名的约定，统一字段名不会让 ORM 更高效 |
| **未来新增表难以规约** | 团队成员总会有偏好，如果不靠 lint 强约束，"统一"会再次破功 |
| **M-25 InvestigationTest 已足够** | 3 个不变量锁死"不会单表内混用"——这是真正的 bug，不是命名风格 |

### 4.2 替代方案：维持现状 + 强化 InvestigationTest

如果团队**确实**认为命名风格需要收敛，推荐路径：

| 阶段 | 行动 | 工期 |
|---|---|---|
| 1 | 编码规范更新：在 `AGENTS.md` 写明"新表必须用 `created_at/updated_at`" | 0.1 人日 |
| 2 | 给 M-25 加上"按表记录"——`M25TableTimestampConventionTest` 列出每张表的命名族 | 0.3 人日 |
| 3 | 给关键写入路径（`setCreateTime` / `setCreatedAt`）加架构测试 | 0.5 人日 |
| 4 | 新表 PR 模板要求"使用 `created_at/updated_at`" | 0.1 人日 |
| 5 | 等"自然退役"：旧表随业务下线/合并逐步减少 | 长期 |
| **合计** | | **1.0 人日** |

### 4.3 真正机械统一的最小化方案（如果必须做）

#### 阶段 A：基础准备（0.5 人日）
- 全量备份所有表结构和数据
- 准备 `pt-online-schema-change` 或 `gh-ost` 工具
- 写一份 Runbook（dev/staging/prod 三步演练）

#### 阶段 B：选命名族（决策点）
- **推荐选 at 族**（更符合现代规范、流行度更高）
- 决策须由 Tech Lead + DBA + 业务 owner 共同签字

#### 阶段 C：建表脚本层（2 人日）
- 13 张 legacy 表新增 v21+ 迁移脚本（每张表独立 SQL；`TimeSlot` 无时间列不计）
- 用 `RENAME COLUMN` 一步到位
- 配套 `InformationSchema` 幂等检查

#### 阶段 D：Entity 层（1 人日）
- 9 个显式 legacy Entity 改 `@TableField` 注解 + Java 字段名
- 4 个隐式 legacy Entity（`ScheduleConflictReport`/`ScheduleRuleConfig`/`ScheduleScoreReport`/`UnscheduledTask`）新增显式 `@TableField` 锁死（`TimeSlot` 无时间字段，无需处理）

#### 阶段 E：Service + Mapper（2 人日）
- 全量 grep + 替换 `setCreateTime` → `setCreatedAt`
- 全量 grep + 替换 `getCreateTime` → `getCreatedAt`
- Controller VO 同步

#### 阶段 F：Frontend（0.5 人日）
- 11 个 TS 文件同步改 `createTime`/`updateTime` → `createdAt`/`updatedAt`（见 §7.6.2）

#### 阶段 G：测试与回归（2 人日）
- 改 `M25 InvestigationTest` 不变量
- 跑全量 backend test
- 关键 E2E 流程（登录、创建任务、自动排课、试算、修复）回归

#### 阶段 H：生产演练（1 人日）
- 维护窗口执行 + 灰度发布 + 回滚预案

#### 总计：约 **9-11 人日 + 1 个维护窗口**

## 5. 风险结论

### 5.1 总体评级：**不推荐改造**

| 维度 | 评级 | 说明 |
|---|---|---|
| 功能正确性风险 | **极高** | 70+ 文件改动 + 数据迁移 |
| 接口契约风险 | **中** | TS 接口同步改，前端可一次性同步 |
| 数据迁移风险 | **高** | RENAME COLUMN 在大表上需演练 |
| 性能风险 | **中** | ALTER TABLE 在大表上需维护窗口 |
| 安全风险 | **无** | 纯字段名重命名 |
| 回归风险 | **极高** | 涉及所有表写入路径 |
| 工期风险 | **高** | 至少 1.5-2 sprint |
| 维护收益 | **零** | 当前不构成任何运行 bug |
| **净收益** | **负** | — |

### 5.2 不实施改造的代价

- **零代价**：项目运行正常，**没有**任何已知的运行 bug 来自命名混用
- **审美代价**：代码风格不统一（但 MyBatis-Plus + 显式 `@TableField` 已能 work）

### 5.3 实施时的强制约束（如必须做）

1. **必须有 DBA 参与** + 维护窗口
2. **必须先 dev 演练** + staging 演练 + 生产灰度
3. **必须备份** + 回滚脚本
4. **必须 14 张表分批**（不要一次性改）
5. **必须全量回归测试**：backend test + frontend build + 关键 E2E
6. **必须改 InvestigationTest** 让不变量反映新状态

|---|---|
| A. 维持现状，标记 M-25 为"不修复" | **强烈推荐**：零 ROI 成本 |
| B. 维持现状 + 强化 InvestigationTest 记录命名族 | 推荐：1 人日内交付 |

| D. 机械统一到 legacy 族 | 更不推荐：legacy 是早期规范，at 是更现代规范 |

**最终建议**：选 **A** 或 **B**。把 M-25 视为"已收敛的历史债务"，而非"待修复 bug"。

- DBA 资源
