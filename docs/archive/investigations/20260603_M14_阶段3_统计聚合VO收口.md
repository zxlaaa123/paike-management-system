## 1. 调查结论

### 1.1 调用方核验（grep 7 个方法名）

- 5 个统计方法（`teacherWorkload`/`classroomUtilization`/`classBalance`/`planOverview`/`dashboardStats`）**仅** `ScheduleStatisticsController` 调用；`dashboardStats` 内部调 `planOverview`。
- 2 个 refresh 端点（`refreshPlanSummary`/`refreshPlanRisks`）仅各自 controller 自身，**无其他 Java 调用方**。
- `src/test` 下**无** `ScheduleStatisticsServiceTest`（蓝图属实）；refresh 服务方法 `getPlanSummary`/`getPlanRisks` 签名不动，无关联测试需改。

### 1.2 前端消费方

- `frontend/src/api/scheduleStatistics.ts`：`TeacherWorkloadItem`(9)/`ClassroomUtilizationItem`(9)/`ClassBalanceItem`(11)/`PlanOverview`(17)/`DashboardStats`(4)。
- 两个 refresh：`v4ScheduleAnalysisApi.ts:157/185` 已声明 inline 类型；消费方 `ScheduleAnalysisDetail.vue:41`、`ScheduleRiskCenter.vue:103` 均**只 `await` 后 `fetchData()`，不读返回体字段**。
- 预期前端零改动。

### 1.3 蓝图/前端漏算的 2 处（以实际 `Map.put` 为准）

1. **`teacherWorkload` 实际 put 10 个 key**：`ScheduleStatisticsService.java:57` put 了 `maxContinuousPeriods=0`，此后全程无更新（恒 0），前端不读。蓝图 §2「9 字段」漏算。
2. **`classBalance` 实际 put 12 个 key**：`:169` 把中间产物 `dailyPeriods`（动态键 Map）put 进 row 随结果输出，前端只读派生的 `day1-5Periods`、不读 `dailyPeriods`。蓝图「11 字段」漏算。
3. **`planOverview` 的 best/applied 共 8 字段是条件 put**（`:240`/`:253` 的 `if` 块内）：无最佳/无应用方案时原 Map 根本不含这些 key（非 null）；前端 TS 声明为 `number|null`（预期 key 恒存在）。

## 3. VO 字段表（按 LinkedHashMap 插入序）

放 `com.paike.scheduler.service.vo`，`@Data @NoArgsConstructor @AllArgsConstructor`，普通 POJO（保留 null 序列化，不加 NON_NULL）。

### TeacherWorkloadVo（10）
`teacherId:Long, totalPeriods:Integer, dailyPeriods:Map<Integer,Long>, maxDailyPeriods:Integer, maxContinuousPeriods:Integer, courseCount:Integer, classCount:Integer, teacherName:String, department:String, evaluation:String`

> 注意原插入序：teacherId/totalPeriods/dailyPeriods/maxDailyPeriods/maxContinuousPeriods/courseCount/classCount（首循环 computeIfAbsent put 占位），第二循环再 put teacherName/department（覆盖 courseCount/classCount 为 size）/maxDailyPeriods/evaluation。LinkedHashMap 中**首次 put 决定顺序**，故 teacherName/department/evaluation 排在末尾。

### ClassroomUtilizationVo（9）
`roomId:Long, roomName:String, building:String, capacity:Integer, roomType:String, usedPeriods:Long, totalPeriods:Integer, utilizationRate:BigDecimal, evaluation:String`

### ClassBalanceVo（12）
`classId:Long, dailyPeriods:Map<Integer,Long>, totalPeriods:Integer, className:String, studentCount:Integer, balanceScore:BigDecimal, evaluation:String, day1Periods:Long, day2Periods:Long, day3Periods:Long, day4Periods:Long, day5Periods:Long`

> 原插入序：首循环 put classId/dailyPeriods/totalPeriods；二循环 put className/studentCount/balanceScore/evaluation/totalPeriods(覆盖)/day1-5Periods。

### PlanOverviewVo（17）
恒存在(9)：`semesterId:Long, totalPlans:Integer, draftPlans:Long, appliedPlans:Long, abandonedPlans:Long, hasAppliedPlan:Boolean, formalScheduleCount:Long, totalUnassignedTasks:Integer, totalConflicts:Integer`
best 块(4)：`bestPlanId:Long, bestPlanName:String, bestPlanScore:BigDecimal, bestPlanStrategy:String`
applied 块(4)：`appliedPlanId:Long, appliedPlanName:String, appliedPlanScore:BigDecimal, appliedPlanAppliedAt:LocalDateTime`

> 原插入序：semesterId/totalPlans/draftPlans/appliedPlans/abandonedPlans → (best 块) → hasAppliedPlan → (applied 块) → formalScheduleCount/totalUnassignedTasks/totalConflicts。VO 字段声明序照此。

### DashboardStatsVo（4）
`teacherCount:Long, classCount:Long, classroomCount:Long, v3Overview:PlanOverviewVo`

### RefreshPlanSummaryVo（3）
`planId:Long, refreshed:Boolean, message:String`

### RefreshPlanRisksVo（3）
`planId:Long, riskCount:Integer, message:String`

## 4. 聚合改法（不改算法/数值）

- `teacherWorkload`：`Map<Long, TeacherWorkloadAcc>`（私有静态内部累加器，持 `Set<Long> courseIds/classIds` + `Map<Integer,Long> dailyPeriods` + `int totalPeriods`），第二循环填关联信息 + `courseIds.size()` → build VO。删 `longSet`/`integerLongMap`（:418-426）。
- `classBalance`：同构累加器（`dailyPeriods` + `totalPeriods`）。
- `classroomUtilization`/`planOverview`/`dashboardStats`：扁平，直接构造 VO。
- BigDecimal 排序：`classroomUtilization` 按 `utilizationRate` 降序、`classBalance` 按 `balanceScore` 升序——改用 VO getter 比较。
