# 20260528 C-07/C-08 事务边界调查

## 结论

`C-07`、`C-08` 均为部分成立，不建议当前改生产代码。

原因：

- `AutoScheduleService.run()` 和 `V3ScheduleGenerateService.generate()` / `generateMultiple()` 都是入口级 `@Transactional`。
- 这表示它们的编排、写入和收尾步骤共享同一事务边界。
- 但目前没有接口级压测、数据库慢日志或回滚放大证据，不能把“事务包得大”直接定成可修复缺陷。
- `generateMultiple()` 只是循环调用 `generate(single)`，不是额外再包一层 TransactionTemplate，也不是死分支。

## 源码证据

目标文件：

- `backend/src/main/java/com/paike/scheduler/service/AutoScheduleService.java`
- `backend/src/main/java/com/paike/scheduler/service/V3ScheduleGenerateService.java`

关键点：

- `AutoScheduleService.run()` 直接标注 `@Transactional(rollbackFor = Exception.class)`。
- `run()` 内部先清理，再加载任务，再创建批次，再安排任务，再收尾。
- `V3ScheduleGenerateService.generate()` 直接标注 `@Transactional(rollbackFor = Exception.class)`。
- `generate()` 内部会插入方案、插入明细、重算分数、写日志。
- `generateMultiple()` 也标注事务，但本质是逐个调用 `generate(single)`。

## 已执行验证

新增测试：

- `backend/src/test/java/com/paike/scheduler/service/TransactionBoundaryInvestigationTest.java`

验证内容：

- `AutoScheduleService` 仍是顶层事务编排，没有 `TransactionTemplate` 分层。
- `V3ScheduleGenerateService` 的 `generate()` 和 `generateMultiple()` 都保留入口事务，且 `generateMultiple()` 内部直接复用 `generate(single)`。
- `scoreService.rescore(plan)` 位于 `generate()` 事务链路内。

## 现阶段判断

可以确认的是：

- 事务边界较大。
- 这是设计事实，不是自动等于 bug。

不能确认的是：

- 还没有数据证明它已经造成慢事务、锁等待或回滚放大。
- 还没有压测结果支持拆事务一定更好。

## 建议

`C-07` / `C-08` 先保持“部分成立，暂不修复生产代码”。

后续只有在以下任一情况成立时，再开修复分支：

1. 接口压测显示事务时间明显偏长。
2. 数据库慢日志显示这些方法是热点。
3. 回滚场景下的重试/失败成本明显过高。

如果要继续，下一步应优先补压测或大批量数据基准，而不是先重构事务。
