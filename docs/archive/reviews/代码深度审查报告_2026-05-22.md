## P0 — 必须修

### P0-1. AutoScheduleService.saveSchedule 没有写入 semesterId，导致同批次内冲突检测失效

**位置**：`backend/src/main/java/com/paike/scheduler/service/AutoScheduleService.java:400-414`

```java
private void saveSchedule(TeachingTask task, TimeSlot slot, Classroom room, Long batchId) {
    Schedule schedule = new Schedule();
    schedule.setTeachingTaskId(task.getId());
    schedule.setCourseId(task.getCourseId());
    schedule.setTeacherId(task.getTeacherId());
    schedule.setClassId(task.getClassId());
    schedule.setTimeSlotId(slot.getId());
    schedule.setClassroomId(room.getId());
    schedule.setSourceType(ScheduleSourceType.AUTO.getCode());
    schedule.setBatchId(batchId);
    schedule.setDeleted(0);
    // ❌ 没有 schedule.setSemesterId(task.getSemesterId());
    ...
    scheduleMapper.insert(schedule);
}
```

而下游 `ScheduleConflictService.checkConflict` 在第 111 行和 159 行都做了：
```java
.eq(task.getSemesterId() != null, Schedule::getSemesterId, task.getSemesterId())
```

**后果**：在 `AutoScheduleService.run` 的事务里，第一条任务的 schedule 写进表里时 `semester_id = NULL`，第二条任务调 `checkConflict` 时按 `semester_id = X` 过滤，**完全看不到刚插进去的那条**。同班 / 同教师 / 同教室在同一批次内会被排进同一个 timeSlot — 仅靠 `uk_schedule_teacher_slot / uk_schedule_class_slot / uk_schedule_classroom_slot` 唯一索引在 INSERT 时报 `DuplicateKeyException`。但 AutoScheduleService 把整个 run 包在 `@Transactional` 里，**`DuplicateKeyException` 会让整个批次回滚**。

**修复**：`saveSchedule` 里加 `schedule.setSemesterId(task.getSemesterId());`。同时 v6 唯一索引应允许 `semester_id IS NULL` 作为可重复值（当前的 `uk_schedule_teacher_slot (time_slot_id, teacher_id, deleted)` 没把 semester_id 纳入键，是另一种麻烦：跨学期排课不能在同一 timeSlot）。

### P0-2. ScheduleConflictService 在编辑场景下漏掉 excludeScheduleId，导致每日上限误报

**位置**：`backend/src/main/java/com/paike/scheduler/service/ScheduleConflictService.java:184-188`

```java
Map<String, Long> dailyCounts = scheduleMapper.selectDailyConflictCounts(
        teacherId, classId, task.getCourseId(), daySlotIds, task.getSemesterId(), null);
```

`selectDailyConflictCounts` 的 SQL（`ScheduleMapper.xml:37-59`）也没有 `excludeScheduleId` 的过滤入参，最后一个 `null` 实际上是 `planId`。

**后果**：当用户**编辑**一条排课记录、新时段还在同一天时，被编辑的那条会被计入"教师每日上限 / 班级每日上限 / 同课同日"三类软规则的计数中。当 `TEACHER_MAX_DAILY_SLOTS = 1`、当前任务原本就排在那天时，任何同日内的微调都会被拒绝 — 这条已经在 reports/ 历史 bug 文档里报过两次，但 daily-counts 分支仍未修复（行 113 的 baseWrapper 已经 ne 了 excludeScheduleId，但 daily-counts 分支没有）。

**修复**：给 `selectDailyConflictCounts` 增加 `excludeScheduleId` 参数，SQL 里加 `AND (#{excludeScheduleId} IS NULL OR s.id <> #{excludeScheduleId})`，Service 层把 `excludeScheduleId` 透传下去。

### P0-3. 前端把 httpOnly Cookie 设计完全废掉

**位置**：`frontend/src/utils/request.ts:65-69` + `frontend/src/stores/auth.ts:21-24, 31-35`

`AuthController.login` 后端做了正确的事：JWT 写入 `paike_token` httpOnly Cookie，外加 `XSRF-TOKEN` 双 token CSRF。但是：

```ts
// auth.ts
function setToken(newToken: string) {
  token.value = newToken
  localStorage.setItem(TOKEN_KEY, newToken)  // ❌ 把真 JWT 存进 localStorage
}

// request.ts
const token = localStorage.getItem(TOKEN_KEY)
if (token) {
  config.headers.Authorization = `Bearer ${token}`   // ❌ 同时以 Bearer 发送
}
```

加上 `AuthInterceptor.preHandle:31-46`：
```java
// 仅对 cookie 认证的状态变更请求强制 CSRF
if (cookieAuth && stateChanging) { ... CSRF check ... }
```

**三连击带来的后果**：

1. JWT 同时存在 httpOnly Cookie 和可被任意 JS 读取的 localStorage 里，httpOnly 保护**形同虚设**。任何 XSS（包括第三方依赖污染、Element Plus 模板字符串注入）拿到 `localStorage.getItem('TOKEN_KEY')` 即可。
2. 攻击者拿到 token 后，可以走 `Authorization: Bearer ...` 路径，**完全绕过 CSRF 双 token 校验**（CSRF 检查只对 cookieAuth 触发）。
3. 后端注释 `// 兼容旧版` + 前端注释 `// localStorage 中的 token 仅作为 UI 登录状态标志` 都和实际代码相悖。

**修复**：
- `setToken` 只存一个布尔 / 用户名做 UI 状态判断，不要存真 token。
- `request.ts` 删掉 `Authorization` 头注入，纯走 cookie。
- 或者反过来：完全去掉 cookie 模式，恢复纯 Bearer + 服务端 token 黑名单方案。两条路二选一，**不能并存**。

### P0-4. SchedulePlanService.applyPlan 在 apply 时不做新一轮冲突检测

**位置**：`backend/src/main/java/com/paike/scheduler/service/SchedulePlanService.java:263-348`

`applyPlan` 把方案明细插入 `schedule` 表为正式课表，但**只验证了 period 奇偶配对**（`validatePeriodPair`），不验证：
- 教师 / 班级 / 教室与既有 schedule 是否冲突（即使之前的 APPLIED 已被软删，并发应用两个方案时仍可能挤入同一 slot）
- 班级人数 vs 教室容量
- 教室类型匹配
- 教师禁排时间

只依赖 `refreshPlanConflictState` 之前留下的 `conflict_flag` —— 这是一个**会过时的快照字段**。如果方案生成后教师设了新的禁排时间、教室停用，apply 会照单全插，仅靠 v6 三条 unique key 兜底硬资源冲突，软约束（容量、类型、禁排）直接漏过。

**修复**：apply 前调 `refreshPlanConflictState` 强制重算一遍，若 `conflictCount > 0` 默认拒绝（提供 `force=true` 开关给运维）。

## P1 — 业务正确性

### P1-1. ScheduleController.create 用了当前学期，而 checkConflict 用了 task.semesterId

**位置**：`ScheduleController.java:91-100`

```java
String conflict = conflictService.checkConflict(
    form.getTeachingTaskId(), form.getTimeSlotId(), form.getClassroomId(), null);
// checkConflict 内部以 task.getSemesterId() 过滤已有 schedule
...
schedule.setSemesterId(semesterService.getCurrentSemester().getId());
```

冲突按 `task.semesterId` 检查，但写入的是 `currentSemester.id`。若教学任务属于一个非当前学期（历史/未来），冲突检测查的是 A 学期，落库挂到 B 学期。

**修复**：统一以 `task.getSemesterId()` 为准（如果空则回落到 current），两处使用同一个值。

### P1-2. AutoScheduleService 的 daily-limit / sameDay 检查不带 semester_id

**位置**：`AutoScheduleService.java:356-398`

`checkTeacherDailyLimit / checkClassDailyLimit / hasSameCourseSameDay` 都只用 `time_slot_id IN (该天的 slot ids)`，**没有按 semester_id 过滤**。多学期数据共存时，A 学期老师在 B 学期已排满会被算进 A 学期的上限里，软规则越严越乱套。

**修复**：把 `semesterId` 透传进这三个方法，加 `eq(Schedule::getSemesterId, semesterId)`。

### P1-3. SchedulePlanService.applyPlan 把旧 APPLIED 改成 DRAFT 后，可被 delete() 直接物理摧毁

**位置**：`SchedulePlanService.java:81-92, 284-298`

```java
public void delete(Long id) {
    ...
    if (!"DRAFT".equals(plan.getStatus())) {
        throw new BusinessException("只能删除草稿方案");
    }
    ...
    planMapper.deleteById(id);
}
```

而 applyPlan 在切换新方案时把旧 APPLIED 改成 `"DRAFT"`，前端从一个曾经被使用过的应用方案进入"草稿"列表后误删 → 历史方案直接消失（虽然 schedule 行是软删，但方案本身没了，**无法 rollback**）。

**修复**：把旧 APPLIED 改成 `SUPERSEDED` 这种独立状态，并在 delete() 里禁止删除 SUPERSEDED。

### P1-4. SchedulePlanService.rollbackPlan 调用 applyPlan(id) 时把自身列为 oldAppliedPlans

**位置**：`SchedulePlanService.java:439-453` → `applyPlan:284-298`

如果当前方案就是 APPLIED 状态，rollbackPlan → applyPlan → `oldAppliedPlans` 包含自己 → 软删自己的 schedule 行 → 然后又重新 INSERT 一模一样的行。事务里能跑通，但：
- 多产生一条更新历史，浪费 IO
- 如果在 INSERT 阶段 unique 索引判定 `deleted=1` 的行还冲突（v6 唯一键含 `deleted` 字段，理论上 `1+1` 也会冲突），会失败

**修复**：在循环里跳过 `oldPlan.getId().equals(plan.getId())`，或者把 rollback 写成独立分支不复用 applyPlan。

### P1-5. ScheduleConflictService.checkConflict 软规则只看 plan_id IS NULL 的记录

**位置**：`ScheduleConflictService.java:184-188` + `ScheduleMapper.xml:51-58`

```xml
<choose>
    <when test="planId != null">AND s.plan_id = #{planId}</when>
    <otherwise>AND s.plan_id IS NULL</otherwise>
</choose>
```

Service 层永远传 `null` 给 planId，所以日上限统计只看"非方案产生"的正式排课。如果一个 APPLIED 方案产生了大量 schedule（plan_id != NULL），这些既不计入日上限也不计入同课同日。
- 手动新增一条时，老师可能已经被 APPLIED 方案排满 8 节课，再加 1 节也不报错。

**修复**：要么传当前 currentSemester 对应的 applied plan 的 id，要么把统计改成 `(plan_id IS NULL OR plan_id IN (applied plans))`。

### P1-6. AuthService.login 在密码正确后才检查 status，泄露停用账号枚举

**位置**：`AuthService.java:49-61`

```java
if (!passwordOk) throw "用户名或密码错误";
if (!Integer.valueOf(1).equals(user.getStatus()))
    throw "账号已停用，无法登录";
```

合法密码 + 停用账号给出 `"账号已停用"`，攻击者撞库时只要看到这个就能锁定有效账号 + 有效密码。

**修复**：把两个错误合成同一条 `"用户名或密码错误"` 返回，停用状态写日志但不告诉前端。

## P2 — 代码质量

### P2-1. SchedulePlanService.applyPlan 与 applySimulationPlan 重复 60+ 行

`applyPlan(Long id)` 和 `applySimulationPlan(Long id) → applyPlanInternal(plan)` 几乎完全重复（行 263-348 vs 350-436）。两份代码各自维护，已经看到细节漂移（applyPlan 里有 status 校验链，applyPlanInternal 没有）。

**修复**：抽出 `private applyPlanInternal(SchedulePlan plan)` 单点，apply / applySimulation 只负责前置校验。

### P2-2. ScheduleConflictService 的反序列化 reasonTag 协议依赖字符串前缀

`tagReason / stripReasonTag / extractReasonType` 用 `"[" + type + "]" + message` 编码。如果 message 本身包含 `[xxx]`，extract 误判。当前 message 都是固定中文，能跑，但脆。

**修复**：返回结构化对象 `ConflictResult { type, message }`，让上层显示文本和 type 解耦。

### P2-3. ScheduleController.ScheduleForm 只有 @Getter 没有 @Setter

`@RequestBody` 反序列化在 Jackson 默认配置下能通过字段访问拿到，但是隐式假设。把 `@Setter` 或者 `@Data` 加上更稳。

### P2-4. WebMvcConfig 注释和实际路径冲突

注释里说 `V3 高级排课功能使用 /v3/ 前缀`，但所有 v3 控制器都是 `@RequestMapping("/api/v3/...")`。注释会误导新人在 SecurityConfig / Interceptor 调试时找错地方。

**修复**：删掉注释或改写实际。

### P2-5. SemesterSchemaInitializer 用 JdbcTemplate 做 schema 演进

11 个 `ensureXxx` 方法、几百行 `ALTER TABLE / CREATE TABLE IF NOT EXISTS`，与 `application.yml` 里禁用的 Flyway + 多个 `schema-locations` 共存，**三套 schema 演进机制混在一起**：
- `schema.sql` 系列（`spring.sql.init.schema-locations`）
- `migration/V1__baseline.sql`（Flyway 风格但 Flyway 是关闭的）
- `SemesterSchemaInitializer`（Java-driven）

哪个先跑、哪个赢、failure 时是否一致都没明确文档。一旦上线，下一次启动可能跑出和开发机不一样的表结构。

**修复**：统一回 Flyway，把这 300 行 Java 翻成 V2/V3 迁移脚本。

### P2-6. AuthInterceptor 每请求一次 DB 查 user.status

`AuthInterceptor.preHandle:64-65` 每个被保护的请求都做一次 `sysUserMapper.selectOne(...).eq(id)`。10 个用户并发刷列表页就是几十个无用查询。`SysUser.status` 变化频率极低，加 Caffeine / Redis 缓存收益明显。

### P2-7. RateLimiterService.cleanupExpiredKeys O(N) 每次登录调用

`cleanupExpiredKeys` 在每次 `isRateLimited` 时遍历整张 ConcurrentHashMap。低并发没事，登录爆破时这个清理本身会拖慢登录路径。改成定时任务（`@Scheduled` 每分钟跑一次）即可。

### P2-8. useCrudForm.openAdd 浅拷贝 formDefaults

```ts
function openAdd() {
  ...
  Object.assign(form, options.formDefaults)
  ...
}
```

`formDefaults` 里如果有嵌套对象（数组、对象），新建 dialog 修改这些字段会污染 `formDefaults` 本身，下次 openAdd 拿到的就是上次留下的脏数据。建议用 `structuredClone(options.formDefaults)`，和下面 `openEdit` 一致。

## 安全相关额外提醒

1. **CORS allow-credentials 默认 false**：`application.yml:48` 默认 `false`，前端在 dev 模式如果走真正的 cross-origin，cookie 不会被携带。Vite 用 proxy 转发掩盖了这个问题，部署架构变化时会暴露。
2. **CSRF cookie sameSite=Strict + 跨 origin**：dev 模式下 `:8090` 写的 `XSRF-TOKEN` cookie 在 `:5173` 上的 JS 是读不到的（不同 origin），CSRF 头永远是空。一旦后端 `cookieSecure=true` 且 sameSite 不变，CSRF 链就废了。
3. **JWT logout 不撤销**：logout 只清前端 cookie；同一 JWT 在过期前仍然可被任何持有副本的客户端使用。需要服务端引入 token 黑名单（Redis）或者短 token + refresh token。
4. **AdminUserInitializer 把随机密码打到 stdout**：进程被 systemd 接管时 stdout 会进入 journal —— 注释里说"不进 logs/"但没说不进 systemd journal。生产部署文档里需要明确这一点。

## 新增 P0

### P0-5. SchedulePlan / SchedulePlanItem / Semester 是物理删除，所有 deleteById 直接抹掉数据

**位置**：
- `entity/SchedulePlan.java`（无 `@TableLogic`，无 `deleted` 字段）
- `entity/SchedulePlanItem.java`（同上）
- `entity/Semester.java`（同上）
- 调用点：`SchedulePlanService.delete:91 planMapper.deleteById(id)`、`V3ScheduleGenerateService.prepareDraftTarget:200 planMapper.deleteById(draft.getId())`、`SemesterService.delete:123`

`SysUser` 和 `Schedule` 都加了 `@TableLogic`，但 plan 三件套和 semester 没加。结果：
- `SchedulePlanService.delete()` 把 plan 行 + plan_item 行 + explainService.clearPlanArtifacts (logs / unassigned / score detail) 一并物理摧毁。
- `V3ScheduleGenerateService` 在 `overwriteDraft=true` 时，会**物理删除同名 DRAFT 草稿**（包括所有日志、未排任务记录、评分明细）。
- 结合 P1-3：APPLIED → DRAFT 转换 + DRAFT 可删 = 历史方案的完整轨迹（生成日志、冲突详情、调整日志的 plan_id 字段悬空）全部不可恢复。

更糟的是 `schedule_adjust_log` 表里的 `plan_id` 是无外键的普通 BIGINT —— 整个 schema 都没 FOREIGN KEY，物理删除 plan 之后所有引用它的日志变成悬空指针，且没有任何告警。

**修复**：给 plan 三件套和 semester 都加 `@TableLogic` 和 `deleted` 列；migration 里给现有表加 `ALTER TABLE schedule_plan ADD COLUMN deleted TINYINT NOT NULL DEFAULT 0`。

### P0-6. 锁定功能(V4ScheduleLockService) 只能创建锁定记录，没有任何地方在写入前检查锁定状态

**位置**：`V4ScheduleLockService.java:38-94` 仅 lock / unlock；下游消费者**零**。

我用 grep 找过 `ScheduleLockedItem` 在所有 Service 的使用情况：

```
ScheduleLockedItemMapper / lockedItemMapper 在 9 个文件出现，但
- V4ScheduleAdjustmentService（调整正式课表）：完全不引用 lockedItemMapper
- V4ScheduleReplanService（局部重排）：不引用
- SchedulePlanService.adjustPlanItem（调整方案明细）：不引用
- ScheduleController.delete（删除排课）：不引用
- AutoScheduleService（自动排课，可清空全部）：不引用
```

仅 V5 系列 (Simulation / ConsistencyCheck / CandidatePosition / RuleEvaluation) 会读 lockedItem 数据 —— 但那是用来生成"修复试算"的候选位置时**过滤**掉锁定项，**没有人在常规调整链路上挡**。

**后果**：用户在 "课程锁定管理" 页面锁定了一节课程，期望它在自动排课 / 调整 / 局部重排里不被动；但：
- 自动排课 `clearAllSchedule=true` 直接 delete schedule 表所有行，锁定记录变成幽灵。
- V4 调整正式课表直接 update 锁定的 schedule.classroom_id / time_slot_id。
- adjustPlanItem 直接 update planItem 字段。

锁了等于没锁。

**修复**：在 `V4ScheduleAdjustmentService.applyToSchedule`、`SchedulePlanService.adjustPlanItem`、`ScheduleController.delete`、`AutoScheduleService` 全部清空入口处加 `lockedItemMapper.selectOne(...active_flag=1)` 校验，命中即拒绝。

### P0-7. V4ScheduleLockService.lock 双锁定竞态：两次 SELECT 同时返回 null，两条 active_flag=1 行同时落库

**位置**：`V4ScheduleLockService.lock:47-59`

```java
ScheduleLockedItem existing = findActiveLock(...);
if (existing != null) {
    throw new BusinessException("该课程已处于锁定状态");
}
ScheduleLockedItem record = new ScheduleLockedItem();
...
scheduleLockedItemMapper.insert(record);
```

`schedule_locked_item` 表 schema（`SemesterSchemaInitializer:253-276`）**没有任何唯一约束**，仅有 4 个普通 index。两个用户同时点锁定，两个 SELECT 都返回 null，两个 INSERT 都成功。然后 `listPlanLocks` 显示同一目标两条锁定，unlock 时按 LIMIT 1 只能取消一条，剩下那条变成"幽灵锁"，前端永远显示已锁定但 unlock 按钮无效。

ensurePassBeforeApply 读的是上次 refreshPlanConflictState 留下的 conflict_flag 快照，但**apply 调用本身先做 ensure，后做 refresh**——意味着 apply 用旧快照判过则放行，然后才更新 conflict_flag。如果在两次调用之间真实数据已经变化（其他用户改了 schedule、locked_item、rule_config），ensure 用旧数据通过，refresh 算出新 conflict，**但 apply 已经走过 gate 了**。

行 330 `if (plan.getConflictCount() > 0)` 是兜底，但 ensurePassBeforeApply 检查的不仅是 conflict count，还有 BLOCKING 级别风险——这些不直接进 conflict_count 字段。

**修复**：调用顺序反过来：先 refresh + rescore，再 ensurePassBeforeApply，保证 gate 看到的是最新状态。
