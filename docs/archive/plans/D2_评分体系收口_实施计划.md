## 0. TL;DR

**D2 的原始诉求**：让"为什么这个方案 90.13 分"可解释——每个维度的语义、量纲、上下界、公式清楚，能从结果反推贡献。

**摸清现状后的核心发现**：评分体系**双轨制**——同一规则码（如 `CLASSROOM_UTILIZATION`）在两个地方用了**完全不同**的公式。

| 规则码 | 在线 `scoreCandidate`（贪心选谁） | 离线 `rescore`（决定 90.13） |
|---|---|---|
| CLASSROOM_UTILIZATION | `studentCount / capacity` 利用率 (0..N) | 教室使用次数方差 (0..1) |
| CLASS_DAILY_BALANCE | `1 / (1 + 同班当天已排数)` (0..1] | 班级日数方差归一 (0..1) |
| TEACHER_DAILY_LOAD | 同结构 (0..1] | 教师日数方差归一 (0..1) |
| COURSE_DISTRIBUTION | `存在同班同课同日 ? 0 : 1` (二值) | `重复天数 / 总天数` (0..1) |
| CONTINUOUS_PERIOD_LIMIT | `相邻 ? 0 : 1` (二值) | 教师每日连续链平均数 (0..1) |
| MORNING_THEORY_PRIORITY | `理论 && periodNo≤2 ? 1 : 0` (二值) | 全部下午课占比（不分课程类型） (0..1) |

外部看 totalScore=90.13，但贪心循环优化的根本不是这 6 个公式——是另一套同名异义指标。这就是"说不清每分怎么来"的根。

**收口的目标不是合并两套**（它们用途不同：在线选下一个候选 vs 离线评估整体方案），而是：
1. **文档化每维度**：语义 / 量纲 / 范围 / 何处使用 / 公式
2. **拆分集中**：把散在两个 service 私有方法里的 12 个评分函数提到一个 `ScoringFunctions` 工具类（在线 6 个 + 离线 6 个），文件名直接昭告身份
3. **离线 detailMessage 升级**：让 `schedule_score_detail.detail_message` 包含"扣分依据 + 量纲"，能 1:1 复盘
4. **回归基线测试**：对一个固定迷你 plan 锁定 90.13 拆分明细，未来公式动了一眼能看出来

**建议方案**：3 个 commit，约 8-10 小时。**不做**双轨合并，**不做**ScoreDimension 接口抽象。

## 1. 现状（基于代码核实）

### 1.1 两套评分公式所在位置

**在线（贪心循环里挑候选）**：`V3ScheduleGenerateService.java`
- `scoreCandidate(task, slot, room, items, refData)` — L413-434：6 个 `weight * scoreXxx` 累加
- `classroomUtilizationScore` — L436-442
- `balanceScore` — L444-450（CLASS_DAILY_BALANCE 和 TEACHER_DAILY_LOAD 共用）
- `courseDistributionScore` — L452-458
- `continuousLimitScore` — L460-466
- `morningPriorityScore` — L468-471
- `weight(refData, ruleCode)` — L473-475：从 `refData.weightMap()` 取 BigDecimal 转 double
- 稳定 tie-breaker：`max(0, 100 - sortOrder) * 0.0001D`（L432）

**离线（事后扣分写库）**：`ScheduleScoreService.java`
- `rescore(plan)` — L75-114：清旧 detail → 按 rule 累加 → `totalScore = clamp(100 + Σscore, 0, 100)` → 写库
- `calculateMetric(rule, context)` — L132-151：switch ruleCode 分发硬/软
- `buildHardMetric` — L153-159：`score = -weight * violationCount`
- `buildSoftMetric` — L161-170：`score = -weight * min(1, factor)`，detailMessage 含"偏差 N%"
- `buildScoreContext` — L172-215：一次性聚合 12 个统计量
- 6 个 penalty 实现：
  - `variancePenalty` — L241-259（班级/教师日均衡共用）
  - `duplicateCoursePenalty` — L261-271
  - `continuousPenalty` — L273-299
  - `classroomUtilizationPenalty` — L301-311
  - `morningPriorityPenalty` — L313-319

### 1.2 90.13 是怎么算出来的

跑 V3 BALANCED → `normalizeStrategyType` 把未知 strategy 映射成 default（`COMPREHENSIVE`，见 `getDefaultRules` switch default 分支）。COMPREHENSIVE 的 11 条规则：

| 规则码 | 类型 | 权重 |
|---|---|---|
| TEACHER_TIME_CONFLICT | HARD | 100 |
| CLASS_TIME_CONFLICT | HARD | 100 |
| CLASSROOM_TIME_CONFLICT | HARD | 100 |
| TEACHER_UNAVAILABLE | HARD | 90 |
| CLASSROOM_CAPACITY | HARD | 80 |
| CLASSROOM_TYPE_MISMATCH | HARD | 80 |
| CLASS_DAILY_BALANCE | SOFT | 30 |
| TEACHER_DAILY_LOAD | SOFT | 30 |
| CONTINUOUS_PERIOD_LIMIT | SOFT | 25 |
| COURSE_DISTRIBUTION | SOFT | 25 |
| CLASSROOM_UTILIZATION | SOFT | 20 |

> 注：COMPREHENSIVE 默认 **没有** MORNING_THEORY_PRIORITY，但在线 `scoreCandidate` 仍然会调用 `weight(refData, "MORNING_THEORY_PRIORITY")`，从 weightMap 拿不到就走默认 0 ——这是一个**隐式失效**，需要文档记一笔。

330 scheduled / 2 unscheduled / 0 conflict → 硬规则全部 0 违规 → 罚分仅来自 5 个软规则（无 MORNING）。
- 90.13 ⇒ 软罚分总和 -9.87 分，分布到 5 维。

**目前没法快速答出每维各扣多少**——这正是 D2 要解决的。

### 1.3 谁在调谁

- 在线 `scoreCandidate` 只被 `findBestCandidate` 调（D1.2 Commit 4 拆出来的）
- 离线 `rescore` 在两处被调：
  1. `V3ScheduleGenerateService.generate()` 生成完调一次
  2. 手动重打分接口（`/api/v3/schedule-score/rescore`，需 codegraph 确认）

权重数据流：
- DB 表 `schedule_rule_weight`（按 `semester_id + strategy_type` 分行）
- `SchedulingReferenceLoader.loadForV3Generate` 一次性灌进 `SchedulingReferenceData.weightMap()`（Map<String, BigDecimal>）
- 在线/离线**读的是同一张表**，只是字段语义被两套公式错配

## 2. 范围 & 非范围

### 范围 ✅
- 文档化每个维度（含两套公式的差异声明）
- 抽 `ScoringFunctions` 工具类（在线 6 + 离线 6 = 12 个静态纯函数 + 1 个常量 doc 表）
- 升级 `schedule_score_detail.detail_message` 内容，让它信息密度更高（量纲、计算依据、阈值）
- 回归基线锁定测试：固定一组 plan items，断言 `rescore` 输出每维度的扣分

### 非范围 ❌
- **不合并**在线/离线评分（它们用途确实不同：贪心需要"下一个候选好坏"，离线需要"整张表多好"）
- **不抽** `ScoreDimension` interface / 策略模式 / 工厂——只有 6 维度且变化频率低，YAGNI
- **不改**数据库表结构（不加新字段；detailMessage 是 varchar(500) 装得下扩展信息）
- **不改**权重读取链路（refData.weightMap 已经统一了）
- **不动**前端展示（前端目前已经能列 `score_detail` 列表，detailMessage 升级后自然更好看）

## 4. Commit 切分

### Commit 1：文档化 + ScoringDimensions 常量表（约 2-3h）
**为什么**：动代码前先把"双轨制"事实写下来，让自己和未来读者不被"同名规则"误导。

**做什么**：
- 新建 `backend/src/main/java/com/paike/scheduler/service/scheduling/ScoringDimensions.java`：一个 record 数组常量，每条含 `code / displayName / formulaOnline / formulaOffline / range / usage`。纯 doc 不被代码读
- 在 `V3ScheduleGenerateService.scoreCandidate` 和 `ScheduleScoreService.calculateMetric` 上方加 javadoc 链接到该常量
- 不动任何算法

**验收**：编译通过；冒烟两条基线不变（V4 253/254 + V3 90.13/330/2）

**风险**：基本无（纯文档）

---

### Commit 2：抽 ScoringFunctions 工具类（约 4-5h）
**为什么**：12 个评分私函数散在两个 service 私有作用域里，长此以往谁也不敢碰。集中后单文件可阅读 + 可单测 + 可对比"同名两公式"。

**做什么**：
- 新建 `backend/src/main/java/com/paike/scheduler/service/scheduling/ScoringFunctions.java`
- 把 V3 的 5 个在线 score* 方法搬过来，重命名为 `candidateClassroomUtilization` / `candidateBalance` / `candidateCourseDistribution` / `candidateContinuousLimit` / `candidateMorningPriority`
- 把 ScheduleScoreService 的 6 个 penalty 方法搬过来，重命名为 `penaltyVariance` / `penaltyDuplicateCourse` / `penaltyContinuous` / `penaltyClassroomUtilization` / `penaltyMorningPriority`（共用方差的 variance 单独函数）
- 全部 `public static` 纯函数
- V3.scoreCandidate 改调用 `ScoringFunctions.candidateXxx(...)`；ScheduleScoreService.buildScoreContext 改调用 `ScoringFunctions.penaltyXxx(...)`
- 行为零变更

**验收**：
- `mvn -DskipTests compile` 通过
- 跑 V3 BALANCED 一次，对比 `schedule_score_detail` 每行 score 和 baseline 严格相等（BigDecimal scale 2 一致）
- 跑 V4 batch 一次，253/254 PARTIAL 不变

**风险**：BigDecimal vs double 来回转。规则：在线返回 double（贪心快），离线返回 BigDecimal（精度）。两套函数签名分开，不混用。

---

### Commit 3：detailMessage 升级 + 回归基线单测（约 2-3h）
**为什么**：当前 `buildSoftMetric` 输出"偏差 N%，扣 X 分"，但不知道这个 N% 是什么单位、怎么算的。给用户一个能复盘的字符串。

**做什么**：
- `ScheduleScoreService.buildHardMetric` / `buildSoftMetric` 改造 message 模板，引入 `ScoringDimensions` 里登记的 `formulaOffline` 和 `range`，让 detail 长这样：
  ```
  班级每日均衡：日数方差归一 0.23 → 罚分系数 0.23 → 扣 6.90 分（满分 30，公式 variance/4）
  ```
- 新建 `backend/src/test/java/com/paike/scheduler/service/ScheduleScoreServiceTest.java`：
  - 手写 10-15 条 `SchedulePlanItem`（包含 1 个教师冲突 + 1 个同课同日 + 几个连续节）
  - mock mapper 返回该 plan，调 `rescore(plan)`
  - 断言每个 rule 的 score 是确定的具体值（不依赖真 DB）
  - 这是 baseline lock，未来公式动一眼能看出

**验收**：
- 单测全过
- 真跑 V3 BALANCED 一次：90.13 不变；每条 detail 含新格式
- 旧 plan 的 detail 看起来"信息更密"

**风险**：detail_message 字段长度（varchar 500），文档化文案不应超过 200 chars/条。

## 7. 决策门槛

下面这些点需要用户拍板，**不要**自己拍板：

1. **MORNING_THEORY_PRIORITY 隐式失效**：COMPREHENSIVE 策略默认权重表没它，但在线评分还在调用——是 bug 还是 feature？
   - 选项 A：D2 不动，留作 D3 议题
   - 选项 B：D2 顺手在 COMPREHENSIVE 默认权重里加一条（权重多少？10？20？）
2. **detailMessage 含公式 vs 不含**：包含公式会让前端表更"工程师感"，少一些用户友好。要不要做？
3. **是否要单独的"在线评分追溯日志"**：当前 scoreCandidate 出的分扔了，每次贪心选完就忘。要不要把每候选的最高分 + 各维度贡献写进 `explainService`？（**警告**：会大幅膨胀日志，行级 6×决策数）
