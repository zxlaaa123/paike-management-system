# M-41 显式 deleted=0 条件整理

## 结论

M-41 部分成立，已整理 Java 侧冗余条件。

原问题是多个 CRUD / Service 手动加 `.eq(deleted, 0)`，与 MyBatis-Plus `@TableLogic` 自动过滤重复。复核后分为两类：

- Java `LambdaQueryWrapper`：确实冗余，本轮清理。
- XML join / SQL 脚本：不属于 MyBatis-Plus 自动逻辑删除范围，保留。

## 本轮修改

清理 `backend/src/main/java` 下 22 个 Java 文件、66 处 `.eq(...::getDeleted, 0)`。

这些实体字段均由 `@TableLogic` 管理，`BaseMapper` 的 `selectList` / `selectCount` / `delete` 等路径会自动附加逻辑删除条件。删除显式条件后，查询语义保持“不查已删除数据”，代码重复度降低。

本轮未处理：

- `if (entity == null || entity.getDeleted() == 1)` 这类对象状态检查，属于 M-40/N-01 风险域，不和 M-41 混改。
- XML mapper 中的 `deleted = 0`，因为手写 SQL join 不会自动套 `@TableLogic`。
- SQL 脚本中的 `deleted = 0`，因为它用于生成列、初始化数据和约束语义。

## 影响范围

主要涉及基础资料、课表、统计、评分、冲突报告、V4/V5 服务和排课参考数据加载等查询 wrapper。所有改动只删除冗余条件，不改变业务筛选字段。

## 本轮验证

- 新增 `M41DeletedZeroConditionCleanupTest`，锁定：
  - `backend/src/main/java` 不再出现 `.eq(...::getDeleted, 0)`。
  - `backend/src/main/resources` 仍保留手写 SQL/XML 中必要的 `deleted = 0` 条件。
  - `Schedule`、`TeachingTask` 等核心实体仍由 `@TableLogic` 管理删除字段。
