## 2. 方向 A：治理门面补齐（性价比最高，零架构风险）

让"菜单里看着有的功能"真的能用、名副其实。三个子项可独立提交，互不依赖。

### A2 错误码中心扩充（小，建议优先）

**现状证据**：`common/exception/SystemErrorCode.java` 只有 9 个通用 HTTP 码
（AUTH 3 / VALIDATION 3 / BUSINESS 2 / CONFLICT 1 / SYSTEM 1），**零个排课领域码**。
而 `V5ConsistencyCheckService` 里已存在大量领域 issue code（`TEACHER_HARD_CONFLICT`、
`CLASSROOM_CAPACITY_OVERFLOW` 等 12 条校验），只是没注册进枚举。架构是对的（枚举驱动 + 统一 VO +
前端真实 API），纯粹是内容撑不起"中心"门面。

**做什么**：把已散落在各处的领域错误码收敛进 `SystemErrorCode`，从 9 个扩到 40-60 个。

**步骤**：
1. 盘点来源：`V5ConsistencyCheckService` 的 issue code、`ScheduleConflictService` 的冲突类型、
   各 `BusinessException` 抛出点的固定文案。
2. 按域分类补枚举：排课冲突域（教师/班级/教室/时段硬冲突）、容量域、规则域（禁排/连续节次/每日上限）、
   方案域（方案不存在/状态不允许 apply）、周次域（V9 新增的单双周相关）。
3. 每个码补齐 5 元组：`code` / `numericCode` / `category` / `defaultMessage` / `frontendPrompt` / `handlingSuggestion`。
4. 前端错误码中心页直接读，无需改前端。

**工作量**：小（纯数据补充，半天）。**风险**：极低，新增枚举不影响现有逻辑。
**验证**：补完跑 `mvn test`（确认枚举不破坏现有引用）+ 前端错误码页查看条数。

### A3 补 V5RepairSuggestionService 审计（小）

**现状证据**：审计接入清单里这是**唯一完全未接审计**的服务。`V5RepairSuggestionService` 字段只有
`riskService` / `objectMapper`，grep `audit/recordSuccess/recordFailure` 零匹配。
邻近服务（`V5SimulationService`、`V4ScheduleReplanService` 等）都已接入，有现成写法可抄。

**做什么**：给修复建议的生成/状态变更加审计埋点，补完后审计 100% 覆盖。

**步骤**：
1. 注入 `SystemAuditLogService`。
2. 在 `SystemAuditLogService` 加 action 常量（如 `GENERATE_REPAIR_SUGGESTION`）。
3. `generate(...)` 成功末尾 `recordSuccess`，catch 分支 `recordFailure`；
   `markForSimulation(...)` 同理（状态变更也该记）。
4. 抄 `V5SimulationService` 的参数组织方式（taskId/planId/建议数等进 detail）。

**工作量**：小（抄邻近服务，1-2 小时）。**风险**：极低。
**验证**：`mvn test` + 触发一次修复建议生成后查审计日志表。

### A1 回归测试中心加执行能力（中，门面里唯一"假能用"）

**现状证据**：`V6RegressionTestService` 只有 `list`/`getById`/`hasText`（只读）；
`V6RegressionTestController` 只有 `GET /api/v6/regression-tests` 和 `GET /{id}`，**无 POST**；
前端 `RegressionTestView.vue` 只有刷新/搜索/重置/详情，**无执行按钮**。
表数据来源是 `V5Stage1DataService.recordRegressionTest`（V5 流程顺带写），不是 V6 主动跑的。
本质是"结果查看中心"而非"执行中心"。

**做什么**：加真正的"执行回归测试"能力——`POST /api/v6/regression-tests/run`，
内部触发选定测试子集并把结果写入 `schedule_regression_test` 表，前端加执行按钮 + 状态轮询。

**步骤**：
1. 后端 `run(...)` 方法：调用受控的测试子集（不建议直接 `mvn test` 全跑——分钟级且重；
   更稳的做法是封装"关键链路自检"为内部可调用的校验集，或异步 `ProcessBuilder` 跑指定 `-Dtest=` 子集）。
2. 异步执行 + 状态机（PENDING/RUNNING/PASSED/FAILED）+ 超时保护 + 输出截断入库。
3. Controller 加 `POST .../run`（写操作，受 `AuthInterceptor` 的 admin 校验保护）。
4. 前端加"执行"按钮 + 运行中禁用 + 轮询刷新状态 + 失败详情展示。

**工作量**：中（需处理进程执行/超时/输出捕获/异步状态，1-2 天）。
**风险**：中——`mvn test` 子进程的环境变量（`JWT_SECRET`/`DB_*`）、超时、并发触发需谨慎。
**决策点**：是否值得做取决于"回归测试中心"是否要在演示/答辩里展示"能跑"。若只是查看历史，维持现状也行。

## 4. 方向 C：排课引擎能力扩展（最有技术叙事）

### C1' 连续周段支持（V9 的天然续作，真实排课刚需）— 建议作为 V10

**现状证据**：V9 的周次模型是**三值枚举** `WeekType = 'ALL' | 'ODD' | 'EVEN'`
（`frontend/src/api/teachingTask.ts:5`），schema 里只有 `week_type VARCHAR(20)`
（`v23_week_type_support.sql`、`V1__baseline.sql:411`），**没有 `start_week`/`end_week` 字段**。
即系统现在能表达"单周/双周上课"，但**不能表达"第 1-8 周上 A 课、第 9-16 周上 B 课"**这种连续周段。

**为什么是刚需**：真实高校里短学期课、模块化课程、前八周/后八周拆分非常普遍，
和单双周同属"周次维度"的核心能力。V9 只覆盖了周次维度的一半（奇偶），另一半（区间）是天然缺口。

**为什么现在做省力**：V9 已经把"周次重叠"的语义地基铺好了——
- 冲突检测已按 weekType 维度判 overlap（`ScheduleMapper.xml` 的 weekType 重叠 SQL）；
- 唯一键已把 `week_type` 纳入约束维度（同时段允许不同 weekType 共存）；
- 评分已按 `WeekOwner(ownerId, weekType)` 独立计数（`DeltaPenaltyScorer` 的 β 实现）。

扩展路径是把"枚举相等比较"升级为"区间相交判定"，地基复用度高，比 V9 从零做轻得多。

**做什么（高层）**：
1. 数据模型：`teaching_task` / `schedule` / `schedule_plan_item` 加 `start_week` / `end_week`（或周次位图）。
   兼容策略：ALL=全程、ODD/EVEN 可保留为"奇偶 + 区间"的组合，或统一抽象为"周次集合"。
2. 重叠判定：冲突检测从 `weekType 枚举重叠` 升级为 `(weekType 奇偶) AND (周区间相交)`。
3. 唯一键：把周次维度的约束语义从枚举扩到区间（这里是最需要谨慎设计的点——区间不像枚举能直接进唯一键，
   需要决定是放宽 DB 唯一约束 + 应用层兜底，还是用周次位图列）。
4. 引擎 / 评分：weekType 桶扩成周次区间桶。
5. 全链路透传 + 前端表单（起止周输入）+ 课表展示（标注周段）。

**工作量**：中-大（动数据模型 + 全链路，但有 V9 地基）。**需正式立项 V10**。
**风险**：唯一键/重叠语义的设计是关键决策点，需要先出可行性研究（类比 V9 的 `V9_00`）。

### C2 软约束扩展（中，提升排课质量）

**现状证据**：`DeltaPenaltyScorer` / `ScoringFunctions` 已实现 6 条软约束：
`CLASS_DAILY_BALANCE`（班级每日均衡）、`TEACHER_DAILY_LOAD`（教师每日负载）、
`COURSE_DISTRIBUTION`（同课分散）、`CONTINUOUS_PERIOD_LIMIT`（连续节次限制）、
`CLASSROOM_UTILIZATION`（教室利用率）、`MORNING_THEORY_PRIORITY`（理论课上午优先），
且 V9 已把它们全部扩成 weekType 维度（β 独立计数）。

**做什么**：审查真实排课还缺哪些软约束并补充，例如：
- 教师跨校区/楼栋的连续课间移动惩罚；
- 班级"空堂"（gap）惩罚——一天中间空一节再上课体验差；
- 教师"集中授课"偏好（有些教师希望课集中在少数几天）；
- 课程难度分布（高难度课别堆在同一天）。

**工作量**：中（每条软约束 = 一个 penalty 函数 + 增量版 + 权重注册 + 测试）。
**风险**：中——增量评分（delta）必须和全量评分（penalty）一致，否则退火会被误导；
每条新约束都要补 `ScoringWeekTypeConsistencyTest` 同款一致性测试。
**适用**：想继续"引擎技术亮点"叙事且不动数据模型时，这是最对口的。

### C3 导出能力审查（小-中）

**做什么**：核查 `TimetableService` 的三种课表（班级/教师/教室）Excel 导出是否齐全、
V9 weekType 标注是否都进了导出（stage2 E2E 已验教师导出，班级/教室待确认）。
**工作量**：小-中。**风险**：低。

## 5. 方向 B：权限体系升级（大、风险高，优先级最低）

**现状证据**：
- 无 Spring Security 方法级安全：全后端零 `@PreAuthorize`/`@Secured`/`SecurityFilterChain`，
  `SecurityConfig` 只注册 `BCryptPasswordEncoder` Bean。
- 角色是裸 `String`（`SysUser.role`），无 Role 枚举。
- 授权只在 `AuthInterceptor`：`requiresAdmin` + `isStateChanging` 判定，
  **只对写操作（POST/PUT/DELETE/PATCH）要求 admin，所有 GET 任何登录用户均可访问**（读权限全开放）。
- 前端无角色控制：`router meta` 仅 `requiresAuth`，菜单静态写死无 `v-if` 角色过滤。

**做什么**：引入 Role 枚举 + 权限点 → 前端菜单/路由按角色控制 →（可选）Spring Security 方法级安全。

**工作量**：大。**风险**：高——触及几乎所有写接口，需完整回归；
读权限全开放在多角色场景是隐患，但改造面广。
**决策**：对"排课系统"核心价值贡献最低，除非答辩明确要问权限设计，否则放最后；
若要做，建议正式立项 + 隔离分支 + 充足回归（同 V8/V9 的执行约束）。

## 6. 推荐组合与决策建议

按"目标 → 路径"给组合，不预设你的选择：

| 你的目标 | 推荐路径 | 理由 |
|---|---|---|
| 把系统收尾做扎实/整洁 | **A2 + A3 + D3**（一个下午） | 全是小改动、可独立提交、零架构风险，补齐治理门面 + 代码整洁 |
| 治理门面要"全都能用" | A2 + A3 + **A1** | A1 补上唯一"假能用"的回归测试执行 |
| 继续引擎技术亮点（不动数据模型） | **C2**（软约束）或 C3（导出） | 复用 V8/V9 架构，有"又做了 X"叙事 |
| 做真实能用的排课系统 | **C1'（V10 连续周段）** | V9 的天然续作，真实刚需，地基已铺 |
| 体现系统设计能力（答辩权限题） | **B**（立项） | RBAC 是评审常问点，但收益/风险比一般 |

**我的倾向（仅供参考）**：
1. 先用一个下午清掉 **A2 + A3 + D3**——小、独立、零风险，立刻让治理门面和代码整洁度补齐。
2. 之后若继续深化：想"真实能用"走 **C1' 连续周段（V10）**，想"纯引擎亮点"走 **C2 软约束**。
3. **B 权限**和 **A1 回归执行**按需再排，不急。

**最不推荐先做**：B（权限）——触及面最广、对核心价值贡献最低、V8/V9 执行约束禁止随手改现有行为。
